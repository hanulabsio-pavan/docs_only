Lesson 1 · Foundations

What this firmware actually is

Firmware is the software that runs inside a device, not on a phone or PC. For SETU it runs on the ESP32-S3 microcontroller sitting in the wall switch. Its job: read finger touches, flip the mains relays that turn your lights on/off, glow the LEDs, and talk to WiFi / the app / voice — all while never doing anything unsafe with 230 V loads.

The two chips it coordinates

  • ESP32-S3 — the brain. Dual-core CPU, WiFi/Bluetooth, runs all our code.
  • CAP1296 — a dedicated touch-sensing chip. It detects finger presses in hardware and just tells the ESP32 “channel 2 was touched” over a wire. The ESP32 never has to measure capacitance itself.
Why this matters A light switch is a safety + utility device first, a gadget second. The #1 design rule you'll see everywhere in this code: local control must always work, even if WiFi, the cloud, and voice are all dead. Network features are an enhancement, never a dependency.

The "hard path" — the one sequence that must never be slow or blocked

finger touch→ CAP1296 detects→ ESP32 reads it→ relay flips→ light on

Our target is under 50 ms from touch to light. Everything in the architecture exists to protect this path from being delayed by slow things like network calls. Hold that picture in your head — it explains almost every decision in lessons 4–7.

Key takeaway Firmware = the device's own software. SETU's prime directive is local-first, safe, fast touch→relay; WiFi/cloud/voice are layered on top and can fail without affecting the switch.
Self-check: If the home WiFi router is unplugged, should the wall switch still toggle lights on touch?

Yes — absolutely. Touch → relay is entirely on-device and never waits on the network. This is design goal G2 (“local-first”). The cloud only adds remote control / voice / telemetry on top.

Lesson 2 · Foundations

ESP-IDF & how the project is built

ESP-IDF (Espressif IoT Development Framework) is the official SDK for ESP32 chips. It bundles: the compiler toolchain, FreeRTOS (a tiny operating system — lesson 4), drivers for the chip's peripherals (WiFi, I2C, GPIO…), and a build system based on CMake.

Components — ESP-IDF's unit of code

ESP-IDF organizes code into components. A component is just a folder with a CMakeLists.txt that lists its source files, its public include folders, and which other components it depends on (REQUIRES). The app is built by composing components.

Our top-level firmware/CMakeLists.txt 
# Each subfolder of src/ becomes a component (hal, drivers, rtos, middleware, main)
set(EXTRA_COMPONENT_DIRS "src")

include($ENV{IDF_PATH}/tools/cmake/project.cmake)
project(setu_firmware)

That one line — EXTRA_COMPONENT_DIRS "src" — tells ESP-IDF “treat every folder inside src/ as a component.” So our architectural layers (hal, drivers, rtos, middleware, main) literally are the build components. The main component is special: ESP-IDF calls its app_main() function at startup.

Three config files you'll meet

FileWhat it controls
partitions.csvHow the 8 MB flash is sliced: two app slots (for OTA), config storage, etc.
sdkconfig.defaultsBuild options: flash size, PSRAM on, watchdog on, CPU at 240 MHz, OTA rollback on…
src/main/Kconfig.projbuildOur own on/off switches (e.g. SETU_ENABLE_MATTER) that appear in menuconfig.
The commands you'll run idf.py set-target esp32s3 (once) → idf.py build → idf.py -p COM5 flash monitor. That last one uploads the firmware and opens the serial log.
Key takeaway ESP-IDF builds components. We map one component per architectural layer via EXTRA_COMPONENT_DIRS=src. main holds app_main(), the entry point.
Self-check: Where does the program start running?

In app_main(), which lives in src/main/app_main.c. ESP-IDF's bootloader → startup code eventually calls it. We walk through it in Lesson 6.

Lesson 3 · Foundations

The layered architecture & the dependency rule

The code is stacked in layers, each only allowed to depend on layers below it. This is the single most important structural idea — it keeps the fast touch→relay path isolated from messy network code.

LayerFolderResponsibility
Applicationsrc/mainThe "business logic": what a gang does, themes, automation, boot orchestration.
Middlewaresrc/middlewareServices: WiFi, Matter, MQTT cloud, OTA, voice, config, time, telemetry.
RTOSsrc/rtosThe event bus, task/sync definitions, watchdog. The "nervous system".
Driverssrc/driversOne module per physical thing: touch, relay, LED, mic, button.
HALsrc/halThin wrappers over chip peripherals: I2C, GPIO, PWM, NVS, power. Pin numbers live here.
Why "downward-only"? If a low-level driver could call up into network code, a slow network call could freeze a relay. By forbidding upward calls, the touch path physically cannot be blocked by WiFi. When a lower layer needs to tell an upper layer something, it doesn't call up — it posts an event (Lesson 5).

The shared "contracts" — include/

Three header files everyone can include without creating dependencies. They define vocabulary, not behavior:

  • include/setu_config.h — constants: SETU_GANG_COUNT (4), timing budgets, feature flags.
  • include/setu_types.h — data types: gang_state_t, theme_t, the device model, error codes.
  • include/setu_events.h — the event IDs and the setu_event_t message struct.
main→ middleware→ rtos→ drivers→ hal→ ESP-IDF

Dependencies only point right. There are no cycles — that's what lets ESP-IDF link them cleanly.

Key takeaway Five layers, dependencies point downward only, and cross-layer messages travel via the event bus rather than upward function calls. Shared types live in include/.
Self-check: The relay driver needs to announce “gang 1 is now ON”. Can it call a function in the cloud module?

No. That would be an upward call (drivers → middleware) and break the rule. Instead it posts an event (EVT_STATE_CHANGED); the cloud module, if present, subscribes and reacts. The driver doesn't even know the cloud exists.

Lesson 4 · Foundations

FreeRTOS in 10 minutes

A microcontroller has no Windows/Linux. FreeRTOS is a tiny real-time operating system bundled with ESP-IDF that lets many tasks (think: independent mini-programs / threads) run "at the same time" by rapidly switching between them.

The five concepts you must know

ConceptPlain meaningIn SETU
TaskAn independent loop the OS schedules. Has its own stack.tsk_touch, tsk_control, tsk_wifi…
PriorityHigher number = more urgent; preempts lower tasks.touch=9, control=8 … telemetry=2
Core pinningWhich CPU core a task runs on (S3 has 2).Control path → core 1; WiFi → core 0
QueueA thread-safe mailbox: one task posts, another receives.event bus, q_relay_cmd
Semaphore / MutexA signal / a lock to share data safely.touch ISR signal, I2C lock, device-model lock
Why priorities + 2 cores matter here We pin the time-critical tasks (touch, control, LED) to core 1 at high priority, and put WiFi/Matter/MQTT on core 0. Result: a busy network can never delay a relay. That's the 50 ms guarantee, enforced by scheduling.

ISR vs task context

An ISR (Interrupt Service Routine) is a function the hardware calls the instant something happens (e.g. the touch chip's ALERT pin drops). ISRs must be tiny and fast — you can't do I2C or logging inside one. The standard trick: the ISR just "gives a semaphore" to wake a normal task, which does the real work. You'll see exactly this in the touch driver (Lesson 9).

Our task table — src/rtos/tasks.h (priorities & stacks in one place) 
/* Core pinning */
#define TASK_CORE_CONTROL   1   /* hard real-time: touch→relay→led */
#define TASK_CORE_NET       0   /* WiFi/BT stacks live here */

/* Priorities (higher = more urgent) */
#define TASK_PRIO_TOUCH       9
#define TASK_PRIO_CONTROL     8
#define TASK_PRIO_EVENT_BUS   7
#define TASK_PRIO_WIFI        5
#define TASK_PRIO_TELEMETRY   2
Key takeaway Tasks run concurrently; priority + core pinning guarantee the control path beats the network. ISRs stay tiny and hand off to tasks via semaphores.
Self-check: Why can't the touch ISR just read the CAP1296 over I2C directly?

I2C is comparatively slow and can block; doing it in an ISR would stall the whole system and risk a watchdog reset. Instead the ISR gives a semaphore to wake tsk_touch, which does the I2C read in normal task context.

Lesson 5 · The core idea

The event bus — the heart of the design

Here's the key architectural pattern. Four different things can want to control a light: a touch, the app (via cloud), a Matter command from Alexa/Google, and a voice command — plus schedules. If each of those called the relay directly, you'd get chaos and race conditions.

Instead, all of them publish an event to a central event bus. Exactly one task — tsk_control — subscribes and is the only code allowed to move a relay. This is the publish/subscribe pattern.

touch+ app+ Matter+ voice→ event bus→ tsk_control→ relay

Every message is the same shape

The universal event — include/setu_events.h 
typedef struct {
    setu_event_id_t id;     // EVT_TOUCH, EVT_CMD_SET, EVT_THEME_SET…
    uint8_t         gang;    // which gang (0..3) or GANG_ALL
    int32_t         value;   // on/off, level, intent code…
    setu_src_t      source;  // SRC_TOUCH, SRC_APP, SRC_VOICE…  ← who asked
    uint32_t        ts_ms;   // timestamp
} setu_event_t;

The source field is clever: because every event remembers who asked, tsk_control can do arbitration — e.g. a fresh touch beats a stale cloud command — and can attribute telemetry correctly.

How publishing works — src/rtos/event_bus.c 
// Anyone, anywhere, posts events with one call:
event_bus_emit(EVT_TOUCH, channel, TOUCH_PRESS, SRC_TOUCH);

// Internally a dispatcher task pulls from a queue and fans out
// to every subscriber whose mask matches the event id.
static void bus_task(void *arg){
    setu_event_t e;
    for(;;){
        xQueueReceive(s_q, &e, portMAX_DELAY);
        for(int i=0;i<s_sub_count;i++)
            if(s_subs[i].mask & (1u << e.id))
                s_subs[i].cb(&e, s_subs[i].ctx);
    }
}
Why this is worth it Decoupling. The touch driver doesn't know relays, Matter, or the cloud exist — it just shouts “touch on channel 2!” into the bus. You can add a whole new control source (say, a future Zigbee bridge) by publishing the same events, changing zero lines in the control logic.

Key takeaway All control sources publish events; one consumer (tsk_control) owns the relays. The source field enables arbitration. This is the spine of the whole firmware.
Self-check: You want to add a physical rocker-button fallback. How much of the control logic changes?

None. The button driver just publishes EVT_CMD_SET (or EVT_TOUCH) like any other source. tsk_control handles it identically. That's the payoff of the event bus.

Lesson 6 · The core idea

Boot sequence — what happens when power comes on

src/main/app_main.c is a careful, ordered checklist. The golden rule: make the device safe and locally usable first; bring up the network last.

  1. Foundations — init NVS (flash storage), create the shared locks/event-groups, start the watchdog, configure power management.
  2. Safety first — relay_init() drives all relays OFF before anything else. No load may energize unexpectedly after a power blip.
  3. Restore state — load the saved gang states + theme from NVS; if “restore on boot” is enabled, re-apply them (staggered to limit inrush current).
  4. Local I/O — init LEDs, touch chip, button, theme engine.
  5. Start the brain — create the event bus + control/touch/LED tasks. The device is now fully usable by touch.
  6. Confirm health — ota_mark_valid() tells the bootloader “this firmware works, don't roll back” (Lesson 13).
  7. Network & extras — WiFi, time sync, Matter, cloud, voice, telemetry, automation.
The shape of app_main() (abridged) 
void app_main(void){
    nvs_hal_init();  setu_sync_init();  watchdog_init();  power_mgmt_init();

    relay_init();                 // ← ALL RELAYS OFF (safe state)

    device_model_init();
    config_store_init();
    config_store_load(device_model_raw());
    if (config_store_restore_on_boot())
        relay_restore(...);       // re-apply saved state, staggered

    led_status_init();  touch_cap1296_init();  button_init();

    event_bus_init();
    start_local_control();        // ← device usable by touch from here

    ota_mark_valid();             // cancel rollback once healthy
    start_network();              // WiFi/cloud/voice — enhancements
}
The safe-state guarantee Relays default OFF out of reset and are explicitly driven OFF first. Restoring last state is a deliberate, configurable step — never an accident. This is non-negotiable for a 230 V device.
Key takeaway Boot order = safe → local control → network. The device toggles lights within ~200 ms, long before WiFi connects.
Self-check: Why is relay_init() called before config_store_load()?

So the relays are in a known-safe OFF state before we even read what they "should" be. We decide to restore only after, and explicitly. Safety precedes convenience.

Lesson 7 · The core idea

Putting it together: trace a finger tap to a light

This is the lesson that makes everything click. Follow one touch through every file.

#What happensFile
1Finger touches the glass. CAP1296 senses it and pulls its ALERT pin low.hardware
2ESP32 fires a GPIO ISR. It does almost nothing — just xSemaphoreGiveFromISR() to wake the touch task.drivers/touch_cap1296.c
3tsk_touch wakes, reads the CAP1296 status register over I2C, figures out which channel, debounces, and publishes EVT_TOUCH.touch_cap1296.c + hal/i2c_bus.c
4Event bus dispatcher delivers the event to its subscriber.rtos/event_bus.c
5tsk_control receives it, sees a tap on gang 2, reads current state, decides "toggle to ON".main/gang_sm.c
6It calls relay_set(2, true) — checking the 300 ms debounce so contacts aren't chattered.drivers/relay.c
7Relay GPIO goes high → BSS138 → relay coil → light on. Then it updates the device model, lights the gang LED, saves to NVS, and emits EVT_STATE_CHANGED.gang_sm.c + relay.c
8Subscribers to EVT_STATE_CHANGED react: the cloud module publishes new state, Matter reports the attribute — without the control task knowing or waiting on them.middleware/cloud_mqtt.c
The decision logic — src/main/gang_sm.c 
// A tap toggles the gang. One function, one responsibility.
static void handle_touch(const setu_event_t *e){
    if (e->value == TOUCH_PRESS && e->gang < SETU_GANG_COUNT){
        bool now = device_model_get_gang(e->gang).on;
        gang_sm_apply(e->gang, !now, 0, SRC_TOUCH);   // toggle
    } else if (e->value == TOUCH_HOLD){
        theme_engine_apply(next_theme, SRC_TOUCH);    // long-press cycles themes
    }
}

// gang_sm_apply() is the single choke-point that touches a relay:
//   debounce → drive relay → update model → LED → persist → emit event
Key takeaway Steps 1–7 are the fast, local hard path (core 1). Step 8 (network reporting) is fire-and-forget on core 0. The event bus is what cleanly separates the two.
Self-check: At step 7, why does tsk_control emit EVT_STATE_CHANGED instead of calling the cloud and Matter directly?

To stay decoupled and fast. Calling network code directly could block the control task (violating the downward-dependency rule and the latency budget). Emitting an event lets reporters react on their own tasks, and lets the control logic stay unaware of which reporters exist.

Lesson 8 · The layers in detail

HAL — talking to the silicon

The Hardware Abstraction Layer is the thinnest layer: small wrappers around the ESP32's peripherals so the rest of the code never touches raw registers. Crucially, this is the only place GPIO pin numbers appear.

FileWraps
board.hThe pin map — mirrors the schematic. Relay pins, I2C pins, LED pins, etc. Change the wiring? Change only this file.
i2c_bus.cThe shared I2C bus to the CAP1296, protected by a mutex so two tasks can't talk over each other.
gpio_wrap.cConfigure output pins / attach input interrupts.
pwm.cLEDC (PWM) channels for LED brightness/animation.
power_mgmt.cLight-sleep / frequency scaling to hit the <2 W budget.
nvs_hal.cBrings up NVS (the flash key-value store) safely.
Pins in one place — src/hal/board.h 
#define BOARD_I2C_SDA        GPIO_NUM_3
#define BOARD_I2C_SCL        GPIO_NUM_4
#define BOARD_CAP1296_ALERT  GPIO_NUM_5   // touch interrupt
#define BOARD_RELAY_GPIO     { GPIO_NUM_7, GPIO_NUM_8, GPIO_NUM_9, GPIO_NUM_10 }
#define BOARD_LED_GANG_GPIO  { GPIO_NUM_11, GPIO_NUM_12, GPIO_NUM_13, GPIO_NUM_14 }
Why a HAL at all? Two reasons: (1) portability — if a future board moves the relay to a different pin, you edit board.h and nothing else; (2) testability — higher layers can be tested against a fake HAL.

Key takeaway HAL = thin, boring, essential. Pin numbers and raw peripheral setup live here and nowhere else.
Self-check: The shared I2C bus has a mutex. What problem does that prevent?

Two tasks issuing I2C transactions simultaneously would corrupt each other's reads/writes. The mutex serializes access so each transaction completes atomically.

Lesson 9 · The layers in detail

Drivers — one module per physical thing

touch_cap1296.c — the interrupt-driven pattern

This is the textbook ISR→task handoff. The ISR is three lines; the task does the work.

ISR + task 
// 1) The ISR: do the absolute minimum, then wake the task.
static void IRAM_ATTR alert_isr(void *arg){
    BaseType_t hp = pdFALSE;
    xSemaphoreGiveFromISR(s_alert_sem, &hp);   // "wake up, touch task!"
    if (hp) portYIELD_FROM_ISR();
}

// 2) The task: wait for the signal, then read I2C + publish.
void touch_task(void *arg){
    for(;;){
        xSemaphoreTake(s_alert_sem, pdMS_TO_TICKS(50));
        i2c_bus_read_reg(... SENSOR_STATUS ...);   // which channels?
        // debounce, detect press/hold/release, then:
        event_bus_emit(EVT_TOUCH, ch, TOUCH_PRESS, SRC_TOUCH);
    }
}
Graceful failure If the I2C read fails, the driver emits EVT_FAULT and tries bus recovery — but it never crashes. Lights already on stay on. Safety over features.

relay.c — the single-writer rule + debounce

Only tsk_control calls relay_set(). The driver enforces a 300 ms minimum dwell between toggles of the same gang, protecting the physical relay contacts (rated ~100k operations) from chatter. It also keeps the authoritative on/off state in firmware (the baseline board has no contact-sense wire).

The rest

  • led_status.c — drives gang LEDs + the WiFi indicator (slow blink = provisioning, solid = cloud connected, double-blink = OTA…) and runs a 30 Hz animation tick for themes.
  • button.c — detects a 10-second hold for factory reset → sets a system flag.
  • audio_i2s.c — mic capture for voice; compiled out unless voice is enabled (Phase 2).
Key takeaway Drivers translate hardware events into bus events and bus commands into hardware actions. Touch uses ISR→semaphore→task; relay enforces single-writer + debounce; failures degrade gracefully.
Self-check: Why is only one task allowed to call relay_set()?

If several tasks drove the relays, two commands could race and leave a load in an undefined or rapidly flipping state. Funnelling all changes through tsk_control gives one consistent, debounced, persisted source of truth.

Lesson 10 · The layers in detail

Application logic — the brain

device_model.c — the single source of truth

One global, mutex-guarded struct holds the entire device state: each gang's on/off + level + name, the active theme, connectivity, firmware info. Everyone reads snapshots; only the control task writes.

The model — include/setu_types.h 
typedef struct {
    gang_state_t gang[SETU_GANG_COUNT];  // per-gang: on, level, name, group…
    theme_t      active_theme;
    bool         locked;                  // child-lock / cleaning mode
    conn_state_t conn;                    // wifi/cloud/matter/time flags
    fw_info_t    fw;                       // version, running OTA slot…
} device_model_t;

gang_sm.c — the state machine + arbitration

Hosts tsk_control. Subscribes to all control events, runs each gang's tiny state machine (OFF ⇄ ON, plus LOCKED), and performs arbitration — e.g. child-lock ignores touch; a fresh touch wins over a stale cloud command. gang_sm_apply() is the one choke-point: debounce → relay → model → LED → persist → emit event.

theme_engine.c — data-driven scenes

Themes (Devotional, Party, Movie, Sleep, Morning) are just a table of which gangs are on for each scene. Because it's data, new themes can ship via app/OTA without firmware changes.

The scene table 
static const bool SCENE[THEME_COUNT][SETU_GANG_COUNT] = {
  /* DEVOTIONAL */ { 1, 0, 0, 0 },   // warm glow on gang 1
  /* PARTY      */ { 1, 1, 1, 1 },   // all on
  /* MOVIE      */ { 0, 1, 0, 0 },   // ambient only
  /* SLEEP      */ { 0, 0, 0, 0 },   // all off
};

automation.c — local schedules

A once-a-minute task that evaluates rules (timers, sunset, Morning ramp) and emits events when they fire. Runs on-device so automations work even when the cloud is down.

Key takeaway The app layer is policy: one source-of-truth model, one state machine that owns relays + arbitrates, data-driven themes, and on-device automation.
Self-check: Themes are stored as a table rather than as code. What does that buy you?

Flexibility without firmware releases — you can tweak or add scenes by shipping new data (app push / OTA), and the engine that applies them never changes.

Lesson 11 · The layers in detail

Middleware — connectivity & services

These modules add the "smart" features. Each one degrades gracefully — none is on the local control path.

ModuleJob
wifi_mgr.cA state machine: provision → connect → (reconnect with exponential backoff). Sets connectivity flags; enables modem-sleep when idle.
provisioning.cFirst-boot / factory-reset onboarding (BLE/SoftAP credentials + Matter commissioning).
cloud_mqtt.cMQTT-over-TLS to the SETU cloud. Subscribes to commands, publishes state on every EVT_STATE_CHANGED.
matter_svc.cExposes each gang as a Matter On/Off endpoint so Apple/Google/Alexa can control it. (Off by default — optional component.)
time_sync.cSNTP + India timezone, so schedules/sunset work.
telemetry.cHeartbeat: uptime, free heap, RSSI, switch counts — for monitoring the pilot fleet. Alarms if heap gets low.
voice_engine.cOn-device "Hey SETU" wake-word + command classifier (Phase 2; uses PSRAM; off by default).
ota_mgr.cOver-the-air updates — covered next lesson.
The recurring pattern Notice how each module either publishes events (a cloud command becomes EVT_CMD_SET) or subscribes to them (publish state on EVT_STATE_CHANGED). They plug into the same bus as touch and voice — that uniformity is the whole point.

Key takeaway Middleware = optional, network-side services. They translate between the outside world and the event bus, and they can all fail without touching local control.
Self-check: A Matter command and a touch arrive within the same second. How do they both reach the relay?

Both become events (EVT_CMD_SET from Matter, EVT_TOUCH from touch) on the same bus. tsk_control processes them in order and arbitrates by source/timestamp. Same path, no special-casing.

Lesson 12 · The layers in detail

Persistence — remembering across power cycles (NVS)

NVS (Non-Volatile Storage) is ESP-IDF's key-value store in flash — like a tiny, durable dictionary. SETU uses it to remember gang states, the active theme, WiFi credentials, and config.

config_store.c organizes NVS into namespaces (think folders): sys, gang, theme, net, cloud. Each gang's state is saved on every change, so after a power cut the device can restore exactly where it was.

Schema versioning — future-proofing

The sys namespace stores a schema version number. On boot, if the stored version is older than the firmware's, a migration routine runs. This lets future OTA updates change the saved data layout without bricking devices already in the field.

Migration check — src/middleware/config_store.c 
nvs_get_u16(h, "schema", &ver);
if (ver != SCHEMA_VERSION) {
    // TODO: run migration steps from `ver` up to SCHEMA_VERSION
    nvs_set_u16(h, "schema", SCHEMA_VERSION);
}
Security note In production, this NVS partition is encrypted (Flash Encryption), so WiFi passwords and device keys can't be read by dumping the flash chip. See Lesson 13.
Key takeaway NVS = durable key-value flash. Namespaced config + a schema version that enables safe migrations across firmware updates.
Self-check: Why store a schema version number at all?

So a newer firmware can recognize and upgrade old saved data instead of misreading it. Without it, an OTA that changes the data layout could corrupt settings or crash on boot.

Lesson 13 · The layers in detail

OTA updates & security

A/B updates with automatic rollback

The flash has two app slots (ota_0, ota_1 — see partitions.csv). An update downloads into the inactive slot, verifies it, then reboots into it. If the new firmware fails to prove itself healthy, the bootloader automatically rolls back to the old slot.

running on A→ download to B→ verify + reboot to B→ B proves healthy? → yes:commit B / no:rollback to A

That "proves healthy" step is the ota_mark_valid() call you saw in the boot sequence — only after self-tests pass does the new image cancel the pending rollback.

Health confirmation — src/middleware/ota_mgr.c 
if (state == ESP_OTA_IMG_PENDING_VERIFY) {
    // run self-tests... if good:
    esp_ota_mark_app_valid_cancel_rollback();   // keep the new image
}
// If we crash/watchdog-reset before reaching here, bootloader reverts.

Security layers (production)

LayerProtects against
Secure Boot v2Running unsigned/tampered firmware — only SETU-signed images boot.
Flash EncryptionReading secrets/firmware by physically dumping the flash.
Signed OTA + SHA-256Installing a malicious update.
TLS 1.2/1.3Eavesdropping/tampering on MQTT + OTA downloads.

Key takeaway OTA is A/B with auto-rollback — a bad update can never brick a unit. Security is layered: signed boot, encrypted flash, signed+TLS updates, per-device identity.
Self-check: A new OTA boots but immediately crashes in a loop. What happens to the device?

It never reaches ota_mark_valid(), so the pending-verify flag is never cleared. On the next watchdog reset the bootloader rolls back to the previous good slot. The device self-heals — that's design goal G3.

Suggested order for Phase 1 bring-up

  1. Install ESP-IDF v5.x, get idf.py build green on an ESP32-S3 DevKit.
  2. Bring up relay.c + led_status.c — blink a gang on a timer. Tangible win.
  3. Bring up touch_cap1296.c on a CAP1296 eval board — get EVT_TOUCH printing.
  4. Wire touch → control → relay end-to-end (the hard path). Measure the latency.
  5. Then WiFi → MQTT → app control. Then Matter, then OTA, then voice.
You now understand the whole system Layers + event bus + single-writer control + safe boot + A/B OTA. Every file you opened slots into one of those ideas. Re-read Lesson 7 anytime you lose the thread — the touch→light trace ties it all together.

Glossary

TermMeaning
ESP-IDFEspressif's official SDK for ESP32 chips (compiler + FreeRTOS + drivers + build system).
FreeRTOSTiny real-time OS that schedules multiple tasks on the MCU.
ComponentESP-IDF's unit of code: a folder + CMakeLists.txt. Our layers are components.
TaskAn independently scheduled loop (like a thread) with its own stack & priority.
ISRInterrupt Service Routine — runs instantly on a hardware event; must be tiny.
QueueThread-safe FIFO mailbox between tasks.
Mutex / SemaphoreA lock to protect shared data / a signal to wake a task.
Event busSETU's central publish/subscribe message router (rtos/event_bus.c).
GangOne switch position / load channel. SETU has 4.
HALHardware Abstraction Layer — thin wrappers over chip peripherals.
GPIOGeneral-Purpose I/O pin on the chip.
I2C2-wire serial bus; how the ESP32 talks to the CAP1296.
PWM / LEDCPulse-width modulation; ESP32's LED control peripheral (dimming/animation).
NVSNon-Volatile Storage — key-value store in flash that survives power loss.
OTAOver-The-Air firmware update.
A/B partitionsTwo app slots so an update can roll back if it fails.
MatterSmart-home interoperability standard (Apple/Google/Alexa).
MQTTLightweight publish/subscribe messaging protocol used for the cloud link.
PSRAMExternal RAM on the module (8 MB) — used for the voice model.
Watchdog (WDT)A timer that resets the chip if a task hangs.
Hard pathThe latency-critical touch→relay sequence that must never be blocked.
