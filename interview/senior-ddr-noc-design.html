Chapter 1: Advanced DDR Controller Design

Production DDR Challenges

Q: "Walk me through a complete DDR read/write pipeline. What are the critical paths?"

DDR Read Path (simplified, typical latency ~40 cycles):

  1. Request arrives at controller (buffer or arbitration stage)
  2. Row buffer hit check → if miss, schedule row close + precharge
  3. Activate row (tRCD delay ~15ns); wait for bank ready
  4. Read command issued; DRAM outputs data after CAS latency (tCL ~15ns)
  5. Data captured on DQS strobes; stored in read FIFO
  6. Optional: DQ swizzling, ECC check, reordering
  7. Return to requester via data path (pipelined or latched)

Critical paths:

  • Command pipeline: Scheduler logic (scheduling constraints across banks, ranks)
  • Timing controller: Maintaining tRCD, tRP, tRAS, tWR, tCL delays (state machine or timer-based)
  • DQ data path: DRAM to controller (high-frequency analog signal, requires careful capture)
  • Arbitration: Choosing next command when multiple banks/ranks ready (fairness vs. throughput)

Interview tip: Discuss row-hit rates and how they drive average latency vs. worst-case. Mention prefetching strategies or heuristics for bank scheduling.

Command Scheduler Architecture

Q: "Design a command scheduler for a dual-channel, quad-rank DDR4 subsystem. What queues do you maintain?"

Architecture approach:

  1. Write buffer (WB): Absorbs write requests, decouples requester from DRAM write latency
  2. Read queue (RQ): Read requests waiting for DRAM availability
  3. Per-bank state: Track row open in each bank (8+ banks per rank)
  4. Rank/channel scheduler: Arbitrate between channels and ranks for bus access
  5. Timing controller: Maintain DRAM timing constraints (tRCD, tRP, tRAS, tWR)

Scheduling heuristics (trade-offs):

  • Row-hit-first: Prioritize commands hitting open rows (high throughput, potential starvation)
  • Aging/fairness: Boost priority of older requests to avoid starvation
  • Write-draining: Periodically flush write buffer to prevent blocking reads (latency fairness)
  • Prefetch hints: Use CPU/requester hints to preemptively open rows

Depth consideration: Write buffer typically 32–128 entries; read queue 16–32 entries. Larger buffers improve burst absorption but increase arbitration complexity.

DQ Data Path & Capture Timing

⚡ Production Insight: DQ-to-DQS skew violations often catch teams off guard during integration. Implement read leveling (DLL tuning) and per-bit lane calibration in firmware to compensate for trace length mismatches. Many DDR4/DDR5 subsystems use built-in DRAM calibration modes; document the calibration sequence carefully in your design spec.

Power Optimization in DDR Controllers

Q: "How do you reduce DDR subsystem power? What's the biggest win?"

Power breakdown (typical SoC):

  • ~60% DRAM I/O (termination, tristate drivers)
  • ~20% command/control timing logic
  • ~15% read/write data paths
  • ~5% other (arbitration, state machines)

High-impact optimizations:

  1. Termination power (biggest): Use on-die termination (ODT) only when necessary (read cycles); disable for idle/precharge states. Can save 50%+ of DRAM power.
  2. Rank interleaving: Stagger accesses across ranks to amortize activation energy; reduce peak power spikes.
  3. Dynamic refresh: Use fine-grained refresh (1X, 2X, 4X) based on temperature; save ~10% in cool environments.
  4. Self-refresh + retention: In sleep mode, switch to low-power self-refresh; minimal controller logic needed.
  5. Clock gating: Disable command/read pipelines when write buffer draining or idle.

Trade-off: Aggressive power saving (ODT gating, refresh tuning) increases latency variability → must validate with real workloads.

SystemVerilog: Rank Interleaving with ODT Control
// Simplified: ODT enable during read, based on rank stagger module ddr_odt_controller #( parameter NUM_RANKS = 4, parameter BURST_LEN = 8 ) ( input clk, reset, input [NUM_RANKS-1:0] rank_read_active, input rank_busy [NUM_RANKS-1:0], output reg odt_enable ); reg [3:0] read_timer; always @(posedge clk) begin if (reset) begin read_timer <= 0; odt_enable <= 1'b0; end else begin // Enable ODT during data capture window if (|rank_read_active) read_timer <= BURST_LEN + 2; // tCL + safety margin else if (read_timer > 0) read_timer <= read_timer - 1; // Turn off ODT immediately after data phase odt_enable <= (read_timer > 0); end end endmodule

Self-Check Quiz

Q1: In a command scheduler, what's the advantage of tracking row-open state per-bank?

Row-open tracking enables row-hit optimization: issuing a Read/Write to an open row skips the Activate command and tRCD delay. Row-hit ratio often 60–80% for real workloads; each hit saves ~15–20ns latency and reduces power (no activation).

Q2: Why is ODT (on-die termination) power the biggest opportunity in DDR subsystems?

ODT dissipates power continuously across the entire read cycle via termination resistors. Enabling ODT only during actual data capture (not during precharge or idle) can reduce DRAM power by 50% or more without affecting functionality, since data only needs stable termination when signals are actively driven.

Q3: What's the typical row-hit-first scheduler priority issue, and how do you mitigate starvation?

Row-hit-first can starve requests to closed rows (different bank/address), reducing fairness. Mitigation: Aging/priority boost for older requests; periodic write-buffer flush; heuristic "every Nth command close the row" to open new rows; prefetch hints from CPU to pre-open rows for upcoming requests.

Key Takeaways

  • DDR pipeline: Command scheduler, timing controller, data path are separate concerns; each has distinct critical paths
  • Scheduling heuristics: Row-hit-first high throughput; add aging to prevent starvation
  • ODT power: Largest DDR subsystem power consumer; selective enable saves ~50%
  • Timing margins: DQ-to-DQS skew, trace matching, read leveling are production-critical; validate early
  • Rank interleaving: Distributes activation load; improves both latency and power

Chapter 2: Network-on-Chip Architecture & Scalability

NoC Routing & Topology Tradeoffs

Q: "Compare mesh, torus, and hierarchical topologies for a 64-core NoC. What's your recommendation and why?"

Mesh (8x8 grid):

  • Pros: Regular, simple routing (XY, YX), low area overhead
  • Cons: High diameter (14 hops worst-case); power consumption scales with distance
  • Latency: 7–14 hops depending on placement

Torus (8x8, wraparound):

  • Pros: Reduced diameter (7 hops max), better load balancing
  • Cons: Routing more complex (wrap-around logic); not all cores benefit equally
  • Latency: 4–7 hops (better than mesh)

Hierarchical (e.g., 2-level tree + mesh):

  • Pros: Scales well (cluster-local latency low); power-efficient clustering
  • Cons: Higher complexity; central bottleneck risk at tree root
  • Latency: Cluster-local ~2–3 hops; inter-cluster ~6–10 depending on tree height

My recommendation (for modern SoC): Mesh or mesh-derived with local clusters for L2/L3. Rationale: Mesh regularity simplifies timing closure and verification; hierarchical adds complexity for marginal latency gain; modern workloads tolerate 100–200 ns latency (mesh worst-case), so focus on throughput and power over latency.

Deadlock Prevention: Virtual Channels & Turn Restrictions

Q: "Design a deadlock-free XY router with minimal VCs. What's the minimum VC count?"

XY routing in mesh: Traffic always goes X-direction first, then Y (or vice versa). This imposes a total order on routes, which can still deadlock if packets wait for output VC.

Deadlock scenario:

  • Packet A at (0,1) → (3,0): Routes +X, then -Y
  • Packet B at (1,2) → (0,3): Routes -X, then +Y
  • Both wait for overlapping router buffers → circular wait

Solution: 2 Virtual Channels (minimum):

  • VC0: X-phase traffic (moving in X-direction)
  • VC1: Y-phase traffic (moving in Y-direction)
  • Packet reserves VC0 for all X-hops, switches to VC1 for Y-hops
  • No cycles possible: VC0 packets only go to VC1 (X-phase → Y-phase transition)

Trade-off: 2 VCs sufficient for XY; but with flit-level VC arbitration, buffer depth increases. In practice, use 3–4 VCs to allow pipelining and reduce VC stalls.

Advanced approach (turn restrictions, 4 VCs total): Partition turns (N→E, N→W, E→S, etc.); assign each VC to forbidden turn set. More flexible routing than XY; requires 4 VCs minimum for guarantee.

NoC Congestion & Arbitration

Q: "How do you handle input-queued arbitration in a router under high congestion? What's the complexity?"

Input-queued router anatomy:

  • N input ports, each with M VCs, each with depth D
  • 1 crossbar switch (N×N mux matrix)
  • Output-side arbitration: decide which input port → output port each cycle

Challenges under congestion:

  • HOL (Head-of-Line) blocking: If packet A at input 0, output 2 is waiting, but packet B at input 0, output 1 is ready, packet B still blocked
  • Starvation: Unfair arbitration can starve low-priority ports
  • Throughput collapse: Random/FIFO arbitration can drop throughput to 50% (well-known result)

Solutions (in order of complexity/throughput):

  1. Round-robin (simple): Rotate priority across ports; fair, ~70% throughput under worst-case
  2. Aging + round-robin: Boost priority of older packets; prevents starvation, ~75–80% throughput
  3. Separable arbitration (iSLIP): Match each output to highest-priority input; decouple input/output arbitration. ~95%+ throughput
  4. Output-queued (ideal, complex): Move buffers to output side; no HOL blocking. Requires N×faster internal bandwidth or speedup.

Typical production choice: iSLIP or round-robin + depth. Complexity trade-off: iSLIP ~20% more logic than round-robin; throughput gain often worth it for high-load scenarios.

NoC Power & Latency Analysis

⚡ Production Insight: Many SoCs over-provision NoC bandwidth (2–3× actual peak) to keep average latency low. This seems wasteful but often cheaper than aggressive arbitration/VC logic. Profile real workloads early; don't assume worst-case uniform traffic.

Self-Check Quiz

Q1: Why do XY routers still need virtual channels despite having a total order on routes?

Even with ordered X-then-Y routes, packets can deadlock waiting for output VC if a packet in the X-phase blocks another in the Y-phase. Two VCs (one for X-phase, one for Y-phase) ensure packets can transition phases without waiting, breaking the cycle.

Q2: What's Head-of-Line (HOL) blocking, and which NoC design best mitigates it?

HOL blocking: packet A at an input port blocks packet B behind it from using its output port. Input-queued routers are susceptible. Output-queued routers eliminate HOL completely (no buffers on input). iSLIP arbitration (separable input/output matching) reduces HOL impact significantly without full output-queueing.

Q3: In a hierarchical NoC, where's the bottleneck and how do you avoid it?

The tree root (cluster-interconnect or central crossbar) can become a bottleneck if inter-cluster traffic is high. Mitigations: (1) Local caching to reduce inter-cluster requests, (2) Multi-rooted hierarchy (fat-tree), (3) Redundant interconnects, (4) Partition traffic (QoS) to prioritize latency-critical flows.

Key Takeaways

  • Topology choice: Mesh simple & scalable; hierarchical better for clustered workloads
  • Deadlock prevention: 2 VCs minimum for XY routing; 4 VCs for turn restrictions
  • Arbitration: Round-robin fair; iSLIP achieves ~95% throughput without HOL
  • Power: Virtualization (VCs, deeper buffers) adds 20–30% area/power; profile workloads to justify
  • Production lesson: Over-provision bandwidth (2–3×) often simpler than aggressive arbitration

Chapter 3: System Integration & Production Challenges

DDR + NoC Integration: Coherency & QoS

Q: "In a multi-core SoC with coherent L2 caches, NoC, and DDR, what's the biggest integration challenge?"

Challenge: Latency variability & coherency deadlock

  • Problem 1: Coherency protocol (e.g., invalidate-on-write) injects snoop traffic into NoC; unpredictable latency for data accesses
  • Problem 2: If read blocks waiting for snoop response, and snoop is queued behind that read in NoC, circular wait → deadlock
  • Problem 3: DDR scheduler has no awareness of coherency deadlines; worst-case DDR latency (row miss + write buffer full) can starve coherency responses

Solutions (typical):

  1. Separate VC for coherency traffic: Snoops/responses use dedicated VC, always have priority in arbitration
  2. Coherency bypass: Short-circuit snoops directly to L2 (not through NoC if possible)
  3. QoS in DDR: High-priority queue for coherency-related DDR requests (reads needed for snoop response)
  4. Timeout & recovery: Watchdog timer on coherency stalls; timeout triggers priority boost or DDR flush

Deep insight: This is a system-level problem; no single component solves it. Require cross-team design review and formal verification of deadlock scenarios.

Timing Closure: Multi-Cycle Paths & CDC

Q: "You're timing-closed at 1.5 GHz (667 ps), but DDR operates at 533 MHz (1.875 ns). How do you handle CDC between these domains?"

Setup:

  • Core clock: 1.5 GHz (667 ps)
  • DDR clock: 533 MHz (1.875 ns) = 2.8 core cycles
  • Need to safely transfer data from core domain to DDR domain and vice versa

Approach (typical):

  1. Generate DDR clock from core PLL: DDR clock = Core / N (e.g., /2.8 via fractional PLL or sync divider)
  2. Phase alignment: Use delay-locked loop (DLL) to phase-align DDR clock with DQS strobes (DRAM output)
  3. Synchronizer (2-flop chain): For async CDC (rare in modern SoCs; usually same PLL family)
  4. Timing guardbands: Account for worst-case skew (PVT: process, voltage, temperature). Subtract from available setup/hold time.

Critical timing paths:

  • Core → DDR command path (multi-cycle): 2–3 core cycles to DDR cycle
  • DDR data capture (tight): tCO (DRAM) + PCB delay + skew < setup at controller capture flop

Watchout: PLL jitter and skew can consume 50+ ps of your timing margin. Validate with post-layout simulations and silicon measurements.

Verification Strategy for Large Subsystems

Q: "How would you verify a complete DDR+NoC subsystem (e.g., 16-core, dual-channel DDR4)?"

Verification pyramid (bottom to top):

1. Unit-level (per component):

  • DDR controller: Functional simulator + constrained-random (DDR model)
  • Router: Synthetic traffic injections (uniform, hotspot, tornado patterns)
  • Coherency engine: Protocol compliance tests (write-invalidate sequences)
  • Expected coverage: >95% code, >85% FSM coverage

2. Integration (sub-blocks):

  • Core + L1 + L2: Run micro-benchmarks (memory stress, cache churning)
  • NoC + DDR: Memory traffic patterns (prefetcher-generated, precomputed workloads)
  • Focus: Timing closure, power, latency tail distribution

3. Full-chip SoC:

  • Formal verification: Deadlock detection (model checking up to ~100K states)
  • Simulation: SPEC2017, custom workloads (boot, media encoding, data analytics)
  • Post-layout: Timing-accurate simulation (SDF back-annotation); gate-level simulation for critical paths
  • Silicon validation: Bring-up on FPGA (if feasible), then silicon tests

Typical coverage at tape-out: ~90% code, ~80% FSM, ~60% coherency scenarios (hard to cover all)

Post-silicon validation: Stress tests, temperature corners, power-supply noise injection. Common issues found: timing margin violations, coherency deadlock (rare but critical), ECC errors under temperature.

Advanced: Formal Verification for Deadlock Detection

Why formal matters for NoC: Simulation may never trigger a deadlock scenario (1-in-a-million sequence); formal exhaustively checks all reachable states.

Setup: Model NoC as state machine (router states, buffer states, packet routing decisions). Use bounded model checker (BMC) or invariant checking.

Property: "For every packet, it eventually reaches its destination" (liveness). Negation (packet stuck) is checked for reachability.

Limitation: Formal scales to ~10–15 routers due to state explosion; larger NoCs require decomposition (verify each router locally + connectivity properties).

Self-Check Quiz

Q1: Why separate VCs for coherency traffic in a DDR+NoC system?

Coherency snoops & responses must not be blocked by regular data traffic. If snoops queue behind data, and data is waiting for snoop response, a circular wait (deadlock) occurs. Dedicated VC with priority ensures snoops always make forward progress.

Q2: You need to transfer a 16-bit address from 1.5 GHz core to 533 MHz DDR domain. What's your approach?

If both clocks are derived from same PLL (synchronous domains), use multi-cycle path constraints in STA (setup time relaxed by clock ratio). If truly async, use 2–3 flip-flop synchronizer chain in DDR domain. Given modern SoCs typically use same PLL family, synchronous approach is standard; document clock relationships clearly in constraints.

Q3: What's the biggest verification gap for DDR+NoC coherency?

Coherency deadlock scenarios. Simulation coverage of coherency is typically low (~30–60%) because triggering a cycle (snoop A blocks B, B blocks C, C blocks A) requires precise timing and traffic interleaving. Formal verification (deadlock detection) scales to ~10 routers; larger systems need clever decomposition or assume deadlock-free VC design.

Key Takeaways

  • Coherency deadlock: Multi-domain system problem; requires QoS prioritization + watchdog timeout
  • CDC at scale: Phase alignment (DLL), timing guardbands (PVT), PLL jitter budgeting critical
  • Verification: Unit → integration → SoC; formal for deadlock; post-silicon stress tests essential
  • Production lesson: Coherency bugs often escape to silicon; invest in formal verification early
  • Latency tail: Profile 99th percentile, not just average; slow coherency responses dominate tail

Chapter 4: Technical Leadership & Career Growth

Transitioning from IC Design to Architectural Leadership

Q: "You've led DDR controller & NoC design. How do you approach a new, unfamiliar subsystem as a staff/principal engineer?"

Framework (proven approach):

Phase 1: Understand the domain (1–2 weeks)

  • Read specs (JEDEC, ARM CHI, Open standard docs)
  • Study prior art (competitor blocks, patents, public architectures)
  • Talk to domain experts (2–3 deep dives with researchers/veterans)
  • Build a mental model: data/control flow, critical paths, power distribution
  • Deliverable: 1-page summary of fundamental tradeoffs

Phase 2: Define architecture (2–3 weeks)

  • List design goals (latency, throughput, area, power, verifiability)
  • Identify 3–4 candidate approaches; rank by risk/benefit
  • Propose preferred approach with clear rationale
  • Highlight assumptions (e.g., "assume row-hit ratio >60%"); plan validation
  • Deliverable: Architecture doc (5–10 pages) + design review

Phase 3: Lead execution (3–6 months)

  • Hire/assign RTL leads; define interfaces & responsibilities
  • Hold weekly architecture reviews; unblock integration issues
  • Mentor junior engineers; delegate deep technical work
  • Track schedule/risk; escalate blockers early
  • Deliverable: Taped-out, verified design; lessons doc

Key insight: At staff level, you're not the fastest coder; you're the multiplier. Your job is to make your team 2–3× more effective.

Mentorship & Growing Your Team

Q: "You have a junior engineer who's struggling with a complex DDR timing problem. How do you mentor them?"

Mentorship approach (NOT micromanagement):

Step 1: Understand their mental model

  • "Walk me through your understanding of the issue." (Listen; don't interrupt.)
  • Identify gaps (e.g., "I see you're thinking about tRCD, but not about back-to-back accesses.")

Step 2: Ask, not tell

  • "What do you think happens if the data arrives 5 ps late?"
  • "How would you measure DQ-to-DQS skew in silicon?"
  • Let them think; resist urge to jump in with the answer

Step 3: Connect to first principles

  • "Remember setup time? It's the same concept—the latch needs stable input before the clock edge."
  • Draw a diagram if they're visual learners

Step 4: Push ownership

  • "I want you to run a sim experiment. Vary DQ delay ±10 ps and measure capture error rate. Report back."
  • Empower them to find the answer, with you as a guide

Step 5: Celebrate learning, not just results

  • "You nailed the root cause analysis. Even though the fix didn't work, you learned why. That's progress."
  • Reinforce: failure is data; process matters

Red flags (you're NOT mentoring):

  • You always know the answer before they finish the question
  • You code for them instead of reviewing their code
  • You assign tasks without context or learning objective

Your goal: In 6–12 months, they should handle 80% of problems independently, escalating only novel challenges.

Driving Innovation & Setting Architecture Strategy

Q: "DDR5 is out; your company's next SoC (2–3 years away) needs DDR design. How do you position the team for success?"

Strategic thinking (not tactical firefighting):

1. Early investment in learning:

  • Allocate 10–15% of team time (1 engineer per sprint) to DDR5 spec study, competitive analysis
  • Build a proof-of-concept (simple test harness) with DDR5 DRAM model; validate calibration algorithms
  • De-risk key assumptions before project officially starts

2. Architecture proposals (3–6 proposals, ranked by risk):

  • Option A (conservative): Extend current DDR4 design; minimal risk, lower power/latency gains
  • Option B (moderate): Redesign scheduler for DDR5 parallelism (16 banks); moderate risk, 10–15% throughput gain
  • Option C (aggressive): Hierarchical memory controller (local SMT caches) + adaptive refresh; high risk, 20–30% gain if successful
  • Recommend Option B or C (depending on risk appetite); justify with silicon data + market trends

    • 3. Build organizational readiness:

    • Hire 1–2 senior architects with DDR5 experience (if internal talent is sparse)
    • Cross-train RTL team on new algorithms (e.g., DDR5 ECC, refresh modes)
    • Establish partnerships with DRAM vendors (early samples, calibration support)

    4. Roadmap alignment:

    • Present findings to leadership: "If we start now, we can ship competitive DDR5 in 2025. If we wait, we'll lag competitors by 1–2 years."
    • Secure budget & headcount; negotiate schedule with product management

    Long-term mindset: You're thinking 3–5 years ahead. Your decisions today (hiring, architecture choices) shape the company's competitive position in the market later.

    Technical Interview: Evaluating Candidates

    Q: "You're interviewing a senior engineer for a principal role on your DDR+NoC team. What would you ask, and what are you looking for?"

    Interview structure (60 min total):

    Part 1: Deep dive (30 min)

    • "Tell me about the most complex subsystem you designed. What was the hardest problem?"
    • Listen for: clear narrative, honest assessment of mistakes, learning from failure
    • Drill down: "How did you debug that? What tools did you use? Would you do it differently now?"
    • Red flags: Vague answers, blame shifting, no reflection

    Part 2: System-level thinking (15 min)

    • "Given a 4-core CPU, DDR4 memory, and NoC interconnect, how do you identify the bottleneck?"
    • Look for: systematic approach (measure, model, simulate), consideration of tradeoffs, awareness of integration challenges
    • Red flags: Jumps to solution; doesn't ask clarifying questions

    Part 3: Leadership & mentorship (15 min)

    • "Describe a time you mentored someone who struggled. How did you help them grow?"
    • Look for: empathy, patience, focus on growth over results
    • Ask: "How do you decide what to delegate vs. do yourself?" → Reveals judgment on empowerment
    • Red flags: "I just did it myself" (not a multiplier); dismissive of junior engineers

    What separates principal from senior:

    • Senior: Solves hard technical problems; owns a subsystem
    • Principal: Multiplies through others; sets architecture direction; influences company strategy

    My hiring bar for principal: Would I follow this person into a startup? Can they lead a team through ambiguity? Do they make other engineers better?

    Advanced: How to Negotiate Your Next Role

    Career transitions: IC Designer → Tech Lead → Staff Engineer → Principal/Distinguished

    Staff level (after ~12 years): You're expected to lead a subsystem end-to-end, influence architecture, and mentor. Compensation typically 2–3× junior engineer (base + equity/bonus).

    Principal/Distinguished: Rare, 1–2 per company. You're a multiplier across multiple teams; you set company technology direction.

    Negotiation tips: (1) Document impact (shipping products, mentored engineers, patents); (2) Get internal advocates (manager, peer principal); (3) Be clear on expectations (what does "principal" mean at your company?); (4) Walk away if the role is inflated title without real authority.

    Self-Check Quiz

    Q1: When taking on a new subsystem, what's your first deliverable as an architect?

    A 1-page summary of fundamental tradeoffs and a 5–10 page architecture document with design goals, candidate approaches, and recommended direction. Do NOT jump to RTL. Upfront architecture clarity saves 2–3 months of rework.

    Q2: A junior engineer asks for help debugging a timing issue. How do you respond?

    Ask them to walk you through their understanding first. Identify gaps and ask guiding questions ("What do you think happens if…?"). Empower them to run experiments and find the root cause. Only jump in if they're truly stuck after 2–3 attempts. Goal: they grow; you're a guide, not the solver.

    Q3: What separates a principal engineer from a senior engineer?

    Senior: solves hard technical problems; owns a subsystem. Principal: multiplies through others; sets architecture direction; influences company strategy; mentors future leaders. Principal must elevate their team's capability 2–3×, not just deliver a single great design.

    Key Takeaways

    • Leadership framework: Understand → Design → Execute → Mentor
    • Mentorship is not micromanagement: Ask, don't tell; empower ownership
    • Think 3–5 years ahead: Strategy, hiring, architecture shape your company's future
    • Multiplier mindset: Your value is in making others 2–3× more effective
    • Hiring for principal roles: Look for systems thinking, leadership qualities, and influence over just technical skills
