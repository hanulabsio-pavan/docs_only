Chapter 1: Digital Design Fundamentals

Core Concepts Revisited

During interviews, foundational knowledge often surfaces indirectly. Interviewers may ask:

Q: "Explain setup and hold time violations. Why do they happen?"

Setup Time: Minimum time data must be stable before clock edge. Violation = data arrives too late to settle before flip-flop captures it.

Hold Time: Minimum time data must remain stable after clock edge. Violation = data changes too quickly after capture.

Root cause: Flip-flop internals (cross-coupled latches) need time to resolve data and propagate to outputs.

Interview tip: Mention metastability risk if domain crossings are involved.

Common Interview Questions

Q: "What causes metastability in a flip-flop?"

Metastability occurs when setup/hold time is violated. The flip-flop's cross-coupled latch enters an undefined state where output oscillates briefly before settling to 0 or 1.

Practical impact: In CDC (clock domain crossing) circuits, use synchronizers (double-flop stage) to reduce MTBF (mean time between failures).

Q: "How do you fix a timing violation in RTL?"

Options (in order of preference):

  1. Increase clock period (reduce frequency) — simple, but may not be acceptable
  2. Add pipeline stages — breaks path into smaller chunks; increases latency but throughput improves
  3. Optimize logic — remove unnecessary gates, use faster cells, or restructure logic
  4. Re-time — move flip-flops to balance delay across stages (compiler-assisted, often automatic)
  5. Parallel processing — increase data width instead of speed

RTL Code Example: Synchronizer

Verilog: CDC Synchronizer (2-stage)
// Clock domain crossing synchronizer module cdc_sync ( input clk_dst, input async_in, output reg sync_out ); reg meta_ff; // Prevent synthesis from collapsing stages (* DONT_TOUCH = "TRUE" *) reg stage1, stage2; always @(posedge clk_dst) begin stage1 <= async_in; // Catch metastability here stage2 <= stage1; // Clean output sync_out <= stage2; end endmodule

Self-Check Quiz

Q1: If setup time is violated, what happens internally?

The flip-flop's cross-coupled latch may not settle in time, causing metastability. Output could be undefined briefly before settling to 0 or 1, or could oscillate.

Q2: Why use a 2-stage synchronizer instead of 1 stage in CDC circuits?

Two stages reduce the probability of metastability propagating. Stage 1 may catch metastability; Stage 2 ensures a clean output. MTBF increases exponentially with more stages.

Key Takeaways

  • Setup Time: Data must be stable before clock edge
  • Hold Time: Data must be stable after clock edge
  • Metastability: Flip-flop undefined state when timing violated; use synchronizers for CDC
  • Fix violations: Pipeline, optimize logic, or reduce frequency
  • CDC: Always use synchronizers (double-flop minimum) for clock domain crossings

Chapter 2: RTL Design & Logic Best Practices

Common RTL Pitfalls

Q: "Write a Verilog always block for a counter. How do you avoid mistakes?"

Common mistakes:

  • Using blocking assignments (=) in sequential logic → causes race conditions
  • Mixing blocking & non-blocking assignments → undefined behavior
  • Over-sensitive sensitivity list → unnecessary re-evaluation
  • Using for-loops with variable iteration counts → synthesizes to large muxes

Counter Design Example

Verilog: 4-bit Counter (Best Practice)
// Good: Uses non-blocking assignments module counter_4bit ( input clk, reset, enable, output reg [3:0] count ); always @(posedge clk) begin if (reset) count <= 4'b0000; else if (enable) count <= count + 1; // Non-blocking! end endmodule // Bad: Blocking assignment (DON'T USE) // always @(posedge clk) begin // if (reset) count = 4'b0000; // Blocking! // else count = count + 1; // May cause race // end
Advanced: Blocking vs. Non-Blocking Assignments

Blocking (=): Assignment completes immediately; next statement executes right away. Suitable for combinational logic (always @* blocks).

Non-Blocking (<=): Assignment deferred until end of time step; all assignments evaluate in parallel. Essential for sequential logic (always @posedge/negedge).

Why it matters: Using blocking in sequential logic simulates differently from synthesis (simulators = race conditions, synthesis = unpredictable behavior).

Q: "How do you design a finite state machine (FSM) in RTL?"

Best practice (3-stage approach):

  1. State register: Holds current state; updates on clock
  2. Combinational next-state logic: Determines next state based on current state + inputs
  3. Combinational output logic: Produces outputs based on current state + inputs (Moore or Mealy)

Advantage: Clean separation; easy to debug. Compare to 2-stage (combines 2 + 3) which is faster but less readable.

Self-Check Quiz

Q1: Why use non-blocking (<=) assignments in sequential always blocks?

Non-blocking ensures all assignments update in parallel at the end of the time step. This matches hardware behavior where flip-flops update simultaneously. Blocking assignments can cause race conditions in simulation.

Q2: What's the difference between a Moore FSM and a Mealy FSM?

Moore: Output depends only on current state (registered output). Mealy: Output depends on current state AND inputs (combinational output). Mealy is faster (reacts immediately to input) but more complex; Moore is slower but safer (no output glitches).

Key Takeaways

  • Always use non-blocking (<=) in sequential logic; blocking (=) in combinational
  • FSM best practice: 3-stage design (state register + next-state logic + output logic)
  • Sensitivity lists: Use @* in combinational blocks; @posedge/negedge in sequential
  • CDC synchronizers: Mandatory for clock domain crossings
  • Testability: Design FSMs to be easily observable and controllable

Chapter 3: Advanced Topics in Digital Design

Pipeline Design & Hazards

Q: "Explain the three types of pipeline hazards."

1. Structural Hazard: Hardware cannot support simultaneous operations (e.g., two instructions need ALU at same cycle). Solution: Add more hardware (dual ALUs) or stall.

2. Data Hazard: Instruction depends on result of prior instruction that hasn't completed. Example: ADD r1, r2, r3 / SUB r4, r1, r5 (r1 not ready). Solution: Forwarding/bypassing or stalls.

3. Control Hazard: Branch outcome unknown until later stages. Solution: Branch prediction, branch delay slots, or speculative execution.

Power Optimization Strategies

Q: "How do you reduce power consumption in an RTL design?"

Techniques (in order of impact):

  1. Dynamic power (P = CV²f): Clock gating (disable unused blocks), voltage scaling, frequency scaling
  2. Leakage power: Power gating (turn off blocks), use high-Vth cells in non-critical paths
  3. Logic optimization: Reduce gate count, minimize switching activity
  4. Memory power: Use SRAM (low power) vs. DRAM; enable memory power-down modes
  5. Data path width: Narrower buses = less switching; use sub-word techniques
Advanced: DVFS (Dynamic Voltage & Frequency Scaling)

DVFS reduces power by adjusting voltage and frequency at runtime:

• Lower frequency → lower voltage needed (respects setup time margins)

• Power ∝ V²: Voltage reduction is quadratic, huge power savings

• Trade-off: Latency increases; suitable for throughput-oriented workloads

• Common in mobile/server CPUs to balance performance and battery life

Verification Mindset

Q: "How would you verify a 32-bit multiplier design?"

Verification strategy:

  1. Sanity checks: Small inputs (2x2, 3x3) verify basic functionality
  2. Boundary conditions: Zero, max value (all 1s), sign alternations
  3. Random testing: Generate thousands of random pairs; compare RTL output to reference model
  4. Coverage analysis: Ensure all code paths, branch conditions, state transitions exercised
  5. Formal verification: Prove equivalence to golden model or math spec
  6. Post-synthesis simulation: Verify timing, gate-level effects
Testbench Snippet: Multiplier Verification
// Simple testbench for 32-bit multiplier module tb_multiplier; reg [31:0] a, b; wire [63:0] result; multiplier dut (.a(a), .b(b), .product(result)); initial begin // Test 1: Small values a = 32'd5; b = 32'd7; #10; assert(result == 64'd35); // Test 2: Maximum values a = 32'hFFFFFFFF; b = 32'hFFFFFFFF; #10; assert(result == 64'hFFFFFFFE00000001); // Test 3: Random 1000 iterations repeat(1000) begin a = $random; b = $random; #10; golden = a * b; // Reference calc assert(result == golden); end end endmodule

Self-Check Quiz

Q1: What is the primary advantage of forwarding to prevent data hazards?

Forwarding (bypassing) routes the result of a prior instruction directly to the next instruction's ALU input, avoiding stalls. This allows the pipeline to continue operating at full throughput despite dependencies.

Q2: In power equation P = CV²f, which factor has the greatest leverage for power reduction?

Voltage (V) has quadratic impact. Reducing voltage by 10% reduces power by ~19%. Frequency (f) is linear; reducing by 10% reduces power by 10%. So voltage scaling is most effective.

Key Takeaways

  • Pipeline hazards: Structural, data (forwarding needed), control (branch prediction)
  • Power reduction: Clock gating most effective; voltage scaling quadratic impact
  • DVFS: Adjust voltage + frequency at runtime for energy efficiency
  • Verification: Sanity tests → random → formal verification → post-synthesis
  • Coverage matters: 100% code coverage ≠ functional correctness; aim for high quality coverage metrics

Chapter 4: Problem-Solving & Communication

How Interviewers Evaluate

What interviewers look for:
  1. Problem decomposition: Can you break complex problems into manageable pieces?
  2. Clear communication: Can you explain design choices? Draw diagrams?
  3. Trade-off analysis: Understand speed vs. power vs. area vs. complexity
  4. Edge cases: Do you think about corner cases (overflow, underflow, boundary conditions)?
  5. Testability: Can your design be verified?
  6. Practical knowledge: Familiarity with EDA tools, simulators, design methodologies

Example Interview Problem

Q: "Design a FIFO queue (first-in, first-out) for 32-bit data, depth 16. What are the tradeoffs?"

My approach (problem-solving framework):

Step 1: Clarify requirements

  • Clock domain? (Synchronous or async CDC?)
  • Read/write on same clock or different?
  • Pipelining? (Ready/valid handshake?)
  • Error flags needed? (Empty, full, almost-full?)

Step 2: High-level architecture

  • Dual-port SRAM (32-bit width, 16-entry depth) for data storage
  • Write pointer (4-bit counter, wraps at 16)
  • Read pointer (4-bit counter, wraps at 16)
  • Empty/full logic (compare pointers)

Step 3: Trade-offs

  • Async FIFO: Different clock domains; requires Gray-coded pointers + CDC synchronizers (complexity++)
  • Registered output: Adds latency but improves timing (pipelined)
  • Depth: Larger = more memory; shallower = simpler control logic
  • Full/empty flags: Can almost-full reduce worst-case latency for back-pressure?

Step 4: Key implementation detail

  • FIFO full when: (write_ptr + 1) == read_ptr (mod 16)
  • FIFO empty when: write_ptr == read_ptr
  • For async FIFO, convert pointers to Gray code to reduce CDC metastability

Communication Tips for Interviews

Drawing & Explaining During Interviews

Best practices:

  • Start with a block diagram: Show main components (SRAM, pointers, control logic)
  • Annotate with signal names: write_ptr, read_ptr, empty, full, data_in, data_out
  • Explain state transitions: "When empty & read request arrives, no data flows"
  • Discuss corner cases out loud: "What if write & read simultaneous? Both increment pointers."
  • Mention verification: "I'd test empty-to-full, full-to-empty transitions, simultaneous read/write"
Common Phrases to Increase Credibility

Avoid these (red flags):

  • "I'm not sure" repeated too often → lack of confidence
  • "I'll just memorize it" → no depth
  • "That's too hard" → gives up easily

Use these (confidence builders):

  • "Let me think through this step-by-step..."
  • "There's a trade-off here between speed and area..."
  • "This relates to CDC concerns..." (shows deep knowledge)
  • "In production, we'd also consider XYZ tool flow..."
  • "Let me draw that out to clarify..."

Post-Interview Checklist

After you solve a problem, verify:
  • ✅ Functional correctness: Does design meet spec?
  • ✅ Timing: Can it meet target frequency?
  • ✅ Area efficiency: Is SRAM/logic sized appropriately?
  • ✅ Edge cases: Empty, full, overflow, underflow, simultaneous operations?
  • ✅ CDC safety: Any clock domain crossings handled correctly?
  • ✅ Testability: How would you verify this in simulation/post-silicon?
  • ✅ Clear communication: Did you explain rationale, not just code?

Self-Check Quiz

Q1: When designing an async FIFO, why convert pointers to Gray code?

Gray code ensures only one bit changes at a time during pointer increment. When synchronizing pointers across clock domains, if only one bit is in flight, metastability risk is limited to that one bit. Binary counters can have multiple bits changing, increasing CDC hazard.

Q2: What would you mention to show you understand practical design work?

Mention tools/flows: synthesis, P&R, timing closure, formal verification, design reviews, lint checking, or post-silicon validation. Also reference realistic constraints: power budgets, area targets, design complexity, NRE cost.

Key Takeaways

  • Problem-solving: Clarify → decompose → architect → implement → verify
  • Communication: Draw diagrams, explain rationale, discuss trade-offs
  • Edge cases: Empty/full, simultaneous access, boundary conditions matter
  • Depth signals confidence: Mention tools, flows, CDC concerns, verification strategies
  • Post-problem checklist: Verify correctness, timing, area, CDC, testability
