Q01 Procedural Blocks Senior Logic Design
Explain the exact behavioral and synthesis differences between `always @(*)` and `always_comb` in SystemVerilog.
▼
Core Technical Answer

While both are used to model combinational logic, always_comb was introduced in SystemVerilog specifically to address the shortcomings of Verilog's always @(*):

  • Implicit Evaluation at Time Zero: always_comb automatically executes once at simulation time zero, guaranteeing that its outputs are evaluated before any other procedural blocks. always @(*) only evaluates when one of its inferred sensitivities changes, potentially leading to 'x' propagation or mismatched initial states.
  • Sensitivity List Accuracy: always @(*) infers sensitivity from signals read within the block. However, it fails to infer sensitivity to variables read inside tasks or functions called from within the block. always_comb recursively analyzes functions/tasks to build a complete, accurate sensitivity list.
  • Tool Intent: always_comb explicitly tells synthesis, lint, and formal tools that the designer intends to create pure combinational logic. If the tool detects a latch (due to an unassigned path), it will generate a strict error or warning.
  • Assignment Restrictions: Variables written on the LHS of an always_comb block cannot be written to by any other process (e.g., another always_comb or always_ff block).
Q02 Data Types & Structs Lead Logic Design
What is the synthesis difference between a `packed` struct and an `unpacked` struct? How do they map to physical hardware registers?
▼
Core Technical Answer

Packed Struct:

  • Declared as typedef struct packed { logic a; logic [3:0] b; } my_struct_t;
  • Hardware Mapping: A packed struct is treated by the synthesis tool as a contiguous, single vector of bits (in this case, 5 bits).
  • Usage: It can be directly assigned to buses, cast to integer types, sliced (e.g., my_sig[4:1]), and passed through module ports seamlessly. It is the standard for representing hardware fields like packet headers, CPU instruction formats, or coherency commands (like a 512-FSM command queue entry).

Unpacked Struct:

  • Declared without the packed keyword.
  • Hardware Mapping: Synthesis tools treat it as a collection of disjoint, independent variables. There is no guaranteed contiguous bit-level representation.
  • Usage: You cannot slice it as a single vector or reliably pass it through standard logic [N:0] module ports without explicit field-by-field assignment. Unpacked structs are primarily used in testbenches (verification) or when arrays need to be passed by reference.
Q03 FSMs & Control Logic Senior Logic Design
Explain the synthesis impact of the `unique` and `priority` keywords in a SystemVerilog case statement. How do they compare to `full_case` and `parallel_case` pragmas?
▼
Core Technical Answer

SystemVerilog introduced unique and priority modifiers as native language features to replace the unsafe, synthesis-only Verilog pragmas (// synopsys full_case parallel_case).

  • `unique case`: Asserts that exactly one condition must match. If multiple conditions match (overlapping cases), or if no condition matches and there is no default clause, the simulator will throw a run-time violation. Synthetically, it behaves like a parallel_case (generating parallel logic like multiplexers or one-hot structures) and full_case (preventing latch inference).
  • `priority case`: Asserts that at least one condition must match, but multiple conditions may be true. It enforces that the first matching condition takes precedence. Synthetically, it behaves like a full_case but explicitly builds priority-encoder hardware logic.
Why is this safer for production tape-outs?

Verilog pragmas are comments ignored by the simulator. If a "don't care" state is reached, simulation might evaluate to 'x' or hold a previous state, while synthesis optimizes the logic away arbitrarily, causing a lethal simulation-synthesis mismatch. SystemVerilog keywords are enforced by the simulator, ensuring that if you violate the hardware assumption in simulation, the testbench fails immediately.

Q04 Interfaces & Modports Lead Logic Design
How do SystemVerilog `interface` constructs and `modport` definitions simplify complex interconnect fabrics (like AXI or PAU Nest Fabric), and what are the synthesis limitations?
▼
Core Technical Answer

Interfaces bundle multiple related signals into a single port connection. In complex designs like a Power12 PAU Nest Fabric or AXI mesh, passing hundreds of signals (e.g., AWVALID, AWADDR, AWID, etc.) explicitly through every hierarchy level is error-prone and brittle.

Modports (Module Ports): While an interface bundles wires, a modport defines the directionality (input, output, inout) of those wires for a specific endpoint.

Example Syntax
interface axi_if (input logic clk, input logic rst_n); logic [31:0] awaddr; logic awvalid; logic awready; // Master drives request, receives ready modport master (output awaddr, awvalid, input awready); // Slave receives request, drives ready modport slave (input awaddr, awvalid, output awready); endinterface
Synthesis Limitations

While highly synthesizable, interfaces have physical design limitations:

  • Parameterized Interfaces: Passing parameters (like data widths) through interface instantiations can sometimes cause issues in older synthesis tools or during structural netlist generation, as the hierarchy gets flattened differently.
  • Tasks/Functions inside Interfaces: While SV allows defining methods inside an interface, these are generally not synthesizable if they contain time delays or complex procedural logic. They are best reserved for verification (BFMs).
Q05 Data Types & Structs Senior Logic Design
In synthesizable RTL, what is the difference between `logic`, `bit`, and `wire`, and why is `logic` preferred in SystemVerilog?
▼
Core Technical Answer
  • `wire`: A Verilog-95 net type. It represents a physical connection and can have multiple drivers (resolution function). It must be driven by continuous assignments (assign) or port connections, never inside an always block.
  • `bit`: A SystemVerilog 2-state data type (0, 1). It is primarily used in verification/testbenches because it defaults to 0 (improving simulation speed). It is highly dangerous for synthesizable RTL because it cannot represent 'X' (unknown) or 'Z' (high-impedance), masking uninitialized registers or multiple-driver contentions during simulation.
  • `logic`: A SystemVerilog 4-state data type (0, 1, X, Z). It is the successor to Verilog's reg. Unlike reg, logic can be driven by either continuous assignments (assign) OR procedural blocks (always_comb, always_ff). This eliminates the tedious need to switch between wire and reg depending on how the signal is driven.

Crucial Restriction: While logic is flexible, SystemVerilog enforces that a logic variable can only have a single continuous driver. If you need tri-state buses or multiple drivers, you must revert to using a wire net type.

Q06 Procedural Blocks Lead Logic Design
Write a synthesizable `always_ff` block for an asynchronous active-low reset flip-flop. Why must the reset condition NOT evaluate `if (rst_n == 1'b0)` inside the block?
▼
Core Technical Answer
always_ff @(posedge clk or negedge rst_n) begin if (!rst_n) begin q <= 1'b0; end else begin q <= d; end end
Why `(!rst_n)` over `(rst_n == 1'b0)`?

This is a subtle simulation-synthesis mismatch trap related to 4-state logic propagation.

If the reset signal goes to an unknown 'X' state during simulation (e.g., during power-up or a CDC violation):

  • If you write if (rst_n == 1'b0), the evaluation of ('x == 0) returns false. The simulator jumps to the else block, and the flip-flop clocks in the value of d instead of resetting or going to 'X'.
  • If you write if (!rst_n), the logical NOT of 'X' is 'X'. An 'X' in the if condition evaluates to false, jumping to the else block, but standard coding guidelines often pair this with X-propagation analysis tools or strict linting to catch it. However, the most robust, synthesis-safe way to handle 'X' in resets across all simulators is to rely on strict logical negation rather than exact equality matching, or to model the 'X' state explicitly using conditional operators (? :) in the datapath.
  • Synthesis Tool Impact: Synthesis ignores the 'X' scenario completely; it just sees a multiplexer tied to the reset pin. The danger is purely in RTL simulation masking physical reset failures.
Q07 Sim/Synth Mismatch Senior Logic Design
How does unintentional latch inference occur in SystemVerilog, and how does `always_comb` handle this compared to continuous assignments?
▼
Core Technical Answer

Unintentional latch inference occurs when a variable within a combinational block is not assigned a value in every possible execution path (e.g., an incomplete if-else tree or a case statement without a default).

To preserve the logic state from the previous evaluation, the synthesis tool builds a physical level-sensitive D-Latch, which wreaks havoc on STA (Static Timing Analysis) and DFT (Design for Test) scan chains.

  • `always_comb` Protection: By using always_comb, you communicate design intent. Modern synthesis and linting tools (like Spyglass or JasperGold) will flag a fatal error if they detect an incomplete path inside an always_comb, whereas Verilog's always @(*) might just issue a warning.
  • Default Assignments: The best defensive coding practice is to make default assignments at the top of the always_comb block before the case or if statements.

    always_comb begin
      next_state = current_state; // Default prevents latch
      case(current_state)...
Q08 Data Types & Structs Lead Logic Design
Can you use Enums for state machine encoding? How do you force synthesis tools to use One-Hot or Gray encoding instead of binary?
▼
Core Technical Answer

Yes, enum is the preferred method for FSMs in SystemVerilog because it provides strongly-typed states and makes waveform debugging human-readable.

typedef enum logic [1:0] { IDLE = 2'b00, REQ = 2'b01, ACK = 2'b10 } state_t; state_t current_state, next_state;

Controlling Synthesis Implementation:

Even if you explicitly define binary values (like above), synthesis tools (like Design Compiler or Genus) will often ignore your values and aggressively re-encode the FSM to optimize for timing or area (e.g., auto-converting a binary FSM to One-Hot if the state count is large).

To force a specific encoding, you must use synthesis attributes directly in the RTL:

// (* syn_encoding = "onehot" *) or (* fsm_encoding = "one_hot" *) depending on tool (* fsm_encoding = "gray" *) typedef enum logic [2:0] { IDLE, REQ, ACK, DONE } state_t;
Q09 FSMs & Control Logic Senior Logic Design
What is the synthesis implication of using a `generate` block (like `genvar` loops) for instantiating logic arrays versus using a behavioral `for` loop inside an `always_comb` block?
▼
Core Technical Answer

`generate` loops (genvar):

  • Evaluated during the elaboration phase of synthesis, before any logic optimization happens.
  • Used to structurally instantiate multiple modules, interfaces, or continuous assignments (assign) dynamically based on parameters.
  • Creates physical, distinct structural hierarchy elements in the netlist.

`for` loops inside `always_comb`:

  • Evaluated as part of the procedural behavior. The synthesis tool unrolls the loop completely and synthesizes the resulting combinational logic equations.
  • Cannot be used to instantiate modules or continuous assignments.
  • Used for things like combinational bit-reversal, priority encoders, or calculating parity across a data bus.
