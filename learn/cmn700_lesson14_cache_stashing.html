Cache Stashing in Depth

The one optimisation that pushes instead of pulls — and the only one whose failure mode makes things actively worse. Previously a section inside Lesson 6; promoted here so it stands on its own.

By the end of this lesson you can

  • Explain how a stash is targeted — which agent, and which cache level.
  • Say why a stash is advisory, and what it means that a target may decline it.
  • Describe the coherency-state and snoop-filter consequences of stashing.
  • Explain the cache-pollution failure mode and the three conditions for a stash to pay off.
  • Contrast stashing with prefetching, and debug a stash that is not helping.

1Push versus pull

caveman mode

Normal way: hungry consumer go fetch data. Stash way: producer push data into consumer cache before consumer even ask. Packet arrive, NIC shove it into the core cache that will process it. Cold miss become hit. But careful — push into wrong cache and you throw out something useful. Then you made it slower.

Every other optimisation in this course is a pull: a requester asks for something, and the fabric answers faster. DMT removes a data leg. DCT avoids DRAM. Atomics avoid line migration. All of them improve what happens after a request is issued.

Stashing inverts the direction. A producer — typically a NIC, an accelerator, or a DMA engine — pushes data toward a cache so that it is already warm when the consumer eventually looks. The consumer's request then hits instead of missing.

It is the only optimisation in the set whose failure mode makes things actively worse rather than merely failing to help. That asymmetry is why it deserves a lesson of its own, and why interviewers use it to separate people who know the feature list from people who understand the memory system.

What is actually being saved

Not bandwidth. The data had to cross the fabric regardless — the packet was arriving either way. What stashing changes is when the memory latency is paid: before the consumer needs the data, off the critical path, rather than in front of the consumer as a blocking miss. Say this precisely, because "stashing saves bandwidth" is wrong and an interviewer may be listening for it.

2Targeting a stash

A stash is not "write this somewhere useful" — the request has to name a destination. Two independent choices matter, and they carry different risk.

ChoiceMeaningRisk if wrong
Which agentThe stash identifies a target requester — conceptually "put this near this core or cluster". This is what lets a NIC aim a packet at the specific core that will process it.High. Target the wrong core and you both fail to help the real consumer and pollute an innocent cache.
Which cache levelThe hint can express whether the line should land in a cache close to the core, or in the shared SLC region.Moderate. Closer means a faster hit but a smaller, more precious resource, so aggressive close-in stashing pollutes sooner.

The trade in one line: closer to the core is a bigger win when right and a bigger loss when wrong. Stashing into the shared SLC is the conservative choice — less upside, much less pollution risk, because the SLC is large and shared by design.

Exact field names and encodings are a CHI and TRM lookup. What matters conceptually is that both who and how close are expressible, because they are separate decisions with separate consequences.

3A hint, not a command

This is the detail most candidates miss, and the one that most changes how you reason about the feature.

A stash is advisory. The target is permitted to decline it. If the target cache is under pressure, or the request arrives at an inconvenient moment, the data may end up at a shared level instead, or simply be written toward memory as an ordinary write would be.

Accepted versus declined — both are correct outcomes
   producer issues write + stash hint (target: core N)
        |
        +--- target ACCEPTS  -> line lands near core N   -> later read HITS
        |
        +--- target DECLINES -> line goes to a shared level
                                or toward memory           -> later read MISSES

   both paths are functionally correct - coherency is never at risk.
   only the performance benefit differs.

The consequence for real systems is important: stashing can be enabled and doing nothing at all, silently. There is no error, no fault, no log line. If you expected a hit-rate improvement and do not see one, the question is not only "is it configured" but "is it being accepted" — and those need different investigations.

4What it does to coherency state

A stashed line is a real cached copy. It is not metadata or a prediction — it is a line in a cache, with all the obligations that implies. Using Appendix B's vocabulary:

  • The line arrives in a defined coherence state and is snoopable like any other copy. A later writer elsewhere must invalidate it.
  • The target cache did not request this line, yet now holds it — so from the home node's perspective a new sharer has appeared for that address.
  • If the stash carries modified data, the usual clean/dirty reasoning applies: someone owes the writeback, and that responsibility has to be well-defined.

So stashing is not a free side channel into a cache. It participates fully in coherency, which is precisely why it has bookkeeping costs — covered next.

5Snoop-filter pressure — the hidden cost

Because a stash creates a sharer, the home node's snoop filter must record it. That consumes a directory entry.

Now recall Lesson 4's sizing argument: the snoop filter should be roughly 1.5× the aggregate private cache it covers, and when it runs out of entries it must evict directory entries, which forces back-invalidation of lines still live in core caches. Connect the two ideas:

Aggressive stashing raises directory occupancy
   stash accepted  ->  new sharer recorded  ->  SF entry consumed
                                                    |
        many stashes in flight                      ▼
        ------------------------------>  SF occupancy rises
                                                    |
                                    if SF becomes capacity-limited
                                                    ▼
                        back-invalidation of lines still in use  (L4)

So stashing can degrade performance through a second, indirect route that has nothing to do with the target cache: by inflating directory occupancy until the snoop filter starts evicting entries for unrelated hot lines. This is a genuinely non-obvious interaction, and naming it is a strong signal that you think about the system rather than the feature.

6Worked flow: the NIC receive path

The canonical use case. A packet arrives and some core must process it.

Cold-miss baseline versus stashed
-- baseline: no stash --
  NIC --DAT--> HN-F --> SN-F          packet written to memory
  ...later, core polls the ring...
  core --REQ--> HN-F --> SN-F         cold miss, full DRAM latency
  core <--------- DAT ---------       latency is IN FRONT of the consumer

-- with stashing --
  NIC --write + stash hint (target: core N)--> HN-F
                                                 | record new sharer in SF
                                                 ▼
                                       push line toward core N
  ...later...
  core N reads  ->  HIT                   latency paid OFF the critical path

Why this case works so well — note that all three conditions from §10 happen to hold:

  • The consumer is known, because receive-side steering has already decided which core handles this flow.
  • Consumption is imminent, because the core is polling or about to be interrupted.
  • The data is genuinely needed — a packet header will certainly be read, not speculatively guessed at.

Change any one of those and the calculation shifts. If the consumer thread migrates to another core, condition one fails and the stash lands in the wrong cache.

7The failure mode: cache pollution

The mechanism, in one sentence

A stash allocates, and allocation evicts. Push data into a cache that does not want it and you have discarded something the core was actively using, to make room for something it may never read.

The common causes, each with its own signature:

CauseWhat happens
Wrong targetThe consumer thread migrated, or steering and affinity disagree. The stash pollutes an uninvolved core while the real consumer still misses — the worst case, because you pay both costs.
Stash rate exceeds drain rateThe producer stashes faster than the consumer processes. Stashed lines begin evicting each other, so even correctly targeted data is gone before it is read.
Read-once dataData that is touched once and never reused still displaces genuinely hot lines. The stash "works" and still loses.
Target cache already under pressureA busy core has no spare capacity, so every stash is a straight trade of something useful for something speculative.
Directory pressureThe indirect route from §5 — SF occupancy rises until back-invalidation starts hurting unrelated lines.

Note the pattern: most failure modes are about the consumer, not the producer. Stashing is a statement about someone else's cache, made by an agent that cannot see its contents. That is what makes it risky.

8Stash versus prefetch

These are mirror images, and the symmetry is genuinely illuminating.

Prefetch (pull)Stash (push)
Initiated byThe consumer, speculating about its own futureThe producer, which is holding real data
Knows the data exists?No — guessing an addressYes — it has the data in hand
Knows the consumer?Yes, trivially — itselfNo — must be told, and can be wrong

Throttled byCBusy prefetch throttling (Lesson 7)Target declining the hint (§3)
caveman mode

Prefetcher know who but guess what. Stash know what but must be told who. Each only as good as the half it not control. That the whole insight.

They are complementary rather than competing: prefetching hides latency for data a consumer can predict, stashing hides latency for data a producer knows is coming. A well-tuned system uses both, on different traffic.

9Interaction with QoS and congestion control

Stashing does not live in isolation from Lesson 7's mechanisms, and the interactions are worth being able to discuss:

  • Stashes are real fabric traffic. They consume mesh bandwidth and home-node tracker capacity like any other write, so they participate in QoS arbitration and can be queued behind other work.
  • Under congestion, stashing gets less useful. When completers are busy, a stash competes with demand traffic — and it is speculative about usefulness even though it is certain about the data. Congestion is exactly when you would rather not spend capacity on optimisations.
  • Declining becomes more likely under load, which is a reasonable behaviour: the mechanism degrades toward "do nothing" precisely when the system is stressed.
  • Prioritisation matters. A stash given the same QoS class as latency-critical demand traffic can displace it. Bulk stashing generally wants a lower class.

Compare with CBusy from Lesson 7: prefetch throttling is a closed loop that reduces speculative load under congestion. Stash declining is a looser analogue — a target-side rather than source-side pressure valve.

10Decision framework: should you stash?

Three conditions, all of which must hold. This is the compact answer to "when should you use stashing?"

1. Consumer known

You can identify which agent will read the data, and that identity is stable — no thread migration between stash and consumption.

2. Consumption imminent

The data will be read soon, so it survives in the cache until it is needed rather than being evicted first.

3. Room to spare

The target cache has capacity, and the snoop filter is not near its limit. Otherwise you are trading away something useful.

ScenarioStash?Why
NIC receive with steering pinned to a coreYesAll three conditions hold; the canonical win.
Accelerator writing results a known core will read nextYesKnown consumer, imminent read.
Bulk DMA of a large bufferNoVolume exceeds any cache; stashes evict each other and pollute. Let it go to memory.
Data consumed much laterNoWill be evicted before use — you paid the pollution cost for nothing.
Consumer thread migrates freelyNoCondition one fails; you will frequently target the wrong cache.
Target cores already cache-pressuredCarefulConsider stashing to the shared SLC instead of close to the core.

11Debugging a stash that is not helping

Using Lesson 9's instrumentation, in order:

StepCheckInterpretation
1Is the consumer's hit rate actually improving?If not, the mechanism is not delivering — continue. Do not assume it works because it is enabled.
2Are stashes being accepted?If largely declined, the target is under pressure — consider stashing to the SLC instead, or reducing rate.
3Is the target correct?Compare steering or affinity configuration against where the consumer thread actually runs. Migration is a common culprit.
4Has the target's eviction rate risen?Rising evictions with flat or worse hit rate is the pollution signature.
5Has snoop-filter back-invalidation risen?The indirect cost from §5 — stashing is inflating directory occupancy and hurting unrelated lines.
6Is stash rate above consumer drain rate?Stashed lines are evicting each other; throttle the producer or stash further out.

The diagnostic pair worth memorising: evictions up while hit rate is flat or falling is pollution. Hit rate flat with no change in evictions suggests the stashes are being declined and nothing is happening at all.

13Interview Q&A

What is cache stashing and what does it save?
It inverts the usual direction of data movement: instead of a consumer pulling data, a producer such as a NIC or accelerator pushes it toward a cache so it is already warm when the consumer looks. Crucially it does not save bandwidth — the data had to cross the fabric regardless. What it changes is when the memory latency is paid: off the critical path, before the consumer needs it, rather than as a blocking miss in front of it. The canonical case is a NIC stashing an inbound packet toward the core that receive-side steering has already assigned to that flow.
You enable stashing and performance gets worse. Why?
Cache pollution. A stash allocates, and allocation evicts, so pushing data into a cache that does not want it discards something the core was actively using in favour of something it may never read. Common causes: the consumer thread migrated so the stash targets the wrong core, which is the worst case because the real consumer still misses; stashing faster than the consumer drains, so stashed lines evict each other; stashing read-once data that displaces genuinely hot lines; and a target cache already under pressure, where every stash is a straight trade of useful for speculative. There is also an indirect route — each accepted stash creates a sharer and consumes a snoop-filter entry, so aggressive stashing raises directory occupancy and can trigger back-invalidation of unrelated lines.
Is a stash guaranteed to land where you asked?
No — it is advisory, and the target is permitted to decline it. Under pressure the line may end up at a shared level or simply be written toward memory. Both outcomes are functionally correct and coherency is never at risk; only the performance benefit differs. That matters for debugging, because stashing can be enabled and silently doing nothing, with no error or log line. So when a stash is not helping, the first two questions are whether it is configured and whether it is being accepted, and those need different investigations.
How does stashing differ from prefetching?
They are mirror images. A prefetch is a pull: the consumer initiates it and trivially knows the consumer is itself, but it is guessing which address it will need, and it can see its own cache. A stash is a push: the producer initiates it and knows the data is real because it is holding it, but it must be told who the consumer is, can be wrong, and cannot see the target cache. So a prefetcher knows who but guesses what; a stash knows what but must be told who. Each is only as good as the half it does not control, and the failure modes follow — wasted bandwidth for prefetch, which CBusy throttles, versus polluting someone else's cache for a stash.
When should you use stashing, and when not?
Three conditions must all hold: the consumer is known and stable, consumption is imminent so the line survives until it is read, and the target has room to spare including snoop-filter headroom. NIC receive with steering pinned to a core satisfies all three, as does an accelerator writing results a known core reads next. Do not stash bulk DMA of a large buffer, because the volume exceeds any cache and the stashes evict each other; do not stash data consumed much later, because it will be evicted before use; and do not stash when the consumer thread migrates freely. If target cores are already pressured, stash to the shared SLC instead of close to the core — less upside, much less pollution risk.
How would you debug a stash that is not helping?
Work outward from the consumer using the PMU. First confirm whether the consumer's hit rate actually improved, rather than assuming the feature works because it is enabled. Then check whether stashes are being accepted or declined, since declining points at target pressure. Then verify the target is correct by comparing steering or affinity configuration against where the consumer thread really runs. Then look at the target's eviction rate, because rising evictions with a flat or falling hit rate is the pollution signature. Then check snoop-filter back-invalidation for the indirect cost. Finally compare stash rate against consumer drain rate. The pair worth remembering: evictions up with hit rate flat means pollution; hit rate flat with evictions unchanged means the stashes are probably being declined and nothing is happening.
How does stashing interact with QoS and congestion control?
Stashes are real fabric traffic, so they consume mesh bandwidth and home-node tracker capacity and participate in QoS arbitration. That means under congestion stashing becomes less attractive, because it competes with demand traffic while being speculative about usefulness even though it is certain about the data. Declining also becomes more likely under load, which is reasonable behaviour — the mechanism degrades toward doing nothing exactly when the system is stressed. And prioritisation matters: a stash sharing a QoS class with latency-critical demand traffic can displace it, so bulk stashing generally wants a lower class. It is a looser, target-side analogue of CBusy's source-side prefetch throttling.

14Recap & key terms

  • Stashing is a push, not a pull — the producer warms a consumer's cache in advance.
  • It saves latency position, not bandwidth: the data moved anyway.
  • Targeting names which agent and which cache level; closer is bigger win when right, bigger loss when wrong.
  • It is a hint the target may decline — so it can be enabled and silently doing nothing.
  • A stashed line is a real sharer → consumes a snoop-filter entry → can trigger back-invalidation (L4).
  • Failure mode is cache pollution: allocation evicts. Most causes concern the consumer, not the producer.
  • Mirror of prefetch: prefetch knows who and guesses what; stash knows what and must be told who.
  • Three conditions to stash: consumer known, consumption imminent, room to spare.
  • Diagnosis: evictions up + hit rate flat = pollution; hit rate flat + evictions unchanged = being declined.
