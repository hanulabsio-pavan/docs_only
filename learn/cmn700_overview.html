Arm Neoverse · Coherent Mesh Network

ARM CMN-700 — the big picture

You already know CHI and how a NoC carries it. CMN-700 is the actual silicon mesh that implements that protocol at scale: the routers, the home nodes, the caches, and the glue that ties cores, memory, and accelerators into one coherent system. This map keeps everything high-level so you can hold the whole thing in your head before the deep dive.

01What is CMN-700?

caveman mode

Many brains (CPU). Many memory. Many helper-chip (accelerator). All must share same data, not fight. CMN-700 = the road grid in the city. Cars = CHI messages. Crossroads = routers. CMN-700 build the roads, put traffic cops, keep everyone's data fresh. Bigger city than old CMN-600. Same CHI language you already know.

CMN-700 is Arm's 3rd-generation coherent interconnect IP — the successor to CMN-600. It is a configurable, scalable 2-D mesh that connects Armv9/Armv8 CPU clusters, accelerators, I/O and memory into a single cache-coherent system. The on-chip transport language is native AMBA 5 CHI (CHI Issue E / "CHI-E"), so everything you learned about REQ/RSP/SNP/DAT, snoops, and cache states applies directly — CMN-700 is the micro-architecture that realises CHI in hardware.

Distributed

No central crossbar. Caches, home nodes and snoop filters are spread across the mesh tiles.

Configurable

Mesh size, node placement, cache size, channel width — all chosen at build time via Arm's Socrates tool.

Scalable

From a 2×4 edge SoC to a 12×12 server backplane spanning multiple dies and sockets.

02Where it fits

CMN-700 is the coherent backplane in Arm's Neoverse infrastructure platform — targeting networking, storage, server, HPC, automotive and industrial SoCs. It is built to pair with Neoverse N2 / V1-class cores and to ride next-gen interfaces: DDR5, HBM3, PCIe Gen5, CXL, CCIX.

04The mesh & crosspoints (XP / MXP)

caveman mode

Grid of crossroads. Each crossroad = XP (router). Talk to 4 neighbor crossroads: north, south, east, west. Each crossroad also has driveways (device ports) where a CPU, a cache, or a memory plug in. Message hops crossroad-to-crossroad until it reach the right driveway.

The mesh is a rectangular grid of crosspoints — the router building block, written XP or MXP (Mesh Cross Point). Each XP has:

  • 4 mesh ports (N/S/E/W) linking to neighbouring XPs — credited, non-blocking links.
  • Device ports where components attach: a CHI agent (cores), an SLC/HN-F slice, a memory interface (SN-F), or an AMBA bridge. CMN-700 supports up to 3 devices per XP (4 on an edge XP).

Every XP has an (X,Y) coordinate: (0,0) is bottom-left, (11,11) top-right on a full grid. These coordinates (XID/YID) form the basis of the node IDs used for routing.

06Node taxonomy — the cast of characters

caveman mode

Three kinds of villager. Requester = asks for data (CPU, I/O). Home = owns the truth for an address, keeps the cache, sends snoops. Subordinate = the memory at the end. Everyone else is a bridge or a doorman.

Request Nodes (RN) — they start transactions
NodeRole
RN-FFully coherent requester. CPU clusters (via DSU) with hardware-coherent caches. The classic "I have a cache, snoop me" node.
RN-II/O-coherent requester. A bridge for AMBA masters (ACE5-Lite); has no coherent cache — acts as a proxy, can be snooped-into but holds nothing.
RN-DAn RN-I that also handles DVM (distributed virtual-memory / TLB-maintenance messages).
Home Nodes (HN) — the point of coherency & serialization
NodeRole
HN-FFully coherent home node. Holds an SLC slice + snoop filter; serialises all requests to its address range, issues snoops, is the Point of Coherency. (In CMN-700 register/PMU naming you'll also see this called HN-S / HNS.)
HN-II/O home node — proxy for AMBA slave subsystems; converts CHI → ACE5-Lite. No caching, generates no snoops.
HN-DHN-I plus the DVM node, the DTC (trace controller) and the configuration (CFG) node. Every CMN-700 must contain one HN-D — it's the boot/config anchor.
HN-PI/O home node with PCIe optimisation — adds a dedicated tracker for PCIe peer-to-peer traffic. Connects PCIe subordinates.
Subordinate Nodes (SN) — the memory endpoints
NodeRole
SN-FFully coherent subordinate = the memory controller interface (DMC for DDR5/HBM). Where reads/writes finally land.
SBSXA CHI → ACE5-Lite bridge that behaves like an SN-F, used to attach ACE5-Lite slaves (e.g. CoreLink DMC-400).
Glue & bridges (worth a name-drop)
CAL — Component Aggregation Layer

Lets multiple devices share one XP device port — key to fitting many components on a modest mesh.

ADB / CDB — domain bridges

AMBA Domain Bridge / CHI Domain Bridge cross clock & power/voltage domains between two interfaces.

CFG — configuration node

Co-located with HN-D; owns CMN-700 config, control and monitoring register space.

CCG — CML gateway

The multichip gateway (see §11). Bridges on-chip CHI to chip-to-chip CXS.

07System Level Cache & snoop filter (inside HN-F)

caveman mode

Home node carry two notebooks. Notebook 1 = SLC: a shared last-level cache slice, so data stay on-chip and brain not wait for far-away memory. Notebook 2 = snoop filter: a list of "who has copy of this line", so home node only poke the caches that actually hold it — not shout at everyone.

The SLC is the system's last-level cache, physically chopped into slices — one per HN-F — and spread across the mesh. Addresses are hashed/interleaved across HN-F slices so traffic and capacity spread evenly. Allocation policy is typically exclusive for data lines (avoids wasteful duplication with the cores' private caches); with MTE enabled, slices store data and tags.

The snoop filter (SF) co-located in each HN-F tracks which RN-Fs hold which lines, so the home node sends targeted snoops instead of broadcasting. A practical sizing rule interviewers like: the SF needs to be roughly 1.5× the aggregate exclusive (private) cache of the cores it covers — undersize it and you get SF-induced back-invalidations that hurt performance.

Why distribute it?

Bandwidth scales with slice count, and a request only travels to the one home node owning that address — no global bottleneck.

Point of Coherency

The owning HN-F serialises all outstanding requests to a line, orders them, and is the single source of truth — your CHI ordering knowledge maps straight here.

08System Address Map (SAM) — how a message finds its target

caveman mode

Message know the address but not which crossroad. SAM = the lookup table: "this address lives at node #40". Requester's SAM say which home node. Home node's SAM say which memory. Without SAM, message lost.

Every RN and HN contains a SAM that turns a physical address into a destination target node ID. Routing on the mesh is by node ID, so the SAM is the address→ID translator that makes coherency work:

SAMMaps
RN SAMPhysical address → home node target ID (HN-F, HN-I, HN-D, HN-P, … or a CCG for remote). Can also target a memory controller directly for prefetch hints.
HN-F SAM / MC SAMAddress → memory-controller (SN) target ID, once the home node decides it must go to DRAM.

The HN-F selection step uses an address hash to interleave across home nodes. Getting the SAM and hashing right is central to balancing the mesh — and is exactly the kind of thing a CMN-700 role cares about.

09CHI-E features CMN-700 leans on

Because the mesh is native CHI Issue E, it exposes the CHI-E performance features in hardware. You know CHI — here's where to point at the silicon:

Direct Memory Transfer (DMT)

Home node lets the SN return data straight to the requester, cutting a hop vs. routing data back through the HN.

Direct Cache Transfer (DCT)

A snooped RN-F forwards the line directly to the requesting RN-F — cache-to-cache, bypassing memory.

Atomics

Near-memory / near-home atomic ops (add, swap, compare) instead of read-modify-write round trips.

Cache stashing

An agent can push data into a target cache (e.g. NIC stashing into a core's SLC region) to pre-warm it.

If asked "what does CMN-700 add over plain CHI?" — the answer is the physical realisation: distributed home nodes/SLC, the SAM/hashing, QoS & congestion control, multichip gateways, and the PMU. CHI is the contract; CMN-700 is the implementation.

10DVM — Distributed Virtual Memory

DVM operations are the broadcast maintenance messages — TLB invalidations, instruction-cache invalidations, sync — that keep virtual-memory state consistent across cores. In CMN-700 they're funnelled through a DVM node (DN) that lives in the HN-D, and the requesters that issue/receive them are the RN-D variants. High-level: this is how an TLBI on one core reaches every other core's MMU.

11Multichip — CML, CCG & the Super Home Node

caveman mode

One die not big enough. Glue many dies/sockets together, still act like one coherent machine. CML = the coherent bridge between chips. CCG = the gateway box that translates on-chip CHI into chip-to-chip language (CXS) and back.

CML (Coherent Multichip Link) extends coherency beyond a single die — for chiplets, multi-die packages and multi-socket SMP. The gateway is the CCG (CML / CXL-CCIX gateway), which bridges on-chip CHI ↔ CXS Issue B (the chip-to-chip transport carrying CCIX 2.0 or CXL).

Inside a CCG you'll find three agents — a clean parallel to the on-chip request/home/link split:

AgentRole
CCRACCIX/CXL Request Agent — proxies remote requesters into the local mesh.
CCHACCIX/CXL Home Agent — represents remote home/coherency on this die.
CCLACXS Link Agent — the link-layer that drives the physical chip-to-chip interface (optionally with an embedded RN-I for PCIe-to-remote-memory).

The older CXG gateway (agents CXRA/CXHA/CXLA) supports CHI + CXS Issue A (CCIX 1.1). The newer CXS-B fast path bypasses the transaction layer straight to the link layer to cut remote-access latency.

Super Home Node

A CMN-700 concept for multi-die systems: a home node (or a whole mesh acting as one) that is the central coherency point for memory shared across dies. It can hold SLC + local home for remote memory, enabling chiplet topologies (a central I/O die + compute dies, AMD-style).

12CXL & CCIX — and why both

CMN-700 supports both because they solve coherency from opposite ends:

CCIX

Coherency resolved near the memory — the home node, cache and snoop filter live nearest the shared memory. Better for distributed cache & snooping across symmetric peers / multi-socket SMP.

CXL

Host-based coherency — the host owns shared memory and maintains snoop state. Simpler to build coherent accelerators and memory-pooling/expansion devices against.

CMN-700 grew CCIX device ports from 4 (CMN-600) to 32, and added CXL gateways — a clear bet on accelerator- and memory-disaggregation-heavy systems.

13QoS & congestion control

caveman mode

Roads get jammed. Two tricks: (1) tell greedy CPU "slow down, stop prefetching so hard" when memory busy. (2) when one road jammed, send some cars a different way for a while.

CBusy (Completer Busy)

Memory/home congestion is signalled back to the core, which throttles prefetcher aggressiveness and outstanding transactions. Arm reported up to ~15% uplift on a Neoverse V1 design. (Early name: "MemBusy".)

Hot-spot re-routing

When an XP/route is congested, traffic is temporarily steered through alternative XPs to relieve the jam.

On top of these, CMN-700 carries CHI QoS priority classes per transaction, so latency-critical flows can be prioritised over bulk traffic across the fabric.

14MPAM — partitioning & monitoring

MPAM (Memory System Resource Partitioning and Monitoring), an Armv8.4 feature, lets software tag traffic with a partition ID and then partition SLC capacity and memory bandwidth per VM/process. CMN-700 implements MPAM in the home nodes (note the HNS_MPAM_S / HNS_MPAM_NS node variants) and extends it to the memory controllers — so a hypervisor can stop one noisy VM from hogging shared cache/bandwidth.

15PMU, debug & trace (DTC / DTM)

caveman mode

Want to know what the roads are doing. Put a little counter at every crossroad (DTM). One boss counter (DTC) adds them up and writes a logbook (trace). Now you can see traffic, find jams, measure bandwidth.

CMN-700 has a distributed PMU — central to any performance/validation role:

BlockWhereWhat it does
DTM — Debug & Trace Monitorone at every XPCounts up to 4 local event signals; supports watchpoints that match/mask specific flits (val + mask, channel/device select) for upload & download.
DTC — Debug & Trace Controllerin HN-D / HN-TGlobal PMU control; aggregates DTM overflows into up to 8 global counters; raises overflow interrupts; emits timestamped trace via ATB.

Linux exposes this as arm_cmn_0 (one PMU per mesh; arm_cmn_1..n for additional linked meshes). Events can be aggregated over a node type or targeted to a specific node by nodeid.

16Power management

CMN-700 is partitioned into multiple clock and power/voltage domains, crossed by the ADB/CDB bridges. Power handshakes use the standard Arm low-power channels: Q-channel (clock/quiescence) and P-channel (power-state) so blocks (XPs, SLC slices, gateways) can be clock-gated or powered down when idle, with hardware ensuring the fabric drains and stays coherent across the transition.

17RAS — reliability, availability, serviceability

As an infrastructure/server interconnect, CMN-700 implements Arm RAS: ECC/parity protection on SLC data and tags, snoop-filter and internal RAM protection, and error-record registers so corrected/uncorrected errors can be logged and reported to software. High-level talking point: a server-class mesh must detect, contain and report data corruption, not just move data fast.

18Programming model & configuration

  • Build-time: the mesh is configured with Arm's Socrates tool — grid size, node placement, SLC size, channel width, gateways. The result is a specific topology baked into RTL.
  • Boot-time: software programs the SAM (address→target maps) and home-node hashing before coherent traffic flows. Until then, RN SAMs default-route to the HN-D, which does not keep coherency — so config order matters.
  • Register space: each node exposes a register region; the CFG node (with HN-D) anchors discovery — software walks the mesh to enumerate node types, IDs and coordinates.

19Likely interview questions

Tap each to reveal a high-level answer framed around what you already know from CHI/NoC. Aim to connect CMN-700 structures to CHI concepts — that's what shows depth.

What is CMN-700 and how does it relate to CHI?
CMN-700 is Arm's 3rd-gen coherent mesh interconnect IP. CHI (Issue E) is the protocol; CMN-700 is the micro-architecture that implements it — a 2-D mesh of crosspoints (routers) connecting RN/HN/SN nodes, with distributed SLC + snoop filters in the home nodes. The four CHI channels (REQ/RSP/SNP/DAT) run as independent flit networks across the mesh.
Walk me through what happens on a read miss from a core.
Core's RN-F issues a CHI REQ. Its RN SAM hashes the address to the owning HN-F and routes by node ID across the mesh. The HN-F (Point of Coherency) checks its SLC slice and snoop filter; on a miss it consults its MC SAM and sends the request to the right SN-F memory controller. Data returns (optionally via DMT directly to the requester), the HN-F updates SF/SLC state, and the line is filled in the right CHI cache state.
What's inside an HN-F, and why distribute it?
An SLC slice (last-level cache) plus a snoop filter. It's the Point of Coherency/Serialization for its address range. Distributing one HN-F per tile means bandwidth scales with slice count and each request travels to exactly one home node — no central crossbar bottleneck. Addresses are hashed across HN-Fs to balance load.
How is the snoop filter sized, and what happens if it's too small?
Rule of thumb: the SF should be ~1.5× the aggregate private (exclusive) cache of the cores it covers. Undersized → SF capacity evictions force back-invalidations of lines still live in core caches, causing spurious misses and performance loss. It's a real area-vs-performance trade in mesh sizing.
What's the difference between RN-F, RN-I and RN-D?
RN-F = fully coherent, has hardware-coherent caches (CPUs). RN-I = I/O-coherent bridge for AMBA masters, no coherent cache (a proxy). RN-D = an RN-I that also handles DVM (TLB-maintenance) messages.
How does CMN-700 scale across multiple chips?
Via CML using CCG gateways that bridge on-chip CHI to chip-to-chip CXS-B (CCIX 2.0 / CXL). Inside the CCG: CCRA (request agent), CCHA (home agent), CCLA (link agent). For shared remote memory, a Super Home Node acts as the central coherency point. This enables chiplets and multi-socket SMP that still look coherent.
CCIX vs CXL — when would you use each?
CCIX: coherency resolved near the memory (home/SF live by the shared memory) — good for symmetric peers and distributed cache. CXL: host-based coherency (host owns shared memory and snoop state) — simpler for accelerators and memory pooling/expansion. CMN-700 supports both.
How would you debug a bandwidth/latency problem on the mesh?
Use the distributed PMU: per-XP DTM counters and watchpoints (match specific flits by channel/device) feed up to 8 global DTC counters in the HN-D, with timestamped ATB trace. In Linux it's the arm_cmn PMU. You'd localise hot XPs/home nodes, check SAM hashing balance, look at CBusy throttling and whether hot-spot re-routing is firing.
What is CBusy and why does it matter?
Completer Busy: when memory/home queues get congested, that pressure is signalled back to cores, which throttle prefetcher aggressiveness and outstanding transactions — preventing collapse under load and improving effective throughput (Arm cited ~15% on a V1 design). It's closed-loop congestion control on the fabric.
What does MPAM do here?
Lets software partition shared SLC capacity and memory bandwidth by partition ID, implemented in the home nodes and extended to memory controllers — so one VM can't starve others of shared cache/BW. Important for multi-tenant server SoCs.
Why are there four separate channels on the mesh?
REQ, RSP, SNP and DAT are independent virtual/physical networks so different message classes can't block each other — this is how the fabric avoids protocol deadlock and stays non-blocking, mirroring CHI's channel separation.
