Link Layer — activate, credit, gate

The plumbing between transport logic and the physical CHI link wires. Owns the link activation FSM, initializes credit pools per channel, gates TX flits on link-up + credits, and pipes RX flits back to transport. Two files: a slim integrated chi_link_layer and a more detailed chi_link_training standalone trainer.

1Why a link layer at all?

The transport layer above produces logical CHI flits; the physical CHI interface below is just wires. The link layer in between handles three things transport shouldn't have to think about.

ResponsibilityWhat it doesWithout it…
Link activation Drives txlinkactivereq and waits for txlinkactiveack before any traffic flows. Flits sent into an un-trained link silently disappear.
Credit accounting Maintains per-channel credit pools. Gates tx_*_ready on credit availability. Sender overruns the receiver's buffer and data is lost.
Channel multiplexing Routes the four CHI channels (REQ/RSP/SNP/DAT) onto / off the physical interface. Transport would have to know modport details (which signal goes which way for which node type).

Note that hanuma has two implementations here. chi_link_layer.sv is the integrated version actually wired into the data path — it has a compact 3-state FSM (RESET → ACTIVATE → ACTIVE) and instantiates three credit_managers directly. chi_link_training.sv is a more thorough standalone trainer with the full 8-state FSM including deactivation handshake and timeout-to-error, intended to be plugged into a future revision of chi_link_layer.

5Known issues

Items flagged in the DV tracker for the link-layer files. Several are stubs awaiting full implementation; one was a real bug.

🔶 Deactivation logic is a stub in chi_link_layer
The compact FSM in chi_link_layer.sv has only 3 reachable states (RESET → ACTIVATE → ACTIVE); LINK_ST_DEACT_REQ and DEACT_ACK are enum-declared but never entered. The full deactivation path lives in chi_link_training.sv instead and needs to be merged in. DV tracker §1.4.
⚠ RX channel sourcing was originally wrong
The DV tracker noted at one point that chi_link_layer.sv:184 had rx_rsp_valid = phys_link.txrspflitv — sourcing from the TX signals on the requester modport. Current RTL fixes RSP and DAT to use rxrspflitv / rxdatflitv correctly. SNP remains on txsnpflitv because on the requester modport, SNP is RX (the completer drives the wire as its TX). Worth re-reading the comment in chi_link_layer.sv:185 to internalize the modport orientation.
🔶 SNP credit pool not instantiated
Parameter INIT_SNP_CREDITS exists but no credit_manager instance for SNP in the requester-side chi_link_layer. That's deliberate — the requester doesn't send SNP, only receives — but the parameter is dead. Either remove it or wire it for the completer-side version.

7Check yourself

Q1. Transport drives tx_req_valid = 1 immediately after reset. Why does the flit not flow?
tx_req_ready = link_up && req_crd_avail. At reset both are 0 — the FSM is in LINK_ST_RESET, so link_up is 0; and credit_manager's credit_count hasn't been initialized yet, so req_crd_avail is also 0. Once the FSM reaches ACTIVATE and the peer acks, the link-training pulse initializes credits and link_up goes high.
Q2. Why does chi_link_training have 8 states but chi_link_layer only really uses 3?
They are two implementations at different maturity levels. chi_link_layer is the integrated path-of-least-resistance — enough to bring up traffic but no graceful shutdown. chi_link_training is the future replacement with full deactivation handshake (DEACT_REQ → DEACT_ACK → STOP → re-RESET) and a timeout-to-ERROR path. The plan is to merge them.
Q3. On the requester modport, why does the link layer read RX SNP from phys_link.txsnpflitv instead of an rxsnp* signal?
Modport orientation. The requester modport in chi_link_if declares SNP as an input direction — but the underlying wires keep the name from the completer's TX perspective. So on the requester side, txsnpflitv is what comes in on the SNP channel. REQ/RSP/DAT have separate rx*-named wires for each direction; SNP is asymmetric (only completer ever sends it).
Q4. The credit-init pulse must fire for exactly one cycle. How is that guaranteed?
chi_link_training.sv:93: crd_init_valid <= (state_d == LT_CRD_INIT) && (state_q != LT_CRD_INIT) — that's a rising-edge detector. state_d == LT_CRD_INIT && state_q != LT_CRD_INIT is true only on the cycle the FSM enters CRD_INIT. The next cycle state_q == LT_CRD_INIT too, so the condition is false and the pulse falls. The FSM then immediately advances to ACTIVE.
