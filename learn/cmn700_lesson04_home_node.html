Home Node Internals — SLC + Snoop Filter

The coherency heart: a distributed last-level cache and the directory that drives targeted snoops.

By the end of this lesson you can

  • Describe the SLC slice: organisation, exclusive allocation, MTE tag storage.
  • Explain the snoop filter as a directory and why snoops become targeted.

1Opening up the HN-F

caveman mode

Home node carry two notebooks. Notebook A = SLC: shared big cache slice, keep hot data on-chip so brains don't wait for far memory. Notebook B = snoop filter: list of "who has a copy", so home only pokes the caches that actually hold the line. This lesson = read both notebooks.

The HN-F (called HN-S in newer naming) is where coherency lives. It does three things: caches data (SLC slice), tracks who else caches it (snoop filter), and orders all requests to its addresses (Point of Coherency). Get these and most "hard" CMN questions become easy.

2The System Level Cache slice

The SLC is the system's last-level cache, physically chopped into slices — one per HN-F — and spread across the mesh. Addresses are hashed across slices (Lesson 5) so capacity and traffic spread evenly. Up to 512 MiB total, roughly 4 MiB per slice.

Exclusive allocation (data)

Data lines are typically allocated exclusively with respect to the cores' private caches — avoids wasting SLC capacity duplicating what a core already holds.

MTE: data + tag

With Memory Tagging Extension enabled, the slice stores the line's data and its memory tags together.

Why a shared LLC at all? On-chip hits avoid a DRAM round trip — the SLC exists to cut average read latency and to absorb I/O-heavy throughput (networking/storage), not just to be "more cache".

3The snoop filter (a directory)

The snoop filter (SF) is a directory co-located in each HN-F. For lines cached by RN-Fs, it records which requesters hold a copy (and roughly in what state). When a request needs to invalidate or fetch a line, the home consults the SF and sends targeted snoops to just those holders — instead of broadcasting to every cache.

Directory → targeted snoop (not broadcast)
  request for line X arrives at HN-F
            |
            ▼
   snoop filter lookup(X)  →  holders = { RN-F #2 }
            |
            ▼
   send SNP to RN-F #2 only     (RN-F #0,#1,#3 untouched)

This is the difference between a snoop-filtered mesh and a broadcast bus: snoop traffic scales with actual sharing, not with core count.

4SF sizing and back-invalidation

The SF must have enough entries to track every line the cores might hold. A common rule of thumb: the SF should be roughly 1.5× the aggregate private (exclusive) cache of the cores it covers. Undersize it and the SF runs out of entries — to make room it must evict a directory entry, which forces a back-invalidation of a line that's still live in a core's cache:

Undersized SF → spurious back-invalidations
  SF full, must track a new line
        |
        ▼  evict an existing SF entry (line Y)
   SNP invalidate → RN-F that still uses Y    ⚠ line was hot!
        |
        ▼  RN-F loses Y, will miss on it again → wasted traffic + latency

So SF capacity is a real area-vs-performance trade: too small and you pay in spurious misses; too big and you burn area/power. This is a favourite interview probe because it shows you understand the directory, not just that one exists.

5Point of Coherency & Serialization

For its address range, the HN-F is the Point of Coherency (PoC) and the Point of Serialization (PoS): every outstanding request to a given line passes through it, so it can order them, resolve hazards (two requesters racing on the same line), and guarantee a single consistent view. Your CHI ordering knowledge maps directly here — the home node is where "who wins" is decided.

  • Multiple outstanding ops to one line are serialized at the home.
  • Hazards (e.g. a snoop in flight while a new request arrives) are detected and held/retried at the home.
  • Ordering rules required by CHI are enforced from this single point.

6Why distribute home nodes at all?

Bandwidth scales

N home nodes = N independent coherency engines and N SLC slices working in parallel. Aggregate bandwidth grows with slice count.

No central bottleneck

A request travels to the one home that owns its address, not through a shared crossbar. Address hashing (L5) keeps the load balanced.

The cost is that "home" for an address might be several hops away — which is why placement and interleaving (Lessons 5 & 7) matter.

8Interview Q&A

What's inside an HN-F?
An SLC slice (last-level cache, ~4 MiB) and a snoop filter (directory of which RN-Fs hold which lines). It is the Point of Coherency/Serialization for its address range — ordering requests, issuing targeted snoops, and resolving hazards.
How is the snoop filter sized and what breaks if it's too small?
Rule of thumb ~1.5× the aggregate private cache of the cores it covers. Undersized, it evicts directory entries, which forces back-invalidations of lines still live in core caches — causing spurious misses and lost performance. It's an area-vs-performance trade.
Why exclusive SLC allocation for data?
To avoid wasting shared cache capacity duplicating lines the cores already hold privately — exclusive allocation maximises effective on-chip cache for data lines.
What is the Point of Coherency here?
The owning HN-F. All requests to a line funnel through it, so it can order them, enforce CHI ordering rules, and resolve hazards — a single source of truth per address.
Why distribute home nodes rather than have one?
Parallelism: each HN-F is an independent coherency engine + cache slice, so aggregate bandwidth scales with the number of slices and there's no central crossbar. Address hashing spreads load across them.

9Recap & key terms

  • HN-F = SLC slice + snoop filter + Point of Coherency/Serialization.
  • SLC: distributed slices (~4 MiB), exclusive data allocation, MTE stores data+tag.
  • Snoop filter = directory → targeted snoops, not broadcast.
  • SF sizing ~1.5× private cache; undersizing → back-invalidations.
  • Distribution → bandwidth scales, no central bottleneck.
