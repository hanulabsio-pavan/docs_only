1input_port — sorting flits into per-VC FIFOs

One input_port sits at each of the 5 router input directions. It decodes the channel field, looks up which VC it belongs to via channel_to_vc(), and writes to that VC's FIFO. Each VC has its own depth-8 storage.

Send a flit on:

Backpressure: ready_out

The input port asserts ready_out only when the selected VC's FIFO has room. If REQ's VC0 is full but RSP's VC1 is empty, the port is not ready for REQ but is for RSP — that's why each VC has its own FIFO.

2output_port — VC priority + credit gating

4 flit_buffers on input side; strict-priority arbitration (VC3>VC2>VC1>VC0) on output. A VC enters arbitration only if its FIFO has a flit AND it has at least one credit. Press Tick.

Dequeue condition: buf_rd_ready[vc] = any_grant && (grant_vc == vc) && link_ready;

3virtual_channel_mgr — occupancy & deadlock

Bookkeeper that tracks how many flits sit in each (port, VC) pair, allocates VCs by mapping channel → VC class, and watches for deadlock. Stall counter increments any cycle the buffer is at BUF_DEPTH; if it hits 0xFFFF the watchdog raises deadlock_suspected.

deadlock_suspected = 1: at least one (port, VC) has been at full capacity for 65,535 cycles. perf_monitor logs the event and error_handler raises irq_error.

6Check yourself

Q1. Why does input_port have four separate FIFOs instead of one shared with VC tags?
Head-of-line blocking. A single FIFO would block flits behind a stuck one even if their output ports were free. Per-VC FIFOs let each channel make independent progress.
Q2. output_port uses strict priority (VC3 > VC2 > VC1 > VC0). Could VC0 ever starve?
In theory yes. In practice the upstream protocol provides a bounded supply per transaction. VC3 (retry) is bounded by transactions in flight. DV plan TC-STRESS-002 checks this.
Q3. Why include link_ready in the dequeue condition when we already have credits?
Downstream can back-pressure for one cycle even with credits available. Without link_ready we'd dequeue from FIFO with nowhere to send — data lost. Credits are upstream flow control; link_ready is downstream readiness.
Q4. The deadlock watchdog uses a 16-bit stall counter at 1 GHz. How long before it trips?
2¹⁶ = 65,536 cycles at 1 GHz ≈ 65 microseconds. Aggressively long for a fabric event — by then either real traffic has unblocked or there's a genuine cycle.
