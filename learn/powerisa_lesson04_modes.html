Operation Modes

Who is allowed to do what. Problem, privileged, hypervisor and ultravisor state — how you enter each one, how you get back, and why Power's virtualisation model looks the way it does.

By the end of this lesson you can

  • Name every privilege state and give the exact MSR bit combination that selects it.
  • Trace an interrupt from the faulting instruction through SRR0/SRR1 and back via rfid.
  • Explain the difference between a system call, a hypervisor call and an ultracall.
  • Say what LPID and PID are for and how nested paging works on POWER9+.
  • Describe lazy FP/vector context switching and why MSR[FP] exists.

1Why an ISA needs privilege levels at all

caveman mode

Some instructions dangerous. Turn off memory protection, wipe TLB, take over machine. Cannot let any program do that. So machine has rings: user can do little, OS can do more, hypervisor can do everything. Ring stored in one register bit.

An application must not be able to reprogram the MMU, disable interrupts, or read another process's memory. But an operating system must be able to do all three. And when several operating systems share one machine, something above them must arbitrate — that's the hypervisor. Power encodes this hierarchy in two bits of the MSR (plus a third for secure mode), and enforces it in the decoder: a privileged instruction executed in problem state raises a Privileged Instruction interrupt rather than executing.

Three things are gated by privilege state:

  • Instructions — mtmsrd, rfid, tlbie, slbmte and most mtspr/mfspr targets.
  • Registers — the SPR number space is partitioned; SPR bit 5 of the encoded number marks a register as privileged.
  • Storage — address translation applies different rules, and some real-mode accesses are only possible in hypervisor state.

2The privilege ladder

Click a state for detail. Note that Power numbers the ladder downward in the MSR: PR=1 means less privilege, HV=1 means more.

naming trap

"Supervisor" in Power means the OS, not the top of the stack. Coming from x86 you may read "supervisor mode" as ring 0 / most-privileged. On Power the hypervisor sits above the supervisor, and on a PowerVM or KVM machine the OS genuinely runs at a reduced privilege with the hypervisor intercepting. MSR[PR] is literally "problem state", the old IBM term for user mode.

3MSR bit explorer

The Machine State Register is the mode register: it says what the processor currently is. Click a bit.

Remember Power bit numbering: MSR bit 3 is near the most-significant end of the 64-bit register, and MSR bit 63 is the least-significant. That is why HV is "bit 3" and LE is "bit 63".

4Interrupts and the save/restore register pairs

Every privilege escalation on Power works the same way, whether it was caused by a page fault, a timer or a deliberate system call. The hardware does four things atomically:

What the hardware does on an interrupt
   1. save the return address       SRR0  ← address of the interrupted instruction
   2. save the old mode             SRR1  ← the current MSR
   3. set the new mode              MSR   ← new privilege, translation off, interrupts off
   4. jump to the handler           PC    ← the fixed vector for this interrupt type

                          ... handler runs ...

   5. rfid  restores MSR from SRR1 and jumps to SRR0 — atomically,
        so you cannot be interrupted between "restore mode" and "jump".

The critical detail is that there are three parallel sets of these registers, one per destination privilege level. That is what lets an OS interrupt be delivered without disturbing hypervisor state that was already saved:

Interrupt vectors

Each interrupt type has a fixed offset from a base address. Classic Power puts these at low real addresses (offset 0x0…0x1000); modern systems use LPCR[AIL] — Alternate Interrupt Location — to relocate them to a virtual base such as 0xC000_0000_0000_4xxx, so the handler can run with translation already on.

A useful diagnostic habit: when a Linux-on-Power oops prints a faulting address plus DSISR, you are reading the state the 0x300 handler was handed.

5System calls, hypervisor calls and ultracalls

All three are the same instruction with a different level field, and that symmetry is worth internalising.

System callsc 0 (usually written sc)the OS kernel0xC00rfid
Hypervisor call (hcall)sc 1the hypervisor0xC00 in hypervisor statehrfid
Vectored system callscv (v3.0)the OS kernelits own vector, lower overheadrfscv
Ultracallucall (sc 2)the ultravisorultravisor vectorurfid

hcalls are how a guest OS asks the hypervisor for things it is no longer allowed to do itself. On a PowerVM or KVM-on-Power partition, a guest cannot write the page table or send an inter-processor interrupt directly, so it calls H_ENTER, H_REMOVE, H_IPI and friends. The hcall number goes in r3, arguments in r4–r10, the return code comes back in r3.

caveman mode

Same door, different knock. sc 0 = knock for OS. sc 1 = knock for hypervisor. sc 2 = knock for ultravisor. Each knock answered by different guard, each guard has own notebook (SRR / HSRR / USRR) so they do not overwrite each other's notes.

7Partitioning: LPAR, LPID and PID

Power was designed for partitioning long before "virtualisation" was a marketing word — IBM shipped LPARs on mainframes and then on POWER4 in 2001. The architecture therefore treats a partition as a first-class object rather than something emulated on top.

Two levels of identity, two levels of translation
   HYPERVISOR (MSR[HV]=1)  owns real memory, assigns partitions
       │
       ├─ LPAR 1  LPID=1          ├─ LPAR 2  LPID=2
       │   guest OS (MSR[HV]=0, PR=0) │   guest OS
       │     ├─ process A PID=7      │     ├─ process C PID=7
       │     └─ process B PID=9      │     └─ process D PID=3

   PID=7 in LPAR 1 and PID=7 in LPAR 2 are different address spaces —
   the (LPID, PID) pair is what actually identifies a translation context.
   TLB entries are tagged with both, so a partition switch needs no full flush.

PowerVM (IBM's firmware hypervisor) and KVM-on-Power both sit at MSR[HV]=1. The difference is packaging, not architecture: PowerVM is a proprietary type-1 hypervisor in firmware, KVM is Linux running in hypervisor state.

8Nested virtualisation and the radix advantage

Lesson 2 introduced the radix MMU. Its real payoff shows up here.

With the hashed page table

A guest OS manages a page table the hardware cannot walk directly on its behalf, so the hypervisor must intercept every guest page-table update via hcalls (H_ENTER, H_REMOVE) and maintain a shadow. Correct, but chatty.

With radix (v3.0, POWER9+)

Two levels of radix tree, both walked in hardware: guest virtual → guest real via the guest's tree, then guest real → host real via the partition's tree. The hypervisor is out of the fast path entirely.

Nested (two-level) radix translation
   guest EA
      │  guest process page table (selected by PID)
      ▼
   guest real address
      │  partition page table (selected by LPID, owned by the hypervisor)
      ▼
   host real address
      Each level of the guest walk itself needs a partition-level walk, so a
      full nested miss is expensive — which is why POWER10 grew its TLB to
      4096 entries and why huge pages matter so much under virtualisation.

POWER9 also added an explicitly nested KVM mode where an L1 guest hypervisor can run its own L2 guests, with the L0 hypervisor providing the partition-table plumbing through hcalls.

9Context switching and the "unavailable" interrupts

Saving and restoring every register on every context switch would be expensive: 32 GPRs is cheap, but 64 × 128-bit VSRs plus 8 × 512-bit MMA accumulators is over a kilobyte of state. Power's answer is lazy switching, and the architecture supports it directly.

Lazy floating-point / vector context switch
   on context switch, the OS simply does:
       MSR[FP] ← 0 ; MSR[VEC] ← 0 ; MSR[VSX] ← 0
       (it does NOT save or restore the FP/vector registers)

   if the new task never touches floating point  →  zero cost, done.

   if it executes an FP instruction:
       hardware raises FP Unavailable (0x800)
           │
           ▼
       OS saves the previous owner's FP state, restores this task's,
       sets MSR[FP]=1, and rfids back to re-execute the instruction.
       The program never knows it happened.

The same mechanism uses 0xF20 for VMX and 0xF40 for VSX, so a task using only scalar FP never pays for vector state. This is a good example of the ISA deliberately exposing a hook that exists purely to let software be efficient.

Two related pieces of state are worth knowing:

  • MSR[EE] — external interrupt enable. Clearing it is how a kernel enters a critical section. Note that it does not mask machine checks or system reset.
  • MSR[IR] / MSR[DR] — instruction and data relocation, i.e. "translation on". An interrupt clears both, so the first instructions of every handler run in real mode at a physical address — which is why early handler code is written so carefully.

10Ultravisor state and the Protected Execution Facility

POWER9 added a fourth privilege state to solve a modern problem: the hypervisor is part of the threat model. In a cloud deployment the tenant may not want to trust the operator's hypervisor with the contents of guest memory.

PEF introduces a small, auditable ultravisor running above the hypervisor, selected by MSR[S]=1, MSR[HV]=1, MSR[PR]=0. Memory is split into secure and normal regions; a Secure Virtual Machine's pages live in secure memory that the hypervisor cannot read.

  • Only the ultravisor can set MSR[S]. Critically, hrfid cannot set it — so a compromised hypervisor cannot forge entry into secure mode; it must go through an ultracall.
  • The hypervisor still schedules and manages the SVM; it simply cannot see inside it. Most hcalls from an SVM are reflected through the ultravisor.
  • The ultravisor is intentionally tiny — a small trusted computing base is the whole point.
caveman mode

Landlord (hypervisor) owns building, decides who gets which room, but new rule: landlord cannot open your door. Small trusted guard (ultravisor) holds only key. Landlord still collects rent, still evicts you — just cannot read your papers.

This is Power's answer to the same problem AMD SEV and Intel TDX address, with a different structure: a new architectural privilege level rather than a memory-encryption engine bolted to the side.

12Interview Q&A

Describe Power's privilege model.
Four states selected by MSR bits. Problem (user) state is MSR[PR]=1. Privileged or supervisor state — the OS — is PR=0, HV=0. Hypervisor state is HV=1, PR=0. POWER9 added ultravisor state at S=1, HV=1, PR=0 for the Protected Execution Facility. Each level has its own interrupt save/restore register pair (SRR, HSRR, USRR) and its own return instruction (rfid, hrfid, urfid), and privileged instructions executed from a lower state raise a Program interrupt rather than executing.
Walk me through what happens on a page fault.
The load or store fails translation, so the hardware takes a Data Storage Interrupt at offset 0x300. It writes the faulting instruction's address into SRR0, the current MSR into SRR1, puts the faulting effective address in DAR and the reason bits in DSISR, then sets a new MSR — privileged state, translation off, interrupts off — and jumps to the vector. The kernel handler reads DAR/DSISR, fixes up the mapping, and executes rfid, which atomically restores MSR from SRR1 and returns to SRR0 so the instruction re-executes.
What is an hcall and when is one needed?
A hypervisor call: sc 1, with the call number in r3 and arguments in r4 onward. A guest OS uses it for operations it is no longer privileged to perform itself — installing or removing page-table entries under the hashed MMU (H_ENTER, H_REMOVE), sending IPIs, managing virtual I/O. It's dispatched to the hypervisor, which returns via hrfid. With the radix MMU on POWER9+, far fewer hcalls are needed because nested translation is walked in hardware.
How does Power do lazy FP context switching?
On a context switch the OS just clears MSR[FP] (and MSR[VEC]/MSR[VSX]) instead of saving and restoring the register file. If the incoming task never touches floating point, nothing is saved or restored at all. If it does execute an FP instruction, the hardware raises the Floating-Point Unavailable interrupt at 0x800; the kernel then saves the previous owner's state, restores the new task's, sets MSR[FP]=1, and returns so the instruction re-executes. It matters because the full VSX plus MMA state is well over a kilobyte per thread.
What are LPID and PID?
LPID is the logical partition identifier — which guest is currently running — and is writable only by the hypervisor. PID is the process identifier within that guest, written by the guest OS. Translations and TLB entries are tagged with the pair, so the same PID in two different partitions is two different address spaces and a partition switch doesn't require a full TLB flush. LPCR and PTCR are the hypervisor-owned control registers that go with them.
Why did IBM add an ultravisor?
To take the hypervisor out of the trust boundary. In a cloud setting the tenant may not want the operator's hypervisor able to read guest memory. PEF splits memory into secure and normal regions and puts a small, auditable ultravisor above the hypervisor at MSR[S]=1. The hypervisor still schedules the secure VM and manages resources but cannot read its pages, and because hrfid architecturally cannot set MSR[S], a compromised hypervisor cannot forge its way into secure mode — it has to go through an ultracall.
Why do interrupt handlers start with translation disabled?
Taking an interrupt clears MSR[IR] and MSR[DR], so the first instructions run in real mode at a physical address. That's deliberate: the interrupt might have been caused by a translation failure, so the handler cannot depend on translation working. The consequence is that early handler code is position- and address-sensitive and must get itself into virtual mode carefully. Modern systems use LPCR[AIL] to relocate the vectors so handlers can start with translation already enabled, which simplifies this considerably.
How does PowerVM differ from KVM on Power, architecturally?
Architecturally they don't — both run in hypervisor state with MSR[HV]=1 and use the same LPID/LPCR/PTCR machinery and the same hcall interface to guests. The difference is packaging and trust: PowerVM is IBM's proprietary type-1 hypervisor living in firmware, presenting partitions to AIX, IBM i and Linux; KVM-on-Power is Linux itself running in hypervisor state on a PowerNV (bare-metal OpenPOWER) machine. POWER9 additionally supports nested KVM so an L1 guest can host its own L2 guests.

13Recap & key terms

  • Four states: problem (PR=1) · privileged (HV=0,PR=0) · hypervisor (HV=1,PR=0) · ultravisor (S=1,HV=1,PR=0).
  • Escalation is always: save SRR0/SRR1, set new MSR, jump to a fixed vector. Return with rfid.
  • Three parallel pairs — SRR / HSRR / USRR with rfid / hrfid / urfid — so nesting never clobbers.
  • Key vectors: 0x300 DSI · 0x500 external · 0x700 program · 0x800 FP unavailable · 0x900 decrementer · 0xC00 system call.
  • sc 0 = OS · sc 1 = hcall · sc 2 = ultracall · scv = fast syscall (v3.0).
  • (LPID, PID) identifies a translation context; TLB entries are tagged with both.
  • Radix nested translation removes the hypervisor from the page-fault fast path.
  • Lazy switching: clear MSR[FP]/[VEC]/[VSX], let 0x800/0xF20/0xF40 pull state in on demand.
