Q01 1-Bit & MTBF Senior Logic Design
Explain the "Three-Edge" (1.5x clock cycle) sampling requirement for CDC, and how a fast-to-slow toggle/pulse synchronizer solves it.
▼
Core Technical Answer

The "Three-Edge" Requirement:

For a destination clock domain ($clk_{dst}$) to reliably capture a control signal from a source domain ($clk_{src}$) without data loss, the signal must remain stable for at least 1.5 to 2 clock cycles of $clk_{dst}$ (guaranteeing that it spans at least three active clock edges: setup edge, capture edge, hold edge).

  • Fast-to-Slow Problem: If $clk_{src} = 1 ext{ GHz}$ and $clk_{dst} = 200 ext{ MHz}$, a single-cycle pulse in the source domain lasts only $1 ext{ ns}$. The destination clock period is $5 ext{ ns}$. The fast pulse can easily rise and fall entirely between destination clock edges, disappearing undetected.
  • Toggle Synchronizer Architecture:
    1. In the source domain, an incoming single-cycle pulse toggles the state of a flip-flop: t_src <= t_src ^ pulse_in. This converts the short pulse into a semi-permanent level transition.
    2. The level signal t_src passes through a standard 2-flop synchronizer in the destination domain (t_dst_sync).
    3. In the destination domain, an edge detector compares the synchronized signal with its 1-cycle delayed copy: pulse_out = t_dst_sync ^ t_dst_sync_q. Every toggle transition reproduces a 1-cycle pulse in the destination domain.
Limitations to Call Out in Interview

A toggle synchronizer cannot accept back-to-back pulses in the fast domain. The minimum spacing between consecutive input pulses must be $\ge 2 imes T_{dst} + T_{src}$ to allow the destination synchronizer to resolve before the level toggles again. If pulses can occur in quick bursts, a handshake synchronizer or an asynchronous FIFO is mandatory.

Q02 1-Bit & MTBF Staff Logic Design
Derive the MTBF formula for a 2-flop synchronizer. How does technology scaling (e.g. 5nm/3nm FinFET) impact MTBF, and why are dedicated synchronizer standard cells used?
▼
Mathematical Derivation
MTBF = 1 / Failure_Rate = (e ^ (t_r / τ)) / (T_0 × f_clk × f_data) Where: t_r = Available resolution time = T_clk - t_setup - t_cq τ = Resolving time constant of the flip-flop bistable latch T_0 = Asymptotic aperture / metastability window parameter f_clk = Frequency of the destination receiving clock f_data = Toggle frequency of the asynchronous input data
Core Technical Insights
  • Why exponential: In a cross-coupled inverter pair, the regenerative feedback amplifies small voltage differences: $\Delta V(t) = \Delta V_0 \cdot e^{t / au}$. Thus, the probability of remaining in an unresolved metastable state decays exponentially with the resolution time $t_r$.
  • Process Scaling Impact: In advanced nodes (3nm/5nm), lower supply voltages ($V_{dd} pprox 0.7 ext{V}$) reduce overdrive voltage ($V_{gs} - V_{th}$), which can degrade gain. However, smaller parasitic capacitances decrease $ au$. The biggest issue is that $f_{clk}$ exceeds 2–3 GHz, shrinking $t_r$ to under 300 ps. Because $t_r$ is in the exponent, a small drop in clock period slashes MTBF by orders of magnitude!
  • Dedicated Synchronizer Cells: Standard library flip-flops are optimized for area and low $t_{cq}$. In contrast, ASIC libraries include dedicated synchronizer cells where:
    • The first latch uses high-gain transistors sized specifically for minimal $ au$ and minimal $T_0$.
    • The physical layout places both flip-flops abutted in silicon with shielded, zero-routing metal to prevent parasitic RC delay and eliminate hold race hazards between sync stage 1 and stage 2.
Q03 Multi-Bit & Handshakes Senior Logic Design
Why is it strictly forbidden to synchronize a multi-bit data bus using individual 2-flop synchronizers? What is the MUX-Recirculation (MCP) synchronization technique?
▼
Core Technical Answer

Why Bit-by-Bit Synchronization Fails:

Even if an entire 32-bit bus transitions simultaneously from 0x00000000 to 0xFFFFFFFF in the source domain, individual bit lines experience different physical wire routing delays, clock tree skew, and independent metastability resolution in destination flip-flops. One bit might resolve in 1 cycle, another in 2 cycles.

The destination clock can easily latch corrupt, intermediate ghost states (e.g., 0x00FF00FF or 0x5555AAAA) that never existed in the source domain.

MUX-Recirculation (Multi-Cycle Path / MCP Scheme):

  • Instead of synchronizing the data bus directly, the multi-bit data is held stable at the source register and routed straight to the data input of a destination register or multiplexer.
  • A single-bit control signal (data_valid or toggle_req) is generated in the source domain once the data bus is stable.
  • The data_valid control signal is passed through a 2-flop synchronizer into the destination domain.
  • The destination register uses the synchronized control signal as a load-enable (en):
    // Destination Domain: always_ff @(posedge clk_dst or negedge rst_dst_n) begin if (!rst_dst_n) data_dst <= '0; else if (sync_load_en) // Asserted only when data has been stable for multiple cycles data_dst <= async_data_bus; end
  • Constraint: The source logic must guarantee the data bus remains 100% stable until the destination has safely latched it (often verified via a returning acknowledge handshake).
Q04 Multi-Bit & Handshakes Staff Logic Design
What is Reconvergence of synchronized control paths in CDC? Show an RTL failure mode and explain how to prevent it.
▼
Core Technical Answer

Reconvergence occurs when two or more related signals generated in the same source domain are synchronized independently through separate 2-flop synchronizers, and their synchronized outputs feed common combinational decision logic in the destination domain.

Failure Scenario:

Suppose a source state machine issues two mutually exclusive control strobes: cmd_read and cmd_write. Even if the source guarantees that cmd_read and cmd_write never assert in the same cycle, synchronizing each through independent 2-flop chains can result in one synchronizer resolving in 1 cycle and the other experiencing a 2-cycle delay. In the destination domain, both signals might appear high simultaneously for one clock cycle, or an unexpected cycle of both being low might occur, corrupting the destination state machine.

// DANGEROUS BUG (Reconvergence): sync_2ff u_sync_rd (.clk(clk_dst), .in(src_rd), .out(dst_rd)); sync_2ff u_sync_wr (.clk(clk_dst), .in(src_wr), .out(dst_wr)); // Destination logic: assign error_condition = dst_rd & dst_wr; // Can inadvertently trigger!

Architectural Solutions:

  1. Consolidate into Encoded Bus: Encode the control signals into a single multi-bit vector (e.g. cmd_type[1:0]: 00=IDLE, 01=READ, 10=WRITE) and cross it using an MCP (Mux-recirculation) or FIFO scheme.
  2. Single Strobe with Data Payload: Generate a single cmd_valid crossing through a 2-flop synchronizer, while the command type is treated as quasi-static data captured by the destination only when the valid strobe fires.
Q05 Async FIFO & Depth Senior Logic Design
Why are FIFO pointers converted to Gray code before clock crossing, and why is Gray code comparison for FIFO FULL/EMPTY inherently conservative ("safe-side")?
▼
Core Technical Answer

1. Why Gray Code:

In standard binary counting, multiple bits can change concurrently (e.g., from 3 (011) to 4 (100), all three bits toggle). If sampled during transition, clock skew causes intermediate values (e.g., 111 (7) or 000 (0)) to be latched, creating massive false EMPTY or false FULL conditions.

In Gray code, adjacent numerical values differ by only one single bit ($B \oplus (B >> 1)$). If that transitioning bit experiences metastability:

  • If it resolves to the new bit value: The destination sees the updated pointer value.
  • If it resolves to the old bit value: The destination sees the previous pointer value (a 1-cycle delay).
  • In neither case does it ever resolve to a bogus, non-adjacent pointer value!

2. Why "Safe-Side" (Conservative) Behavior:

  • Empty Flag Generation: Evaluated in the Read domain by comparing the local binary read pointer with the synchronized write pointer. Because the write pointer was synchronized through a 2-flop chain, the read domain sees a delayed, older version of the write pointer. The FIFO might believe it is empty when a write has already occurred. This is completely safe: it merely stalls the reader by 1–2 cycles; it never underflows.
  • Full Flag Generation: Evaluated in the Write domain by comparing the local binary write pointer with the synchronized read pointer. Because the read pointer is delayed by 2 cycles, the write domain may believe the FIFO is full even though the reader has just popped entries. This is also completely safe: it merely stalls the writer; it never overflows.
Q06 Async FIFO & Depth Staff Logic Design
Calculate the minimum depth of an Asynchronous FIFO: Write Clock = 200 MHz, Read Clock = 100 MHz, Burst Size = 80 words, 1 read/write per clock, 2-flop sync latency.
▼
Step-by-Step Numerical Calculation
Given Parameters: f_wr = 200 MHz --> T_wr = 5 ns f_rd = 100 MHz --> T_rd = 10 ns Burst = 80 data words (continuous writes, 1 write per T_wr) Read = Continuous reads once available (1 read per T_rd) Sync Latency = 2 destination clock cycles to synchronize pointers Step 1: Time required to complete the write burst: T_burst = Burst_Size × T_wr = 80 × 5 ns = 400 ns Step 2: Number of words read during this burst period: Note: When does reading begin? The write pointer takes 2 read cycles (2 × T_rd = 20 ns) to synchronize into the read domain. Actual available read time during burst = T_burst - (2 × T_rd) = 400 ns - 20 ns = 380 ns. Number of words read = Floor(380 ns / T_rd) = Floor(380 / 10) = 38 words. Step 3: Calculate remaining words left in FIFO: Remaining backlog = Total Written - Total Read = 80 - 38 = 42 words. Step 4: Power of 2 Allocation: Minimum theoretical depth = 42. Because Gray-code wrap-around requires power-of-2 depth: Allocated FIFO Depth = 2^(ceil(log2(42))) = 64 words!
Senior Interview Caveats

Always clarify with the interviewer whether the read domain is capable of back-to-back zero-latency reads or if the read logic has pipeline bubbles (e.g. Memory read latency, DFI/DDR interface cycles, or Skid Buffers). If the write domain receives an additional backpressure cycle before deasserting wready, you must add 1-2 words to the headroom.

Q07 Async FIFO & Depth Staff Logic Design
Can an Asynchronous FIFO have a depth of 2? Compare a 2-deep Async FIFO with a Ping-Pong buffer in high-frequency NoC routers.
▼
Core Technical Answer

Yes, a 2-deep Async FIFO is structurally possible and widely used in latency-critical NoC routers and pipeline bridges where data throughput is needed with minimal register overhead.

  • Pointer Representation: A 2-deep FIFO has 2 memory locations (indexes 0 and 1). A 2-bit pointer (1 bit for index, 1 bit for MSB wrap-around) is used:
    Binary sequence: 00, 01, 10, 11.
    Gray sequence: 00, 01, 11, 10.
    Because it is a power of 2, 1-bit transitions are preserved across all 4 state transitions!
  • Throughput Limitation: While functionally correct, a 2-deep FIFO cannot achieve 100% sustained throughput if the clock frequency ratio is large or synchronization takes multiple cycles. Once 2 words are written, the FIFO goes FULL and stalls the writer until the read pointer synchronizes back (which takes 2-3 clock cycles).
  • Ping-Pong Buffer Alternative: In high-frequency NoC fabrics (like CMN-700 crosspoints), ping-pong buffers with credit-based flow control are favored:
    • The receiver allocates a bank of 2 registers.
    • Instead of passing Gray pointers continuously, single-bit credit pulses are returned asynchronously across domains, or an explicit toggle handshake alternates between Buffer A and Buffer B.
Q08 RDC & Power Gating Senior Logic Design
Explain the architecture of an Asynchronous Reset Synchronizer (Asynchronous Assert, Synchronous Deassert). Why is synchronous release mandatory?
▼
Core Technical Answer

An asynchronous reset pin allows the entire chip to enter a known state immediately upon power-up without waiting for the PLL or clock tree to stabilize. However, deasserting an asynchronous reset asynchronously causes metastability.

  • Reset Recovery & Removal Violations: Like setup and hold times, flip-flops have recovery time (minimum time reset must be inactive before the clock edge) and removal time (minimum time reset must remain active after the clock edge). If the reset release edge falls inside this window, some flip-flops in the pipeline wake up in cycle $N$, while others miss it and wake up in cycle $N+1$, splitting state machines into illegal states.
  • Reset Bridge (Synchronizer) Implementation:
always_ff @(posedge clk or negedge async_rst_n) begin if (!async_rst_n) begin sync_rst_stage1 <= 1'b0; // Asynchronous assertion sync_rst_n <= 1'b0; end else begin sync_rst_stage1 <= 1'b1; // Synchronous deassertion sync_rst_n <= sync_rst_stage1; end end
  • Assertion: When async_rst_n goes LOW, both flops reset to 0 immediately (propagation through async reset pin, 0 clock cycles).
  • Deassertion: When async_rst_n goes HIGH, logic 1 ripples through the D inputs synchronously with clk, aligning the rising edge of sync_rst_n perfectly with the clock tree and meeting recovery/removal constraints across the entire domain.
Q09 RDC & Power Gating Staff Logic Design
How do UPF Isolation cells interact with Clock Domain Crossing boundaries when power-gating an IP core? What is the correct power-down/power-up sequence?
▼
Core Technical Answer

When a power domain is switched off ($V_{dd} o 0 ext{V}$), all output nets become floating/high-Z. If these nets feed an always-on clock domain or a CDC synchronizer, they inject intermediate voltage levels, causing massive crowbar current in CMOS gates and propagating illegal 'X' states.

UPF Isolation Placement: Isolation cells (AND/OR clamp gates driven by an always-on isolation enable signal iso_en) must be placed on every net exiting the power-gated domain.

Strict Power-Down Sequence:

  1. Quiescence / Flush: Halt incoming transactions at the CDC interface (assert backpressure or wait for FIFO empty).
  2. Clock Gating: Gate off the clock to the domain being powered down.
  3. Isolation Assertion: Assert iso_en = 1 to clamp all boundary outputs to a safe, inactive state (typically 0 for control strobes, 1 for active-low resets).
  4. Reset Assertion: Apply local reset.
  5. Power Cut: Switch off power FET switches ($V_{dd\_switched} o 0$).

Power-Up Sequence: Restore power $ o$ Wait for Power-Good acknowledge $ o$ Turn on clock $ o$ Deassert isolation $ o$ Release reset through the synchronous reset bridge $ o$ Re-enable CDC traffic.

Q10 SDC & Static Verification Senior Logic Design
Why is using `set_false_path` on CDC paths considered a dangerous anti-pattern? What exact SDC constraints should be used for Gray pointers and MCP data?
▼
Core Technical Answer

The Danger of `set_false_path`:

When you define set_false_path -from [get_clocks clk_a] -to [get_clocks clk_b], you tell the Place-and-Route (P&R) tool: "Timing does not matter at all on this path."

Consequently, the physical synthesis tool may route Bit 0 of a Gray pointer through a direct 100 ps route, while routing Bit 1 through an unbuffered detour spanning the entire chip with a 5 ns delay. This massive routing skew completely destroys the single-bit transition property of Gray code! Multiple bits will arrive at the synchronizer in different cycles, corrupting the FIFO pointers.

Proper SDC Timing Constraints:

# 1. Constrain maximum datapath delay to prevent unconstrained routing latency: set_max_delay -from [get_cells rptr_gray_reg*] -to [get_cells sync_rptr_reg[0]*] -datapath_only [get_property -min_period [list clk_wr clk_rd]] # 2. Constrain maximum skew across all bits of the Gray pointer bus: set_bus_skew -from [get_cells rptr_gray_reg*] -to [get_cells sync_rptr_reg[0]*] [expr 0.5 * [get_property -min_period [list clk_wr clk_rd]]] # 3. For MCP Data buses: set_max_delay -from [get_cells src_data_reg*] -to [get_cells dst_data_reg*] -datapath_only [expr 2 * [get_property period clk_dst]]

-datapath_only ignores clock skew between asynchronous domains while strictly bounding the physical wire delay, allowing STA tools to verify skew without false setup/hold violations.

Q11 SDC & Static Verification Staff Logic Design
Compare Static CDC Analysis (Spyglass/JasperGold) with Dynamic CDC Verification (VCS/Questa CDC random delay injection). How do they complement each other?
▼
Core Technical Answer

1. Static CDC Analysis (Spyglass / JasperGold CDC):

  • Mechanism: Formal/structural rule checking on RTL netlists without requiring test vectors.
  • Strengths: 100% path coverage. Flags structural issues: missing synchronizers, combinational logic feeding synchronizers, reconverging control signals, Gray code sequence violations, and improper SDC waivers.
  • Weakness: Generates false positives on protocol-protected paths (e.g. Quasi-static registers or handshake-protected MCPs that require functional analysis to prove safety).

2. Dynamic CDC Verification (EDA CDC Jitter Injection / Random-Stage Models):

  • Mechanism: During RTL simulation, the simulator automatically detects 2-flop synchronizers and randomly injects a 0-cycle or 1-cycle delay (or random 'X' during the setup/hold window) on the first stage flip-flop.
  • Strengths: Proves whether the functional protocol/testbench survives real-world asynchronous race conditions. It catches bugs that static tools miss, such as a state machine that makes premature decisions assuming 0-cycle transfer or a handshake that drops data when delayed by 1 cycle.
  • Sign-Off Recommendation: Static CDC is mandatory for structural sign-off; Dynamic CDC simulation is mandatory for functional protocol verification.
