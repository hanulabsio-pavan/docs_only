Snoop Filter Architecture, Sizing & Performance

The Snoop Filter is the most critical data structure inside an HN-F node — it tracks which RN-F caches hold which cache lines, enabling targeted snoops instead of expensive broadcasts. Its size determines system coherency overhead.

What the Snoop Filter Tracks

Every HN-F maintains a Snoop Filter — a hardware CAM/SRAM structure that records, for each cached cache line in the system, which RN-F nodes hold a copy and in what coherency state.

// Implementation Note

The Snoop Filter is typically implemented as a set-associative SRAM structure, similar to a CPU L2 cache's tag array — but tracking where data lives, not the data itself. The address tag uses the upper bits of the physical address (minus the 6-bit line offset) as the tag + index. A 4-way set-associative design with 16K sets = 64K total entries ≈ 512KB SRAM at 8 bytes/entry. The CMN-700 supports up to 262,144 entries per HN-F with configurable associativity.

// CHI Spec Note

The CHI specification (ARM IHI 0050) does not mandate a snoop filter size — it is entirely implementation-defined. The spec only defines the protocol behaviour when the filter is full (eviction must happen). SoC architects choose the size based on workload characterisation, die area budget, and power targets. A filter that is too small causes constant broadcast snoops; too large wastes expensive SRAM.

Snoop Filter Eviction Flow

When the filter is full and a new entry must be installed, HN-F must evict an existing entry by forcibly invalidating all CPU caches that hold that line. This is expensive and should be minimised.

01
New REQ arrives, Filter is Full
CPU0 issues ReadShared for address 0xNEW_ADDR. HN-F's Snoop Filter has no free entries — all slots are occupied by currently-tracked cache lines.
HN-F: filter_full=1, need_eviction=1
02
Select Victim Entry (LRU / Pseudo-LRU)
HN-F's replacement policy selects a victim entry — typically the Least Recently Used line. It reads the sharer bitmap and state of the victim entry from the filter SRAM.
victim = LRU_entry; sharers = victim.bitmap; // e.g. CPU1, CPU3
03
Send SnpMakeInvalid / SnpCleanInvalid to All Sharers
HN-F sends an invalidating snoop to every node in the victim's sharer bitmap. If the line is dirty, it uses SnpCleanInvalid (requests writeback). If clean, SnpMakeInvalid (just invalidate, no data needed).
SNP → CPU1: SnpMakeInvalid(victim_addr)
SNP → CPU3: SnpMakeInvalid(victim_addr)
04
Wait for SnpResp from All Snoopees
HN-F stalls the new REQ until all snoopees respond. CPU1 and CPU3 must evict the victim line from their caches and acknowledge. If either had a dirty copy, they return data on DAT channel.
CPU1 → HN: SnpResp_I (clean, no data)
CPU3 → HN: SnpResp_I (clean, no data)
05
Free the Victim Entry
Once all SnpResp are received, HN-F knows the victim line is globally invalid — no node caches it anymore. The filter entry is cleared and the slot is free.
filter[victim_idx].valid = 0; // slot freed
06
Install New Entry & Resume Original REQ
HN-F writes the new address into the freed slot, initialises the sharer bitmap, and resumes processing CPU0's original ReadShared request normally. Total eviction overhead: 1–2 extra snoop round-trips.
filter[victim_idx] = {addr:0xNEW_ADDR, sharers:0, state:I};
resume ReadShared(CPU0);

The Coverage Problem

The Snoop Filter only tracks a subset of all cached data. The mismatch between total L3 cache capacity and filter coverage is a fundamental performance design trade-off.

Why is coverage always low? Because filter SRAM is much more expensive per bit than cache SRAM — it must be fully associative (CAM-like) for fast lookups, whereas L3 cache SRAM is set-associative. A 100% coverage filter for a 64MB L3 would require ~32MB of filter SRAM — impractical. The filter relies on temporal locality: recently-accessed lines are most likely to be requested again, so they stay in the filter while cold lines are evicted.

📐
Die Area
Filter SRAM occupies real chip area. A 4MB filter in 5nm is roughly 3–4mm². Doubling filter size doubles this cost — area that could otherwise be used for more CPU cores or cache.
↑ Area → ↑ Cost
⚡
Lookup Latency
Every incoming REQ hits the filter. Larger SRAM = more complex access = longer lookup latency. This adds to every coherent read path. Target: <5ns lookup.
↑ Size → ↑ Latency
🔋
Leakage Power
SRAM leaks current even when not being accessed. A large filter in a mobile SoC significantly impacts idle power — critical for battery life.
↑ Size → ↑ Power
📉
Eviction Rate
Larger filter = fewer evictions = fewer forced invalidations = lower snoop traffic. A 4× larger filter can reduce eviction-related snoops by 80% in typical workloads.
↑ Size → ↓ Evictions
📡
Broadcast Rate
Filter misses cause broadcasts. A well-sized filter for a given workload can keep miss rate <5%, dramatically reducing SNP channel bandwidth consumption.
↑ Size → ↓ Broadcasts
🏃
Workload Fit
The filter must cover the active working set of all CPUs combined. Server workloads have large working sets (need big filters); mobile workloads are smaller but more varied.
Must match workload

Snoop Filter Tuning Guide

Practical rules for SoC architects when sizing and configuring the snoop filter. These are derived from workload profiling and silicon experience.

✅ Best Practice
Size for Active Working Set
Profile your target workloads and measure the combined active cache footprint of all CPU clusters. Size the filter to cover at least 10–15% of peak working set for <5% miss rate.
✅ Best Practice
Use Pseudo-LRU Replacement
Pseudo-LRU replacement policy keeps recently-used entries, naturally favouring hot cache lines. True LRU is too expensive in hardware; 4-bit PLRU achieves 95% of LRU effectiveness.
✅ Best Practice
Distribute HN-F Nodes
Multiple HN-F nodes each own a portion of the address space — so each runs a smaller filter. Distributing load reduces per-filter lookup pressure and spreads SRAM across the mesh.
⚠️ Watch Out
Filter Thrashing Under Streaming
Streaming workloads (video decode, memcpy) sequentially access huge address ranges, thrashing the filter with entries that will never be re-requested. Use non-temporal hints / CMO to bypass the filter.
⚠️ Watch Out
GPU Workloads Spike Filter Pressure
GPU compute kernels access large buffers with low reuse. GPU cache lines in the filter are rarely re-snooped but consume slots, evicting CPU lines that are frequently reused. Consider separate filter partitions.
❌ Anti-Pattern
Undersizing for Server Workloads
Server workloads (databases, VMs) have very large working sets. An undersized filter causes constant broadcast storms — every coherent miss becomes a global SNP broadcast, saturating the mesh.
❌ Anti-Pattern
Ignoring Eviction Latency in Budget
If your latency budget assumes filter-hit paths only, you will be surprised by 4–6× latency spikes under heavy multi-threaded load when evictions trigger. Always model the eviction path in worst-case analysis.
✅ Best Practice
Use Performance Counters
CMN-700 exposes filter hit rate, miss rate, and eviction rate via PMU counters. Always profile real silicon — filter behaviour under actual workloads often surprises designers compared to simulation.
