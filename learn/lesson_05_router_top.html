router_top — the 5-stage pipeline

The capstone. Every primitive from Lessons 2 and 3 and every building block from Lesson 4 is instantiated and wired inside router_top.sv. The router has five pipeline stages — RC, VA, SA, ST, LT — and once you can walk one flit through all five, the rest of the NoC is just more of these.

1The pipeline — RC → VA → SA → ST → LT

2Internals — what's inside the box

The full router floor-plan. Five input ports feed into the RC/VA/SA logic, which drives a 5×5 crossbar, which feeds the LT registers that drive the five output links. All instantiated inside router_top.sv.

3How earlier lessons compose

Each stage maps to specific modules you've already read. This is the moment everything clicks: router_top isn't doing anything new — it's just orchestrating modules from Lessons 2, 3, and 4 in a 5-stage pipeline.

Stage 1 — RC
For each input port, instantiate one route_compute_unit parameterized with MY_X, MY_Y. Feed the flit's tgt_node_id; receive an out_port direction.
route_compute_unit.sv chi_pkg::node_id_to_x/y
Stage 2 — VA
Currently a static alloc_vc[ip] = ip % NUM_VC placeholder in router_top:154 (flagged 🔶 Partial in the DV tracker). Production version uses channel_to_vc() + the virtual_channel_mgr from Lesson 4.
virtual_channel_mgr.sv noc_pkg::channel_to_vc
Stage 3 — SA
One arb_unit per output port, in gen_sa_arb. Each gathers sa_req[op][ip] from inputs whose RC chose this op, runs round-robin, produces a one-hot sa_grant.
arb_unit.sv round_robin_arb.sv
Stage 4 — ST
Single crossbar instance. sa_grant wires directly to sel[op][ip]. xbar_in[ip] comes from the head of the chosen VC's FIFO in input_port.
crossbar.sv input_port.sv
Stage 5 — LT
Pure flip-flop stage (ff_lt block). Registers xbar_out into the five {n,s,e,w,local}_flit_out ports. The valid_out is ANDed with ready_out — that's the back-pressure from the next router.
router_top.sv :: ff_lt

4Known issues — from the DV tracker

Reading the RTL alongside the DV tracker (docs/verification/noc_dv_tracker_and_testplan.md), these are the items in router_top.sv and its instances that need fixes before Phase 1 sign-off. Knowing them now means you won't be surprised when sim breaks.

🔶 VA stage is a placeholder
router_top.sv:154 assigns alloc_vc[ip] = 2'(ip % NUM_VC) — a static modulo mapping that ignores the actual channel of the incoming flit. Real VA must use channel_to_vc(flit_channel) via the virtual_channel_mgr instance. Flagged in DV tracker §1.2.2.
🔶 Input port VC decode misaligned
input_port.sv:42 extracts vc_sel from flit_in[20:18]. The actual channel field offset in chi_flit_hdr_t is different — needs to align with the packed-struct field layout. P1.1 in the DV plan.
⚠ noc_mesh wiring (one level up)
Not in router_top itself, but worth flagging: the parent noc_mesh.sv:79–104 shares the same wire for both north_flit_in and north_flit_out on adjacent routers. Inputs and outputs must be on separate nets. This bug means simulation will see undefined behavior on every inter-router link until fixed.
Status counter not a true counter
status.flit_count in comb_status sums ibuf_valid bits combinationally each cycle — that's an instantaneous occupancy, not a cumulative flit count. Likely fine as a debug snapshot, but rename or rewire if a real cumulative counter is wanted.

6Check yourself

Q1. A flit arrives at this router's North port at cycle 0. Which cycle does it appear on the output link (assuming nothing stalls)?
5 cycles. RC (1) → VA (2) → SA (3) → ST (4) → LT (5). LT is the only registered stage in this RTL — the others are combinational, so they actually share a single clock cycle's worth of logic. In production silicon, you'd register between each stage to hit 1 GHz; the current RTL collapses RC/VA/SA into one clock and registers only LT, so a flit really only spends 2 cycles in the router. (The DV tracker mentions NOC_PIPELINE_STAGES = 3 as the eventual target.)
Q2. Two input ports both want the same output port in the same cycle. Walk through what happens.
(1) RC computes the same out_port for both input flits. (2) sa_req[op] has two bits set. (3) The arb_unit for that output picks one winner via round-robin — one-hot sa_grant. (4) The crossbar passes the winner's flit through. (5) The loser's flit stays in its input port FIFO, waiting for the next arbitration cycle. $onehot0(sa_grant[op]) fires if the arbiter ever messes up.
Q3. What happens to valid_out if the downstream router asserts ready_out = 0?
Look at ff_lt: north_valid_out <= xbar_out_v[PORT_NORTH] & north_ready_out. If ready_out is 0, valid_out stays 0 — the flit is dropped from the LT register. This is OK only because the input-side FIFO still holds the flit (SA didn't actually dequeue it from ibuf). The credit accounting upstream prevents another flit from coming in.
Q4. Where in the file does router_top instantiate flit_buffer?
It doesn't directly. flit_buffer is instantiated inside output_port (via gen_vc_buf) — but router_top.sv as currently written doesn't even instantiate output_port! It has a custom ff_lt block that registers crossbar outputs directly. That's why the credit-management logic from Lesson 4's output_port is also missing here — it's a known gap that will be addressed when output_port is wired in. The DV tracker covers this in §1.2.5.
