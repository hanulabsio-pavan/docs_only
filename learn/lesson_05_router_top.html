3How earlier lessons compose

Each stage maps to specific modules from earlier lessons. router_top orchestrates them in a 5-stage pipeline.

Stage 1 — RC
For each input port, one route_compute_unit parameterized with MY_X, MY_Y. Feed tgt_node_id; receive out_port.
route_compute_unit.sv chi_pkg::node_id_to_x/y
Stage 2 — VA
Static alloc_vc[ip] = ip % NUM_VC placeholder in router_top:154 (🔶 Partial). Production uses channel_to_vc() via virtual_channel_mgr.
virtual_channel_mgr.sv noc_pkg::channel_to_vc
Stage 3 — SA
One arb_unit per output port in gen_sa_arb. Gathers sa_req[op][ip] from inputs whose RC chose this op, runs round-robin.
arb_unit.sv round_robin_arb.sv
Stage 4 — ST
Single crossbar. sa_grant wires directly to sel[op][ip]. xbar_in[ip] comes from the head of the chosen VC's FIFO.
crossbar.sv input_port.sv
Stage 5 — LT
Pure flip-flop stage (ff_lt). Registers xbar_out into the five output ports. valid_out is ANDed with ready_out.
router_top.sv :: ff_lt

4Known issues — from the DV tracker

Items in router_top.sv (and one in noc_mesh) needing fixes before Phase 1 sign-off. Knowing them now means you won't be surprised when sim breaks.

🔶 VA stage is a placeholder
router_top.sv:154 assigns alloc_vc[ip] = 2'(ip % NUM_VC) — static modulo, ignores the flit's actual channel. Real VA must use channel_to_vc(flit_channel). Flagged in DV §1.2.2.
🔶 Input port VC decode misaligned
input_port.sv:42 extracts vc_sel from flit_in[20:18]. Actual offset in chi_flit_hdr_t differs — needs to align with packed-struct layout. P1.1 in the DV plan.
⚠ noc_mesh wiring (one level up)
Not in router_top itself, but worth flagging: parent noc_mesh.sv:79–104 shares the same wire for both north_flit_in and north_flit_out on adjacent routers. Inputs and outputs must be on separate nets. Until fixed, simulation sees undefined behavior on every inter-router link.
Status counter not a true counter
status.flit_count in comb_status sums ibuf_valid bits each cycle — an instantaneous occupancy, not a cumulative count.

6Check yourself

Q1. A flit arrives at North port at cycle 0. Which cycle does it appear on the output link (no stalls)?
Conceptually 5 cycles (RC, VA, SA, ST, LT). In the current RTL only LT is registered, so a flit really spends 2 cycles. The DV tracker mentions NOC_PIPELINE_STAGES = 3 as the eventual target.
Q2. Two input ports both want the same output port in the same cycle. Walk through.
(1) RC computes the same out_port for both. (2) sa_req[op] has two bits set. (3) arb_unit picks one winner — one-hot sa_grant. (4) Crossbar passes winner's flit through. (5) Loser stays in input FIFO for next cycle. $onehot0(sa_grant[op]) fires if the arbiter messes up.
Q3. What happens to valid_out if downstream asserts ready_out = 0?
ff_lt: north_valid_out <= xbar_out_v[PORT_NORTH] & north_ready_out. If ready_out is 0, valid_out stays 0 — flit dropped from LT register. OK only because input-side FIFO still holds it (SA didn't actually dequeue from ibuf).
Q4. Where does router_top instantiate flit_buffer?
It doesn't directly. flit_buffer is in output_port — but router_top.sv as currently written doesn't instantiate output_port! It has a custom ff_lt block that registers crossbar outputs directly. Known gap, DV tracker §1.2.5.
