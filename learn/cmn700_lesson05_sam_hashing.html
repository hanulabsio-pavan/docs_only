System Address Map & Address Hashing

How a physical address becomes a route — and how interleaving spreads load across home nodes and memory.

By the end of this lesson you can

  • Explain the SAM hierarchy: RN SAM vs HN-F/MC SAM and what each maps to.
  • Describe address hashing/interleaving across HN-F and why it balances load.
  • Explain regions, the default node, and why programming order matters at bring-up.
  • Trace an address from RN → HN → SN.

1Address → route

caveman mode

Message know the address but not which crossroad. SAM = lookup table: "this address lives at node #40." Requester's table says which home. Home's table says which memory. Bad table → message lost or all crammed onto one poor home node.

Routing on the mesh is by node ID (Lesson 1), but software and caches speak in addresses. The System Address Map is the translator. It also decides balance: spread addresses well and every home node shares the load; spread them badly and one HN-F becomes a hot spot.

2The SAM hierarchy

There are two translation steps, each owned by a different node:

3The RN SAM in a bit more depth

Each requester's RN SAM holds the memory map: which address regions exist and which target each maps to. Targets can be HN-F (coherent), HN-I/HN-P (I/O), HN-D, or a CCG (remote/multichip). It can even generate a memory-controller target directly for certain prefetch hints. The RN SAM is what turns "I want address A" into "send this to node N."

4Address hashing & interleaving across home nodes

The crucial part: for a coherent region, the RN SAM doesn't map a whole region to one HN-F — it hashes the address to spread lines across many HN-F slices. The interleave granularity (often a cache-line or small block) means consecutive lines land on different home nodes:

Interleave: consecutive lines → different HN-F
  line @ A+0   → hash → HN-F 0
  line @ A+64  → hash → HN-F 1
  line @ A+128 → hash → HN-F 2
  line @ A+192 → hash → HN-F 3      load spread, not piled on one home

This is why a single hot buffer doesn't melt one home node — its lines fan out across slices. Tuning the hash/interleave to avoid hot spots is a core CMN-700 system-design skill, and a great thing to mention unprompted.

5The HN-F / MC SAM

Once a home node misses and must go to memory, its MC SAM maps the address to the right SN-F (memory controller) target ID. With many controllers (up to 40), and mixed memory types (HBM3 + DDR5), this second map decides which physical memory serves the line — and can itself interleave across channels for bandwidth.

6Bring-up order (the gotcha)

Before the SAM is programmed, RN SAMs default-route everything to the HN-D. The HN-D does not manage coherency, so any real traffic sent there during configuration would be mishandled — writes might not reach DRAM, reads might return stale data. Hence the rule:

Quiesce during SAM programming

While programming the SAM, all requesters except the configuring one should be prevented from issuing requests, until the use_default_node behaviour is cleared. Otherwise default-routed traffic to the HN-D causes incoherent/incorrect results.

This is exactly the kind of bring-up detail that separates "read about it" from "understands it."

7Worked example — address to memory

  • Core wants physical address A. Its RN SAM hashes A → HN-F 2; the REQ routes to that node.
  • HN-F 2 checks SLC + snoop filter for A: miss, no sharers.
  • HN-F 2's MC SAM maps A → SN-F 5 (a DDR5 controller); a read goes out.
  • Data returns on DAT (optionally DMT toward the core), HN-F 2 fills its SLC and updates the SF, core installs the line.

Two SAM lookups, two routes, one coherent result — that's the address path end-to-end.

9Interview Q&A

How does a request find the right home node?
The requester's RN SAM translates the physical address into a home-node target ID (usually via an address hash that interleaves across HN-F slices). The mesh then routes by that node ID. If the home misses, its MC SAM maps the address to the SN-F memory controller.
How do you avoid a hot home node?
Tune the address hash / interleave granularity so consecutive lines fan out across many HN-F slices. Contiguous mapping would pile a hot buffer onto one home; fine-grained interleaving spreads the load.
What are the two SAM levels?
RN SAM (address → home-node target ID, in every RN) and HN-F/MC SAM (address → SN memory-controller target, in every HN-F). Two translation hops: RN→HN, then HN→SN.
What's the bring-up gotcha with the SAM?
Until the SAM is programmed, RN SAMs default-route to the HN-D, which doesn't manage coherency. So during programming you must quiesce all other requesters (until use_default_node is cleared); otherwise default-routed traffic to the HN-D yields incoherent/incorrect results.
Can an RN SAM target memory directly?
Yes — for certain prefetch hints the RN SAM can generate a memory-controller target ID so the requester can issue a prefetch toward the SN, in addition to the normal home-node targets (including a CCG for remote/multichip memory).

10Recap & key terms

  • RN SAM: address → home target ID (in every RN). HN-F/MC SAM: address → SN target (in every HN-F).
  • Coherent regions are hashed/interleaved across HN-F slices to balance load.
  • MC SAM can also interleave across memory channels/controllers.
  • Pre-config default route is the HN-D → quiesce traffic during SAM programming.
  • Good SAM/hash tuning = no hot home node = balanced mesh.
