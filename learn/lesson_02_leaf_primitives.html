Leaf Primitives

Four small modules that appear in nearly every router and link block: a synchronous flit FIFO, a credit counter, a 2-flop synchronizer, and an asynchronous (Gray-code) FIFO. Master these and the bigger modules collapse into "FIFO + arbiter + state machine" patterns you already know.

1flit_buffer — the synchronous FIFO

A power-of-2-depth synchronous FIFO that stores one flit per slot. Write and read pointers are $clog2(DEPTH)+1 bits — the extra MSB is the "wrap bit" that lets full and empty be distinguished without a separate counter. Press Write and Read to watch the pointers move.

Pointers & status

Each pointer is 4 bits for a depth-8 FIFO. The bottom 3 bits index the storage; the top bit is the wrap. Full when wrap bits differ but indices match. Empty when both halves match exactly.

2credit_manager — counting permits to send

Each CHI channel uses credit-based flow control: the sender starts with INIT_CREDITS tokens (loaded during link training), spends one per flit, and gets one back via lcrd_return each time the receiver drains its buffer. The trick is the simultaneous {flit_sent, lcrd_return} = 2'b11 case — net zero, no race. Press play to walk it.

3cdc_sync — 2-flop synchronizer

The smallest module in the codebase, and the most important. A single bit from clock domain A can violate setup/hold on a flop in domain B; the result is metastability. Two cascaded flops in domain B give the metastable signal time to resolve before any logic reads it. This block protects every cross-domain control signal in the NoC.

Why 2 flops? The first flop captures the asynchronous signal — its output may be metastable for some duration τ_resolve. The second flop samples after one full clk_dst period, by which time the first flop has almost certainly settled. This gives a mean- time-between-failure (MTBF) of years-to-millennia in modern processes.

4async_fifo — Gray-code pointer FIFO

To pass a multi-bit value (the whole flit) between two clock domains, you can't just use cdc_sync on each bit — bits could synchronize on different cycles and the receiver would briefly see a corrupted value. The classic answer: store data in a shared memory, and synchronize only the Gray-coded pointers. Gray code guarantees only one bit changes per increment, so the worst case is one bit transitioning while sampled.

Binary vs Gray, depth-8

Watch which bits change as you advance the pointer. Binary: multiple bits often flip together (e.g. 0011 → 0100 flips three). Gray: always one bit.

6Check yourself

Q1. Why does flit_buffer use a pointer one bit wider than $clog2(DEPTH)?
The extra MSB is a wrap bit. Without it, wr_ptr == rd_ptr is ambiguous — it could mean "FIFO empty" or "FIFO full with same indexes". With the wrap bit, full = (MSBs differ) && (indexes equal); empty = full pointer match. No counter needed.
Q2. In credit_manager, what would go wrong if the 2'b11 case decremented instead of doing nothing?
You'd "leak" credits. Each cycle where both events happen would lose one credit forever — eventually the sender runs out and stalls even though the receiver had room. The 2'b11 net-zero case keeps the credit pool stable at steady-state sustained throughput.
Q3. Why is a single cdc_sync not enough for a multi-bit bus?
Each bit's metastability resolves independently. If the bus is changing when sampled, some bits may catch the new value and others the old — producing a transient corrupted word never present in either domain. Use async_fifo instead: only Gray-coded pointers cross domains, and the data itself sits in a shared memory.
Q4. What's the (* ASYNC_REG = "TRUE" *) attribute doing in cdc_sync.sv?
It tells the synthesis tool: don't optimize, retime, or clock-gate these flops; place them physically adjacent. Without it, synth might decide that sync_q[0] looks redundant and combine it with sync_q[1], breaking the metastability margin.
