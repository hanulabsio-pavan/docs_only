Building a Verilog Testbench Debug Agent

A hands-on deep dive into LLM agent design, using a problem you already understand: a failing testbench.

Estimated time: ~75 minutes of reading across 4 chapters, plus ~14–16 hours of build time following the roadmap.

Prerequisites: comfortable with Verilog/SystemVerilog and basic Python. No prior agent or LLM-API experience assumed.

Stack: Python 3.11+, the anthropic SDK with a hand-written tool loop (no framework), Icarus Verilog (iverilog + vvp) on Windows.

What you'll learn:

  • What an "agent" actually is under the hood — a loop, a model, and a set of tools — and how to write that loop yourself in ~30 lines.
  • How to design tools whose outputs an LLM can reason over, using EDA tool logs as a deliberately hostile example.
  • Why tool descriptions and output shaping matter more than clever prompting.
  • How to evaluate an agent objectively, keep it sandboxed, and make it verify its own fix.

Chapter 1: Anatomy of a Tool-Using Agent

Strip away the marketing and an LLM agent is three things: a model that can emit structured "call this tool with these arguments" requests, a set of tools (ordinary functions), and a loop that ferries results back to the model until it stops asking for tools. Every framework — LangGraph, the Claude Agent SDK, AutoGen — is this loop with extra decoration. Writing it by hand once is the single most clarifying thing you can do, which is why this lesson avoids frameworks entirely.

1.1 The system you are building

Notice what is not in the picture: no planner, no memory store, no vector database. For this task the model's context window is the working memory and the tool results are its senses. That minimalism is a feature — when the agent misbehaves in Chapter 3, there are only three places to look.

1.2 One turn of the conversation

The Messages API is stateless. Every call sends the entire history. An agent turn therefore looks like this: you send a user message plus your tool schemas; the model replies with an assistant message whose content is a list of blocks. If any block is of type tool_use, the model is asking you to run something. You run it, and you reply with a user message containing tool_result blocks — one per request, matched by tool_use_id. Then you call again. When the reply has stop_reason == "end_turn" and no tool blocks, the model is done.

// What the model sends you when it wants a tool
{
  "role": "assistant",
  "content": [
    {"type": "text", "text": "Let me run the simulation first."},
    {"type": "tool_use", "id": "toolu_01AbC", "name": "simulate",
     "input": {"files": ["counter.sv", "tb_counter.sv"], "timeout_s": 30}}
  ]
}

// What you must send back (same tool_use_id!)
{
  "role": "user",
  "content": [
    {"type": "tool_result", "tool_use_id": "toolu_01AbC",
     "content": "... last 80 lines of vvp output ...",
     "is_error": false}
  ]
}
Missing from most tutorials: the is_error flag. If your tool raised an exception, return the traceback as the content and set is_error: true. The model treats it as "that didn't work, try something else" rather than as data about the design. Forgetting this is a common cause of agents that confidently mis-diagnose a Python bug as an RTL bug.

1.3 Tool schemas: the part that does the most work

A tool is declared to the model as a JSON schema: a name, a description, and an input_schema. The description is read by the model on every call and is the single strongest lever you have over its behaviour — stronger than the system prompt, because it sits right next to the decision the model is making. Write it as if onboarding a new hire: what the tool does, what it returns (including size limits), and when to prefer it over another tool.

SIMULATE_SCHEMA = {
    "name": "simulate",
    "description": (
        "Compile the given Verilog/SystemVerilog files with iverilog -g2012 and run "
        "them with vvp. Returns the compiler errors if compilation fails, otherwise "
        "the LAST 80 lines of simulation stdout (use grep_log to search the full log). "
        "Always run this first to see the actual failure before reading source."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "files": {"type": "array", "items": {"type": "string"},
                      "description": "Paths relative to the case directory, DUT first."},
            "timeout_s": {"type": "integer", "default": 30,
                          "description": "Kill the simulation after this many seconds."},
        },
        "required": ["files"],
    },
}
Advanced: why not just give the model a shell?

You could expose a single run_command(cmd) tool and let the model type iverilog ... itself. It works, and many coding agents do exactly that. But for learning it hides the lesson: with a raw shell you cannot shape outputs per tool, cannot enforce a timeout per tool, and cannot sandbox paths per tool. Narrow tools make the agent more predictable and make Chapter 3's experiments possible. Once you've done it the narrow way, try the shell version in Stage 7 and compare transcripts.

Self-Check Quiz

Q1: The model returns a message with stop_reason: "tool_use" containing two tool_use blocks. How many tool_result blocks must your next message contain, and where do they go?

Exactly two, one per tool_use_id, all inside a single user message. The API rejects a turn that leaves a tool call unanswered, and results for calls the model never made are also an error.

Q2: Which has more influence over whether the agent runs the simulation before reading source: (a) the system prompt, (b) the simulate tool description, (c) the model temperature?

(b), in practice. The description is attached to the exact decision point. The system prompt helps too, but a tool description that says "run this first" reliably changes tool ordering; temperature mostly changes variance, not strategy. You'll measure this yourself in Stage 4.

Q3: Your read_file tool throws FileNotFoundError. What should you send back?

A tool_result whose content is the error text (e.g. "No such file: counter.v — available files: counter.sv, tb_counter.sv") with is_error: true. Never let the exception escape the loop; a crashed loop loses the whole transcript.

Key Takeaways

  • An agent = model + tools + a loop you can write in ~30 lines. Frameworks add convenience, not capability.
  • The API is stateless; the loop owns the message history and must answer every tool_use with a matching tool_result.
  • Tool descriptions are the highest-leverage text in the system. Say what the tool returns and when to use it.
  • Return tool failures as is_error: true so the model distinguishes "my tool broke" from "the design is broken".

Chapter 2: Test Material & Tools (No LLM Yet)

This chapter covers Stages 0–2 of the roadmap. It contains zero API calls, which is deliberate. Agents fail for boring reasons — a tool that hangs, a path that doesn't resolve on Windows, a log that's 2,000 lines long — and every one of those is easier to catch before a model is in the loop adding its own randomness.

2.2 Stage 1 — Designs with planted bugs

You cannot judge an agent without a grading key. So the first artefacts are designs whose bug you planted and wrote down. Case A is an 8-bit counter with a reset-polarity mismatch: the RTL treats rst as active-low, the testbench drives it active-high. The counter therefore never leaves reset and the check fails with expected 10 got 0.

// designs/counter/counter.sv  — DUT with a planted bug
module counter #(parameter W = 8) (
    input  logic         clk,
    input  logic         rst,      // testbench thinks: active-HIGH
    input  logic         en,
    output logic [W-1:0] count
);
    always_ff @(posedge clk) begin
        if (!rst)                  // BUG: treats rst as active-LOW
            count <= '0;
        else if (en)
            count <= count + 1'b1;
    end
endmodule
// designs/counter/tb_counter.sv
`timescale 1ns/1ps
module tb_counter;
    logic clk = 0, rst, en;
    logic [7:0] count;
    counter dut (.*);
    always #5 clk = ~clk;

    initial begin
        $dumpfile("counter.vcd"); $dumpvars(0, tb_counter);
        rst = 1; en = 0;
        repeat (2) @(posedge clk);
        rst = 0;
        en  = 1;
        repeat (10) @(posedge clk);
        #1;
        if (count !== 8'd10) begin
            $display("FAIL: expected 10 got %0d at t=%0t", count, $time);
            $finish;
        end
        $display("PASS");
        $finish;
    end
endmodule

And the grading key, one sentence, in designs/counter/EXPECTED.md:

root_cause: reset polarity mismatch — counter.sv line 9 uses `if (!rst)` (active-low)
            while tb_counter.sv drives rst high to reset (active-high).
keywords:   polarity, active-low, active-high, !rst
fix:        change `if (!rst)` to `if (rst)` in counter.sv

Case B (Stage 5) is a 4-deep synchronous FIFO where full is computed as wr_ptr == rd_ptr instead of comparing the wrap bit, so it never asserts and the testbench overflows. It's a better test because the failure shows up several cycles after the buggy line executes — the agent has to reason across time, not just find a line.

import subprocess, shutil, tempfile
from pathlib import Path

IVERILOG = shutil.which("iverilog") or r"C:\iverilog\bin\iverilog.exe"
VVP      = shutil.which("vvp")      or r"C:\iverilog\bin\vvp.exe"

def simulate(files: list[str], case_dir: Path, timeout_s: int = 30,
             tail: int = 80) -> str:
    paths = [safe_path(case_dir, f) for f in files]          # Stage 6: raises on escape
    work  = Path(tempfile.mkdtemp(prefix="sim_", dir="runs"))
    out   = work / "sim.vvp"

    comp = subprocess.run([IVERILOG, "-g2012", "-o", str(out), *map(str, paths)],
                          capture_output=True, text=True, encoding="utf-8",
                          errors="replace", cwd=case_dir)
    if comp.returncode != 0:
        return f"COMPILE FAILED (rc={comp.returncode})\n{comp.stderr}"

    try:
        run = subprocess.run([VVP, "-n", str(out)], capture_output=True, text=True,
                             encoding="utf-8", errors="replace", cwd=work,
                             timeout=timeout_s)
    except subprocess.TimeoutExpired as e:
        partial = (e.stdout or b"").decode("utf-8", "replace") if isinstance(e.stdout, bytes) else (e.stdout or "")
        return (f"TIMEOUT after {timeout_s}s — simulation never reached $finish. "
                f"Likely an infinite loop or missing $finish. Last output:\n"
                + "\n".join(partial.splitlines()[-20:]))

    log = run.stdout + run.stderr
    (work / "sim.log").write_text(log, encoding="utf-8")   # grep_log reads this later
    lines = log.splitlines()
    head  = "" if len(lines) <= tail else f"[{len(lines)-tail} earlier lines omitted; use grep_log]\n"
    return head + "\n".join(lines[-tail:])

Every branch returns a string. Never let an exception leave a tool; the loop catches whatever slips through and wraps it as is_error, but that's a safety net, not the plan.

Unit tests before any model

# tests/test_tools.py
from pathlib import Path
from agent.tools import simulate, read_file, grep

CASE = Path("designs/counter")

def test_simulate_reports_fail():
    out = simulate(["counter.sv", "tb_counter.sv"], CASE)
    assert "FAIL: expected 10 got 0" in out

def test_read_file_has_line_numbers():
    out = read_file("counter.sv", CASE, 1, 5)
    assert out.splitlines()[0].startswith("1 |")

def test_grep_finds_reset():
    assert "!rst" in grep(r"rst", "counter.sv", CASE)

def test_escape_is_blocked():
    out = read_file("../../.env", CASE)
    assert "outside case directory" in out.lower()
Advanced: what "gnarly" actually looks like in a vvp log

A real run interleaves at least five kinds of line: VCD info: dumpfile counter.vcd opened for output., timestamp-prefixed $display output, compile-time warnings that iverilog forwards (warning: implicit definition of wire), assertion messages if you use SVA-lite constructs, and the $finish called at ... footer. None of these carry a severity tag the way a UVM log does. Part of Stage 4 is deciding whether the tool should add one — e.g. prefixing lines matching /FAIL|ERROR|error:/ with [!] — or leave the model to cope. Do the experiment before deciding.

Self-Check Quiz

Q1: Why write EXPECTED.md before writing any agent code?

Because without a ground-truth root cause you can only judge the agent's answer by whether it sounds right, and LLM output always sounds right. The grading key turns "seems plausible" into a pass/fail you can count across runs (Stage 5).

Q2: The testbench in 2.2 uses !== rather than !=. Why does that matter for the agent's job?

!= returns X when either operand has X bits, so the if would be skipped and the testbench would wrongly print PASS with an X count. !== is a case inequality that compares X literally. A testbench that silently passes is a "misleading log" case — exactly the Stage 4 experiment 3 scenario.

Q3: Name two reasons the simulate tool writes the full log to disk instead of returning it all.

(1) Context budget: a 2,000-line log can swamp the model's window and bury the one FAIL line. (2) It enables a second tool, grep_log, so the model can search on demand — which also produces a transcript you can read to see what it searched for.

Key Takeaways

  • Build and test tools with pytest before any model touches them; most agent bugs are tool bugs.
  • Plant bugs deliberately and write the root cause down first — that's your grader.
  • Every tool returns a string on every path; timeouts are non-negotiable for anything that runs a simulator.
  • Windows specifics: list-form subprocess, NUL, UTF-8 with errors="replace", temp files outside OneDrive-synced source folders.

Chapter 3: The Loop & Taming Gnarly Output

This chapter covers Stages 3 and 4. Stage 3 is short: the loop is small and will probably work first time on the counter case. Stage 4 is where the learning is. You'll deliberately make the tool outputs hostile and watch the agent get worse, then fix it with tool shaping rather than prompt tweaking.

3.1 The loop as a state machine

It helps to see the loop as a tiny FSM. It has one decision point, after each model call, and two ways out: a clean final answer or a budget stop. Step through it below, or let it auto-play a typical run: simulate, grep, read, answer.

Current state: IDLE (waiting for a task)

3.2 Stage 3 — Writing the loop

import json, time
from pathlib import Path
from anthropic import Anthropic
from dotenv import load_dotenv
from agent.tools import TOOL_SCHEMAS, dispatch
from agent.prompts import SYSTEM_V1

load_dotenv()
client = Anthropic()
MODEL = os.getenv("AGENT_MODEL", "claude-sonnet-4-5")  # check docs.claude.com for current model IDs

def run(task: str, case_dir: Path, max_steps: int = 15, token_cap: int = 200_000) -> dict:
    messages = [{"role": "user", "content": task}]
    used = 0
    for step in range(1, max_steps + 1):
        resp = client.messages.create(model=MODEL, max_tokens=4096, system=SYSTEM_V1,
                                      tools=TOOL_SCHEMAS, messages=messages)
        used += resp.usage.input_tokens + resp.usage.output_tokens
        messages.append({"role": "assistant", "content": [b.model_dump() for b in resp.content]})

        if resp.stop_reason != "tool_use":
            return save(messages, case_dir, step, used, status="done")
        if used >= token_cap:
            return save(messages, case_dir, step, used, status="token_cap")

        results = []
        for block in resp.content:
            if block.type != "tool_use":
                continue
            try:
                out, err = dispatch(block.name, block.input, case_dir), False
            except Exception as e:                  # safety net, tools should not raise
                out, err = f"{type(e).__name__}: {e}", True
            results.append({"type": "tool_result", "tool_use_id": block.id,
                            "content": out, "is_error": err})
        messages.append({"role": "user", "content": results})
    return save(messages, case_dir, max_steps, used, status="max_steps")

def save(messages, case_dir, steps, tokens, status):
    Path("runs").mkdir(exist_ok=True)
    rec = {"case": str(case_dir), "status": status, "steps": steps, "tokens": tokens,
           "model": MODEL, "messages": messages}
    Path(f"runs/{case_dir.name}_{int(time.time())}.json").write_text(json.dumps(rec, indent=2))
    return rec

The first system prompt should be short. You want to see what the model does on its own before you steer it:

SYSTEM_V1 = """You are a digital design verification engineer.
You are given an RTL design and a testbench that fails. Use the tools to find the root cause.
Finish with exactly these three sections:
ROOT CAUSE: one sentence.
EVIDENCE: file:line references and the log lines that support it.
SUGGESTED FIX: the minimal code change."""
Added: read the transcript, not just the answer. After every run, open the JSON in runs/ and answer three questions in NOTES.md: what did it call first, did it read whole files or grep first, and did it ever look at the testbench as a suspect? Those tool-ordering choices are the agent design you're here to study. A tiny scripts/show_run.py that prints one line per tool call (name, args, first 60 chars of result) makes this painless.

3.3 Stage 4 — Four hostile experiments

Run each experiment as a before/after pair. Change one thing at a time, run 3 times each (the model is non-deterministic), and write a short paragraph in NOTES.md.

#Make it hostileTypical failureFixes to try (one at a time)
1Volume. $display every cycle for 2,000 cycles.FAIL line buried; context bloats; agent summarises noise.Tail only; head+tail; grep_log tool; pre-extract FAIL|ERROR|error: lines to the top.
2Noise. Add benign warnings (unused signal, implicit wire).Agent "fixes" the warning and declares victory.Split errors vs. warnings in lint; description says "warnings are hints, not root causes".
3Misleading log. Checker in the TB has the wrong expected value.Agent edits a correct DUT to match a wrong TB.Prompt: "the testbench itself may be wrong"; require evidence from both files.

import re
SIGNAL = re.compile(r"\b(FAIL|ERROR|FATAL|error:|Assertion)\b", re.I)

def shape_log(log: str, edge: int = 5, max_hits: int = 20) -> str:
    lines = log.splitlines()
    hits  = [(i + 1, l) for i, l in enumerate(lines) if SIGNAL.search(l)]
    fin   = next((l for l in reversed(lines) if "$finish" in l), "no $finish seen")
    out   = [f"SUMMARY: {len(hits)} failure/error lines, {len(lines)} lines total. {fin}"]
    out  += [f"[!] line {n}: {l}" for n, l in hits[:max_hits]]
    if len(hits) > max_hits:
        out.append(f"... {len(hits) - max_hits} more; use grep_log")
    out += ["--- first lines ---", *lines[:edge], "--- last lines ---", *lines[-edge:]]
    out.append("Full log saved. Use grep_log(pattern) to search it.")
    return "\n".join(out)
Advanced: prompt caching and cost control (added)

Every loop step re-sends the whole history, so costs grow roughly quadratically with step count. Two cheap mitigations: mark the system prompt and tool schemas with cache_control: {"type": "ephemeral"} so repeated prefixes are billed at the cache rate, and truncate old tool results once they've been used (e.g. replace a result older than 4 steps with "[elided; call again if needed]"). The second one is a real agent-design lever: it's a form of memory management, and you can measure whether it hurts accuracy in Stage 5.

Advanced: parallel tool calls

The model may request several tools in one turn (e.g. read_file on both the DUT and TB). Your loop already handles this because it iterates all tool_use blocks. Running them concurrently with a thread pool is easy but gains little here since iverilog runs are short. Keep it sequential for readable transcripts.

Self-Check Quiz

Q1: In experiment 1 you switch simulate from tail-80 to shape_log, and accuracy goes from 1/3 to 3/3. What else changed that you should record?

Steps taken and tokens used. Shaped output usually cuts both, because the model stops paging through the log. Accuracy alone hides cost, and cost is the main reason agents get turned off in practice.

Q2: In experiment 3 (buggy checker), which answer should count as correct: "fix the DUT to output 9" or "the TB's expected value is wrong"?

The second. Update EXPECTED.md for that variant so the grader reflects it. An agent that bends the DUT to match a wrong testbench is the most dangerous failure mode, because the fix makes the test pass.

Q3: Why change only one thing per experiment and run it three times?

The model is non-deterministic, so a single run can't tell a real improvement from luck. Changing two things at once means you can't attribute the effect. It's the same discipline as isolating a bug with one waveform change at a time.

Key Takeaways

  • The loop is a small FSM with one decision (stop_reason) and two exits (done, budget). Always have both exits.
  • Log every run as JSON and read the tool sequence. That is where you learn agent behaviour.
  • Most gains in Stage 4 come from shaping tool output and rewriting tool descriptions, not from the system prompt.
  • Good shaped output says what it contains, what it omitted, and how to get the rest.

Chapter 4: Eval, Safety, Verification & Roadmap

Stages 5–7. By now the agent solves the counter. This chapter turns "it seems to work" into numbers you can track, puts walls around the tools, and adds the step that makes the agent reliable instead of just plausible: it has to prove its fix works.

4.1 Stage 5 — A second case and an eval harness

Add the FIFO case from 2.2, then write scripts/eval.py. It runs every case N times and prints a table. Keyword grading is crude but good enough to spot regressions. If you want better grading later, a second LLM call that compares the answer to EXPECTED.md ("LLM-as-judge") is the usual next step.

# scripts/eval.py
import sys, re
from pathlib import Path
from agent.loop import run

TASK = ("The testbench in this directory fails. Find the root cause. "
        "Files: {files}")

def load_key(case: Path) -> list[str]:
    txt = (case / "EXPECTED.md").read_text()
    m = re.search(r"keywords:\s*(.+)", txt)
    return [k.strip().lower() for k in m.group(1).split(",")] if m else []

def grade(answer: str, keys: list[str]) -> bool:
    rc = answer.lower().split("evidence:")[0]          # only grade the ROOT CAUSE part
    return sum(k in rc for k in keys) >= 2              # at least two keywords

def main(n: int = 3):
    print(f"{'case':10} {'run':>3} {'pass':>5} {'steps':>6} {'tokens':>8} status")
    for case in sorted(Path("designs").iterdir()):
        files = ", ".join(p.name for p in case.glob("*.sv"))
        keys  = load_key(case)
        for i in range(n):
            rec = run(TASK.format(files=files), case)
            final = rec["messages"][-1]["content"]
            text  = " ".join(b.get("text", "") for b in final if isinstance(b, dict))
            ok = grade(text, keys)
            print(f"{case.name:10} {i+1:>3} {'✓' if ok else '✗':>5} "
                  f"{rec['steps']:>6} {rec['tokens']:>8} {rec['status']}")

if __name__ == "__main__":
    main(int(sys.argv[1]) if len(sys.argv) > 1 else 3)

Two things to decide and write down: whether eval runs use temperature=0 (less variance, but hides brittleness), and a budget per eval run (e.g. 6 runs × ~40k tokens). Record the eval table in NOTES.md every time you change a prompt or tool, so you get a history of what helped.

4.2 Stage 6 — Sandbox, propose, verify

# agent/sandbox.py
from pathlib import Path

class SandboxError(ValueError): ...

def safe_path(case_dir: Path, rel: str) -> Path:
    root = case_dir.resolve()
    p = (root / rel).resolve()
    if not p.is_relative_to(root):                 # blocks ../, absolute paths, C:\...
        raise SandboxError(f"'{rel}' is outside case directory; allowed: "
                           + ", ".join(x.name for x in root.iterdir()))
    return p
  1. Sandbox. Every tool path goes through safe_path. Test it by asking the agent to "also read C:\Windows\win.ini" and confirm it gets a clean refusal.
  2. propose_fix(file, old, new). It writes a patch, not the source. It then copies the case to a temp dir, applies the patch, runs simulate, and returns PASS or the new failure. The agent only answers once the fix passes, or after two failed tries, in which case it has to say so.
  3. Budgets. Stop at max_steps or token_cap, and make the final record say which one fired.
  4. Metric (added). Track first-fix pass rate: how often the first proposed patch makes the testbench pass. This is the number that says whether you can trust the agent.
Advanced: a guard against "make the test pass" cheating

An agent with a verify step can learn that editing the testbench is the quickest way to PASS. Block it: propose_fix refuses files that start with tb_ unless the agent sets testbench_is_wrong=true and gives a reason. The reason ends up in the transcript for you to judge. It's the agent version of a code-review rule that says "don't weaken the checker to close a bug".

Self-Check Quiz

Q1: Why does safe_path call .resolve() before the is_relative_to check?

Without resolving, designs/counter/../../.env still starts with designs/counter as a string and would pass a naive prefix check. Resolving collapses .. and symlinks to the real location first.

Q2: Your eval shows 6/6 passes but the first-fix pass rate is 2/6. What does that tell you?

The agent finds the right area but usually proposes a wrong or incomplete patch first, and the verify step is rescuing it. The diagnosis is good, the fix quality isn't, and without verification 4 of 6 answers would have been wrong. Look at the failed patches to see why.

Q3: Short answer: which Stage 7 idea best tests whether the agent can reason about time, and why?

The valid/ready protocol bug, ideally combined with the VCD tool. The bug is only visible as a relationship between signals across cycles, so the agent can't just grep for a bad line.

Key Takeaways

  • Without an eval, prompt changes are guesswork. Even a keyword grader over 3 runs per case catches regressions.
  • Sandbox at the tool layer with resolved paths, and never let the agent edit the originals.
  • Propose-then-verify is what makes the agent trustworthy. Track first-fix pass rate.
  • Record accuracy, steps, and tokens together. An agent that's right but costs 10× isn't better.
