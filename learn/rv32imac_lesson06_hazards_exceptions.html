Hazard resolution and precise exceptions

This is where most candidates get caught. Not because the theory is hard, but because the corner cases are specific and the panel knows exactly which ones to ask about.

By the end of this lesson you can

  • Enumerate every forwarding path and state the priority between them.
  • Explain the x0 forwarding bug and the one-gate fix.
  • Prove that the load-use bubble is unavoidable without a longer clock period.
  • Write the full stall and flush condition for a decoupled M unit.
  • Say why an AMO cannot be replayed and what that forces.
  • Define precise exceptions and name which of the four letters contributes which trap.
  • State what goes in mepc, mcause and mtval for each case.

1The interview frame

crux

Hazards are about values arriving late. Exceptions are about state being undone. Forwarding solves the first. A single commit point solves the second. Every question in this lesson is one or the other.

The specific thing panels test is whether your qualifying conditions are complete. "I forward from EX/MEM and MEM/WB" is half an answer. The full answer includes the write-enable qualifier, the x0 qualifier, the source-used qualifier and the priority between the two paths.

3The forwarding network

Every path in a five-stage RV32IMAC core
Forwarding paths
   ID            EX            MEM           WB
  ┌──────┐     ┌──────┐      ┌──────┐      ┌──────┐
  │ read │────→│ ALU  │─────→│ cache│─────→│ write│
  └──────┘     └──────┘      └──────┘      └──────┘

Path 3 is often free: if the register file writes on the rising edge and reads combinationally from the same array, a same-cycle read returns the old value — so you either add the bypass mux or build the array write-first. Say which you did.

Priority — nearest producer wins

If both EX/MEM and MEM/WB hold a write to the same register, the EX/MEM one is younger and therefore correct.

Why priority matters
    addi  x5, x0, 1      # in MEM/WB when the consumer is in EX
    addi  x5, x0, 2      # in EX/MEM  — this is the correct source
    add   x6, x5, x0     # must see 2, not 1
implementation note

A cascaded priority mux is correct but adds a level of logic in front of the ALU. Faster: compute one-hot selects in parallel, with the MEM/WB select explicitly ANDed with the negation of the EX/MEM match. Same logic, flatter, and it removes a mux level from the EX critical path.

Fully qualified forwarding condition
All four qualifiers — this is the answer panels want
// Forward from EX/MEM to the rs1 operand of the instruction in EX
wire fwd_a_ex =  ex_mem.rd_we               // 1. producer actually writes
              & (ex_mem.rd != 5'd0)        // 2. destination is not x0
              & (ex_mem.rd == id_ex.rs1)    // 3. indices match
              &  id_ex.rs1_used;            // 4. consumer really reads rs1

wire fwd_a_mem = mem_wb.rd_we
              & (mem_wb.rd != 5'd0)
              & (mem_wb.rd == id_ex.rs1)
              &  id_ex.rs1_used
              & ~fwd_a_ex;                  // 5. younger producer wins

assign op_a = fwd_a_ex  ? ex_mem.result
            : fwd_a_mem ? mem_wb.result
            :             id_ex.rs1_data;
QualifierOmitting it causes
rd_weForwarding from a store or branch, which has no destination — garbage operand
rd != 0The x0 bug. See the next section.
rs_usedSpurious stalls and needless mux toggling. Correctness survives, power and timing do not.
~fwd_a_exStale value when two producers target the same register
Store data forwarding — the path people forget

Store data is consumed in MEM, not EX. So a store whose data register is written by the immediately preceding instruction needs a forward into MEM, not into EX.

MEM-stage forward
    lw    x5, 0(x10)     # load data available at end of MEM
    sw    x5, 0(x11)     # needs x5 in ITS MEM stage — one cycle later

// No bubble needed. The load's MEM/WB register holds the data exactly
// when the store reaches MEM. A MEM/WB → MEM forward covers it.
// A core lacking this path inserts a pointless stall on a very common
// load-then-store idiom.
crux

Load-to-store at distance 1 costs no bubble, because store data is needed one stage later than ALU operands. Load-to-ALU at distance 1 costs one bubble. Being able to distinguish these two cases is a strong signal.

4The x0 forwarding bug

this is asked constantly

Suppressing the register file write when rd = x0 is not sufficient. The forwarding comparator also matches on rd = x0, and forwards a non-zero result to an instruction reading x0. The architectural register file stays correct; the bypassed value is wrong.

The failure
    add   x0, x1, x2     # result discarded — a legal RISC-V nop idiom
    add   x3, x0, x0     # must compute 0 + 0 = 0

// Without the rd != 0 qualifier:
//   comparator sees ex_mem.rd (= 0) == id_ex.rs1 (= 0)  → MATCH
//   forwards (x1 + x2) into both operands
//   x3 = 2 * (x1 + x2)   ← wrong, and silently so

The fix is one AND gate per comparator: & (producer_rd != 5'd0). It costs nothing and is trivially verified — but it is omitted often enough that it is a standard interview probe.

why the idiom exists at all

Writing to x0 is the canonical way to discard a result. ADD x0, x1, x2 is a nop that still exercises the ALU. More practically, C.SWSP x0, off(sp) stores a zero, and hint encodings in the base ISA deliberately write x0. The case is real, not theoretical.

5The load-use interlock

The one bubble you cannot forward away in a classic five-stage pipeline.

Load-use at distance 1
cyc      1     2     3     4     5     6
lw x5    IF    ID    EX   MEM   WB
                           └─ data valid at END of cycle 4
add x6,x5     IF    ID   ■    EX   MEM   WB
                     └─ needs x5 at START of cycle 4 — impossible
                          ■ = injected bubble
why it is unavoidable

The cache access consumes the whole MEM cycle. Forwarding its output to the EX input of an instruction in the same cycle would mean cache access plus forwarding mux plus ALU in one period. That is a longer clock, not a free forward. So the bubble buys you frequency.

Detection
Load-use stall condition
wire load_use_stall = id_ex.mem_req & ~id_ex.mem_we          // producer is a load
                    & (id_ex.rd != 5'd0)
                    & ( (if_id.rs1_used & (if_id.rs1 == id_ex.rd))
                      | (if_id.rs2_used & (if_id.rs2 == id_ex.rd)) );

// On assert: hold IF and ID, inject a bubble into EX.
// Note rs2_used must be FALSE for a store's data register here —
// a store consuming the load result needs no stall (MEM→MEM forward).
the refinement worth mentioning

A naive condition stalls lw x5 followed by sw x5. That is unnecessary, because store data is consumed in MEM where the MEM/WB forward already covers it. Distinguishing "rs2 used as an ALU operand" from "rs2 used as store data" removes a bubble from a very common idiom. Small change, measurable IPC.

no delay slots

MIPS I exposed the load delay slot architecturally — the instruction after a load could not use its result, and the compiler filled the slot. RISC-V deliberately does not. The hardware must interlock. The upside is that deeper or shallower pipelines remain binary-compatible; the downside is that you cannot omit the interlock logic.

6M extension hazards — the full condition

With a decoupled multi-cycle unit, ID needs three additional stall terms.

Complete M interlock
// Scoreboard state, one entry for a non-pipelined unit
logic       md_busy;
logic [4:0] md_dest;

// --- 1. RAW: consumer needs a result that does not exist yet ---------
wire md_raw = md_busy & (md_dest != 5'd0)
             & ( (id.rs1_used & (id.rs1 == md_dest))
               | (id.rs2_used & (id.rs2 == md_dest)) );

// --- 2. WAW: a younger writer would be overtaken ---------------------
wire md_waw = md_busy & id.rd_we & (id.rd != 5'd0)
             & (id.rd == md_dest);

// --- 3. Structural: unit already occupied ----------------------------
wire md_struct = md_busy & id.md_valid;

wire md_stall = md_raw | md_waw | md_struct;
TermExample that trips itAlternative to stalling
md_rawdiv x5,.. then add x6, x5, x7None. The value genuinely does not exist.
md_wawdiv x5,.. then addi x5, x0, 1Cancel the divide's writeback — legal because DIV has no other effect.
md_structmul then mulPipeline the multiplier so it accepts one per cycle.
the pipelined-multiplier refinement

Split the scoreboard: a pipelined multiplier with fixed 3-cycle latency needs no busy bit at all — it behaves like a deeper forwarding problem, and a shift register of pending destinations suffices. The iterative divider keeps the busy bit. Treating M as one monolithic unit throws away that distinction and costs IPC.

7A extension hazards

The AMO must be non-speculative when it issues

In a classic five-stage pipeline this comes free, and that is worth stating explicitly because it sounds like it should be hard.

  • Branches resolve in EX. An instruction in MEM is therefore past any mispredict shadow.
  • Execution is in order, so every older instruction is already in MEM or WB and has passed its own fault point.
  • Therefore an AMO reaching MEM is guaranteed to commit.

What breaks this: a deeper pipeline where branches resolve later than the memory stage, any out-of-order issue, or a store buffer that lets younger memory operations bypass older ones. Then the AMO must be explicitly held until it is the oldest uncommitted instruction.

Why an AMO cannot be replayed

Many pipelines recover from a stall or a cache miss by replaying the instruction from an earlier stage. An AMO forbids this once it has touched memory.

The double-increment bug
    amoadd.w x5, x6, (x10)

// cycle N   : read mem → 100, compute 100 + x6, write 105
// cycle N+1 : unrelated replay condition re-issues the instruction
// cycle N+2 : read mem → 105, compute 105 + x6, write 110
//
// The counter incremented twice for one instruction. Silent corruption.

So the design rule is: an AMO is either fully performed or not started. Any replay mechanism must be gated off for the AMO once the read phase has committed, and the line must stay locked across the read and write phases so no snoop can observe the intermediate state.

the snoop deadlock

Locking a line for two cycles creates a window where an incoming snoop to that line must be delayed. If the snoop path has no retry and the lock waits on something the snoop is blocking, you deadlock. Give the snoop path a retry response, or bound the lock duration so it always releases. Mention this — it shows fabric awareness.

Fault checks precede modification
  1. Translate the address. A translation failure raises a store/AMO page fault, cause 15.
  2. Check write permission. An AMO to a read-only page faults as a store, not a load.
  3. Check alignment. A misaligned AMO raises store/AMO address misaligned, cause 6.
  4. Check the physical region. A failure raises store/AMO access fault, cause 7.
  5. Only now issue the read-modify-write.
trap

LR and SC are governed by the same rules. An SC that faults must not clear the reservation in a way that a restarted sequence cannot recover from — and crucially, must not have stored anything. The fault is taken before the conditional store is attempted.

Ordering annotations as stall sources
AnnotationWhat must drainCost driver

In a simple in-order core with blocking accesses and no store buffer, all four rows cost approximately nothing — the machine is already ordered. Say that plainly if it is true of your design. It is an honest answer and it explains why small cores get A cheaply.

8Control hazards, and what C changes

Resolution pointInstructions flushedCost
Branch resolved in ID with a dedicated comparator11 cycle
Branch resolved in EX22 cycles
Branch resolved in EX, with an extra expand stage33 cycles
JALR target from EX2Always, unless predicted

Resolving in ID sounds attractive but pulls the comparator, and therefore the forwarded operands, into ID — often making ID the critical path. The usual compromise is EX resolution with a static or dynamic prediction.

What C changes
  • Flush depth is unchanged. The same number of stages are killed.
  • Redirect granularity becomes 2 bytes. The PC mux and every PC-indexed structure must carry bit 1.
  • The fetch buffer must be flushed too, including any pending fault status, or a stale fault from a discarded path will surface later.
  • A redirect target at 2 mod 4 may immediately require a straddling fetch, so the first instruction after a taken branch can cost an extra fetch cycle.
a real bug class

Flushing the pipeline registers but not the fetch buffer leaves pre-fetched bytes from the wrong path. With fixed-length instructions this is usually caught by a simple valid bit. With C, the buffer also holds partial instructions and boundary state, so the flush must reset the alignment state machine — not just clear a valid flag.

9What "precise" actually means

definition

An exception is precise when, at the moment the handler begins, every instruction before the faulting one has completed and written its results, the faulting instruction and every instruction after it have written nothing, and mepc identifies the faulting instruction exactly.

How a five-stage pipeline achieves it
  1. Exceptions are detected in whatever stage discovers them, but not acted upon there.
  2. The exception flag and cause travel down the pipeline with the instruction, in the pipeline registers.
  3. They are taken at one single point — conventionally at the WB boundary, the commit point.
  4. At that point, all younger instructions in earlier stages are flushed, so none of them writes back.
  5. Older instructions are already past commit, so their writes stand.
Exception flowing to the commit point
cyc      1     2     3     4     5
ok        IF    ID    EX   MEM    WB      ← completes normally
fault           IF    ID    EX   MEM   WB  ← page fault detected in MEM,
                                         carried to WB, taken there
younger1              IF    ID    ✕      ← flushed
younger2                    IF    ✕      ← flushed

  mepc ← PC of `fault`     mcause ← 13 (load page fault)
  mtval ← faulting address PC ← trap vector
why M does not disturb this

The M extension writes back out of order, which normally threatens precision. It is safe here for one specific reason: no M instruction can raise an exception. There is no divide-by-zero trap. So an out-of-band M writeback can never need to be undone, and can never be the faulting instruction. This is the payoff of the no-trap design decision in Lesson 02.

the one-line answer

"M contributes no exceptions at all. A contributes store-class faults even for its read phase. C contributes reserved-encoding illegals plus a second instruction-fetch fault path for straddling instructions. The base contributes everything else."

note on cause 0

Instruction-address-misaligned is reported on the branch or jump that would produce the misaligned target, not on the fetch of the target. With C implemented, IALIGN is 16 and every encodable target is already even, so this exception becomes unreachable. It remains in the table for IALIGN=32 implementations.

11Trap priority

One instruction can qualify for several exceptions at once. The architecture defines which wins.

OrderGroupRationale
1Instruction address breakpointDebug must see the instruction before anything else happens to it
2Instruction page faultYou cannot decode bits you could not translate
3Instruction access faultYou cannot decode bits you could not read
4Illegal instructionDecode-time faults, once the bits exist
5Instruction address misalignedReported on the transferring branch or jump
6ECALL, EBREAK, load/store/AMO address breakpointExplicit and debug traps
7Load/store/AMO address misalignedOptionally here; otherwise lowest — see note
8Load/store/AMO page faultTranslation before physical access
9Load/store/AMO access faultPhysical region check
the shape to remember

Fetch-stage faults beat decode-stage faults, which beat memory-stage faults. Within each group, translation faults beat physical access faults. That ordering is just pipeline order, which makes it easy to reconstruct under pressure.

the misaligned-access subtlety

An implementation may check address alignment either before or after the translation and access-fault checks. So a misaligned access to an unmapped page may report either misaligned or page fault, depending on the design. The specification permits both. If asked, say "implementation-defined ordering, and I chose to check alignment first because it needs no TLB lookup".

interrupts versus exceptions

Interrupts are not in this table. An interrupt is taken between instructions, and when an interrupt is pending and enabled it takes priority over any synchronous exception that the next instruction would raise — because that instruction simply does not execute. Do not merge the two priority schemes.

mepc alignment

mepc[0] is always zero. With C implemented, IALIGN is 16 and mepc[1] can be set. Without C, IALIGN is 32 and mepc[1:0] is always zero — a core built without C that later adds it must widen the mepc write path accordingly.

returning from a trap

ECALL and EBREAK set mepc to their own address, not the following instruction. So the handler must advance mepc itself before MRET, and it must advance by 2 or 4 depending on whether the trapping instruction was compressed. The handler reads inst[1:0] at mepc to decide. A handler that blindly adds 4 breaks on C.EBREAK — another consequence of C reaching further than people expect.

the two rules underneath the table

Stall propagates backwards. If a stage cannot advance, every stage in front of it must hold. Flush propagates forwards. When a redirect or trap is taken, every stage behind it is killed. Any control bug in a pipeline is almost always a violation of one of these two rules.

why FENCE.I flushes

FENCE.I makes prior stores visible to instruction fetch. So the I-cache must be invalidated and any already-fetched instructions discarded — they may be stale copies of code that was just rewritten. Note it is part of Zifencei, not the base, as covered in Lesson 01.

15Interview Q&A

List every forwarding path in your core and the priority between them.

Four. EX/MEM to the EX operand muxes, covering distance-one dependencies on ALU results. MEM/WB to the EX operand muxes, covering distance two and load results at distance two. MEM/WB to the MEM store-data port, covering a load or ALU result consumed as store data at distance one. And WB to ID, which I implemented as a write-first register file rather than an explicit mux.

Priority is nearest-producer-wins: EX/MEM overrides MEM/WB. I implemented that as parallel one-hot selects with the MEM/WB term ANDed against the negation of the EX/MEM match, rather than a cascaded priority mux, to keep a level of logic out of the EX path.

Every match is qualified four ways: the producer writes, its destination is not x0, the indices match, and the consumer actually reads that source.

Prove your exceptions are precise.

The argument has three parts. First, there is exactly one commit point — the WB boundary — and nothing writes architectural state before it except the register file write, which is itself gated by the trap signal at that boundary.

Second, exception status is data, not control. It is detected wherever it is discovered and carried in the pipeline registers alongside the instruction, so it arrives at commit with the right instruction and cannot overtake or lag it.

Third, taking a trap flushes every stage behind the commit point in the same cycle, so no younger instruction can write. Older instructions are already past commit.

The two things that could break it are handled explicitly. The M unit writes out of band, which is safe only because M raises no exceptions. And the AMO modifies memory in MEM, before commit — which is safe only because in-order MEM is already non-speculative, and because all its faults are checked before the modification is issued.

An interrupt arrives while a load is stalled on a cache miss. What happens?

Two legitimate policies. The simple one is to let the miss complete, then take the interrupt at the next instruction boundary. Interrupt latency then includes the full miss penalty, which for an external memory access can be long.

The other is to abort the load and set mepc to the load's own PC so it re-executes on return. That is safe because a load writes nothing until writeback — it is idempotent in the same sense as a divide. But it is only safe for ordinary loads. An AMO that has already performed its read-modify-write must not be aborted, and a load from device memory with read side effects must not be re-executed.

So the honest answer is that abort-and-restart is a per-region decision: safe for normal cacheable memory, unsafe for anything with side effects. If I had a hard interrupt-latency budget I would implement abort for cacheable loads only.

Where do you detect illegal instructions, and why not in ID?

I compute it from the registered instruction word in the stage after decode. The illegal cone touches nearly every instruction bit — opcode, funct3, funct7, funct5, reserved-field checks across all four extensions — so it is wide and slow, and it sits on no other signal's path.

Since the exception is not taken until the commit point anyway, there is no correctness reason to have it early. Moving it one stage later cost a few flops for the instruction word and bought real slack in ID.

The structure matters as much as the placement: illegal is the complement of an explicit legal signal built as the OR of every match term, with reserved-field checks ANDed into each term. It is never a default arm, because a default silently aliases reserved encodings onto real instructions.

Your core passes every directed test but fails a random instruction-stream test intermittently. Where do you look?

Directed tests exercise intended cases; random streams exercise interactions. So I would look at the interactions first, in this order.

Forwarding qualifiers — specifically the x0 case and the store-data path, because directed tests rarely write x0 deliberately or chain a load straight into a store.

WAW against the M unit, because it needs a long-latency operation followed by a short one to the same destination, which random streams generate and hand-written tests almost never do.

Flush completeness on redirect — especially whether the fetch buffer's alignment state and pending fault status are reset, not just a valid bit cleared. With C that is a genuine bug class.

And reserved encodings, because a random generator will emit them and a default-arm decoder will silently execute them as something else.

Method-wise I would bisect with a shrinking harness on the failing seed rather than reading waveforms first — an intermittent failure usually reduces to a three or four instruction sequence.

Does the C extension make exceptions harder?

In two specific ways, yes. First, a 32-bit instruction can span two pages, so one instruction has two fetch-fault sites — and the reporting rule is asymmetric: mepc holds the instruction's start while mtval holds the portion that actually faulted.

Second, mepc can now have bit 1 set, and trap handlers must advance mepc by 2 or 4 after ECALL or EBREAK depending on the trapping instruction's length.

There is one way it makes things easier: instruction-address-misaligned becomes unreachable, because every encodable branch or jump target is already even when IALIGN is 16.

16Defend your claim — Hanu 1.0

write your answers down
  • List your forwarding paths. Is the rd != 0 qualifier present on every comparator? Point to the line.
  • Does a load followed by a store of the same register cost you a bubble? If yes, do you know why?
  • Where is your commit point, and what exactly is gated by the trap signal there?
  • Where do you check alignment relative to translation, and can you justify the ordering?
  • Is your fetch buffer flushed completely on redirect, including alignment state and pending fault status?
  • Does your handler advance mepc by 2 or 4 after EBREAK? How does it decide?
  • Can an interrupt abort a stalled load or an in-flight divide in your design?
  • How did you verify precision — a reference model comparison at every commit, or directed trap tests only?

17Recap

  • Four forwarding paths. Nearest producer wins. Four qualifiers on every match.
  • The rd != 0 qualifier is one gate and its absence is a silent corruption bug.
  • Load-use costs one bubble and cannot be forwarded away without lengthening the clock.
  • Load-to-store at distance one costs zero bubbles. Know the difference.
  • M adds RAW, WAW and structural stall terms. WAW is the one that is new.
  • An AMO is non-speculative for free in a five-stage pipeline, must never be replayed, and faults as a store.
  • Precise means: one commit point, exception status carried as data, younger instructions flushed.
  • M raises no exceptions at all. That is what makes its out-of-order writeback safe.
  • Fetch faults beat decode faults beat memory faults. Translation beats physical access.
  • Interrupts are taken between instructions and sit outside the synchronous priority table.
  • With C, mepc can have bit 1 set, and a handler must advance it by 2 or 4.
  • Stall propagates backwards. Flush propagates forwards.
