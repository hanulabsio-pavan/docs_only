4Boundary termination — no wrap-around

A 4×4 mesh has no torus wraparound — the edges genuinely end. For each directional bus the entries outside the mesh are tied off: valid = 0 for inbound (no sender exists), ready = 0 for outbound (no receiver exists). The generate loop in noc_mesh.sv:78 handles this.

BoundarySignalTied toReason
South edge (row 0)vn_valid[0][c]1'b0No router below row 0 to send northward
South edgevs_ready[0][c]1'b0No receiver below row 0 for southbound
North edge (row ROWS)vs_valid[ROWS][c]1'b0No router above top row to send south

West edge (col 0)he_valid[r][0]1'b0No router left of col 0

Boundary tiles still route correctly — route_compute_unit will never select a direction that points off the mesh, thanks to its translate_off assertions. The boundary terminations are belt-and-braces for cases where buggy logic might try.

5noc_top — the wrapper

noc_top.sv sits one level above noc_mesh. It packetizes CHI flits arriving from external CHI links into router-internal flits, drives mesh injection ports, depacketizes ejection ports back into CHI flits, and aggregates error/status signals.

6Critical bug from the DV tracker

The DV tracker flagged this with ⚠ severity — it's the one that prevents simulation from making forward progress. The current RTL already shows the fixed version (four directional arrays), but worth understanding what could go wrong.

⚠ Inputs and outputs must be on separate nets
The original report flagged that north_flit_in and north_flit_out shared the same wire. Two routers each driving the same net = X propagation in sim, fight + short in synthesis. The fix (now in noc_mesh.sv:59-73) declares four separate arrays — vn_flit, vs_flit, he_flit, hw_flit — one per direction. Each router writes onto its outbound array and reads from its inbound array.

8Check yourself

Q1. Router at (r=1, c=2) sends a flit out its East port. Which array does it write?
he_flit[1][3]. East output of router (r, c) writes he_flit[r][c+1] — the eastbound link between columns c and c+1. The destination router (r, c+1) reads its West input from the same net, he_flit[r][c].
Q2. Why does the mesh need four directional arrays instead of two (one per axis)?
Because each axis has two opposite traffic flows that need independent buses. Northbound flits at link r+1 are not the same as southbound flits at link r+1 — they go in opposite directions, driven by different routers. Putting them on one shared net = collision. Four arrays (vn, vs, he, hw) = four logically independent unidirectional buses.
Q3. Tiles 10 and 11 are marked spare. What does noc_top do with their injection/ejection ports?
See gen_idle_tiles in noc_top.sv:68: it ties inject_flit[t] = 0, inject_valid[t] = 0, and eject_ready[t] = 0. The routers at those tiles still exist and still route traffic that needs to pass through; only the local inject/eject is silenced.
Q4. Why does noc_top need a packetizer and depacketizer per CHI port?
The mesh internally moves noc_flit_ctrl_t — a router-friendly struct with channel, VC, QoS, head/tail bits, route_mask. The external CHI links use the four protocol-defined flit types (REQ/RSP/SNP/DAT). Packetizer translates outbound (CHI → internal), depacketizer translates inbound (internal → CHI). The router doesn't care about CHI semantics and the CHI agents don't care about router internals.
