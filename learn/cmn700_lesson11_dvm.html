DVM — Distributed Virtual Memory & TLB Maintenance

The one coherency mechanism that is not address-based — and therefore the one that scales differently. Commonly probed, and previously the course's largest gap.

By the end of this lesson you can

  • Explain what DVM operations are and which maintenance classes they cover.
  • Name the players: the DVM node (DN) in the HN-D, RN-D requesters, and which agents receive DVM.
  • Walk a TLB invalidate end to end, including the two-part message structure and the sync.
  • Explain why DVM scales differently from address-based traffic — the point interviewers probe.

1Why DVM does not fit the rest of the course

caveman mode

All other traffic so far: "here is an address, hash it, find the one home node that owns it." DVM different. DVM say "everyone who caches translation info, throw it away." No single owner. Must reach many agents. So it not hashed — it go to one special node that broadcasts. Different shape, different scaling problem.

Every mechanism in Lessons 3 to 8 is address-based: the SAM hashes an address to exactly one home node, and that home node is the single point of ordering. DVM breaks that model. A TLB invalidate is not a request about one cache line that one home owns — it is a maintenance operation that must reach every agent holding translation state.

That structural difference is exactly why DVM is a good interview question: it tests whether you understand the coherency model or have merely memorised the address path.

2What DVM operations cover

DVM stands for Distributed Virtual Memory. DVM operations are the messages that keep virtual-memory and instruction-fetch state consistent across a system where many agents cache translations and instructions independently.

ClassPurpose
TLB invalidate (TLBI)The important one. Software changed a page table entry, so every cached translation of that mapping must be discarded. Can be scoped — by address, by ASID (address space), by VMID (virtual machine), or all.
Instruction cache invalidateSelf-modifying or newly loaded code means stale instructions must be dropped.
Branch predictor invalidateDiscard predictor state associated with changed code.
SyncNot a maintenance action itself — a barrier. It completes only once prior DVM operations have completed everywhere, so software knows the maintenance has actually taken effect.

The architectural driver: an Arm core executes a TLBI instruction, and the architecture requires that after the corresponding barrier, no agent in the system is still using the stale translation. The interconnect is what makes that guarantee real.

3The players in CMN-700

PlayerRole
DVM node (DN)Lives in the HN-D. This is the ordering and distribution point for DVM: it receives DVM requests and issues the corresponding DVM snoops to the agents that must act on them. It plays for DVM the role an HN-F plays for an address.
RN-DThe request-node variant that supports DVM. Recall from Lesson 2: RN-D is an RN-I that additionally handles DVM. An I/O agent with its own translation cache needs this.
RN-F (via DSU)CPU clusters hold TLBs and instruction caches, so they are DVM receivers — they act on DVM snoops and respond when done.
This is the third job of the HN-D

Lesson 2 said the HN-D carries the CFG node, the DTC and the DVM node. Lesson 9 covered the DTC; Lesson 10 covered configuration. The DN is the remaining piece — and it is another reason the HN-D is mandatory in every mesh.

Agents that hold no translation or instruction state do not need to participate. Whether a given configuration has one DN or supports more than one for scaling is a configuration detail — confirm against the TRM for your target release before asserting a number.

4Two-part messaging — the detail worth knowing

A DVM operation carries more information than an ordinary request: not just an address, but context such as ASID, VMID, exception level and operation scope. That payload does not fit the space available in a single snoop message.

CHI therefore splits a non-sync DVM operation into two parts, sent as two messages that the receiver reassembles before acting.

A DVM operation arrives as two parts, then is acted on
   DN (in HN-D)                     receiver (RN-F / RN-D)
      |   DVM snoop, part 1              |
      | ------------------------------>  |  hold, incomplete
      |   DVM snoop, part 2              |
      | ------------------------------>  |  reassemble -> act
      |                                   |  invalidate TLB entries
      |   response (done)                |
      | <------------------------------  |
   sync operations are the exception - they are single-part

Why care? Because it explains a real hardware consequence: a receiver must buffer part one while waiting for part two, and the two parts must not be interleaved with another DVM operation's parts. That is a concrete ordering requirement, and being able to state it signals you have gone past the summary level.

5Walk: a TLB invalidate across the system

Software on one core updates a page table entry and must ensure nobody uses the stale translation.

TLBI: core -> DN -> all translation-holding agents -> back
  RN-F (initiator)        DN (HN-D)        RN-F #2  RN-F #3  RN-D
        |                        |                 |        |        |
   1. DVM request (TLBI)        |                 |        |        |
        -------------------->       |                 |        |        |
        |            2. DN orders it                  |        |
        |                        | 3. DVM snoops (x2 parts each)
        |                        ------------------>       |        |
        |                        --------------------------->       |
        |                        ------------------------------------>
        |                        |   each invalidates matching entries
        |                        | 4. responses collected
        |                        <--------------------------------------
   5. completion to initiator  |
        <--------------------       |
  6. a later DVM sync completes only after all of the above have completed

Note what is not happening: no SAM hash, no HN-F, no snoop filter narrowing the recipient list by address. The DN must reach every agent that could hold the translation, because there is no directory of "who cached which translation" the way there is for cache lines.

6Sync and completion — what the barrier waits for

Maintenance is only useful if software can know it has taken effect. That is the sync operation's job.

  • An individual DVM operation completes back to its initiator once the system has accepted responsibility for it.
  • A DVM sync completes only once prior DVM operations have completed across all participating agents. It is the point at which the stale translation is guaranteed to be unused system-wide.
  • This is why a TLBI in software is followed by a barrier: the barrier is what turns "I sent the invalidate" into "the invalidate has landed everywhere."

Interview-ready framing: the DVM operation does the work, the sync provides the guarantee. Conflating the two is the common mistake.

7The scaling problem

caveman mode

Cache-line snoop: filter say "only cache #2 has it" → one message. TLBI: no filter exist → must tell everybody. 128 cores = many messages, and sync wait for slowest one. So DVM cost grow with core count in way normal traffic does not.

Here is the crux, and the thing to say unprompted:

Address traffic scales well

The snoop filter narrows recipients to actual sharers, so snoop traffic tracks real sharing, not core count. Address hashing spreads load across many home nodes working in parallel.

DVM scales poorly

There is no directory of cached translations, so distribution is broadcast-natured. Cost grows with the number of participating agents, and a sync is bounded by the slowest responder.

Consequences a system architect should be able to name:

  • The DN is a serialization point for DVM, so a DVM-heavy workload can queue behind itself in a way address traffic does not.
  • A sync is a convoy: it waits on every participant, so one slow or busy agent sets the latency.
  • Software mitigations matter — using the narrowest possible TLBI scope (by ASID or VMID rather than invalidating everything), and batching maintenance so one sync covers several operations rather than syncing after each.
  • This is why heavy page-table churn — certain virtualisation and JIT patterns — can look like an interconnect problem when it is really a DVM-rate problem.

10Interview Q&A

How does a TLB invalidate on one core reach every other MMU in the system?
The initiating agent issues a DVM request, which goes to the DVM node in the HN-D rather than being hashed to an address-owning home node. The DN orders it and issues DVM snoops to every agent that holds translation state — CPU clusters via their RN-F, and I/O agents with translation caches via RN-D. Each non-sync operation arrives as two messages that the receiver reassembles before acting, then responds. A subsequent DVM sync completes only once all of those have completed, which is what makes the guarantee architecturally visible to software.
What is the difference between a DVM operation and a DVM sync?
The operation does the maintenance — invalidate these translations, or this instruction-cache state. The sync is a barrier that provides the guarantee: it completes only after prior DVM operations have completed across all participating agents. The operation is the work; the sync is the proof. Software issues the TLBI and then relies on the barrier, because until the sync completes another agent may still be using a stale translation.
Why does DVM not use the SAM and snoop filter like everything else?
Because it is not about an address that one home node owns. There is no directory recording which agents have cached which translations, the way the snoop filter records which caches hold which lines. So there is nothing to narrow the recipient list with — distribution has to reach every agent that could hold the state. That is why DVM goes to a single distribution and ordering point, the DN, rather than being hashed across many home nodes.
What is the scaling concern with DVM at high core counts, and what can be done?
Two problems. First, the DN is a single serialization point for DVM, so DVM-heavy workloads queue behind themselves rather than spreading across parallel home nodes the way address traffic does. Second, a sync is a convoy — it is bounded by the slowest responder, so one busy agent sets the latency for everyone. Mitigations are mostly about reducing DVM rate and scope: use the narrowest TLBI scope available (by ASID or VMID rather than invalidating all), and batch maintenance so one sync covers multiple operations. Workloads with heavy page-table churn, such as some virtualisation and JIT patterns, can present as an interconnect problem when the real issue is DVM rate.
Which agents participate in DVM, and which do not?
Agents that cache translations or instructions participate: CPU clusters through their RN-F, and I/O or accelerator agents with their own translation caches through RN-D, which is the RN-I variant that adds DVM support. Agents with no translation or instruction state have nothing to invalidate and do not need to take part. The DN sits in the HN-D, which is one of the reasons that node is mandatory in every mesh.
What ordering constraint does two-part messaging impose?
A receiver must buffer the first part while it waits for the second, and the two parts of one operation must not be interleaved with the parts of another. So there is a real hardware requirement to keep DVM message pairs associated and in order at the receiver, which is a constraint ordinary single-message requests do not have. Sync operations are the exception, being single-part.

11Recap & key terms

  • DVM = Distributed Virtual Memory: TLB invalidate, instruction-cache invalidate, branch-predictor invalidate, and sync.
  • Ordered and distributed by the DN in the HN-D — not hashed to an HN-F by address.
  • RN-D is the DVM-capable request node; RN-F clusters are receivers.
  • Non-sync operations are two-part messages, reassembled at the receiver; sync is single-part.
  • The sync is the barrier that guarantees prior operations completed everywhere.
  • Scales poorly: no directory to narrow recipients, single distribution point, sync bounded by the slowest responder.
