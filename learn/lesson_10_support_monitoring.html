Support & Monitoring

Six cross-cutting modules that observe the data path you've spent nine lessons learning. They don't move flits — they count, score, watchdog, arbitrate by QoS, track credits, and gate clocks. Each is small in isolation but together they're how silicon survives in production.

1What "support" means here

Everything in this lesson is on the side of the data path, observing or controlling it rather than carrying flits. If you removed them all, a flit could still traverse RN → HN → SN. But you'd have no idea how, no protection if something jammed, no fair QoS sharing, and no way to save power when traffic was light.

ModuleObservesActs onIf removed
perf_monitor flit injections, ejections, stalls, retries read-only counters via CSR blind to performance — can't tune the design
error_handler error pulses from every sub-block sticky status + 3-tier IRQ + first-fault capture errors lost as soon as they fire — unrecoverable
timeout_mgr arm / disarm pulses, free-running counters timeout_hit pulse with txnid stuck transactions never detected, design hangs forever
qos_manager per-agent QoS values + valids arbitrated single output, class-weighted FCFS only — no priority for latency-critical traffic
flow_control_unit flit send / lcrd return per channel stall outputs to SA, credit counters flits sent into receiver overflow → silent data loss
power_mgmt per-tile activity + idle counter clock-gate enables to ICG cells full power consumption even when idle

2perf_monitor — 8 configurable counters per tile

Each router tile carries one perf_monitor with eight 32-bit counters. Each counter watches one configurable event from noc_pm_event_e (REQ_INJECT, RSP_EJECT, STALL_VC_FULL, etc.). Click an event chip to fire it; pick the readout index to inspect that counter.

3error_handler — aggregate, prioritize, latch

Errors fire as single-cycle pulses from sub-blocks all over the design. The handler latches them in sticky err_status bits, captures the node_id at first fault, priority-encodes the highest-severity active error into err_code, and groups severity into three IRQ levels.

4timeout_mgr — 64 watchdog timers in parallel

A pool of timer slots. start_valid arms a slot with a threshold and a TXNID; the counter decrements every cycle until stop_valid disarms it or it reaches zero (timeout). On expiry, the slot fires timeout_hit with the captured timeout_txnid.

Why centralized? Every individual transaction tracker (RN MSHR, HN slot, SN slot) could maintain its own timer, but that's 100+ counters ticking every cycle. Centralizing into timeout_mgr lets one comb scan pick the first expiring slot per cycle, share a single CSR-configurable threshold, and capture the offending TXNID for debug.

5qos_manager — class-weighted round-robin

Four agents each present a flit with a 4-bit QoS value (0-15). The manager maps QoS into four classes (BE / LE / ME / HI), runs weighted round-robin across classes (default weights 1 / 2 / 4 / 8), and within each class runs simple round-robin across agents. Adjust the sliders below.

6flow_control_unit — per-channel credit pool

All four CHI channels on one physical port, gathered into one place. Each channel has a credit counter that decrements on flit-sent and increments on lcrd-return. When a counter hits zero, the matching *_stall output tells SA to stop choosing that channel.

crd_overflow_err = 0
Fires if an lcrd_return arrives when the counter is already at max_count. Indicates a programming bug — either the peer returned a credit you never spent, or the init value was wrong.

7power_mgmt — per-tile clock gating FSM

Each of the 16 router tiles runs an independent 3-state FSM: ACTIVE (clocked, ticking idle counter), IDLE (clocked, safe handoff), GATED (clock off). Click any tile to toggle its activity input. Press Tick to advance counters.

Click a tile to toggle its activity (incoming flit). Yellow = idle counting, dim = gated.

State definitions

PM_ACTIVE
Tile clocked, traffic in flight. Idle counter resets to 0 whenever activity is seen. Counts up otherwise; transitions to IDLE at IDLE_THRESHOLD = 256.
PM_IDLE
Still clocked (safe handoff). One more cycle of quiescence and we drop to GATED. Any activity returns to ACTIVE immediately.
PM_GATED
clk_en = 0 — flops not toggling, power saved. Wake on any incoming flit or credit return.

9Check yourself

Q1. perf_monitor's counters saturate at '1 (all ones) instead of wrapping. Why?
Software polling the CSR should never see a non-monotonic counter — if the count went from 0xFFFFFFFE to 0xFFFFFFFF to 0x00000000 mid-poll, the next read would suggest activity went to zero. Saturating preserves monotonicity. The companion ovf bit is the warning that you've lost precision, prompting either a longer counter width or more frequent reads.
Q2. The error_handler priority encoder runs if (err_status[7])...if (err_status[0])... in order — but it's structured so the last match wins. Why is that the right priority order?
Look at the body: if (err_status[0]) err_code = ERR_ECC_UNCORRECTABLE comes last. In SystemVerilog always_comb, the last assignment wins. ECC uncorrectable is the highest severity — silent data corruption — and must win over everything else even if it fires alongside a routing error. The code orders the if-chain from lowest severity to highest so the final assignment is the most severe live error.
Q3. In timeout_mgr, what happens if you arm and stop the same slot on the same cycle?
Both assignments are non-blocking, but order matters within an always_ff: the arm assignment runs first (line 105), then the stop assignment (line 112) — stop wins. The slot ends up with active = 0 and count = thr. Whether that's correct depends on intent; in practice arm and stop on the same cycle for the same slot shouldn't happen because they come from different parts of the FSM. If it does, it's a sign of a higher-level bug.
Q4. qos_manager replenishes tokens "when all classes with requests are drained". Why that condition instead of "when all classes are drained"?
If a class has no requesters, it doesn't need tokens — those tokens are wasted. Waiting only for the active classes to drain means we refill as soon as we're truly out of work for everyone currently asking, not pessimistically waiting for hypothetical traffic. Side effect: a class that was inactive starts a round with full tokens, which is the correct behavior — it shouldn't be penalized for being quiet earlier.
Q5. power_mgmt keeps the clock on during PM_IDLE. Why not gate immediately when traffic stops?
Safe-state handoff. Gating mid-flit or mid-credit-return would freeze internal state inconsistently. PM_IDLE is a one-cycle "are you really sure?" buffer — if any activity arrives during IDLE, return to ACTIVE without ever having dropped the clock. Only after IDLE confirms no activity for one more cycle do we drop to PM_GATED. The cost is one extra cycle of power; the benefit is correctness.
