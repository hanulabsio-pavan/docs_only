CHI Nodes — RN, HN, SN

1The three-node ensemble

Every transaction on a CHI fabric flows through exactly these three node families. Each speaks the same protocol but plays a different role.

chi_rn

The initiator. CPU clusters, DMA engines, accelerators.

Channels TX:REQ · RSP · DAT Channels RX:SNP · RSP · DAT TXNIDs:16 outstanding Snoop queue:8 deep FSM states:9 + ERROR

chi_hn

Coherency arbiter. Owns directory + last-level cache slice.

Channels TX:RSP · SNP · DAT Channels RX:REQ · RSP · DAT Slots:64 outstanding Directory:1024 × 4-way FSM states:14 + ERROR

chi_sn

Memory endpoint. DDR/HBM controllers, peripherals.

Channels TX:RSP · DAT Channels RX:REQ · DAT Slots:32 outstanding Backend:AXI4 (5 channels) FSM states:7 + ERROR

2chi_rn — Request Node

The simplest of the three. Translates cache controller requests into REQ flits, allocates TXNIDs, receives SNP/RSP/DAT, and forwards snoops to the local cache. The TXNID bitmap below is interactive — click slots to allocate/free.

The transaction lifecycle is roughly: IDLE → DIR_LOOKUP → either LLC_CHECK (read hit) or ISSUE_SNOOP (need other RNs' data) or FETCH_MEM (line evicted). Eventually SEND_DATA_RN or SEND_COMP_RN, then WAIT_COMP_ACK before freeing the slot.

Snoop fan-out tracking

Each transaction slot carries two bitmaps: snp_pending_bitmap[NUM_RN_PORTS] for snoops issued, and snp_done_bitmap[NUM_RN_PORTS] for responses received. The HN advances state only when (pending & ~done) == 0 — i.e. all snoops have been answered.

6Known issues — from the DV tracker

The CHI nodes have the most outstanding TODOs in the codebase — full protocol implementation is a multi-quarter effort. These are the items to know about.

🔶 RN — RSP opcode dispatch not implemented
chi_rn.sv:222 is a stub. RSP flits arrive (link credit is returned), but the actual opcode decode logic that would update tracker state on Comp / CompDBIDResp / RetryAck / PCrdGrant is a comment block.
🔶 RN — TXNID never freed
chi_rn.sv:296: TXNIDs are allocated on send_req but txnid_used[i] <= 1'b0 on transaction completion is a TODO. After 16 transactions the RN deadlocks — first NUM_TXNID tests pass, then never another.
🔶 HN — Snoop opcode hardcoded
chi_hn.sv:255: snp_flit_d.opcode = SNP_SnpShared always. Real implementation must derive opcode from the requesting REQ opcode (ReadUnique → SnpUnique, etc.) and current directory state.
🔶 HN — Round-robin REQ arb is priority encoder
chi_hn.sv:172 uses break on first hit, which is strict-priority not round-robin. RN0 will starve RN1-3 under load. Needs an arb_unit instance instead.
🔶 HN — SN request drive is tied off
chi_hn.sv:270: sn_link.txreqflitv = 1'b0. The path from HN to memory controller is not wired — any directory miss that needs FETCH_MEM stalls forever.
⚠ SN — AXI4 backend stubbed
chi_sn.sv:232–246: mem_arvalid and mem_awvalid are tied to 1'b0. The SN can receive REQs and allocate slots, but never actually drives memory. No reads complete. Listed as P2.1 (Phase 2 prerequisite) in the DV plan.

8Check yourself

Q1. RN0 issues a ReadShared. The directory at the HN shows the line is in Shared state with RN1 holding a copy. Walk through what happens next.
HN looks up directory (DIR_LOOKUP → LLC_CHECK). Since the line is Shared and LLC may have a clean copy, HN can serve from LLC without snooping RN1 — but it still updates the directory to add RN0 to the sharers bitmap. Sends DAT_CompData (with resp = SC) on the DAT channel and RSP_Comp on RSP. RN0 caches the line as Shared Clean, sends RSP_CompAck, and the HN frees its slot. RN1 is undisturbed.
Q2. Why does the HN have 64 transaction slots but each RN has only 16 TXNIDs?
A single HN can have 4 RNs talking to it (in this design). If each RN has 16 outstanding, that's 64 transactions the HN needs to track — one slot per (RN, RN_TXNID) pair. Plus internal snoop fan-outs and SN requests. 64 is the minimum to avoid being the bottleneck under worst-case load. The DV plan's TC-STRESS-001 exercises this.
Q3. The SN's RSP opcode is decided by (opcode == REQ_WriteNoSnpFull || opcode == REQ_WriteNoSnpPtl) ? RSP_DBIDResp : RSP_Comp. Why?
For write requests, the SN must first tell the HN "I'm ready to receive the data, send it with this DBID" — that's DBIDResp. The actual Comp comes after the write completes (line 196 sends DBIDResp, and a separate Comp follows once mem_bvalid arrives in a full implementation). For read requests, no data transfer is needed from the requester, so the SN can immediately signal Comp alongside returning the read data.
Q4. The HN has both llc_* ports (to LLC slice) and sn_link (to memory). When does each get used?
llc_* is hit by every directory lookup that needs cache data — the directory says the line is Shared (or somewhere in LLC), read LLC, return that data. sn_link is used only on a full miss: directory says nothing has the line, LLC says no data, so HN promotes the request to REQ_ReadNoSnp and forwards to SN. Writes go to LLC first (to update the directory and capture modified data) and eventually to SN via writeback.
