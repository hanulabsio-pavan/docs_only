🔹 Session 1: Protocol Layering & Why CHI Exists

Core Concept (45 min)

AXI Limitations

  • Single-layer protocol: Handshake = protocol layer + physical signaling mixed
  • No native multi-hop routing: Point-to-point only
  • No native coherency: ACE is a bolt-on extension
  • VALID/READY deadlock: Cannot handle cyclic topologies at scale

CHI Solution: Three-Layer Stack

  1. Protocol Layer — Transaction semantics, coherency state machine
  2. Network Layer — Routing, QoS, ordered/unordered paths
  3. Link Layer — Credit-based flow control, flit packetization, retry/poison
💡 Key Insight: Multi-hop fabrics (ARM CMN-700, Neoverse mesh) need protocol-agnostic routing. Link-layer credits decouple backpressure from protocol handshakes — prevents deadlock in cyclic topologies.
Aspect AXI CHI
Flow Control VALID/READY handshake (immediate) Credit-based (sender pre-allocates buffer)
Channels 5 channels (AR/R/AW/W/B) 4 virtual channels (REQ/RSP/SNP/DAT)
Topology Point-to-point only Multi-hop routing via interconnect nodes
Coherency ACE bolted on Native coherency in Protocol Layer
Scalability Limited (~16 cores) Scales to 100+ cores
📋 Interview Drill (15 min)

Q1: "Why can't AXI scale to 100+ core coherent systems?"

Answer:

  • No multi-hop routing (requires full crossbar = area explosion)
  • VALID/READY creates deadlock in cyclic graphs
  • No ordered/unordered separation (all traffic treated equally)
  • ACE broadcast snooping doesn't scale (N² snoop traffic)

Q2: "What problem does credit-based flow control solve?"

Answer:

  • Prevents head-of-line blocking in multi-hop networks
  • Sender knows buffer availability before transmission
  • Each hop manages credits independently
  • No wasted cycles on rejected transactions

🔹 Session 2: Node Types & System Topology

Core Concept (45 min)

CHI defines node roles, not IP blocks. One physical component can implement multiple roles.

Node Type Definitions

Node Type Full Name Role AXI Equivalent
RN-F Request Node — Fully coherent CPU core, GPU, coherent accelerator (has cache, receives snoops) ACE master with snooping
RN-I Request Node — I/O coherent DMA, PCIe, NIC (no cache, but respects coherency) ACE-Lite master
RN-D Request Node — DMA Pure DMA, no coherency participation AXI master
HN-F Home Node — Fully coherent DDR controller with coherency directory/snoop filter Memory controller in ACE
HN-I Home Node — I/O Peripheral slave (UART, SPI, non-coherent memory) AXI slave
SN-F Slave Node — Fully coherent Cache-attached SRAM, CXL device with coherency — (new in CHI)

Typical System Topology

(Core0)
🔹 RN-F
(Core1)
🔹 RN-F
(Core2)
🔹 RN-F
(Core3)
🌐 Interconnect (CMN-700)
💾 HN-F
(DDR)
📤 RN-I
(DMA)
🔧 HN-I
(IO)
🔑 Key Insight: HN-F = DDR controller + snoop filter. RN-F cores request from HN-F. HN-F may snoop other RN-Fs based on directory state.

🔹 Session 3: Virtual Channels & Flit Structure

Core Concept (45 min)

CHI replaces AXI's 5 channels with 4 virtual channels over physical links.

Virtual Channel Mapping

Virtual Channel Direction Purpose AXI Analogue
REQ RN → HN or RN → SN Read/Write requests AR + AW combined
RSP HN → RN or SN → RN or RN → RN Acknowledgments, CompAck, data-less responses B channel
SNP HN → RN Snoop requests to coherent caches AC channel (ACE)
DAT Any → Any Data transfer (bidirectional) R + W combined
✅ Why Virtual Channels?
  • Prevents deadlock: Snoops can't be blocked by requests
  • Simplifies routing: Data is direction-agnostic
  • Enables QoS: Different channels can have different priorities

Flit Structure

All CHI messages are encoded as flits. Flit width = 256 or 512 bits (configurable).

Flit Header Fields:

QoS [3:0]
TgtID [11:0]
SrcID [11:0]
TxnID [11:0]
Opcode [6:0]
...

Key Fields

  • TxnID — Ties request to response (12 bits = 4096 parallel transactions)
  • TgtID / SrcID — Node identifiers for routing
  • Opcode — Transaction type
  • QoS — Quality of Service priority

AXI → CHI Opcode Mapping

  • AR → ReadShared / ReadUnique / ReadNoSnoop
  • AW+W → WriteUniqueFull / WriteUniquePtl / WriteBackFull
  • AC → SnpShared / SnpUnique / SnpCleanInvalid
  • R → CompData (on DAT channel)
  • W → Data flit (on DAT channel)
  • B → Comp / CompAck (on RSP channel)

🔹 Session 4: Credit-Based Flow Control (Link Layer)

Core Concept (45 min)

CHI Credit System

Receiver pre-advertises available buffer slots via LCRDV (Link Credit Valid) signal.

💡 How It Works:
  • Sender maintains local credit counter
  • Sender decrements counter on every flit sent
  • When credits = 0, sender stalls
  • Receiver replenishes credits as it drains buffers

Credit Grant & Flit Transmission Waveform

⚡ ASCII Timing Diagram
Clock:      |  1  |  2  |  3  |  4  |  5  |  6  |  7  |  8  |
LCRDV:      |  1  |  0  |  1  |  0  |  0  |  1  |  0  |  0  |  ← Receiver grants credits
FLITPEND:   |  0  |  1  |  1  |  1  |  0  |  0  |  1  |  0  |  ← Sender has flit ready
FLITV:      |  0  |  0  |  1  |  1  |  0  |  0  |  0  |  1  |  ← Flit valid (transmitted)
Flit Data:  |  -  |  -  | REQ | DAT |  -  |  -  |  -  | RSP |

Credits (Sender's view):
  Initial:   2 (from earlier LCRDV pulses)
  Cycle 1:   +1 (LCRDV) → 3
  Cycle 3:   -1 (FLITV sent REQ) → 2
  Cycle 3:   +1 (LCRDV) → 3
  Cycle 4:   -1 (FLITV sent DAT) → 2
  Cycle 6:   +1 (LCRDV) → 3
  Cycle 8:   -1 (FLITV sent RSP) → 2

Implementation Details

Aspect Description
Separate Pools REQ, RSP, SNP, DAT each have own credit counter
Credit Init Receiver sends N LCRDV pulses (N = buffer depth)
Stall Condition credits_available == 0 → sender stalls (FLITPEND without FLITV)
Deadlock Prevention Separate credit pools for REQ/RSP/SNP/DAT prevent circular dependency
⚠️ RED FLAG: Sharing credit pools across virtual channels causes deadlock. CHI spec mandates separate pools.

🔹 Session 5: Cache Coherency States — CHI vs. MESI

Core Concept (45 min)

CHI uses an extended MOESI-like model with additional states for optimization.

CHI Cache States

State Meaning MESI Equivalent Key Difference
I Invalid I (Invalid) Same — line not present
UC UniqueClean E (Exclusive Clean) Can be written without snoop (already unique)
UD UniqueDirty M (Modified) Same — exclusive + dirty
SC SharedClean S (Shared) Same — read-only, other caches may have copies
SD SharedDirty O (Owned in MOESI) Dirty data shared! One cache owns, others read-only
🔑 The SD (SharedDirty) State: Allows dirty sharing — one cache owns dirty line, others have read-only copies. This is a game-changer for producer-consumer patterns!

MESI vs. CHI Comparison

Scenario MESI Behavior CHI Behavior Winner
A writes, B reads A: M → S (must write back to memory first)
B: I → S		 A: UD → SD (keeps dirty copy)
B: I → SC
✓ Less memory traffic		 CHI
A has E, wants to write Silent transition E → M Silent transition UC → UD Same
A has S, wants to write Must invalidate other sharers Send MakeUnique, others transition SC → I Same

Why SD Matters: Concrete Example

❌ MESI (No SD State)

Core 0 writes X = 5 (state M) ↓ Core 1 reads X → Core 0 must write back to memory (M → S) → Core 1 reads from memory (I → S) → High latency → Wasted memory bandwidth

✅ CHI (With SD State)

Core 0 writes X = 5 (state UD) ↓ Core 1 reads X → Core 0 transitions UD → SD (keeps dirty data) → Core 0 sends data directly to Core 1 (cache-to-cache) → Core 1: I → SC → No memory access needed!

🔹 Session 6: ReadShared Transaction — End-to-End Flow

Core Concept (45 min)

Scenario: Core A (RN-F) reads a cache line. Cache B (another RN-F) has it in UD state. HN-F (DDR controller + snoop filter) coordinates.

Step-by-Step Flow

1
Core A → HN-F: REQ channel
ReadShared(Addr, TxnID=0x123)
Opcode: ReadShared | SrcID: Core A node ID
↓
2
HN-F checks snoop filter
Finds: Cache B owns line in UD state (unique dirty)
↓
3
HN-F → Cache B: SNP channel
SnpShared(Addr, FwdTxnID=0x123)
Request data + transition to SD state
↓
4
Cache B processes snoop:
  • Reads cache line from L1/L2
  • Transitions: UD → SD
  • Cache B → Core A: SnpRespData (DAT channel) 🚀 Direct to Core A!
  • Cache B → HN-F: SnpResp (RSP channel)
↓
5
HN-F → Core A: RSP channel
CompData_SD(TxnID=0x123)
Completion: "You now have line in SC state"
↓
6
Core A updates cache:
  • Writes data to cache
  • Sets state: I → SC
  • Sends CompAck to HN-F
↓
7
HN-F updates snoop filter
Cache A: SC | Cache B: SD
💡 Direct Data Forwarding (DDT): Cache B sends data directly to Core A (not through HN-F). This reduces latency by one hop while HN-F still maintains coherency via SnpResp tracking.
📋 Key Optimizations
  • Direct Data Forwarding: Cache B sends data directly to Core A (not through HN-F)
  • State Transitions: Cache B: UD → SD; Cache A: I → SC
  • Memory Access: None needed (cache-to-cache transfer)

🔹 Session 7: WriteUnique Transaction — End-to-End Flow

Core Concept (45 min)

Scenario: Core A wants to write a full cache line (64 bytes). Other caches (B, C) may have the line in SC or SD. HN-F must invalidate sharers.

WriteUniqueFull vs. WriteUniquePtl

Opcode Meaning When to Use Memory Behavior
WriteUniqueFull Write entire 64-byte cache line All 64 bytes are written No Read-Modify-Write needed
WriteUniquePtl Write partial cache line (e.g., 8 bytes) Byte-level write (e.g., single word) May need to fetch line first, merge, then write

Examples

// WriteUniqueFull (memset entire line)
memset(addr, 0, 64);  // Writes all 64 bytes → WriteUniqueFull

// WriteUniquePtl (single word write)
*(int*)addr = 42;  // Writes 4 bytes → WriteUniquePtl

WriteUnique Transaction Flow

1
Core A → HN-F: REQ channel
WriteUniqueFull(Addr, TxnID=0x456)
Write entire line, invalidate sharers
↓
2
HN-F checks snoop filter
Finds: Cache B, Cache C have line in SC state (shared clean)
↓
3
HN-F → Cache B, Cache C: SNP channel
SnpCleanInvalid(Addr)
Invalidate your copies, no data needed
↓
4
Cache B, Cache C process snoop:
  • Transition: SC → I (invalidate)
  • Cache B → HN-F: SnpResp_I
  • Cache C → HN-F: SnpResp_I
↓
5
HN-F collects all SnpResp
Waits for responses from both Cache B and Cache C
↓
6
HN-F → Core A: RSP channel
Comp_UC(TxnID=0x456)
Completion: You uniquely own the line
↓
7
Core A → HN-F: RSP
CompAck(TxnID=0x456)
Final acknowledgment
↓
8
HN-F updates snoop filter:
  • Cache A: UC (sole owner)
  • Cache B, C: Removed from filter
✅ Best Practice: WriteUniqueFull for bulk writes (memset, DMA) — saves memory bandwidth and latency by avoiding Read-Modify-Write.

🔹 Session 8: Snoop Filter & Directory (HN-F Internals)

Core Concept (45 min)

The snoop filter at HN-F is a coherency directory tracking which caches hold which lines. It's the brain of the system.

Directory Data Structure (Conceptual)

Address Tag Sharers Bitmap State
0x1000_0000 [RN0=1, RN1=0, RN2=0, …] SC
0x2000_0000 [RN0=0, RN1=1, RN2=0, …] UD
0x3000_0000 [RN0=1, RN1=1, RN2=0, …] SC
0x4000_0000 [RN0=0, RN1=1, RN2=0, …] SD
🔑 Fields:
  • Address Tag: Cache line address (upper bits, e.g., bits [47:6] for 64-byte lines)
  • Sharers Bitmap: One bit per RN-F (1 = this cache has the line)
  • State: Aggregated state (SC = all sharers clean, UD/SD = one owner)

Snoop Filter Capacity & Over-Snooping

Issue Description Impact
Limited Size Filter has finite size (e.g., 4MB coverage for 128MB aggregate cache) Can't track all cached lines
Over-Snooping When filter is full or address not tracked, HN-F broadcasts snoop to all RN-Fs Wasteful, but correct (ensures coherency)
Trade-off Larger filter = less over-snooping, but more area/power Design choice based on system requirements
⚠️ Over-Snooping: When filter doesn't have an entry for an address, HN-F broadcasts snoop to ALL RN-Fs. This is pessimistic but maintains correctness.

ACE vs. CHI Comparison

Aspect ACE CHI
Directory No formal directory (optional) Mandatory snoop filter at HN-F
Snooping Broadcast to all masters Targeted snooping (based on directory)
Scalability N² snoop traffic (N cores) O(sharers) snoop traffic
Complexity Simpler (no directory state) More complex (directory management)

🔹 Session 9: CHI Issue F Additions — MTE, RME, Atomic Ops

Core Concept (45 min)

CHI Issue F (2021 spec) added support for ARMv8.5-A and ARMv9-A features.

1. Memory Tagging Extension (MTE)

What is MTE? ARMv8.5-A Memory Tagging Extension:

  • 4-bit tag per 16-byte granule for memory safety
  • Detects: use-after-free, buffer overflows, temporal/spatial violations
  • Used in: Android, iOS, server security
TagOp Behavior Use Case
Match Verify tag matches before data transfer (catch violations) Runtime tag check
Fetch Retrieve tag without checking (for debug) Debug/monitoring
Update Write new tag to memory (allocation time) Memory allocation
None No tag operation (legacy mode) Backward compatibility

2. Realm Management Extension (RME)

What is RME? ARMv9-A Realm Management Extension:

  • Confidential computing for trusted VMs ("Realms")
  • Isolates Realms from hypervisor, secure OS, and each other
  • Four security states: Root Secure Realm Non-Secure
Security State Purpose Can Access
Root Firmware, RMM (Realm Manager) All memory
Secure Secure OS (e.g., OP-TEE) Secure + Non-Secure
Realm Trusted VMs (confidential workloads) Realm only
Non-Secure Normal OS (Linux, Android) Non-Secure only

3. Atomic Operations

Why Atomics in CHI? Lock-free algorithms need hardware atomics (fetch-and-add, compare-and-swap, exchange).

Opcode Operation Example
AtomicStore_ADD Atomic add atomic_fetch_add(&x, 1)
AtomicStore_CLR Atomic clear bits atomic_fetch_and(&x, ~mask)
AtomicStore_SET Atomic set bits atomic_fetch_or(&x, mask)
AtomicStore_SWAP Atomic exchange atomic_exchange(&x, new_val)
AtomicCompare Compare-and-swap atomic_compare_exchange(&x, &old, new)
🔑 Atomicity Guarantee: HN-F locks the address during operation. Other requests to same address queue. No interleaving (appears as single instruction).

🔹 Session 10: Interview Scenarios & Whiteboard Drills

Drill 1: Debug a Deadlock (15 min)

🔍 Scenario

You have a 4-core SoC (4× RN-F, 1× HN-F). Under stress test, the system deadlocks. How do you debug?

Expected Answer:

  1. Check Credit Exhaustion: Are any REQ/RSP/SNP/DAT credits stuck at 0?
  2. Check for Cyclic Dependencies: REQ blocked on SNP, SNP blocked on DAT, DAT blocked on REQ → Deadlock!
  3. Verify Separate Credit Pools: REQ, RSP, SNP, DAT must each have own credit counter
  4. Trace TxnID Flow: Find stuck TxnID, trace through REQ → SNP → DAT → RSP

Common Root Causes:

  • ❌ Shared credit pools (violates CHI spec)
  • ❌ Insufficient buffer depth (credit starvation)
  • ❌ HN-F response tracker overflow (too many in-flight TxnIDs)
  • ❌ Snoop filter deadlock (filter lookup blocks REQ queue)

Drill 2: Cache State Corner Case (15 min)

🔍 Scenario

Race Condition: Core A has line in UD, Core B issues ReadShared. While snoop is in-flight, Core A issues WriteBackFull (evicting the line). What happens?

CHI Handling:

1. Core A's WriteBackFull arrives at HN-F:
   - HN-F writes data to memory
   - HN-F updates snoop filter (Core A no longer owns line)

2. SnpShared arrives at Core A:
   - Line already evicted
   - Core A → HN-F: SnpResp_I (line not present)

3. HN-F receives SnpResp_I:
   - Knows line was evicted
   - Retries: fetches from memory (has latest data from WriteBackFull)
   - HN-F → Core B: CompData(Data from memory)

4. Core B: I → SC (receives data from memory, not from Core A)
🔑 Key Insight: HN-F serializes conflicting transactions using TxnID tracking. WriteBackFull completes before SnpShared retry. Correctness maintained!

CHI Issue F Flit Opcodes (Most Common)

Opcode Direction Purpose State Transition
ReadShared RN → HN Read with sharing I → SC
ReadUnique RN → HN Read exclusive I → UC
WriteUniqueFull RN → HN Write full line, invalidate sharers I → UC/UD
WriteBackFull RN → HN Evict dirty line to memory UD/SD → I
SnpShared HN → RN Snoop: provide data, transition to SD UD → SD
SnpCleanInvalid HN → RN Snoop: invalidate (no data needed) SC/UC → I
CompData HN → RN Completion + data transfer —
CompAck RN → HN Acknowledge completion (final) —

Cache State Quick Reference

State Meaning Can Write? Must Snoop?
I Invalid No No
UC UniqueClean Yes No
UD UniqueDirty Yes No
SC SharedClean No Yes
SD SharedDirty No Yes

Interview Red Flags to Avoid

❌ "CHI is just AXI with credits"
Wrong. CHI has native multi-hop, coherency directory, ordered/unordered separation.
❌ "Snoop filter is optional"
Technically true, but without it you regress to broadcast snooping (terrible for scalability).
❌ "CompAck is pointless"
Wrong. Without CompAck, HN-F can't safely reuse TxnID.
❌ "All transactions are ordered"
Wrong. CHI separates ordered (device I/O) vs. unordered (normal CPU) for performance.
