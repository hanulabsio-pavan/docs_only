Arbitration & Routing

The decision-makers inside the router. When multiple inputs want the same output, arbiters pick one. When a flit arrives, the route compute unit (or a routing table) decides which way to send it. The crossbar then physically connects chosen input to chosen output. These five files turn "I have a flit" into "the flit is at the next router".

1round_robin_arb — fair sharing

When several input ports request the same output, somebody has to pick a winner. Round-robin gives everyone a fair turn: the arbiter remembers who won last and grants the next requester clockwise from there. Click any cell to toggle a request, then press Grant to step the arbiter.

The pointer starts at 0. Search starts at (ptr + 1) % NUM_REQ = 1 — meaning requestor 1 has highest priority, then 2, 3, 4, 0. On grant, the pointer advances to the winning index so it goes to the back of the queue.

Why search from ptr + 1?

Because the pointer remembers who just won. To be fair, the next round starts after that winner — so they go to the back of the line. If only the previous winner is requesting, they still get the grant (since the search wraps around), but anyone else who shows up first gets priority.

2arb_unit — a policy switchboard

The arb_unit wrapper picks between three policies via a generate block: round-robin (the default), strict-priority (lowest index wins), and a fallback "lowest set bit" for unsupported modes. Weighted round-robin is declared in the enum but not implemented — that's the 🔶 Partial entry in the DV tracker.

POLICYGenerate blockBehaviorStatus
ARB_ROUND_ROBIN gen_rr Rotates request vector by rr_ptr, finds the lowest set bit in the rotated vector, un-rotates the grant back. Pointer advances to (winner+1) % N. ✅ Implemented
ARB_STRICT_PRIO gen_strict Pure priority encoder — lowest-index requester wins every cycle. Used for VC priority in output_port. ✅ Implemented

3route_compute_unit — XY-deterministic routing

Click any tile to set the source, click another to set the destination. The orange highlighted path is what XY routing chooses: move East/West first until the X coordinate matches, then North/South until Y matches, then eject to Local. It's purely combinational — one case on (dst_x, MY_X, dst_y, MY_Y).

Click a tile to set the source.

The full algorithm (4 if/else branches)

ConditionOutput port
dst_x > MY_XPORT_EAST

Why XY is deadlock-free: it forbids the "180° turn" pattern (east→west→north→south→east). Routing dependencies form a directed acyclic graph instead of a ring, so the standard wormhole-routing deadlock cycle cannot exist. This is what makes the deadlock proof a one-page exercise in Phase 2 of the DV plan.

4routing_table — the table-based alternative

For irregular topologies or traffic-engineering overlays you can swap XY for a programmable table — boot software writes one entry per destination node, and a one-cycle registered lookup returns the output-port mask. A miss (un-programmed entry) raises lookup_miss so the caller knows to drop or trap.

5crossbar — the physical switch

Five-input, five-output, fully non-blocking. Each output picks at most one input via a one-hot sel[op][ip] signal. The whole module is one always_comb block — no state. The only protection is a sim-only assertion that sel[op] is one-hot. Click cells below to set connections; turning on two inputs to one output will trigger the assertion.

Rows = output port · Columns = input port · Cell = one bit of sel[op][ip]
Assertion would fire: sel[op] is not one-hot. Two inputs are being driven onto the same output bus — guaranteed data corruption in real silicon.

What this module isn't doing

Notably no arbitration, no flow control, no buffering. The crossbar assumes someone upstream (the SA stage in router_top) has already done one-hot arbitration. It just wires the bits.

7Check yourself

Q1. Why does arb_unit's round-robin block rotate the request vector by rr_ptr before priority-encoding?
So a simple "lowest set bit" priority encoder produces a round-robin grant for free. After rotation, position 0 in the rotated vector corresponds to the next-fairness winner; the priority encoder picks the lowest set bit; we un-rotate to get the grant in original coordinates. This is much smaller than a full barrel-shifter arbiter.
Q2. Two RNs on different tiles both want to send to the same HN. Will XY routing ever deliver them via different paths?
Different sources, different paths — yes. Each source computes its own X/Y deltas. But XY is deterministic: from any single source to a fixed destination, the path is always the same. There is no adaptive re-route around congestion.
Q3. If you wanted to support a 5×5 mesh in v2, which of these five modules would need a real change?
Almost none of the logic — but route_compute_unit still uses [2:0] for the X/Y coordinates, which caps at 8. Past 8×8 mesh you'd need to widen those slices (and the node_id_to_x/y helpers in chi_pkg.sv). The arbiter and crossbar parameterise cleanly via NUM_REQS / NUM_PORTS.
Q4. The crossbar has no arbitration. Why is that OK?
Because the Switch Allocation (SA) stage that drives sel has already arbitrated, and is required to produce a one-hot vector per output. The crossbar's only safety net is the runtime assertion $onehot0(sel[op]) — if SA ever issued a malformed grant, sim fires immediately rather than producing silent data corruption.
