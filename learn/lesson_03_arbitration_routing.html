3route_compute_unit — XY-deterministic routing

Click any tile to set source, click another to set destination. The highlighted path is what XY routing chooses: East/West first until X matches, then North/South until Y matches, then eject Local.

● Source  ·  ● Destination  ·  ● XY path
Click a tile to set the source.

The algorithm (4 if/else branches)

ConditionOutput port
dst_x > MY_XPORT_EAST
dst_x < MY_XPORT_WEST
dst_y > MY_YPORT_NORTH
dst_y < MY_YPORT_SOUTH
all equalPORT_LOCAL (eject)

Why XY is deadlock-free: it forbids the 180° turn pattern. Routing dependencies form a DAG instead of a ring. This makes the deadlock proof a one-page exercise in Phase 2.

5crossbar — the physical switch

Five inputs, five outputs, non-blocking. Each output picks at most one input via a one-hot sel. Pure combinational. Click cells to set connections — two inputs on one output triggers the assertion.

Rows = output port · Columns = input port · Cell = one bit of sel[op][ip]
Assertion would fire: sel[op] is not one-hot. Two inputs driven onto the same output bus — guaranteed corruption in silicon.

7Check yourself

Q1. Why does arb_unit's round-robin block rotate the request vector by rr_ptr before priority-encoding?
So a simple "lowest set bit" priority encoder produces a round-robin grant. After rotation, position 0 corresponds to the next-fairness winner; the encoder picks the lowest set bit; we un-rotate to get the grant in original coordinates. Much smaller than a full barrel-shifter.
Q2. Two RNs on different tiles both want to send to the same HN. Will XY ever pick different paths?
Different sources, different paths — yes. Each computes its own X/Y deltas. But from a fixed source to a fixed destination, the path is always the same. No adaptive re-routing.
Q3. To support 5×5 mesh in v2, which of these modules need real changes?
Almost none of the logic — but route_compute_unit uses [2:0] for X/Y coordinates, capping at 8. Past 8×8 you need wider slices (and node_id_to_x/y in chi_pkg.sv). The arbiter and crossbar parameterize cleanly.
Q4. The crossbar has no arbitration. Why is that OK?
Because SA (in router_top) has already arbitrated and is required to produce a one-hot per output. The crossbar's only safety net is the runtime assertion $onehot0(sel[op]).
