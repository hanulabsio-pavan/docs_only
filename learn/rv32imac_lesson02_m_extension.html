M extension — multiply, divide and variable latency

M adds eight instructions and one enormous microarchitectural problem: an instruction that does not finish in one cycle. Everything difficult about M follows from that single fact.

By the end of this lesson you can

  • State the exact result of divide-by-zero and signed overflow, and why there is no trap.
  • Explain MULHSU's purpose in one sentence.
  • Describe the recommended fusion sequences and what hardware does with them.
  • Compare array, Booth-encoded and iterative multipliers on area, latency and timing.
  • Compare restoring, non-restoring, SRT and Newton-Raphson division.
  • Design the scoreboard and write-port arbitration for a decoupled multi-cycle unit.

1The interview frame

crux

M is the extension that breaks the "every instruction takes one EX cycle" assumption. Once latency varies, you need a busy indication, a RAW interlock, a WAW interlock and write-port arbitration. Describe those four and you have described M's real cost.

Candidates who only list the mnemonics get marked down. Candidates who say "a 34-cycle divider and a 3-cycle multiplier sharing one write port" get a follow-up conversation.

crux

funct3[2] splits multiply from divide. Within each half the low two bits select the variant. A clean two-level decode, no lookup table.

rounding convention

RISC-V uses truncated division — quotient rounds toward zero, remainder takes the sign of the dividend. Same as C99. So -7 / 2 = -3 and -7 % 2 = -1. Not floored division. Panels sometimes probe this because Python and some ISAs floor instead.

the classic trap

"What exception does DIV x5, x6, x0 raise?" The answer is none. x5 becomes all ones. Any candidate who says "divide-by-zero trap" has not read the specification. Any candidate who says "undefined" is also wrong — it is precisely defined.

Why no trap?
  • A trap on a common arithmetic operation forces every implementation to build a precise-exception path through a long-latency, decoupled unit. Expensive for a rare case.
  • It keeps the ALU exception-free, which in turn keeps out-of-order writeback of M results safe.
  • Software that cares can branch on the divisor in two instructions. Software that does not care pays nothing.
Checking for divide by zero in software
    beqz  a1, div_by_zero      # explicit test, 1 instruction
    div   a0, a0, a1
    ...
div_by_zero:
    # language-defined behaviour goes here
hardware consequence

Because DIV cannot trap, your divider does not need to be squashable mid-flight for exception reasons. It only needs to be squashable for branch mispredicts and interrupts. That simplifies the control significantly — say this if asked why M is easier than a floating-point unit.

4Why MULHSU exists

It looks arbitrary. It is not.

crux

MULHSU is for multi-word arithmetic. When you multiply two large signed numbers held as arrays of words, the most significant word is signed but every lower word is unsigned. The cross-product of the signed top word with an unsigned lower word needs exactly signed×unsigned.

Without MULHSU, bignum and cryptographic libraries would need a correction sequence on every such partial product. With it, the inner loop is clean. The hardware cost is near zero — the multiplier already builds a signed array; MULHSU just changes how the sign-extension of one operand is driven.

Signed 64×64 via 32-bit ops — where MULHSU lands
   A = {a1(signed), a0(unsigned)}     B = {b1(signed), b0(unsigned)}

   a0×b0  → MULHU  / MUL     unsigned × unsigned
   a1×b0  → MULHSU / MUL     signed   × unsigned  ◄── this one
   a0×b1  → MULHSU / MUL     signed   × unsigned  ◄── and this
   a1×b1  → MULH   / MUL     signed   × signed

Two of the four cross-products are signed×unsigned. That is half the inner loop. Hence the instruction.

5The fusion idiom

The specification recommends specific instruction orderings so implementations can fuse a pair into one operation.

High and low halves of one product
Recommended sequence
    mulh  a2, a0, a1     # high half FIRST
    mul   a3, a0, a1     # low half, same operands, same order
  • High-half instruction must come first.
  • Source registers must be in the same order in both.
  • The high-half destination must not be rs1 or rs2, otherwise it clobbers an operand the second instruction still needs.
Quotient and remainder from one division
Recommended sequence
    div   a2, a0, a1     # quotient FIRST
    rem   a3, a0, a1     # remainder, same operands

Same constraint: the quotient destination must not be rs1 or rs2.

This matters far more than the multiply case. A divider produces quotient and remainder in the same iteration loop. Fusing saves roughly 32 cycles — a real speedup, not a micro-optimisation.

Implementing the fusion

The detection is a small comparator block in ID looking at the instruction pair in the decode buffer:

  1. First is MULH/MULHU/MULHSU, second is MUL (or first DIV[U], second REM[U]).
  2. rs1 and rs2 match, in the same order.
  3. First instruction's rd is not rs1 or rs2.

On a match, issue one operation to the M unit, retain both result halves in the unit's output registers, and write back over two cycles using a two-entry result queue. The second instruction becomes a writeback-only micro-op.

honest scoping

Fusion is optional. A simple core may execute both separately and still be correct. If Hanu 1.0 does not fuse, say so and say what it would have cost — a pair comparator in ID plus a second result register. That is a better answer than pretending.

6Multiplier microarchitecture

You must be able to pick one and defend it. The axes are area, latency, and whether it fits your clock period.

Iterative shift-add

One partial product per cycle. A 33-bit adder, two shift registers, a counter. Roughly XLEN cycles.

Radix-2 iteration
always_ff @(posedge clk) if (busy) begin
  if (mplier[0]) acc <= acc + mcand;
  mcand  <= mcand  << 1;
  mplier <= mplier >> 1;
  cnt    <= cnt - 1;
end

Use when: area is the binding constraint and multiply is rare. Deeply embedded control cores, area-limited FPGA fabric.

Cost: ~32 cycles. In a loop with a multiply in it, this dominates.

Booth radix-4 encoding

Encode the multiplier three bits at a time with one bit of overlap. Each group selects one of {0, ±M, ±2M}. That halves the number of partial products: 32 becomes 17 for a 32-bit operand.

bi+1 bi bi−1Selection
000 / 1110
001 / 010+M
011+2M
100−2M
101 / 110−M

±2M is a shift, free. −M is a two's complement, done as invert plus a hot-one folded into the reduction tree. So the encoding costs a small mux per partial product row.

Booth also handles signed operands naturally, which is why signed and unsigned multiply can share one array with only sign-extension control differing.

Use when: you want either an iterative radix-4 multiplier at ~16 cycles, or fewer rows to feed a tree.

Carry-save reduction tree

Generate all partial products, then reduce them to two vectors with carry-save adders, then do one carry-propagate add.

  • Wallace tree — reduce as aggressively as possible at each level. Minimum depth, irregular layout.
  • Dadda tree — reduce only as much as needed to stay on the reduction schedule. Fewer full adders, slightly more irregular, usually smaller.
  • Reduction depth grows as log1.5 of the row count, so 17 Booth rows reduce in about 6 CSA levels.
  • The final CPA is a fast adder — carry-lookahead, carry-select or a parallel-prefix Kogge-Stone.

Timing reality: a full 32×32 tree plus final adder is a long path. In most processes you pipeline it into 2 or 3 stages. Partial product generation and first reduction levels in stage 1, remaining reduction in stage 2, final CPA in stage 3.

crux

Pipelining the multiplier is what turns M from "variable latency" into "fixed but longer latency". A 3-cycle pipelined multiplier is far easier to schedule than a 16-cycle iterative one — it is just a deeper forwarding problem.

FPGA: hard DSP blocks

If Hanu 1.0 targets FPGA, do not build an array. Use the DSP slices.

  • Typical hard multipliers are asymmetric, around 25×18 signed. A 32×32 product therefore needs several of them plus an adder tree.
  • Straightforward decomposition uses four blocks. Karatsuba reduces it to three at the cost of extra adds.
  • The blocks have internal pipeline registers. Use them — an unregistered DSP inference will wreck your Fmax.
  • Signed versus unsigned matters: hard blocks are signed, so unsigned operands need a zero-extension to 33 bits and careful partitioning.
strong answer
  • "On FPGA I inferred DSP slices with two levels of internal pipelining, giving a 3-cycle multiply. On ASIC I would have used Booth radix-4 into a Dadda tree with a Kogge-Stone final adder, pipelined to match the target period."

7Divider microarchitecture

Division is the slowest thing in an integer core. There is no cheap fast divider.

Restoring division

Shift the partial remainder left, subtract the divisor. If the result is negative, restore by adding the divisor back and emit quotient bit 0. Otherwise keep it and emit 1.

One bit per cycle, so XLEN cycles plus setup. The restore step costs an extra add in the worst case, or a mux if you compute both and select.

Simplest to verify. Reasonable default for a first core.

Non-restoring division

Never restore. If the partial remainder went negative, add the divisor on the next iteration instead of subtracting. Quotient digits come out in {−1, +1} and are converted to binary at the end.

Same one-bit-per-cycle rate but a shorter cycle — one add/subtract, no conditional restore. A final correction step fixes a negative remainder.

This is the sensible baseline for an RV32 core. Same iteration count as restoring, better timing.

SRT radix-4

Two quotient bits per cycle using a redundant digit set, typically {−2, −1, 0, +1, +2}. Redundancy means the quotient digit can be chosen from a truncated partial remainder and a truncated divisor — so no full-width comparison is needed in the loop.

  • Partial remainder kept in carry-save form. No carry propagation inside the loop.
  • Quotient digit selected by a small lookup driven by a few high bits of each operand.
  • On-the-fly conversion turns redundant digits into binary without a final wide add.
  • Roughly 16 iterations for RV32, plus normalisation and correction.
historical trap

The Pentium FDIV bug was a handful of missing entries in exactly this quotient-digit selection table. If you claim SRT, expect the question "how did you verify the selection table". The answer is exhaustive or formal checking of the P-D plot region boundaries, not directed tests.

Newton-Raphson and Goldschmidt

Multiplicative division. Compute an approximate reciprocal from a small seed table, refine it with iterations that double the accurate bits each time, then multiply by the dividend.

  • Quadratic convergence: a 8-bit seed reaches 32 bits in two iterations.
  • Each iteration is two multiplies. So it only makes sense if you already have a fast pipelined multiplier.
  • Getting the last bit exactly right for integer division needs a correction step — the approximation can be off by one.

Verdict for RV32IMAC: usually not worth it. Integer division is rare, and the seed ROM plus correction logic costs more than a non-restoring loop. It earns its place in floating-point units where division and square root share the datapath.

Sign handling for DIV and REM

Signed dividers are almost always built as unsigned cores with sign wrappers.

  1. Take absolute values of dividend and divisor, remembering both signs.
  2. Run the unsigned division.
  3. Negate the quotient if the operand signs differ.
  4. Negate the remainder if the dividend was negative.
two special cases bypass the loop

Divisor zero and the −231 ÷ −1 overflow case are detected up front and force the defined results directly. Never let them enter the iteration — taking the absolute value of −231 overflows in 32 bits.

8Pipeline integration — the real question

Two architectures. Know both, and know why you chose yours.

Stall in place

The M instruction occupies EX. A busy signal freezes IF, ID and EX. MEM and WB drain naturally. When the unit asserts done, the result enters the normal EX/MEM register and the pipeline resumes.

DIV with 34-cycle stall
cyc   1    2    3    4   ...  36   37   38
div   IF   ID   EX───────────EX   MEM  WB
add        IF   ID───────────ID   EX   MEM  WB
xor             IF─────────IF   ID   EX   MEM
              └── stalled 34 cycles, independent or not ──┘
  • Pro: trivially correct. No scoreboard. Writeback stays in order. Exceptions stay precise for free.
  • Con: every instruction behind the divide stalls, including ones that do not use the result.
Decoupled unit with a scoreboard

The M instruction is issued to a side unit and leaves the main pipe. Younger independent instructions continue.

Decoupled — independent work continues
cyc   1    2    3    4    5   ...  36   37
div   IF   ID   issue ───── M unit busy ─────→ WB
add        IF   ID   EX   MEM  WB        ← independent, proceeds
xor             IF   ID   EX   MEM  WB
sub rd=div_rd      IF   ID──── stalled on scoreboard ──→ EX
What the scoreboard must hold
StatePurpose
busyUnit occupied — a second M instruction must stall in ID
dest[4:0]Pending destination register
pendingSet at issue, cleared at writeback
Three interlocks in ID
  1. RAW: stall if rs1 or rs2 equals the pending destination. Cannot be forwarded — the value does not exist yet.
  2. WAW: stall if rd equals the pending destination. Otherwise a short instruction writes first and the late divide overwrites it.
  3. Structural: stall if the unit is busy and another M instruction arrives.

WAR is not a hazard here. Operands are read at issue, so a later write to rs1 or rs2 cannot disturb an in-flight divide.

  • "I stalled for divide and decoupled for the pipelined multiplier. Divides are rare enough in my workload that the scoreboard was not worth the verification cost; multiplies are frequent enough that a 3-cycle bubble was."
  • That answer shows you weighed it. A panel accepts either choice if the reasoning is real.

9WAW and the write-port conflict

The specific failure a decoupled unit creates. Be ready to draw it.

The WAW bug
    div   x5, x6, x7      # issued to M unit, ~34 cycles
    addi  x5, x0, 1       # writes x5 at cycle 5
    ...
                          # cycle 38: divide writes x5 — WRONG, x5 must be 1

Three correct fixes:

  1. Stall the younger writer in ID until the divide retires. Simplest, small IPC loss.
  2. Cancel the divide's writeback. Legal only because DIV has no other architectural side effect. Mark the pending entry as dead when a younger instruction with the same rd issues.
  3. Enforce in-order writeback with a write-port reservation table — the classic approach where each instruction reserves its WB cycle at issue and stalls if the slot is taken.
The write-port conflict

Separately from WAW, two units may want the single regfile write port in the same cycle — a load returning from MEM and the divider completing. Options:

  • Priority to the main pipe, with the M unit holding its result in an output register until a free slot appears. Needs the unit to stay occupied, so a following M instruction stalls.
  • Priority to the M unit, stalling the main pipe for one cycle. Simpler but injects bubbles into the common path.
  • Add a second write port. Real area cost, and it is rarely justified in a single-issue core.
the exception subtlety

Out-of-order writeback of the divide is safe for the divide, since DIV cannot trap. It is not automatically safe for the program. If a younger load takes a page fault after the divide has already written back, the architectural state now contains a result from an instruction that, in program order, sits before the faulting one — which is fine — but if the divide were still pending and you restarted it, you must ensure it is not executed twice. Define your restart point explicitly.

10Interrupting a long divide

An interrupt arrives at cycle 10 of a 34-cycle divide. What do you do?

PolicyInterrupt latencyComplication
Let it complete, then take the interrupt+24 cycles worst caseNone
Abort and restart on returnImmediateMust not have written rd; mepc points at the DIV
Abort and re-execute is forbidden—Only if the unit has committed state
why restart is safe

An integer divide is idempotent. It reads two registers and writes one, at the end. Nothing is written until completion, so aborting mid-flight leaves no partial architectural state. Set mepc to the DIV's own PC and it simply re-executes.

The one requirement: rs1 and rs2 must still hold the same values on return. They will, because the trap handler saves and restores the register file. If rd happens to equal rs1, restart is still safe precisely because rd was never written.

real-time argument
  • "For a control core with hard interrupt-latency requirements, I made the divider abortable. A 34-cycle non-interruptible window was more than my latency budget allowed."

11Zmmul — the area escape hatch

Zmmul is the multiply-only subset: MUL, MULH, MULHSU, MULHU. No divide.

  • The divider is often comparable in area to the multiplier while being used far less.
  • Many embedded workloads multiply constantly and divide almost never — and compilers turn division by a constant into a multiply-and-shift anyway.
  • Zmmul lets you keep hardware multiply and let libgcc emulate division in software.
say this if asked to cut area

"First thing I would drop is the divider, moving from M to Zmmul. Division by a constant is already strength-reduced by the compiler, so the dynamic divide count in my workload was negligible."

RV64 delta

RV64M adds MULW, DIVW, DIVUW, REMW, REMUW — 32-bit operations whose results are sign-extended to 64 bits. Note that DIVUW and REMUW sign-extend too, despite being unsigned operations. There is deliberately no MULHW: the high half of a 32-bit product is just the upper bits of the 64-bit MUL, obtained with a shift.

13Interview Q&A

Your multiplier is the critical path. Give me three fixes in order of preference.

One: pipeline it. Split partial-product generation, tree reduction and the final carry-propagate adder across two or three stages. The core sees a fixed 2 or 3-cycle latency instead of a timing violation. This is almost always the right answer.

Two: reduce the row count with Booth radix-4, cutting reduction depth.

Three: replace the tree with an iterative radix-4 loop. Trades a lot of throughput for timing closure and area. Only if the first two are not enough.

What I would not do is retime blindly across the array — the carry-save structure does not retime cleanly and you end up with a register wall.

Does the M extension need a separate result bus to the register file?

Not necessarily, and usually not in a single-issue core. The M unit can arbitrate for the existing write port, holding its result in an output register until a free writeback slot appears.

The cost of sharing is that the M unit stays occupied while it waits, so a following M instruction stalls even though the datapath is free. If M instructions are back-to-back and frequent, a small result queue fixes that far more cheaply than a second write port.

A second write port is justified only when you go superscalar, where you need multiple writes per cycle anyway.

Compilers strength-reduce division by constants. Does that change your divider design?

Yes, materially. Division by a compile-time constant becomes a multiply-high by a magic reciprocal plus a shift and a correction. So the divides that survive to hardware are the ones with a runtime divisor — genuinely rare in most embedded and control code.

That is the whole argument for a slow, small, non-restoring divider, or for Zmmul with software emulation. Profile the dynamic divide count before spending area on SRT.

How would you verify the M unit?

Constrained random against a reference model, with directed corners: zero divisor for all four divide forms, the −231÷−1 overflow pair, operands at ±maximum, sign combinations for MULHSU specifically, and the fusion pairs if implemented.

For a tree multiplier, a full 32×32 exhaustive sweep is 264 and impossible, so either formally prove the reduction against a behavioural *, or exhaustively verify a parameterised narrow instance and rely on structural induction over the array.

For an SRT divider, the quotient-digit selection table needs exhaustive or formal coverage of the P-D plot boundaries. That is the Pentium lesson.

Signed and unsigned multiply in one array — how?

Extend both operands to XLEN+1 bits. For a signed operand, replicate the sign bit into the extra position; for unsigned, insert zero. Then run a single signed multiplier over the widened operands and take the appropriate slice.

This handles all four cases uniformly. MULHSU falls out naturally: sign-extend rs1, zero-extend rs2. The control is two bits — one per operand — driven from funct3[1:0].

The cost is one extra Booth row, which is cheaper than a second array or a correction adder.

15Recap

  • Eight instructions, one funct7 value, same opcode as the base ALU.
  • No divide-by-zero trap. DIV gives −1, DIVU gives all ones, REM and REMU give the dividend.
  • Signed overflow: DIV gives −231, REM gives 0.
  • Truncated division. Remainder takes the dividend's sign.
  • MULHSU exists for the signed×unsigned cross-products of multi-word arithmetic.
  • Fusion pairs: MULH then MUL, DIV then REM, same operands, rd not a source.
  • Variable latency creates RAW, WAW and write-port hazards. WAW is the one that is new.
  • Divide is idempotent, therefore abortable and restartable on interrupt.
  • Zmmul drops the divider when area is tight.
