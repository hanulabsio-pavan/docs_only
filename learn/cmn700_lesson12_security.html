Security on the Mesh — Secure, Non-Secure & Realm

Why isolation is an interconnect problem and not only an MMU problem — and what that forces on the SLC, the snoop filter and the address map.

By the end of this lesson you can

  • Explain physical address spaces and why they are more than an access-permission bit.
  • Describe granule protection checking and where in the path it happens.
  • Say what the mesh itself must enforce — in caches, the snoop filter, and configuration.
  • Explain why MPAM has separate secure and non-secure partition spaces.

1Why an interconnect has to care about security

caveman mode

Isolation is easy if you only check at the door. But data live in caches all over the mesh, and the snoop filter remember who has what. If cache mix up "secure copy" and "normal copy" of same address, isolation broken — and no software can fix it. So fabric must keep them apart, not just the MMU.

It is tempting to think of security as an MMU concern: check permissions at translation, and the rest of the system just moves bytes. That breaks down in a coherent fabric for one reason — the fabric caches things and remembers who has them.

If a shared last-level cache slice can hold a line without knowing which security context it belongs to, then two contexts referencing the same physical address could hit each other's data. If a snoop filter tracks sharers without that distinction, a snoop could leak the existence — or the content — of another context's line. So isolation has to be enforced in the interconnect, in the same structures Lessons 4 and 5 covered.

2Physical address spaces

Classic Arm TrustZone defines two security states and, correspondingly, Secure and Non-secure address spaces. Armv9's Realm Management Extension (RME), part of Arm's Confidential Compute Architecture (CCA), extends this to four physical address spaces (PAS):

PASBroadly for
Non-secureNormal-world software: the OS, hypervisor, ordinary applications.
SecureTrustZone secure world — trusted firmware and secure services.
RealmConfidential VMs whose memory is protected even from the hypervisor.
RootThe most privileged space, owning the monitor that manages the others.

The critical architectural point: the same physical address in two different PAS is architecturally a different location. This is not "the same memory with different permissions" — the PAS is effectively part of the address. That is precisely why caches and directories cannot ignore it.

Same PA, different PAS = distinct locations
   PA 0x8000_0000 in Non-secure  |
   PA 0x8000_0000 in Secure      |  four architecturally
   PA 0x8000_0000 in Realm       |  distinct locations
   PA 0x8000_0000 in Root        |

   a cache tag must therefore carry PAS, not just the address bits

3Granule protection checking

Something must decide whether a given access is allowed to target a given PAS. Under RME that is the granule protection check (GPC), driven by a granule protection table (GPT) that records, per granule of physical memory, which PAS may access it.

Two things to keep straight:

  • Translation converts a virtual address to a physical address and a target PAS. This happens in the MMU for a core, or the SMMU for a device (see Appendix C).
  • Granule protection checking then validates that the resulting PAS is permitted for that physical granule. A failure is a fault, not a silent wrong answer.

Because checking happens at or near the translation point, requests that reach the mesh have already been validated. The mesh's job is therefore faithful carriage and correct separation — keep the PAS attached to the request, and never let two PAS collide in a shared structure.

This division of labour is the answer to "does the interconnect do the security check?" — not the permission decision, but the isolation that makes the decision meaningful downstream.

5Caches and the snoop filter — the interesting part

This is where a security question becomes a coherency question, and where your Lesson 4 knowledge pays off.

The SLC slice

A shared last-level cache is, by construction, shared across everything on the mesh. For it to be safe, a lookup for address A in one PAS must not match a line cached for address A in another. So the PAS participates in identifying the line — conceptually part of the tag rather than an attribute hanging off it.

A capacity consequence worth naming: if several contexts are active on the same physical addresses, they occupy separate cache entries. Isolation is not free — you can lose effective capacity to duplication across contexts.

The snoop filter

The directory has the same requirement for a subtler reason. Recall from Lesson 4 that the snoop filter's job is to tell the home node who to snoop. If it conflated contexts:

  • A snoop could be sent to an agent in a different security context — at minimum leaking that an address is in use, potentially worse.
  • An invalidation in one context could destroy another context's line, which is an availability and correctness problem as well as a security one.

So sharer tracking is per-context. And that has the same capacity implication: directory entries, like cache entries, are consumed per context rather than per address.

Isolation costs capacity in both structures
   without contexts:   addr A  -> 1 SLC line, 1 SF entry
   with two contexts:  addr A  -> NS line + S line       (2 SLC lines)
                                NS entry + S entry     (2 SF entries)

   so heavy multi-context use tightens the SF sizing pressure from L4

6Why MPAM is split secure / non-secure

Lesson 10 introduced MPAM and mentioned node variants named for secure and non-secure MPAM. Now the reason is clear.

MPAM lets software tag traffic with a partition ID and then partition SLC capacity and memory bandwidth by that ID. If there were a single partition-ID space shared across security contexts, then:

  • Secure and non-secure software would have to agree on the meaning of partition IDs — an unacceptable coupling.
  • One context could infer or influence the other's resource allocation, which is a side channel.

So the partition-ID spaces are separate, each with its own configuration, which is why you see distinct secure and non-secure MPAM node variants in the register and node naming. Each security context partitions resources independently.

Good interview beat: MPAM's split is not bureaucracy — a shared ID space would be both a coupling problem and an information-leak surface.

7Protecting the interconnect's own configuration

Here is a point candidates routinely miss. The mesh's configuration is a security asset. Consider what an attacker could do with unrestricted access to it:

  • Remap the SAM so a secure address range targets somewhere it should not — redirecting or exposing traffic without touching a single page table.
  • Reconfigure MPAM to starve another context of cache or bandwidth, a denial-of-service or a timing side channel.
  • Use the PMU as a measurement device: per-crosspoint counters and watchpoints (Lesson 9) observe traffic patterns, which is exactly the primitive a side-channel attack wants.

So access to configuration, MPAM control and debug/trace facilities must itself be restricted by security context. The observability that makes the fabric tunable is the same observability an attacker would like — which is why debug and trace access control is a security feature, not an inconvenience.

8An honest caveat on versions

Confirm the RME support level for your target release

Secure / non-secure separation is long-standing and solidly applicable to CMN-700 — the secure and non-secure MPAM node variants are direct evidence of it. Full RME / CCA support (the four-PAS model with granule protection) arrived with the Armv9 confidential-compute wave, and exactly which interconnect generations and configurations implement which parts is a release-specific question. Before asserting a specific RME capability of CMN-700 in an interview, verify against the TRM for the release in question. The architectural reasoning in this lesson holds regardless; the implementation checklist is what varies.

Saying "the four-PAS model is where Arm is going, and here is what any coherent fabric has to do to support it — I would confirm the specific support level in the TRM" is a strong answer. Asserting a capability you have not verified is not.

10Interview Q&A

Why does a coherent interconnect need to be security-aware at all — isn't that the MMU's job?
The MMU or SMMU makes the permission decision, but the fabric caches data and remembers who holds it, and those structures would break isolation if they were context-blind. A shared SLC slice must not let a lookup for an address in one security context hit a line cached for the same address in another, and the snoop filter must not track sharers in a way that lets a snoop cross a boundary or invalidate another context's line. So the split is: translation and granule protection decide what is allowed, and the interconnect provides the separation that makes that decision meaningful in every structure downstream.
What are the four physical address spaces, and why does the distinction matter to caches?
Non-secure, Secure, Realm and Root, under Armv9's Realm Management Extension as part of Arm CCA. The key point is that the same physical address in two different PAS is architecturally a distinct location, not the same memory with different permissions. So the PAS effectively participates in identifying a cache line rather than being an attribute hanging off it. A consequence worth naming is capacity: if multiple contexts touch the same addresses, they occupy separate cache lines and separate directory entries, so isolation costs effective capacity and tightens snoop-filter sizing pressure.
Where does granule protection checking happen relative to the mesh?
At or near the translation point — the MMU for a core, the SMMU for a device. Translation yields a physical address and a target PAS, and the granule protection check validates against a granule protection table that this PAS may access that granule; a failure is a fault rather than a silently wrong result. Requests therefore arrive at the mesh already validated, and the mesh's responsibility is faithful carriage of the security attribute plus correct separation in every structure that retains state.
Why is MPAM split into secure and non-secure partition spaces?
Because a single shared partition-ID space would create two problems. Secure and non-secure software would have to agree on what each ID means, which is an unacceptable coupling between contexts that are supposed to be isolated. And one context could infer or influence the other's resource allocation, which is an information-leak and denial-of-service surface. Separate ID spaces with separate configuration let each context partition cache capacity and bandwidth independently, which is why distinct secure and non-secure MPAM node variants appear in the naming.
Why does interconnect configuration access need protecting?
Because the configuration is itself a security asset. Remapping the SAM could redirect or expose a secure address range without touching a page table. Reconfiguring MPAM could starve another context of cache or bandwidth, giving denial of service or a timing channel. And the PMU is a traffic-observation primitive — per-crosspoint counters and watchpoints reveal patterns, which is exactly what a side-channel attack wants. So configuration, MPAM control and debug and trace access all have to be restricted by security context; observability is dual-use.
Does CMN-700 support full RME?
Secure and non-secure separation is solidly there — the secure and non-secure MPAM node variants are direct evidence. Full RME and CCA support, meaning the four-PAS model with granule protection, came in with the Armv9 confidential-compute wave, and precisely which interconnect generations and configurations implement which parts is release-specific. I would confirm the support level against the TRM for the target release rather than assert it. The architectural requirements on any coherent fabric are the same either way, which is what I would talk through.

11Recap & key terms

  • Classic TrustZone: Secure / Non-secure. RME under Arm CCA adds Realm and Root — four PAS.
  • The same PA in different PAS is architecturally distinct — PAS effectively part of the address.
  • Translation yields PA + target PAS; granule protection check validates it against the GPT.
  • The mesh must carry the attribute end to end and distinguish contexts in SLC, snoop filter and address decode.
  • Isolation costs capacity: separate lines and directory entries per context.
  • MPAM is split secure / non-secure to avoid coupling and side channels.
  • Configuration and PMU access are security-relevant — observability is dual-use.
  • Verify RME support level per release in the TRM; do not assert it.
