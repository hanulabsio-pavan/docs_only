Architecture Overview

Every architected register, how memory behaves, and exactly how 32 bits of instruction word are carved into fields. This is the lesson you keep coming back to.

By the end of this lesson you can

  • Name every architected register class and say what each is for.
  • Explain the VSX overlay: how FPRs and VRs live inside 64 VSRs.
  • Describe Power's weakly-ordered memory model and the barrier that fixes each problem.
  • Read a raw 32-bit instruction word and identify its form and fields by hand.
  • Avoid the two classic beginner traps: RA|0 and MSB-is-bit-0 numbering.

1The programming model at a glance

caveman mode

Machine has three big buckets of registers: 32 integer, 64 vector-float, and a few special ones for branching and flags. Memory only touched by load/store. Everything else register-to-register.

The architected state a program can see
  ┌──────────────────────── USER STATE (Book I) ────────────────────────┐
  │                                                                     │
  │  GPR0 .. GPR31      32 x 64-bit    integer / address arithmetic     │
  │                                                                     │
  │  VSR0 .. VSR63      64 x 128-bit   vector + scalar floating point   │
  │    └─ FPR0..31     overlay the high 64 bits of VSR0..VSR31           │
  │    └─ VR0..31      are exactly VSR32..VSR63                          │
  │    └─ ACC0..7      512-bit MMA accumulators (v3.1)                   │
  │                                                                     │
  │  CR  32-bit, 8 fields x 4 bits   comparison + branch conditions    │
  │  LR  64-bit link register        return addresses                   │
  │  CTR 64-bit count register       loop counts + indirect branches    │
  │  XER carry / overflow / summary-overflow                          │
  │  FPSCR FP status & rounding   VSCR vector status                 │
  └─────────────────────────────────────────────────────────────────────┘
  ┌────────────────── PRIVILEGED STATE (Book III) ──────────────────────┐
  │  MSR machine state   ·  SPRs (SRR0/1, DAR, DSISR, PID, LPCR, …)   │
  └─────────────────────────────────────────────────────────────────────┘

Two design choices dominate everything else: load/store (memory is only reached by explicit loads and stores) and triadic instructions (most operations take two source operands and one distinct destination, so neither source is destroyed).

2Register explorer

Pick a register class. The bit bars use Power bit numbering, where bit 0 is the most-significant bit.

classic trap #1

RA|0 — GPR0 is not always GPR0. In load/store and addi-style instructions the base-register field is written RA|0: if the field encodes 0, the value used is the literal number zero, not the contents of r0. That's why li r3,5 assembles as addi r3,0,5 and works, and why r0 is nearly useless as a pointer.

3The VSX overlay — one file, three names

Before v2.06 there were two separate register files: 32 FPRs (64-bit, scalar floating-point) and 32 VRs (128-bit, AltiVec/VMX). VSX unified them into 64 architected 128-bit VSRs. Nothing was thrown away — the old names became views onto the new file.

One big cupboard, 64 shelves, each shelf 128 bits wide. Old float name "FPR5" = left half of shelf 5. Old vector name "VR5" = whole shelf 37. Same cupboard, three ways to point at it.

Consequence worth remembering: an MMA accumulator, while primed, occupies four VSRs — so ACC and the underlying VSRs cannot be used for other purposes at the same time.

4The Condition Register and the Rc bit

Power has no single "flags register" that every instruction silently clobbers. Instead there is a 32-bit Condition Register divided into eight independent 4-bit fields, CR0–CR7. A compiler can keep several live comparisons at once — that's the whole point.

CR layout — 8 fields, 4 bits each
 bit  0        4        8       12       16       20       24       28    31
      ┌────────┬────────┬────────┬────────┬────────┬────────┬────────┬────────┐
      │  CR0   │  CR1   │  CR2   │  CR3   │  CR4   │  CR5   │  CR6   │  CR7   │
      └────────┴────────┴────────┴────────┴────────┴────────┴────────┴────────┘
        │
        └─ each field = LT GT EQ SO
             LT less than / negative   GT greater than / positive
             EQ equal / zero           SO summary overflow (copied from XER[SO])
  • An instruction whose mnemonic ends in . has the Rc bit set and updates CR0 automatically: add. r3,r4,r5 sets CR0 by comparing the result against zero.
  • Explicit compares choose their own field: cmpd cr3,r4,r5 writes CR3.
  • Floating-point instructions with Rc=1 update CR1 (a copy of FPSCR exception summary bits), not CR0.
  • CR bits can be combined logically without branching: crand, cror, crxor, mcrf.

XER is the companion: it holds CA (carry), OV (overflow) and SO (sticky summary overflow), plus 32-bit-mode variants CA32/OV32 added in v2.06. Instructions opt into carry/overflow behaviour explicitly — addc writes CA, adde reads and writes it, and the o suffix (addo) writes OV/SO.

caveman mode

x86 has one flag drawer everyone dumps into. Power has eight small drawers plus opt-in carry box. Instruction must ask to write flags (dot suffix). Compiler happy — keeps three comparisons alive, no clobber.

Addressing modes

There are only two, and everything else is built from them:

  • Base + displacement (D-form / DS-form): EA = (RA|0) + sign_extend(D) — e.g. lwz r3,8(r4).
  • Base + index (X-form): EA = (RA|0) + (RB) — e.g. lwzx r3,r4,r5.

Both come in an update flavour (mnemonic suffix u) that writes the computed EA back into RA — lwzu r3,8(r4) loads and advances the pointer, which is why walking an array costs one instruction per element.

6Endianness lab

Type a 64-bit value and flip the mode. This is what a std (store doubleword) actually puts in memory.

Endianness in Power is a storage property, not a register property: the register always holds the same 64-bit number. Only the byte order written to and read from memory changes. That is why byte-reversing loads and stores (lwbrx, ldbrx, stwbrx) exist — they let you read foreign-endian data without switching modes.

7Memory ordering & atomics

Power is one of the most weakly ordered mainstream architectures. Unless you say otherwise, the processor may reorder loads with loads, stores with stores, and loads with stores, and other cores may observe your writes out of order. Code that "just works" on x86 (which is nearly total-store-ordered) can break on Power — this is the single most common porting bug.

InstructionGuaranteesUse it when
sync (a.k.a. hwsync)Full barrier: all prior accesses complete before any later one starts.The heavy hammer — mutex release/acquire pairs, sequential consistency.
lwsyncLightweight: orders load→load, load→store, store→store — but not store→load.Almost all producer/consumer and publish patterns. Much cheaper than sync.
isyncInstruction-fetch serialisation; discards speculated instructions.After an acquire (paired with a conditional branch), and after modifying instruction memory.
eieioOrders accesses to caching-inhibited / device storage.MMIO device drivers.
Atomics: load-and-reserve / store-conditional

Power has no compare-and-swap instruction. It has an LL/SC pair, which is strictly more general:

Atomic increment of a word at 0(r3)
retry:
    lwarx   r4, 0, r3      # load word and RESERVE the address
    addi    r4, r4, 1      # modify in a register
    stwcx.  r4, 0, r3      # store ONLY if reservation still held; sets CR0[EQ]
    bne-    retry          # someone else won the race — go again
    lwsync                 # acquire barrier if this guards later accesses

If any other processor writes the reserved block between the lwarx and the stwcx., the reservation is lost, the store fails, CR0[EQ] is 0, and the loop retries. Doubleword and other widths use ldarx/stdcx., byte/halfword variants exist from v2.06+, and quadword from v2.07.

porting trap

x86 gives you store→load ordering almost for free; Power does not. A publish pattern like data = x; ready = 1; needs an lwsync between the two stores, and the consumer needs a dependency or barrier before reading data. Missing barriers produce bugs that appear only under load, on real multi-socket hardware.

8Address translation & privilege

An address goes through up to two translations before it reaches DRAM:

EA → VA → RA
  Effective Address (what the instruction computes, 64-bit)
          │  segment / process table lookup
          ▼
  Virtual Address
          │  page-table walk  ──  HPT (hashed page table)  classic Power
          │                   └─  Radix (4-level tree)      v3.0 / POWER9+, Linux default
          ▼
  Real Address (physical)

The radix MMU introduced in v3.0 was a big deal: a conventional multi-level page-table tree is what Linux, KVM and every other modern OS already expect, and it made nested (guest-inside-host) translation far cheaper than the hashed page table.

Other key MSR bits: SF (64-bit mode), EE (external interrupts enabled), IR/DR (instruction/data relocation, i.e. translation on), LE (endianness), FP/VEC/VSX (unit availability — used for lazy context switching).

9Bit numbering — the gotcha that bites everyone

classic trap #2

Power numbers bits from the most-significant end. In a 32-bit instruction word, bit 0 is the MSB and bit 31 is the LSB. In a 64-bit register, bit 0 is the MSB and bit 63 is the LSB. This is the exact opposite of the x86/RISC-V/C convention you probably have in your fingers. When the spec says "XER bit 34 is CA", that is counting from the left.

Same 32-bit word, two conventions
  Power spec   bit  0 ────────────────────────────────→ bit 31
                    MSB                                  LSB
  C / x86      bit 31 ←──────────────────────────────── bit 0

  So "primary opcode = bits 0:5" means the top six bits:
      word >> 26  &  0x3F

The practical conversion when writing code: a field at Power bits [hi:lo] of a 32-bit word is (word >> (31 - lo)) & ((1 << (lo - hi + 1)) - 1).

10Instruction formats (the "forms")

Every base instruction is exactly 32 bits, and the top 6 bits are always the primary opcode. Beyond that, the layout depends on the form. Most forms reuse an extended opcode field to pack many instructions under one primary opcode — primary opcode 31 alone hosts hundreds of them.

13Interview Q&A

Walk me through the Power register file.
32 general-purpose registers, 64 bits each, for integer and address arithmetic. 64 vector-scalar registers of 128 bits each — the VSX file — where the legacy 32 FPRs are the high doublewords of VSR0–31 and the 32 VMX vector registers are VSR32–63. Then the special registers: a 32-bit Condition Register split into eight 4-bit fields, the Link Register and Count Register for branching, XER for carry and overflow, FPSCR and VSCR for FP/vector status. v3.1 adds eight 512-bit MMA accumulators that overlay VSR0–31. Privileged state — MSR and the SPRs — sits in Book III.
What is the RA|0 convention and why does it exist?
In load/store and immediate-arithmetic instructions, the base-register field is specified as RA|0: if the 5-bit field encodes register 0, the value used is the literal zero rather than the contents of GPR0. It exists so that the same encoding gives you both "base register plus displacement" and "absolute small address / load immediate" without spending a separate opcode. It's why li rX,n is just addi rX,0,n, and why compilers avoid using r0 as a pointer.
Explain the VSX overlay and why IBM did it.
Before v2.06 there were two disjoint files: 32 × 64-bit FPRs and 32 × 128-bit VMX vector registers. VSX defines 64 architected 128-bit VSRs and maps the old files onto them — FPRn is bits 0:63 of VSRn, VRn is VSR n+32. The motivation is register pressure and unification: vector code gets twice the registers, scalar FP and vector code share one datapath and one context-switch footprint, and instructions can move data between the scalar and vector worlds without going through memory.
Power is weakly ordered. What does that mean in practice, and what are the barriers?
The hardware may reorder loads and stores relative to program order, and other cores can observe your accesses in a different order, unless you insert barriers. sync/hwsync is the full barrier. lwsync is the cheap one, ordering load→load, load→store and store→store but not store→load — it's what most acquire/release and publish patterns need. isync serialises instruction fetch and is used after an acquire (with a conditional branch) and after modifying code. eieio orders device/caching-inhibited accesses. The porting hazard is that x86's near-TSO model hides missing barriers that Power exposes.
How do you do an atomic compare-and-swap on Power?
There isn't a CAS instruction. You build it from load-and-reserve and store-conditional: lwarx (or ldarx) takes a reservation on the address, you compare and compute in registers, then stwcx. (or stdcx.) stores only if the reservation survived, reporting success in CR0[EQ]. On failure you branch back and retry. Add lwsync/isync as needed for acquire/release semantics.
Why does Power have eight condition register fields instead of one flags register?
To reduce false dependencies and let the compiler keep several conditions live simultaneously. With a single flags register every comparison clobbers the last one, which serialises code and forces branches to sit right after their compare. With CR0–CR7, a compiler can evaluate several conditions early, combine them with the CR logical instructions (crand, cror) and branch once — good for deep pipelines. Flag writing is also opt-in via the Rc bit, so ordinary arithmetic doesn't create a dependency at all.
What's the deal with Power's bit numbering?
Power numbers bits from the most-significant end: bit 0 is the MSB. In a 32-bit instruction, bits 0:5 are the primary opcode — the top six bits. In a 64-bit register, bit 63 is the least-significant. Everyone coming from x86, Arm or RISC-V gets this backwards once. The conversion for a field at Power bits [hi:lo] is (word >> (31-lo)) & ((1<<(lo-hi+1))-1).
Hashed page table vs radix — why did v3.0 add radix?
The classic Power MMU used segments plus a hashed page table, which is unusual and awkward for operating systems designed around multi-level page-table trees, and it's especially painful for nested virtualisation because the host has to shadow guest translations. The radix MMU in v3.0 (POWER9) is a conventional 4-level radix tree, matching what Linux and KVM already expect, and it supports nested translation directly — so guest page-table walks get hardware support instead of hypervisor emulation.

14Recap & key terms

  • 32 GPRs (64-bit) · 64 VSRs (128-bit) with FPRs and VRs as views · CR, LR, CTR, XER, FPSCR.
  • CR = 8 × 4-bit fields (LT GT EQ SO); the . suffix sets Rc=1 and updates CR0 (CR1 for FP).
  • Load/store only; two addressing modes — base+displacement and base+index — each with an update form.
  • Bi-endian via MSR[LE]; endianness affects memory, never register contents.
  • Weakly ordered: sync full · lwsync cheap · isync fetch · eieio device. Atomics via lwarx/stwcx..
  • EA → VA → RA; radix MMU from v3.0. Privilege: problem / privileged / hypervisor via MSR.
  • All base instructions are 32 bits, top 6 bits = primary opcode; forms D, DS, X, XO, XL, XFX, A, M, MD, I, B. Bit 0 = MSB.
