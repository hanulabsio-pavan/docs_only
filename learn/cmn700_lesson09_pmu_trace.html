Observability — PMU, DTC/DTM, Debug & Trace

How the mesh is instrumented, and the method for turning a vague performance complaint into a root cause.

By the end of this lesson you can

  • Describe the distributed PMU: DTM at every XP, DTC in the HN-D.
  • Explain watchpoints with flit match/mask and channel/device selection.
  • Use the mental model behind the Linux arm_cmn PMU.
  • Run a structured playbook from symptom to hot node to root cause.

1You cannot tune what you cannot see

caveman mode

Put little counter at every crossroad (DTM). One boss counter (DTC) add them up, write logbook with timestamps. Now you see which road jammed, which home node overworked. Without this, tuning is guessing.

Lessons 5 and 7 kept saying "retune the hash" and "find the hot crosspoint". This lesson is how you actually find them. For performance and validation roles this is often the most important lesson in the course, because it is the part you use daily.

2A two-level distributed PMU

CMN-700 does not have one central performance counter block. It has a small monitor at every crosspoint plus one global controller, which is the only way to observe a mesh this large without a bottleneck.

DTMs everywhere, one DTC to aggregate
   XP+DTM   XP+DTM   XP+DTM   XP+DTM
      |         |         |         |
      +---------+----+----+---------+
                     |  overflow / events
                     ▼
                DTC (in HN-D)
                 |  up to 8 global counters
                 |  overflow interrupts
                 ▼
             timestamped trace out via ATB

3DTM — Debug and Trace Monitor

One DTM sits at every XP. Each can count up to 4 local event signals and can also match traffic with watchpoints. Because it is local, it sees exactly what passes through that crosspoint and its device ports — which is precisely the granularity you need to localise a hot spot.

  • Up to 4 local event counters per XP.
  • Watchpoint match/mask on flits, for both upload and download directions.
  • Can be aggregated by node type, or targeted to a specific node.

4DTC — Debug and Trace Controller

The DTC lives in the HN-D (the mandatory node from Lesson 2 — this is one of its jobs). It provides global PMU control and aggregation:

FunctionDetail
Global countersAggregates DTM events and overflows into up to 8 global counters.
InterruptsRaises overflow interrupts so software can sample without polling.
Trace outputEmits timestamped trace off-chip or to a buffer via ATB (Arm Trace Bus).
ControlGlobal enable/disable, so all DTMs start and stop coherently for a valid measurement window.

That last point matters more than it sounds: counters started at different times produce numbers that cannot be compared. Global control is what makes the measurement trustworthy.

5Watchpoints: match and mask

Raw mesh traffic is far too much to record. A watchpoint filters it: you specify a value and a mask over flit fields, plus which channel and which device / direction to observe, and only matching flits are counted or traced.

Watchpoint = value + mask + channel + direction
   flit fields  ......  (source, target, opcode, addr, QoS ...)
        |
        ▼
   compare against  value  under  mask     mask = "don't care" bits
        |
        +-- channel select   (REQ/RSP/SNP/DAT)
        +-- device / direction (upload / download)
        ▼
   match -> count it and/or emit trace

This is how you answer questions like "how many snoops target this specific RN-F?" or "which requester is generating traffic to this address region?" without drowning in data.

6The software view: Linux arm_cmn

Linux exposes this hardware as a normal perf PMU named arm_cmn_0, with one PMU instance per mesh (arm_cmn_1 and upward for additional linked meshes). Events can be aggregated across all nodes of a type, or targeted to one node by its nodeid — which is exactly the coordinate-based node ID from Lesson 1.

The practical loop is: measure aggregate first to see whether there is an imbalance, then target specific nodes to see where it is.

9Interview Q&A

How would you debug a bandwidth problem on the mesh?
Use the distributed PMU. Per-XP DTMs count up to four local events each and support watchpoints that match flits by value and mask with channel and device selection; the DTC in the HN-D aggregates into up to eight global counters, raises overflow interrupts, and emits timestamped trace over ATB. In Linux this is the arm_cmn PMU. Method: characterise bandwidth versus load, find whether one home node or crosspoint is disproportionately hot, classify it as a hashing problem, a placement problem, or genuine saturation, check SLC hit rate and snoop-filter back-invalidations, check whether CBusy throttling is engaging, then zoom in with watchpoints and change one variable at a time.
Why is the PMU distributed rather than central?
A mesh can have up to 144 crosspoints, and funnelling all event traffic to one central block would be both a bandwidth bottleneck and a source of measurement distortion. Local DTMs observe exactly what passes through their crosspoint, which is also the granularity you need to localise a hot spot; the DTC only needs to aggregate and control.
What is the DTC's role beyond counting?
Global control and output. It aggregates DTM events and overflows into up to eight global counters, raises overflow interrupts so software can sample without polling, emits timestamped trace via ATB, and provides coherent global enable and disable so every DTM measures over the same window. Without that last function the counters would not be comparable.
How do you observe just one node?
Events can be aggregated across all nodes of a type or targeted at a specific node using its nodeid, which is the coordinate-based node ID that encodes the crosspoint position plus port and device. In practice you measure aggregate first to detect imbalance, then target individual nodes to locate it.
Why do watchpoints matter?
Raw mesh traffic is far too voluminous to record. Watchpoints reduce it to the flows you care about by matching flit fields against a value under a mask, restricted to a channel and a device or direction. That is what makes questions like "how many snoops target this requester" or "which agent drives traffic to this address region" answerable.

10Recap & key terms

  • DTM at every XP: up to 4 local events, watchpoints, upload/download.
  • DTC in the HN-D: up to 8 global counters, overflow interrupts, timestamped ATB trace, global enable.
  • Watchpoint = value + mask over flit fields, plus channel and device/direction.
  • Linux exposes it as arm_cmn_0 (one per mesh); target nodes via nodeid.
  • Playbook: characterise → find hot node → classify → check caches → check throttling → zoom in → change one thing.
