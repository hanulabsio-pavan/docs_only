A extension — LR/SC, AMO and memory ordering

A is the extension that reaches outside your core. Everything here lands in the cache controller, the coherency protocol and the interconnect. If you have done coherent fabric work, this is the lesson where you can outclass the room.

By the end of this lesson you can

  • State the exact SC success and failure conditions, including spurious failure.
  • Define a reservation set and list everything that invalidates one.
  • Recite the constrained LR/SC rules and explain why the bound is 16 instructions.
  • Argue near-atomic versus far-atomic placement with a contention model.
  • Explain aq and rl precisely, and name the pattern software is told not to use.
  • Describe why an AMO must be non-speculative and where the page fault is taken.

1The interview frame

crux

M breaks fixed latency. A breaks two other assumptions: that an instruction can be executed speculatively and undone, and that your core's memory behaviour is your core's business. An AMO is a read-modify-write that some other agent must not be able to interleave with.

Panels probing A are usually probing whether you understand coherency. Answer in protocol terms — line states, invalidations, points of serialisation — not in software terms.

2Encoding and the funct5 map

All A instructions are R-type with opcode AMO = 0101111. The top five bits select the operation. Two bits carry ordering annotations.

funct3 = 010 for .W, 011 for .D. RV32A has only .W. rs1 is always the address — never an offset form, so there is no immediate.

decode shortcut

funct5[4] selects the min/max family. funct5[3:2] then picks the logical operation within the lower family. The ALU inside the atomic unit only needs add, the three logicals, a pass-through for swap, and a comparator. It can be a stripped-down copy of the main ALU.

note

AMOs always return the original memory value, never the new one. So AMOADD is fetch-and-add, not add-and-fetch. Getting this backwards in an interview is an instant correction.

3LR/SC semantics

Canonical atomic increment with LR/SC
retry:
    lr.w    t0, (a0)        # load and reserve the address in a0
    addi    t1, t0, 1        # compute new value
    sc.w    t2, t1, (a0)   # t2 = 0 on success, nonzero on failure
    bnez    t2, retry         # backward branch is OUTSIDE the constrained body
SC succeeds only if all of these hold
  1. A reservation is currently valid for this hart.
  2. The reservation set still contains the SC's address.
  3. No store from another hart to the reservation set has been observed since the LR.
  4. Nothing has cleared the reservation for an implementation-specific reason.
the big one

SC is permitted to fail spuriously. No contention is required. A cache eviction, a context switch, an interrupt, or a conservative implementation policy can all cause failure. Software must always loop. A candidate who says "SC only fails if another hart wrote" has missed the entire point of the retry loop.

rd is written with zero on success and a nonzero implementation-defined code on failure. Both outcomes write rd — SC is never a no-op from the register file's point of view. Note that SC with rd = x0 is legal and simply discards the status, which is almost always a bug in software.

alignment

LR and SC must be naturally aligned. A misaligned LR or SC raises a misaligned-address exception or an access fault. There is no hardware fixup path — an atomic that spans two cache lines cannot be made atomic cheaply, which is exactly why the requirement exists.

4The reservation set

definition

A reservation set is an implementation-defined set of bytes that always contains the bytes the LR accessed. Granularity is your choice. The choice trades hardware cost against spurious failure rate.

GranuleComparator widthSpurious failuresTypical use
Exact word (4 bytes)Full address compareMinimalSingle-core, simple L1
Cache line (32–64 bytes)Tag compare, reuses coherenceFalse sharing possibleMost real cores
Whole hart — any store clearsOne valid bitVery highTiny cores, no cache

The cache-line granule is the usual answer, because the coherence protocol already delivers an invalidation at exactly that granularity. You get the monitoring for free — a snoop or invalidate that hits the reserved line clears the reservation valid bit.

Reservation monitor — minimal RTL shape
logic        resv_valid;
logic [31:6] resv_line;   // 64B granule → tag is addr[31:6]

always_ff @(posedge clk) begin
  if (rst | trap_taken | sc_executed)      resv_valid <= 1'b0;
  else if (lr_commit)                       begin resv_valid <= 1'b1;
                                             resv_line  <= addr[31:6]; end
  else if (snoop_inval & (snoop_line == resv_line)) resv_valid <= 1'b0;
  else if (line_evicted & (evict_line == resv_line)) resv_valid <= 1'b0;
end

wire sc_success = resv_valid & (addr[31:6] == resv_line) & ...;

One valid bit and a tag register per hart. That is the whole cost of LR/SC in the core — everything expensive lives in the coherency protocol you already had.

Be able to list these without hesitating. It is a standard question.

trap

"Does a context switch clear the reservation?" The specification does not mandate it in those words, but every practical implementation clears on trap entry — otherwise a reservation taken by thread A could be consumed by an SC in thread B after a switch, and the atomicity guarantee collapses. Say "implementations clear it on trap, and must, for context-switch safety".

6Constrained LR/SC sequences

The specification makes a forward-progress guarantee, but only for sequences that obey strict rules. Know the rules, and know why each one exists.

A sequence is constrained when
  1. The LR and SC address the same naturally aligned word (or doubleword for .D).
  2. At most 16 instructions execute dynamically between the LR and the SC.
  3. The intervening instructions come only from the base integer set, and its compressed forms when C is present.
  4. No loads or stores in between.
  5. No backward jumps and no taken backward branches in between.
  6. No JALR, no FENCE, no SYSTEM instructions in between.
crux

The retry branch that jumps back to the LR is outside the constrained body. Looping to retry is fine. Looping inside the LR-to-SC window is not.

Each rule exists for a hardware reason
RuleHardware reason
Same aligned addressA single reservation register holds one tag. No second monitor exists.
16-instruction boundBounds the window during which the implementation must protect the reservation against remote invalidation. Longer windows would make the progress guarantee unimplementable.
No loads or storesAn intervening memory access can evict the reserved line, or alias into the same set, destroying the reservation through pure capacity pressure.
No backward branchesBackward branches make the dynamic instruction count unbounded, defeating rule 2.
No FENCE or SYSTEMBoth can have arbitrary latency and side effects, including taking a trap, which clears the reservation.
No JALRAn indirect jump can leave the sequence entirely. The hardware cannot bound what runs next.
Non-constrained examples — no progress guarantee
Broken: a load inside the window
retry:
    lr.w  t0, (a0)
    lw    t1, 0(a1)      # ← load may evict the reserved line
    add   t0, t0, t1
    sc.w  t2, t0, (a0)
    bnez  t2, retry     # may never terminate on some implementations
Broken: a loop inside the window
retry:
    lr.w  t0, (a0)
inner:
    addi  t1, t1, -1
    bnez  t1, inner     # ← taken backward branch, count unbounded
    sc.w  t2, t0, (a0)

Both assemble. Both may run correctly on your test silicon. Neither is guaranteed to terminate. This is the kind of bug that only appears under load on a different implementation.

7Livelock and forward progress

Two harts, same address, both in a constrained loop. Each LR-SC pair can invalidate the other's reservation. Without help, neither ever completes.

The livelock pattern
  hart 0            hart 1
  LR   (reserve)
                    LR   (reserve, invalidates hart 0? no — LR does not store)
  SC   ───────────→ invalidates hart 1's reservation
                    SC   fails, retry
                    LR   (reserve)
  LR   (reserve)
                    SC   ───────────→ invalidates hart 0's reservation
  SC   fails, retry
  ... and so on, forever, if the timing stays symmetric

The specification requires that a constrained sequence eventually succeeds. So the implementation must break the symmetry. Mechanisms, roughly in order of how often they appear in real designs:

MechanismWhere it livesNote
Reservation hold windowL1 / reservation monitorAfter an LR, delay or retry incoming invalidations to that line for a bounded number of cycles, giving the SC a chance to land.
Hardware backoffCoreOn repeated SC failure, insert a randomised delay before allowing the next LR to reserve.
Home-node arbitrationInterconnect / point of coherencyFair ordering of ownership requests so no requester is starved. Natural fit if the fabric already has QoS and anti-starvation logic.
Nack with priority escalationSnoop pathA requester repeatedly denied raises its priority until it wins.
your fabric background is an advantage here
  • Anti-starvation and fair arbitration at a shared point of serialisation are exactly the mechanisms you have built in interconnect work.
  • "The forward-progress guarantee for constrained LR/SC ultimately reduces to a starvation-freedom property at the point of coherency. That is the same problem as ensuring no requester is indefinitely nacked in a mesh."
  • Say it in those terms. It reframes a RISC-V question as a fabric question you already know cold.

8AMO semantics

An AMO does four things indivisibly: read the memory word, apply the operation with rs2, write the result back, return the original value in rd.

Atomic increment — AMO versus LR/SC
# With AMO: one instruction, no retry loop
    li      t0, 1
    amoadd.w t1, t0, (a0)    # t1 = old value, mem = old + 1

# With LR/SC: four instructions, unbounded retries
1:  lr.w    t1, (a0)
    addi    t2, t1, 1
    sc.w    t3, t2, (a0)
    bnez    t3, 1b
when to use which

AMO when the operation is one of the eleven provided. LR/SC when it is not — compare-and-swap, conditional update, or any read-modify-write whose function is data-dependent. AMO is always faster when it applies, because there is no retry loop and no reservation to lose.

the rd = x0 optimisation

If rd is x0 the old value is discarded. The implementation can then issue a non-returning atomic — no read data has to come back across the interconnect. In a CHI-style fabric this is exactly the AtomicStore versus AtomicLoad distinction. Worth mentioning: it saves a data flit and a whole return path in the common "atomic increment, do not care about the old value" case.

9Near versus far atomics

The highest-value question in this lesson, and the one where fabric experience shows.

Near atomic — perform it in your own L1
  1. Request the line in a writable state. Coherency invalidates all other copies.
  2. Once the line is exclusive or modified locally, read it, apply the operation, write it back.
  3. The line stays in your cache.

Good: the next atomic to the same address by the same hart is a local hit. Lock acquisition by a thread that already owns the line is nearly free.

Bad under contention: N harts hammering one counter means the line migrates N times per round. Every migration is a full coherency transaction with snoop latency. Throughput collapses.

Far atomic — perform it at the point of coherency
  1. Send the operation and the operand to the shared point — home node, last-level cache, or memory controller.
  2. That agent performs the read-modify-write locally, where the line already lives.
  3. Only the old value comes back, and only if rd is not x0.

Good under contention: the line never moves. N atomics from N harts serialise at the home node at roughly one per pipeline slot. No ping-pong.

Bad for private data: every atomic is a full round trip to the shared point even if nobody else is touching the line.

crux

Far atomics turn a data-movement problem into a message-passing problem. The operation travels to the data instead of the data travelling to the operation. That is the entire argument.

Choosing
ScenarioBetter choiceWhy
Uncontended lock, same thread reacquiresNearLocal cache hit, no fabric traffic
Shared counter, many hartsFarNo line migration, serialises at one point
Producer-consumer queue headFarOwnership alternates constantly otherwise
Thread-local reference countNearLine is already exclusive
Atomic on uncacheable or device memoryFarNo cacheable state exists to own

Sophisticated implementations do both and choose dynamically — near if the line is already owned locally, far otherwise, sometimes with a contention counter that promotes a hot line to far-only. Saying "I would make it adaptive based on whether the line is already in a writable state" is a strong answer.

Mapping onto a coherent protocol

A CHI-style interconnect carries far atomics natively as distinct transaction types, broadly:

  • Non-returning atomic — apply the operation, return no data. Matches an AMO with rd = x0.
  • Returning atomic — apply the operation, return the original value. Matches a normal AMO.
  • Swap — unconditional exchange. Matches AMOSWAP.
  • Compare — conditional exchange on a match. This is what a compare-and-swap extension would use; base RV32A has no CAS instruction to map onto it.

The home node or a dedicated atomic unit at the point of serialisation executes the operation. Note that the arithmetic unit now lives in the fabric, not the core — so the fabric must implement add, the logicals and signed and unsigned min/max.

a very strong line to have ready
  • "RV32A's AMO set maps cleanly onto far-atomic transactions at the home node. The interesting design decision is not the instruction, it is where you put the ALU — in the requester's L1 or at the point of coherency — and that decision is driven entirely by the expected contention profile."

10aq, rl and RVWMO

RISC-V uses a weak memory model, RVWMO. Ordering is not free; you request it.

AnnotationMeaning
aq = 1Acquire. No memory operation later in program order may be observed by another hart before this one.
rl = 1Release. No memory operation earlier in program order may be observed by another hart after this one.
aq = rl = 1Both directions. The operation becomes sequentially consistent with respect to other similarly annotated operations.
aq = rl = 0Relaxed. Ordered only by RVWMO's preserved program order rules.
The standard lock idiom
# Acquire: LR carries .aq — nothing in the critical section escapes upward
1:  lr.w.aq  t0, (a0)
    bnez     t0, 1b
    li       t0, 1
    sc.w     t1, t0, (a0)
    bnez     t1, 1b

    # ... critical section ...

# Release: the unlocking store carries .rl — the section completes first
    amoswap.w.rl x0, x0, (a0)
the annotation trap

Software should not set rl on an LR unless aq is also set, and should not set aq on an SC unless rl is also set. A lone sc.w.aq is the wrong pattern. Interviewers ask "what does lr.w.rl mean" to see whether you know it is a discouraged combination rather than a clever optimisation.

FENCE, for when annotations are not enough

FENCE pred, succ orders the predecessor set against the successor set. Each set is drawn from device input, device output, memory read, memory write — written i o r w.

  • fence rw, rw — full memory barrier. The common one.
  • fence r, rw — acquire-style barrier after a plain load.
  • fence rw, w — release-style barrier before a plain store.
  • fence.tso — a distinct encoding giving total-store-order semantics, ordering everything except store-to-load.
  • fence.i — instruction fetch fence, part of Zifencei. Different purpose entirely: it makes prior stores visible to instruction fetch. Do not conflate the two.
preserved program order — the short version

RVWMO orders two accesses when there is a syntactic address, data or control dependency; when they are to overlapping addresses under specific rules; when a FENCE separates them; or when acquire and release annotations require it. Everything else may be reordered. If asked to prove a litmus test, reason from those rules, not from intuition.

11Pipeline implications

An AMO must not be performed speculatively

Once memory is modified, it cannot be un-modified. So the AMO may only be issued to the memory system when it is guaranteed to commit.

  • In-order five-stage: by the time an instruction reaches MEM, all older instructions have passed their exception points and branches resolved in EX. So MEM is already non-speculative. No extra logic is needed, which is a nice property to point out.
  • Out-of-order: the AMO must wait until it is the oldest uncommitted instruction, or at least until no older instruction can fault or mispredict. It issues from the head of the reorder buffer.
  • Deeper in-order with a store buffer: the AMO must drain past any older store that could alias, or be forwarded correctly from the buffer, and it cannot itself sit in a write-combining buffer.
Faults must be taken before memory changes

An AMO touches a page for both reading and writing. Therefore:

  1. Translate the address and check permissions first.
  2. An AMO to a page without write permission must raise a store/AMO page fault, not a load page fault — even though the operation reads.
  3. A misaligned AMO raises store/AMO address misaligned, cause 6.
  4. Only after all checks pass may the read-modify-write be issued.
trap

"An AMO hits a read-only page. Which fault?" Store/AMO page fault. Candidates who answer "load page fault, because it reads first" are testing the wrong half of the operation. The architectural rule is that an AMO is a store for permission purposes.

D-cache port pressure

An AMO is a read and a write to the same location. Three ways to build it:

  • Two MEM cycles. Read in the first, write in the second, with the line locked in between so no snoop can intervene. Simple. Costs a bubble on every AMO.
  • Read-modify-write in one access. Needs a cache design that can read and write in one cycle, plus an ALU in the cache datapath. Faster, more area.
  • Send it out as a far atomic. The L1 does not perform it at all; the fabric does. No local port pressure, higher latency.

Whichever you choose, the line must be protected between the read and the write. Locking one line for two cycles is the usual answer, and it must not deadlock against an incoming snoop — so the snoop path needs a retry or a defined ordering.

Where the pipeline actually stalls

The aq/rl row matters. An ordering annotation can cost far more than the atomic itself, because it may require draining a store buffer or waiting for outstanding transactions to be globally observed. Mention that the annotation, not the atomic, is often the expensive part.

12Zalrsc, Zaamo and Zacas

NameContentsWhy it exists
ZalrscLR and SC onlyCheapest path to atomicity. One reservation register. Everything else is software loops.
ZaamoThe eleven AMOs, no LR/SCFits systems where a far-atomic unit exists but no reservation monitor does — some accelerator and device contexts.
AZalrsc + ZaamoThe full extension, which is what the "A" in RV32IMAC means.
ZacasCompare-and-swap atomicsAdds a true CAS, which base A does not have. Lock-free algorithms written against CAS otherwise need an LR/SC loop.
trap

"Does RISC-V have compare-and-swap?" Not in the A extension. CAS is emulated with an LR/SC loop. A separate extension, Zacas, adds native compare-and-swap. Saying "yes, AMOCAS is part of A" is wrong and easy to check.

RV64 delta

RV64A adds the .D forms — LR.D, SC.D and all eleven AMO*.D — selected by funct3 = 011. The .W forms remain, and on RV64 they sign-extend the returned 32-bit value to 64 bits. Reservation granularity and every ordering rule are unchanged.

14Interview Q&A

Why does RISC-V provide both LR/SC and AMOs? Is one not enough?

They solve different problems. AMOs cover a fixed set of operations and are optimal for them — one instruction, no retry, and they can be shipped to a remote point of coherency. LR/SC is general: any read-modify-write whose function is arbitrary or data-dependent, including compare-and-swap, which base A does not provide as an instruction.

Implementation cost also differs. Zalrsc alone needs one reservation register. Zaamo alone needs an atomic ALU somewhere in the memory path but no reservation monitor. A minimal system can pick either.

Your reservation granule is a 64-byte cache line. What goes wrong, and do you care?

False sharing. Two unrelated lock words in the same line mean an SC on one can fail because another hart wrote the other. Correctness is preserved — SC is allowed to fail spuriously — but throughput suffers and, in the worst case, the eventual-success guarantee becomes harder to meet.

Do I care? Usually not enough to change the design, because the coherency protocol already delivers invalidations at line granularity and a narrower monitor would need its own address comparator and its own snoop filtering. The fix belongs in software: pad lock words to a line. That is why concurrent data structures align hot atomics to a cache line.

What I would add is a reservation hold window, so a burst of remote invalidations cannot starve a constrained sequence on an adjacent word.

Where exactly does the AMO's arithmetic happen?

It depends on the placement policy, and that is the real answer. In a near-atomic design it happens in the core's load-store unit or in an ALU attached to the L1 datapath, after the line has been brought to a writable state. In a far-atomic design it happens at the point of coherency — the home node, the last-level cache slice, or the memory controller — and the core never owns the line.

Systems that support both need the atomic ALU replicated at each site, which means add, XOR, OR, AND, swap, and signed and unsigned min/max have to exist in the fabric as well as in the core. That replication is a real cost and it is the usual reason a small design picks one placement and stays with it.

Does a single-hart core need the A extension at all?

Yes, for two reasons beyond multi-hart coherence. First, interrupt handlers and the main thread share data, and an atomic read-modify-write is the clean way to update a shared counter or flag without disabling interrupts. Second, DMA engines and other bus masters write memory concurrently; if they are coherent, the reservation mechanism must see their writes.

On a genuinely single-agent system with no coherent DMA, the atomics degenerate — the reservation is never invalidated by anyone else and an AMO is just a locked read-modify-write — but the instructions still need to exist because compiled libraries and the ABI assume them.

Prove that your LR/SC implementation cannot livelock.

You cannot prove it from the core alone; it is a system property. The argument has three parts.

One: bound the window. The constrained-sequence rules cap the dynamic instruction count between LR and SC at 16 and forbid anything of unbounded latency, so the reservation only needs to survive a bounded number of cycles.

Two: protect the window. After an LR, the reservation monitor holds off or retries incoming invalidations to that line for at least that bounded period, so a remote store cannot destroy the reservation arbitrarily often.

Three: guarantee fairness at the serialisation point. Ownership requests to the line must be served under a starvation-free arbitration policy, so no hart is indefinitely denied. Without part three, parts one and two only shift the livelock into the fabric.

Verification is by bounded model checking of the two-hart symmetric case plus directed stress with adversarial timing, not by random testing — random testing almost never hits the symmetric phase.

What does aq actually cost in hardware?

In a simple in-order core with no store buffer and blocking memory accesses, almost nothing — the pipeline is already effectively ordered, so the annotation is decoded and then satisfied for free. That is worth saying, because it explains why small cores implement A cheaply.

The cost appears as soon as you have a store buffer, non-blocking misses or any reordering in the memory system. Then a release requires that every earlier access be globally observable before the annotated one is, which means draining or at least fencing the store buffer, and an acquire requires blocking later accesses from being observed early, which means holding them at issue.

So the honest answer is that aq and rl cost exactly as much as your memory system reorders. Design the reordering first; the annotations then price themselves.

16Recap

  • One opcode, 0101111. funct5 selects the operation, aq and rl carry ordering, funct3 selects width.
  • SC writes 0 on success, nonzero on failure, and may fail spuriously. Always loop.
  • A reservation set is implementation-defined but always contains the LR's bytes. Cache-line granularity is the usual choice.
  • Constrained sequences: same aligned address, at most 16 instructions, no loads, stores, backward branches, JALR, FENCE or SYSTEM in between.
  • Forward progress is guaranteed only for constrained sequences, and requires a hold window plus fair arbitration at the point of coherency.
  • AMOs return the original value. rd = x0 enables a non-returning atomic.
  • Near atomics win uncontended; far atomics win under contention. The decision is where you put the ALU.
  • aq blocks later operations from being observed early; rl blocks earlier ones from being observed late. Do not set rl alone on LR or aq alone on SC.
  • An AMO must be non-speculative, and faults as a store for permission purposes.
  • Base A has no compare-and-swap. Zacas adds it.
