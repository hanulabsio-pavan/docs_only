C extension — compression and the fetch path

C adds no new operations and no new architectural state. Every compressed instruction is an existing one, written shorter. And yet it is the extension that causes the most microarchitectural damage — because it destroys the assumption that instructions are 4-byte aligned.

By the end of this lesson you can

  • Name the three quadrants and how inst[1:0] selects them.
  • Explain why the compressed register fields cover x8–x15 specifically.
  • Place the decompressor and defend the placement on timing grounds.
  • Say which RV32 compressed encodings mean something else entirely in RV64.
  • Walk through a 32-bit instruction spanning two pages and name mepc and mtval.
  • Describe how a fetch unit finds instruction boundaries in parallel.
  • State what a BTB must change when IALIGN becomes 16.

1The interview frame

crux

The decompressor is trivial. The fetch unit is not. Candidates talk about the expander because it is easy; interviewers ask about alignment because it is hard. Lead with alignment and you have already separated yourself.

Two sentences to have ready: "C costs a few hundred gates of expander and roughly a quarter of the instruction memory. It costs a fetch buffer, a boundary scanner, predecode bits and a finer-grained BTB. The second list is where the real design effort goes."

2Three quadrants

A 16-bit instruction has inst[1:0] ≠ 11. Those two bits select a quadrant. inst[15:13] — funct3 — selects within it.

Quadrant 0 — memory with a compressed base register

Loads and stores whose base register comes from the restricted 3-bit field. Offsets are small, zero-extended and scaled by the access size.

the two-operand constraint

Most compressed ALU forms are destructive: rd is also rs1. That is how they fit in 16 bits. So the compiler can only emit them when the source is dead after the operation. This is why compression ratio depends heavily on register allocation quality.

Quadrant 2 — stack-pointer forms and full-width registers

This quadrant keeps 5-bit register fields, so it can name any of the 32 registers. It pays for that with sp-relative-only addressing.

The sp-relative forms exist because function prologues and epilogues are overwhelmingly stack traffic. C.LWSP and C.SWSP alone recover a large share of the compression in real code.

Why 11 is excluded

inst[1:0] = 11 marks a 32-bit instruction. The encoding scheme extends further: inst[4:2] = 111 with inst[6:5] = 11 and more low bits set indicates 48-bit, 64-bit and longer instructions.

Instruction length encoding
  xxxxxxxxxxxxxxxaa     aa ≠ 11        → 16-bit
  xxxxxxxxxxxbbb11     bbb ≠ 111      → 32-bit
  ...011111          reserved pattern  → 48-bit
  ...0111111         reserved pattern  → 64-bit
crux

Length is determined entirely by the first halfword. That is the property that makes parallel length decoding possible. A variable-length ISA where length depended on later bytes — as with x86 prefixes — would make parallel boundary discovery far harder.

3Why x8–x15

The 3-bit compressed register fields rs1', rs2', rd' encode exactly eight registers: x8 to x15. The mapping is simply x(8 + field) — an OR of a constant, not a lookup table.

FieldRegisterABI nameRole
000x8s0 / fpSaved / frame pointer
001x9s1Saved
010–111x10–x15a0–a5Argument and return registers
crux

These eight are the highest-frequency registers in compiled code — the first six arguments plus the two most-used callee-saved registers. The ABI and the compressed encoding were designed together. That is why the mapping is a constant offset and not an arbitrary permutation.

hardware consequence

The register index expansion is {1'b1, field} — one constant bit concatenated with three. Zero gates. The decompressor's register handling is free; all its real logic is in the immediates.

4Decompression — where and how

Every compressed instruction maps to exactly one 32-bit instruction. So the expander is a pure combinational function, 16 bits in, 32 bits out, with no state.

Option A — expand between fetch and decode

The standard choice. The instruction buffer presents 32 bits; if inst[1:0] ≠ 11, route the low halfword through the expander and feed the result to the single 32-bit decoder.

  • Pro: one decoder for the whole ISA. Nothing downstream of the expander knows C exists.
  • Pro: smallest area. The expander is a permutation network plus sign extension.
  • Con: serial. Expand delay adds directly to the decode path.

If timing bites, move the expander into its own pipeline stage, or duplicate the decode for the two cases and mux the control outputs at the end rather than muxing the instruction at the start.

Option B — a native 16-bit decoder in parallel

Decode the compressed form directly into control signals, alongside the 32-bit decoder, and mux the control outputs.

  • Pro: removes the serial expand-then-decode dependency. Better timing.
  • Con: two decoders to build, verify and keep consistent. Every base-ISA change must be mirrored.
  • Con: larger. Control decode is duplicated for operations that overlap.

Justifiable in a high-frequency design where the decode path is the critical path. Rarely worth it in an embedded core.

Option C — expand on cache fill

Store already-expanded 32-bit instructions in the I-cache.

this is a trap answer

It defeats the entire purpose. The point of C is that the instruction cache holds more instructions per byte. Expanding on fill means the cache holds exactly as many instructions as an uncompressed ISA, and you have paid the expander cost for nothing. Only the off-chip instruction memory benefits.

The legitimate variant is predecode on fill: store a few derived bits — instruction start markers, branch-present flags, instruction class — alongside the compressed bytes, without expanding them. That is covered under fetch hardware below.

What the expander actually contains

Three parts:

  1. Opcode synthesis. Emit the 7-bit base opcode, funct3 and funct7 as constants selected by the compressed funct3 and quadrant. Pure decode into constants.
  2. Register field placement. Either {1'b1, rs1'} for compressed fields or a straight copy for the 5-bit fields, into bit positions 19:15, 24:20 and 11:7.
  3. Immediate reassembly. The real work. RVC immediate bits are scattered to maximise density, and they do not line up with the base formats the way base immediates line up with each other.
C.LW immediate reassembly — illustrative
// C.LW  rd', offset(rs1')   offset is 5 bits, scaled by 4, zero-extended
//   inst[12:10] = offset[5:3]   inst[6] = offset[2]   inst[5] = offset[6]
wire [11:0] off = {5'b0, inst[5], inst[12:10], inst[6], 2'b00};

wire [31:0] expanded = { off,                 // 31:20  I-type immediate
                       2'b01, inst[9:7],  // 19:15  rs1' → x8+field
                       3'b010,             // 14:12  funct3 = LW
                       2'b01, inst[4:2],  // 11:7   rd'  → x8+field
                       7'b0000011 };       // 6:0    LOAD

Still no gates — it is all bit selection and constants. Across every compressed instruction the expander comes to a modest block of muxes driven by the quadrant and funct3. A few hundred gate equivalents is the usual ballpark.

5Encoding reuse across XLEN — high-value trap

The compressed opcode space is dense. Some encodings mean one thing in RV32 and something completely different in RV64.

Encoding slotRV32 meaningRV64 meaning
C1, funct3 = 001C.JALC.ADDIW
C0, funct3 = 011C.FLW (needs F)C.LD
C0, funct3 = 111C.FSW (needs F)C.SD
C2, funct3 = 011C.FLWSP (needs F)C.LDSP
C2, funct3 = 111C.FSWSP (needs F)C.FSDSP / C.SDSP
the trap question

"Is C.JAL available in RV64?" No. RV64 needs C.ADDIW — a 64-bit ISA generates far more 32-bit-result arithmetic than it generates short calls — so that slot was reallocated. The same halfword pattern decodes to a different instruction depending on XLEN. A decoder is therefore not XLEN-portable for the compressed quadrants, even though the base decoder largely is.

strong follow-up
  • "This is why a parameterised RV32/RV64 core cannot share one compressed decoder by simply widening the datapath. The compressed decode tables differ structurally, not just in width."
  • If you built a parameterised core in Hanu 1.0, say how you handled it — separate tables selected by a parameter, or RV32-only by design.
note for RV32IMAC specifically

C.FLW, C.FSW, C.FLWSP and C.FSWSP all require the F extension. RV32IMAC has no F. So in your ISA those slots are simply not implemented, and instructions using them must raise illegal-instruction. Do not claim to decode them.

6IALIGN drops to 16

the single most important consequence

Without C, IALIGN = 32: every instruction address is a multiple of 4. With C, IALIGN = 16: instruction addresses need only be even. A 32-bit instruction may therefore begin at an address that is 2 mod 4.

Everything painful about C follows from that one sentence. Consequences, in order of severity:

  1. A 32-bit instruction can span two 32-bit fetch words.
  2. It can span two cache lines.
  3. It can span two pages, and therefore two TLB entries and two permission checks.
  4. The next PC is PC+2 or PC+4, resolved from inst[1:0].
  5. Any structure indexed by PC now needs 2-byte granularity.
a consequence in your favour

Instruction-address-misaligned exceptions effectively disappear. Branch and jump immediates encode bit 0 as implicitly zero, and JALR explicitly clears bit 0 of its computed target. With IALIGN = 16, every achievable target is already legally aligned. So the cause-0 exception cannot arise. Worth saying — it shows you thought about which exceptions remain reachable.

7Straddling instructions — walk this carefully

This is the question that separates people who have built a fetch unit from people who have read about one.

A 32-bit instruction spanning a page boundary
          page N                          │  page N+1
  ... c.addi │ lw  (low half)                │ lw  (high half) │ ...
      0x0FFA   0x0FFC                      │  0x1000
                └──────── one instruction ─┴───────┘
                     starts at 0x0FFC, ends at 0x1001

  Fetch 1: 0x0FFC → page N   translation, permission check
  Fetch 2: 0x1000 → page N+1 SEPARATE translation, SEPARATE check

  If page N+1 is not mapped:
     mepc  = 0x0FFC   ← the instruction's own address
     mtval = 0x1000   ← the portion that actually faulted
memorise this pair

On an instruction access fault or instruction page fault for a straddling instruction, mepc points to the beginning of the instruction while mtval points to the portion that caused the fault. They are different values. That asymmetry exists precisely because variable-length instructions can span a boundary.

What the fetch unit must therefore do
  1. Issue two fetch requests and hold the first halfword until the second arrives.
  2. Track two sets of fault status, one per halfword.
  3. Report the fault with the instruction's start address in mepc, not the faulting halfword's address.
  4. Not commit a fault from the second half until the instruction is actually going to execute — otherwise speculative fetch-ahead across a page boundary raises spurious faults for code you never run.
the spurious-fault trap

A fetch unit that prefetches past the end of a basic block will routinely read into the next page. If it raises the page fault eagerly, a program that never executes past the branch takes a fault it should never have seen. Faults from fetch must be carried as attributes with the instruction and raised only at the point of execution. This is a genuine bug class, not a theoretical one.

8Fetch hardware

The instruction fetch buffer

The I-cache returns naturally aligned words or lines. Instructions do not align to them. So you need a buffer that decouples the two.

Aligner behaviour
  I-cache word  │ h3 h2 │ h1 h0 │    32-bit fetch = 2 halfwords

  PC = word-aligned:   instruction starts at h0
       if h0[1:0] == 11 → 32-bit, uses h0+h1, next PC = +4
       else            → 16-bit, uses h0,    next PC = +2
                          h1 is retained for next cycle

  PC = 2 mod 4:        instruction starts at h1
       if h1[1:0] == 11 → 32-bit, needs h1 + h2 from the NEXT fetch
                          → one extra cycle unless the buffer is pre-filled

Minimum viable buffer is two halfwords. Practical designs use a wider buffer — four to eight halfwords — so that the aligner rarely runs dry and a straddling instruction does not cost a bubble.

Finding boundaries in parallel

Naively, boundaries are serial: you cannot know where instruction 2 starts until you know how long instruction 1 is. That would cap fetch at one instruction per cycle.

The escape is that length depends only on the first halfword. So:

  1. For every halfword position i in the buffer, compute len16[i] = (h[i][1:0] != 2'b11). All in parallel, one gate each.
  2. Given that position k is a known instruction start, the next start is k + 1 if len16[k], else k + 2.
  3. Chain this as a prefix computation. A serial chain is O(N) in depth; a parallel-prefix formulation is O(log N).
crux

The length bits are parallel. Only the start-position chain is sequential, and that chain is a prefix problem, which parallel-prefix logic solves in logarithmic depth. That is the whole trick, and it is the answer to "how do you decode boundaries fast".

Predecode bits in the I-cache

Move the boundary scan off the critical fetch path by doing it once, on cache fill, and storing the result.

Stored bitWidthUse
Instruction start marker1 per halfwordAligner knows boundaries without scanning
Branch / jump present1 per halfwordPredictor lookup gating, early redirect
Is-compressed1 per halfwordNext-PC increment select
  • Cost: a few bits per halfword of cache data — a real but modest area and power overhead on every line.
  • Benefit: fetch-stage timing improves and the scan happens once per fill rather than once per fetch.
  • Caveat: the scan assumes entry at the line start. Code that is entered mid-line at a position the scan marked as a continuation must still work — so the aligner has to be able to treat any branch target as a valid start and re-derive from there.

For a modest embedded core, parallel scan at fetch is usually sufficient and predecode bits are not worth the storage. For a high-frequency or superscalar core, predecode is standard.

Next-PC logic
PC increment with C
// Without C: pc_next = pc + 4. One constant.
// With C:    the increment depends on the CURRENT instruction's length.

wire is_compressed = (inst[1:0] != 2'b11);
wire [31:0] pc_seq = pc + (is_compressed ? 32'd2 : 32'd4);

// And the return address for JAL / JALR follows the same rule:
// C.JALR must write pc+2, not pc+4. Getting this wrong breaks every
// compressed function call and is a classic first-silicon bug.
trap

The link value for a compressed call is PC + 2. If your expander turns C.JALR into JALR x1, 0(rs1) and the writeback path hard-codes PC + 4, every compressed call returns two bytes past where it should. The expander must carry the original length forward, or the writeback must recompute it from inst[1:0] of the pre-expansion halfword.

9Superscalar fetch with C

If Hanu 1.0 is single-issue this is a "what would you do" question rather than a "what did you do" one. Answer it anyway — it is commonly asked.

crux

With a fixed-length ISA, fetch width in bytes equals issue width times four. With C, they decouple completely. The standard architectural answer is an instruction queue between fetch and decode, so the fetch unit delivers bytes at a steady rate and the decoder consumes instructions at a variable rate.

10Branch prediction impact

StructureWithout CWith C
BTB indexPC[k:2]PC[k:1]
Entries for equal coverageN2N, or accept aliasing
Branches per fetch groupAt most width/4Up to width/2
Target alignment4-byte2-byte
Return address stackPush PC+4Push PC+2 or PC+4

Three practical points to raise:

  • Doubling the BTB is expensive. The usual compromise is to keep the index at 4-byte granularity and store a small offset field identifying which halfword within the aligned word holds the branch. Cheaper than doubling entries.
  • Branch density rises. Compressed code packs more branches into the same bytes, so predictor pressure increases even at constant instruction count per byte fetched.
  • The RAS needs the right link value. C.JALR pushes PC + 2. A RAS that assumes PC + 4 mispredicts every return from a compressed call site — and that mispredict is systematic, not random, so it shows up as a flat IPC loss.
RAS hint rules

RISC-V defines return-address-stack behaviour for JALR from whether rd and rs1 are link registers — x1 or x5. C.JR rs1 expands to JALR x0, 0(rs1), so it pops when rs1 is a link register. C.JALR rs1 expands to JALR x1, 0(rs1), so it pushes. Your predictor must apply the hint rules to the expanded form, not the compressed one.

design rule

The RVC encoding recovers space by forbidding the degenerate cases — writing x0, adding zero, moving from x0 — and reusing those slots for genuinely useful instructions. Your decoder must actively check these constraints and raise illegal-instruction. Silently aliasing a reserved encoding onto a nearby instruction is a conformance failure.

12The Zc* re-cut

C was later decomposed into finer extensions. Mentioning this signals you follow the specification, not just a textbook.

ExtensionContentsRelevance to RV32IMAC
ZcaThe base compressed set, excluding the floating-point loads and storesThis is effectively what your C means, since IMAC has no F or D
ZcfRV32 compressed single-precision FP loads and storesNeeds F. Not applicable.
ZcdCompressed double-precision FP loads and storesNeeds D. Not applicable.
ZcbExtra simple compressed ops: byte and halfword loads and stores, sign and zero extension, and a compressed multiplyUseful addition for embedded code density
ZcmpPush and pop of multiple registers, and combined pop-and-returnBig prologue/epilogue savings
ZcmtTable jump — an index into a jump-vector tableLarge code-size win for call-heavy code
the important structural point

Zcmp and Zcmt break the one-to-one rule. A push or pop instruction expands to multiple base instructions, not one. That means the decompressor is no longer a combinational 16-to-32 function — it becomes a small sequencer emitting a series of micro-operations, with all the exception and interrupt complications that implies mid-sequence. If asked "is decompression always combinational", the correct answer is "for C and Zca yes, for Zcmp and Zcmt no".

Zcmp and Zcmt also reuse the encoding space that Zcd occupies, so they are mutually exclusive with compressed double-precision loads and stores. A design must choose.

13Is C worth it?

Have both arguments ready. You may be asked to argue either side.

Keep C

Roughly 25 to 30 percent smaller static code, because typically 50 to 60 percent of instructions in ordinary integer code have a compressed form.

Smaller code means a higher effective I-cache hit rate for the same cache area, less instruction fetch traffic, less fetch energy, and less ROM or flash on a cost-sensitive part.

The expander itself is small — a permutation network. The gate cost is not the reason to drop it.

Drop C

The fetch unit gets materially harder: aligner, wider buffer, boundary scan or predecode bits, dual fault tracking, finer BTB granularity.

Straddling instructions add fetch bubbles and a two-page fault path that is easy to get wrong and hard to verify.

Verification cost is real. Every reserved encoding must be checked, and the RV32-versus-RV64 slot reuse is a portability hazard.

If the core runs from tightly-coupled SRAM with no cache and code size is not a constraint, none of the benefits apply.

a balanced answer that lands well
  • "C is worth it whenever instruction memory is a cost or a bottleneck — which is almost always in embedded. It is not worth it if you are fetch-bandwidth limited at high frequency and have plenty of instruction memory, because then you pay all the alignment complexity for a benefit you do not need."
  • Then give your own number: what did compression actually do to your binary size in Hanu 1.0?

The 25–30 percent and 50–60 percent figures are the commonly quoted ranges from the specification's own commentary. Present them as ranges, and better still, quote your own measurement.

15Interview Q&A

Where did you put the decompressor, and why there?

Between the fetch buffer and the decoder, so one 32-bit decoder serves the whole ISA and nothing downstream knows C exists. That is the smallest option and the easiest to verify.

The cost is that expansion delay sits in series with decode. If that path had failed timing, the next step would be to compute both the compressed and uncompressed control decodes in parallel and mux the control signals at the end, rather than muxing the instruction at the start — same area penalty as a second decoder but only on the paths that matter.

What I would not do is expand on cache fill. That stores 32-bit instructions in the I-cache and throws away the entire density benefit.

Your fetch unit prefetches ahead. How do you avoid spurious page faults?

Faults from fetch are carried as attributes attached to the fetched bytes, not raised at fetch time. The fetch buffer holds, per entry, the instruction bytes plus a fault status and cause. The fault is only converted into an architectural trap when that instruction reaches the point of execution.

This matters most at page boundaries. A prefetch that runs past a taken branch and into an unmapped next page must not trap — the program never executes there. The same mechanism handles the straddling case: the second halfword's fault status travels with the instruction and is raised with mepc set to the instruction's start.

The corollary is that the fetch buffer must be flushed on redirect, and flushing must discard pending fault status along with the bytes.

Does C change the register file or the execution units at all?

No. That is the key property. Every compressed instruction expands to exactly one existing base instruction, so by the time control signals reach the execute stage, the pipeline is identical to a non-C core.

The only thing that must travel downstream is the instruction's length, because the link value for a compressed call is PC+2 and the sequential next-PC is PC+2. So one extra bit rides along the pipeline.

The exception is Zcmp and Zcmt, which do expand to multiple instructions and therefore do change the front end into a sequencer. Base C does not.

How would you verify the C extension?

Three layers. First, exhaustive expansion checking: there are only 216 compressed encodings, so sweep all of them through the expander and compare against a reference expansion table, including which ones must be flagged illegal. That is a small, complete, mechanically checkable proof.

Second, directed alignment tests: a 32-bit instruction at every offset within a cache line, instructions straddling a line boundary, instructions straddling a page boundary with the second page unmapped, and branch targets landing at 2 mod 4.

Third, random mixed-length instruction streams with the boundary scanner compared against a software model, plus RISC-V compliance suites.

The exhaustive expander sweep is the one people forget, and it is the cheapest complete check available anywhere in a core.

Convince me that C hurts more than it helps in a high-frequency core.

At high frequency the front end is usually the constraint, and C adds work to exactly that stage: a rotator on the cache output, a boundary scan or the area and power of predecode bits, a deeper fetch buffer, and expansion before decode. All of it sits on the fetch-to-decode path you are trying to shorten.

Meanwhile the benefit is instruction memory density, which matters when the I-cache is small or off-chip fetch is expensive. A high-frequency core typically has a generous I-cache and a prefetcher, so the marginal hit-rate gain is small.

Add the straddling fault path, which is a verification liability, and the BTB granularity problem, and the balance can genuinely tip.

I would qualify it, though: the counter-argument is that fetch bandwidth in bytes is fixed, so compressed code delivers more instructions per fetch — which helps a wide machine rather than hurting it. The honest position is that it depends on whether your front end is limited by bytes or by boundaries.

17Recap

  • Three quadrants selected by inst[1:0]; funct3 at inst[15:13] selects within each.
  • Compressed register fields cover x8–x15 — the ABI's hottest eight. Index expansion is free.
  • Every C instruction expands 1:1 to one base instruction. No new state, no new operations.
  • Expand between fetch and decode. Never expand on cache fill.
  • RV32 and RV64 reuse compressed slots differently. C.JAL becomes C.ADDIW; C.FLW becomes C.LD.
  • IALIGN becomes 16. Everything hard follows from that.
  • Straddling instruction fault: mepc is the instruction start, mtval is the faulting portion.
  • Fetch faults must be carried as attributes and raised at execution, never eagerly.
  • Length depends only on the first halfword, so boundary scan is a parallel-prefix problem.
  • BTB granularity becomes 2-byte. C.JALR pushes PC+2 onto the return stack.
  • Zcmp and Zcmt break the 1:1 rule and turn the expander into a sequencer.
