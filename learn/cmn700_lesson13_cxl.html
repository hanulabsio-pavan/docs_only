CXL Deep Dive — Sub-Protocols, Device Types & Pooling

Past “host-based coherency”: the three sub-protocols, the three device types, why bias modes exist, and how CXL memory becomes just another SAM target.

By the end of this lesson you can

  • Distinguish CXL.io, CXL.cache and CXL.mem and say which direction each serves.
  • Classify Type 1, Type 2 and Type 3 devices by sub-protocol usage.
  • Explain host and device bias, and why bias flipping exists.
  • Describe how CXL-attached memory reaches the mesh through the gateway and SAM.

1Past the coherency model

caveman mode

Lesson 8 said "CXL is host-based coherency." True but not enough. Real question interviewer ask: which CXL? Device with cache but no memory? Device with own memory? Plain memory box? Each use different mix of three sub-protocols. Learn the three, learn the three types, and it all click.

Lesson 8 established the contrast that matters most — CXL resolves coherency host-side, whereas CCIX resolves it near the memory. That is the right first answer. But CXL is not one thing, and a follow-up question will usually go straight to which flavour you mean.

The whole structure follows from a simple observation: a device attached over a coherent link might want to cache the host's memory, or expose its own memory to the host, or both, or neither. Three sub-protocols cover those needs, and three device types are just the useful combinations.

2The three sub-protocols

Sub-protocolDirectionWhat it does
CXL.io—The PCIe-based foundation: discovery, enumeration, configuration, register access, interrupts, plain DMA. Every CXL device uses it — it is how the device is found and set up.
CXL.cacheDevice → host memoryLets the device cache host memory coherently. The device becomes a caching agent that the host must keep coherent, so the host snoops it.
CXL.memHost → device memoryLets the host access memory attached to the device as if it were ordinary system memory. The device is the memory target.
The two coherent sub-protocols point in opposite directions
                 HOST                       DEVICE
                   |                            |
   CXL.io      |<--- discovery / config / DMA --->|   always present
                   |                            |
   CXL.cache   |<--- device caches HOST memory ---|   device is a cache
                   |      host must snoop it      |
                   |                            |
   CXL.mem     |--- host reads DEVICE memory --->|   device is memory
                   |                            |

Keeping the two coherent ones straight is the whole game: CXL.cache is the device reaching into host memory; CXL.mem is the host reaching into device memory. Opposite directions, different implications for who tracks coherency.

3The three device types

The types are simply which sub-protocols a device uses:

TypeSub-protocolsHas device memory?Typical device
Type 1CXL.io + CXL.cacheNoA coherent accelerator or smart NIC that caches host memory but exposes none of its own.
Type 2CXL.io + CXL.cache + CXL.memYesA full accelerator — GPU or ML accelerator — with its own memory, which both caches host memory and exposes its own to the host.
Type 3CXL.io + CXL.memYesA memory expander or buffer. No device cache; it is memory the host consumes.

Note what is absent: there is no type using CXL.io alone, because that would just be a PCIe device. And Type 3 has no CXL.cache because a memory box has nothing to cache — it is the memory.

Type 1 — cache only

Needs to be snooped by the host. Simplest coherency footprint, but adds a remote caching agent.

Type 2 — both

The most complex: a caching agent and a memory target. Bias modes exist for this case.

Type 3 — memory only

The memory-capacity and pooling workhorse. No device cache means no snooping into the device.

4Bias modes — the Type 2 problem

caveman mode

Accelerator has own memory. Accelerator want to chew on it fast, thousands of times. If every access must ask host "may I? is anyone else holding this?" → slow, pointless. So: flip a switch. Device bias = "this memory is mine right now, I work alone, no asking." Host bias = "host may be looking, go through coherency." Flip when handing work over.

A Type 2 device owns memory that the host can also access coherently. That creates a tension: while the accelerator is computing over its own memory, routing every access through host coherency would add latency for no benefit. Bias modes resolve it:

ModeWho effectively owns itUse
Host biasHost coherency governsThe host is reading or writing the region — typically while staging input or collecting results. Device access pays coherency cost.
Device biasDevice operates locallyThe accelerator is working on the region and the host is not touching it. Device accesses avoid host coherency overhead.

The transition between them — bias flip — is the synchronisation point: it happens at the handover between host and device phases of a computation. The mental model is a baton pass rather than continuous shared access.

Interview framing: bias exists because coherency has a cost, and sometimes nobody needs it. That is a more sophisticated point than reciting the two mode names.

5Host-managed device memory

Memory a device exposes via CXL.mem is host-managed device memory (HDM). The wording matters: the memory is physically on the device, but it is mapped into the host's physical address space and managed by the host. Software sees system memory; it happens to live across a link.

Consequences to be able to state:

  • It occupies host physical address space, so it must be discovered and mapped at configuration time.
  • It has different performance characteristics from directly-attached DRAM — higher latency, and bandwidth bounded by the link. This is a NUMA problem, and software placement matters.
  • For Type 3 devices this is the entire point: capacity expansion beyond what the host's own memory channels can provide.

6How this reaches the CMN-700 mesh

Now connect it to the machinery from Lessons 5 and 8. The gateway is the CCG, whose internal agents map neatly onto the two coherent sub-protocols:

This is the satisfying part: nothing new is needed in the addressing model. Lesson 5 said the RN SAM maps an address to a target ID and that a target can be a CCG for remote memory. CXL memory expansion is exactly that case. And where memory is shared across dice or devices, the Super Home Node from Lesson 8 can act as the central coherency point.

7Pooling, switching and sharing

Later CXL generations add topology beyond one host and one device:

  • Switching lets multiple devices sit behind a switch rather than being point-to-point, which is what makes fabric-like topologies possible.
  • Pooling lets a memory device's capacity be divided among several hosts, each getting a portion. The economic driver: stranded memory. In a conventional server, memory bought for one machine cannot help a neighbouring machine that needs it. Pooling turns memory into an allocatable resource.
  • Sharing — multiple hosts coherently accessing the same region — is the harder step, and the one with the most demanding coherency requirements.

Exact capabilities are versioned across CXL 1.1, 2.0 and 3.x, and which are supported depends on both the CXL revision and the interconnect release. Speak about the capability progression confidently, and confirm specific version support in the TRM and CXL specification rather than asserting it.

10Interview Q&A

What are the three CXL sub-protocols?
CXL.io is the PCIe-based foundation used by every device for discovery, enumeration, configuration, interrupts and plain DMA. CXL.cache lets the device cache host memory coherently, which makes the device a caching agent the host must snoop. CXL.mem lets the host access memory attached to the device as if it were system memory. The two coherent ones point in opposite directions, and that is the distinction to keep clear: CXL.cache is the device reaching into host memory, CXL.mem is the host reaching into device memory.
Explain the three device types.
They are just which sub-protocols a device uses. Type 1 is CXL.io plus CXL.cache: an accelerator or smart NIC that caches host memory but exposes none of its own. Type 2 adds CXL.mem: a full accelerator with its own memory that both caches host memory and exposes its own, which is the most complex case and the one bias modes exist for. Type 3 is CXL.io plus CXL.mem with no device cache: a memory expander or buffer, which is the pooling and capacity-expansion workhorse. There is no CXL.io-only type, because that would simply be a PCIe device.
What are bias modes and why do they exist?
They apply to Type 2 devices, which own memory the host can also access coherently. Under host bias, host coherency governs the region, which suits phases where the host is staging input or collecting results. Under device bias, the device operates on its own memory locally without paying host coherency overhead, which suits the compute phase. The transition, a bias flip, is the synchronisation point at handover between phases. The underlying insight is that coherency has a cost and sometimes nobody needs it — so the model is a baton pass rather than continuous shared access.
How does CXL-attached memory integrate with the CMN-700 mesh?
Through the CCG gateway, and crucially it needs no new addressing model. The RN SAM maps a physical address to a target ID, and a target can be a CCG for remote memory — CXL memory expansion is exactly that case. A core's request routes across the mesh to the gateway, where the CCHA represents the remote memory locally, and the CCLA drives the link. In the other direction, a remote device caching host memory is proxied into the local mesh by the CCRA so local home nodes treat it as a participant to snoop. Where memory is shared across dice or devices, a Super Home Node can serve as the central coherency point.
What is host-managed device memory, and what is the catch?
Memory physically resident on the device but mapped into the host's physical address space and managed by the host, exposed through CXL.mem. Software sees system memory that happens to live across a link. The catch is performance asymmetry: latency is higher and bandwidth is bounded by the link, so it is a NUMA problem and software placement matters. For Type 3 devices that trade is the entire point — capacity beyond what the host's own memory channels can provide, accepting slower access for more of it.
Why is memory pooling economically interesting?
Stranded memory. In a conventional server, DRAM bought for one machine cannot help a neighbouring machine that needs it, so fleets are provisioned for peak per-node demand and much of that capacity sits idle. Pooling lets a device's capacity be divided among several hosts, turning memory into an allocatable resource. Sharing, where multiple hosts coherently access the same region, is the harder step with the most demanding coherency requirements. Which of these is available depends on the CXL revision, so I would confirm specific version support rather than assume it.

11Recap & key terms

  • CXL.io always present (PCIe-based: discovery, config, DMA).
  • CXL.cache = device caches host memory. CXL.mem = host accesses device memory. Opposite directions.
  • Type 1 io+cache (no device memory) · Type 2 all three (accelerator + memory) · Type 3 io+mem (memory expander).
  • Bias modes (host / device, with bias flip) let a Type 2 device skip coherency cost during local compute.
  • HDM = device memory mapped into host address space — a NUMA tier, not free capacity.
  • On the mesh: CCRA proxies a remote caching device; CCHA represents remote memory; the RN SAM simply targets the CCG.
  • Pooling addresses stranded memory; sharing is harder. Confirm version support in the specs.
