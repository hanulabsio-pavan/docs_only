Advantages & Comparison with x86 and Arm

The comparison everyone asks for, done honestly: where the three architectures genuinely differ, where the differences are folklore, and which ones will actually break your code when you port.

By the end of this lesson you can

  • Separate real architectural differences from microarchitectural and business ones.
  • Rank the three memory models and name the litmus test that distinguishes each pair.
  • Explain why Power is non-multi-copy-atomic and why that is the sharpest difference of all.
  • Read the same function in three assembly languages and name what each ISA is optimising for.
  • State honestly where Power wins, where it loses, and what to check when porting.

1How to compare fairly

caveman mode

People argue "RISC beats CISC". Argument is 30 years stale. Modern x86 chip translates its complicated instructions into simple ones inside anyway. Real differences left: how many registers, how strict is memory ordering, who owns the spec, who ships the chips.

Three categories of difference, and only one of them is architecture:

CategoryExamplesDoes it affect your code?
ArchitecturalRegister count, encoding, memory ordering model, addressing modes, privilege structureYes. Correctness and portability live here.
MicroarchitecturalPipeline width, cache sizes, branch predictors, SMT degree, clockPerformance only, and it varies more within an architecture than between them.
CommercialLicensing, who ships silicon, toolchain maturity, distro support, priceOften decisive in practice — and nothing to do with the ISA's technical merit.

The "RISC vs CISC" framing belongs to the second and third categories more than the first. Every modern high-performance x86 core decodes into internal micro-operations that look RISC-like; every modern Arm and Power core is a wide out-of-order machine with the same structural ingredients. What is left of the original argument is decode complexity — real, but a fixed overhead rather than a per-instruction one.

4Memory ordering — the difference that actually breaks code

  
If you remember one thing from this lesson, make it this. Register counts and encoding are aesthetics; the memory model is the thing that silently corrupts data on one architecture and not another.


  
The three models, strongest to weakest


  x86-64  —  TSO (Total Store Order)
     Only store→load may be reordered. Everything else is in order.
     Multi-copy atomic: a store becomes visible to all cores at once.
     → sloppy code often works by accident.

  AArch64  —  weak, but multi-copy atomic (revised in 2018)
     Loads and stores reorder freely without barriers or dependencies.
     BUT a store still becomes visible to all other cores together.
     → catches most missing barriers; still one global store order.

  Power  —  weak AND non-multi-copy atomic
     Loads and stores reorder freely, and two stores by different
     threads can be observed in different orders by different cores.
     → there is no single global order of stores to reason about.



  
That last property is the sharpest architectural difference between Power and both of its rivals, and it is worth stating precisely:


  
the deep difference
  
Power is non-multi-copy-atomic. On x86 and on modern Arm, if two threads each write to a different variable, every other thread agrees on which write happened first — there is one global order. On Power there need not be: core A may observe X before Y while core B observes Y before X, even though neither reordered anything locally. This is not fixable with dependencies or with lwsync; it needs the full sync. Arm was also like this before its 2018 revision to a multicopy-atomic model — Power is now one of the few mainstream architectures that still isn't.

The historical point worth carrying: x86 was not classically virtualisable — a set of instructions behaved differently in ring 3 without trapping, which is why early VMware had to do binary translation and why VT-x exists. Power and Arm both put a real hypervisor level in the architecture, so the same problem never arose. That is a genuine architectural advantage for Power, and one of the older ones.






  
7Code density, decode, and what "RISC" costs

  

    
x86-64
Variable length, 1–15 bytes. Best code density — a common operation can be two bytes. The cost is a serial decode problem: you cannot find instruction n+1 until you have decoded n, so wide decode needs expensive predecode and length-marking hardware, and micro-op caches exist partly to skip decode entirely.

    
Power
Fixed 32-bit (plus optional 64-bit prefixed in v3.1). Decode is trivially parallel — every 4-byte boundary is an instruction. Density is worse than x86; building a 64-bit constant historically took several instructions, which is exactly what prefixed instructions address.

    
AArch64
Fixed 32-bit, same decode advantage. Somewhat better density than Power in practice thanks to richer immediate encodings and addressing modes — but it dropped the Thumb-style compressed encoding that made AArch32 dense.

  


  
Where the fixed-width choice really pays is not decode speed in isolation but everything downstream: branch target alignment, instruction cache utilisation predictability, trace and debug hardware, and the ability to scale decode width without a quadratic cost. Where it costs is I-cache footprint — and with a 48 KB L1I on POWER10, IBM clearly decided to spend area rather than density.


  
caveman mode
  
x86 words different lengths — book smaller, but reader must read each word to know where next starts. Power and Arm words all same length — book bigger, but ten readers can start at ten places at once. Modern chips want many readers.

9Where Power actually wins

  

    
Per-socket throughput
SMT8, very large shared L3, and high memory bandwidth. For a large database or analytics workload that is bottlenecked on memory and thread count rather than single-thread latency, one Power socket does a lot of work.

    
RAS
Reliability, availability, serviceability inherited from mainframe practice: extensive error detection and correction, predictive failure analysis, spare cores that can be substituted at manufacture, and processor recovery. This is a genuine and under-discussed differentiator for the systems Power targets.

    
Virtualisation maturity
Partitioning has been architected since 2001, not retrofitted. PowerVM's live partition mobility and fine-grained resource allocation reflect twenty years of the hypervisor being part of the machine rather than a layer on top.

    
Coherent accelerator attach
CAPI, OpenCAPI, PowerAXON and (on POWER9) NVLink 2.0 let accelerators share virtual addresses and participate in coherence. Summit and Sierra were built on exactly that.

    
Numerics heritage
FMA since 1990, hardware decimal floating-point, hardware IEEE binary-128, and MMA. For financial and scientific arithmetic the FPU is a genuine strength rather than a checkbox.

    
Licensing
The only one of the three you can implement, extend and ship with no fee and no architecture licence — while still getting a thirty-year-hardened server ISA rather than a young one.

  






  
10Where it does not

  

    
Ecosystem breadth
Many projects ship x86-64 and aarch64 binaries and nothing else. Container images, proprietary tools, game engines, ML frameworks with vendor kernels — the long tail is thin, and building from source is a tax that compounds.

    
Silicon availability
Practically, IBM is the source for high-end parts, and machines are expensive. There is no equivalent of the dozens of Arm licensees producing parts at every price point.

    
The memory model is a porting hazard
Being weaker and non-multi-copy-atomic means concurrency bugs latent on x86 become real failures on Power. That is technically defensible — the bugs were always there — but it costs engineering time and it feels like the platform's fault.

    
Encoding space is largely spent
Thirty years of allocation left little room for extension, and there is no reserved custom opcode region the way RISC-V has. Prefixed instructions relieve this but do not reset it.

    
Power and thermals at the low end
The architecture is fine, but the implementations are aimed at high-throughput servers. There is no mature low-power Power core competing with Cortex-M or Cortex-A class parts.

    
Mindshare
Fewer engineers have written Power assembly than x86 or Arm, which shows up in library tuning, in how quickly bugs are found, and in hiring.

  


  
A fair summary: Power is technically competitive and commercially niche. Choosing it is usually driven by an existing AIX or IBM i estate, by a specific need for RAS or coherent accelerator attach, or by wanting an open server-class ISA — rarely by raw price-performance against a commodity x86 or Arm server.






  
11Porting checklist: x86 or Arm → Power

  
In rough order of how often each one actually bites:

  

    
#CheckWhy

    
1Memory barriers in lock-free codeAnything relying on x86's TSO will break. Use C11/C++11 atomics or the kernel's primitives rather than hand-rolled barriers; if you must hand-roll, remember lwsync does not order store→load and does not fix multi-copy-atomicity issues.

    
2Endianness assumptionsppc64le is little-endian, so most code is fine — but code carrying a legacy big-endian Power path, or reading binary formats with hand-rolled byte handling, needs review.

    
3Cache line size128 bytes, not 64. Padding constants and false-sharing avoidance must use a cache-line constant, not a literal.

    
4Intrinsics and inline assemblySSE/AVX and NEON intrinsics have no automatic equivalent. Either use a portable wrapper layer or write VSX paths; x86intrin-compat shims exist but are partial.

    
5char signednessPlain char is unsigned on Power by default and signed on x86 — a classic source of quiet behavioural differences.

    
6long doubleOn ppc64le this may be IBM double-double or IEEE binary128 depending on the toolchain and distribution. It is an ABI-visible choice.

    
7Self-modifying or generated codeJITs need dcbst / sync / icbi / isync. x86 keeps I- and D-caches coherent for you; Power does not.

    
8Unaligned accessGenerally works, but performance varies and some instructions require alignment. Do not assume it is free.

    
9Timing and RNG assumptionsrdtsc has no direct equivalent — use the time base. Anything reading a cycle counter needs a portability layer.

    
10Build baselineDecide the target ISA version and subset explicitly (-mcpu=power9 vs power10). Building for POWER10 and deploying to POWER9 gives illegal-instruction traps.

  


  
caveman mode
  
Number one is always memory barriers. Bug was there on x86 too, x86 just hid it. Power does not hide it. Blame the code, not the chip — but budget the week anyway.

13Interview Q&A

  
Compare Power, x86-64 and AArch64 in a minute.
All three are 64-bit, out-of-order in their high-performance implementations, and much more alike than the RISC-versus-CISC framing suggests. Encoding: x86 is variable 1–15 bytes and denser; Power and AArch64 are fixed 32-bit and decode in parallel. Registers: 16 GPRs on x86-64, 31 on AArch64, 32 on Power plus 64 128-bit VSRs. Memory model: x86 is TSO, AArch64 is weak but multicopy-atomic, Power is weak and non-multi-copy-atomic — the weakest of the three. Privilege: rings plus VMX on x86, four exception levels on Arm, four MSR-selected states on Power. Commercially: x86 is closed, Arm is licensed, Power is open and royalty-free.

  
What does non-multi-copy-atomic mean and why does it matter?
It means there is no single global order in which stores become visible. Two threads writing to different variables can be observed in one order by one core and the opposite order by another, even though neither core reordered anything locally. On x86 and on ARMv8 since its 2018 revision, a store becomes visible to all other cores together, so there is one global store order to reason about. On Power there isn't. Practically it means some scenarios cannot be fixed with dependencies or with lwsync — they need the full sync — and it makes Power the hardest of the three to reason about in lock-free code.

  
Walk me through the SB and MP litmus tests.
SB — store buffering: two threads each store to their own variable then load the other's. The outcome where both loads return 0 is allowed on all three architectures, because even TSO permits store→load reordering. It's the one case x86 doesn't protect you from, and on Power you need a full sync between the store and the load because lwsync doesn't order store→load. MP — message passing: one thread writes data then sets a flag; the other reads the flag then the data. Seeing the flag set but stale data is forbidden on x86 by TSO but allowed on Power and Arm. It's the classic publish pattern and the single most common thing that breaks when porting from x86.

  
Is RISC still meaningfully different from CISC?
Not in the way the term implies. Modern x86 cores decode into internal micro-ops and run a wide out-of-order machine that looks structurally like a Power or Arm core, and all three have accumulated complex SIMD and crypto instructions. What survives is decode: variable-length encoding forces serial length determination, so wide decode needs predecode hardware and micro-op caches, which is a real fixed cost in area and power. Fixed-width encoding makes decode trivially parallel at the price of code density. That's a genuine engineering trade-off, but it's a much narrower claim than the original argument.

  
You're leading a port of a large C++ service from x86 to Power. What's your plan?
Memory ordering first — audit every hand-rolled lock-free structure and push it onto C++11 atomics with explicit orderings, because x86's TSO has been hiding real bugs. Then the mechanical items: cache-line padding constants from 64 to 128 bytes, plain char signedness, long double representation, and any SSE or AVX intrinsics that need VSX equivalents or a portable wrapper. Then anything generating code at runtime, which needs I-cache synchronisation. Then decide and pin the build baseline — POWER9 versus POWER10 — so you don't ship illegal instructions to older machines. Throughout, run with thread sanitisers and stress on real multi-socket hardware, because the ordering failures are load-dependent and won't show up on a laptop.

  
Where would you genuinely choose Power today?
Three cases. An existing AIX or IBM i estate, where the migration cost dominates any architectural comparison. Workloads that are memory-bandwidth and thread-count bound rather than single-thread bound — large databases and analytics — where SMT8, the very large shared L3 and the memory subsystem pay off per socket. And situations needing either serious RAS or coherent accelerator attach, which is exactly the combination that made Summit and Sierra work. What I wouldn't choose it for is general commodity compute on price-performance, or anything needing a broad supply of prebuilt binaries.

  
What does Power's openness actually get you that RISC-V doesn't?
Maturity. You inherit a thirty-year-old server architecture with a hypervisor model that has been in production since 2001, a hardened memory model with a full formal specification, decimal and quad floating-point, and mainline support in GCC, LLVM, glibc and Linux. RISC-V gives you a cleaner slate, reserved custom opcode space, and a much larger and faster-moving open ecosystem, but you're building on a younger foundation. The flip side is Power's encoding space is largely spent and governance is still IBM-led, so it's "mature architecture made free" versus "free architecture growing up".

  
Why does Power have 8 condition register fields when x86 and Arm each have one flags register?
To avoid a single serialising resource. With one flags register every comparison clobbers the previous one, which forces branches to sit close to their compares and creates false dependencies in an out-of-order machine. Power's eight independent CR fields let a compiler evaluate several conditions early, combine them with crand/cror, and branch once — and because flag writing is opt-in via the Rc bit, ordinary arithmetic creates no dependency at all. Arm made a partial version of the same choice with conditional-compare instructions and csel; x86 mitigated it in hardware with flags renaming instead.
