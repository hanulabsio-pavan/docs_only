Compliance Levels & Design Flexibility

A 1,300-page specification is not something you implement on a weekend. The compliancy-subset model is what makes an open Power ISA actually buildable — and it is the single most important thing v3.0 added for anyone outside IBM.

By the end of this lesson you can

  • Explain why "implement everything" was a barrier and what replaced it.
  • Name the Base architecture, the four compliancy subsets, and what each is aimed at.
  • Decide which subset a given design should target, and what software that unlocks.
  • Distinguish the old category mechanism from the current subset mechanism.
  • Describe how the ISA is changed — the TWG, the RFC process, and the rules for extensions.

1The all-or-nothing problem

caveman mode

Old rule: to say "my chip is Power", must build everything — decimal maths, vectors, hypervisor, transactional memory. Small team cannot. So nobody outside IBM built one. New rule: build the mandatory core plus one named tier. Now small team can, and still say "Power" honestly.

Power ISA describes a full server architecture. Taken literally, a compliant implementation would need scalar and vector floating-point, decimal floating-point, 64 VSX registers, transactional memory, a hypervisor mode, two MMU designs, and hundreds of storage-control instructions. For an FPGA softcore or a microcontroller-class part, that is not a high bar — it is an impossible one.

The result before v3.0 was a fork in practice: everyone building small Power cores implemented "PowerPC-ish" subsets and described compliance informally. That is bad for everyone — software cannot know what it may assume, and vendors cannot make a claim that means anything.

Version 3.0 fixed this by making partial implementation a first-class, named, testable thing. The question changed from "are you compliant?" to "which subset are you compliant with?" — and that second question has a checkable answer.

2The model: Base + one subset + optional features

How compliance is composed

   │  BASE ARCHITECTURE  — mandatory for every implementation    │
   │  32 GPRs · 32-bit fixed instructions · load/store ·         │
   │  branch & CR model · the storage/ordering model ·           │
   │  interrupt framework · privilege framework                 │
   └────────────────────────────────────────────────────────────┘

Three rules make this work:

  • The Base is non-negotiable. Register model, instruction encoding, memory ordering, the interrupt mechanism. Everything a compiler and an OS assume without asking.
  • You claim exactly one subset, and the subsets nest: satisfying ACS implies satisfying LCS, and so on down.
  • Optional facilities are all-or-nothing individually. You may omit VSX entirely, but you may not implement "most of" VSX — partial facilities are what fragment an ecosystem.
the important rule

Omitting a facility is legal; implementing it wrongly or partially is not. This is what keeps the model from degenerating. Software can test for a facility once — via the ELF hardware capability bits on Linux, or the PVR and feature registers — and then rely on it completely. A "90% VSX" implementation would force every library to probe every instruction, which is exactly the failure mode the subset model exists to prevent.

3The four compliancy subsets

SubsetRoughly meansAimed atRough scale
SFS
Scalar Fixed-point Subset		 Integer scalar core. No floating-point required at all. Deeply embedded controllers, minimal FPGA softcores, sequencers Smallest useful Power core
SFFS
Scalar Fixed-point + Floating-point Subset		 Adds scalar binary floating-point. Still no vector requirement. Microcontroller-class parts, teaching cores, Microwatt-class designs A capable general-purpose core
LCS
Linux Compliancy Subset		 Everything a mainstream Linux kernel and userspace actually depend on. Open Linux-capable SoCs, application processors Needs an MMU, full privilege model, atomics
ACS
AIX Compliancy Subset		 The full server-class surface AIX and IBM i depend on. IBM POWER-class server processors Essentially the whole architecture

The jump that matters most in practice is SFFS → LCS. That is the boundary between "a core that runs firmware or an RTOS" and "a core that boots Linux". Crossing it means committing to a real MMU, the full interrupt and privilege model, and the atomic primitives the kernel's locking depends on — a substantial engineering step, and the reason most hobby and academic Power cores sit at SFFS.

5Optional facilities in practice

Above the subset line, facilities are independent choices. Each is discoverable by software, and each has a real cost in area and verification effort.

How software finds out

On Linux, the kernel publishes a bitmask through the ELF auxiliary vector — AT_HWCAP and AT_HWCAP2 — with entries such as PPC_FEATURE_HAS_VSX, PPC_FEATURE2_ARCH_3_00 and PPC_FEATURE2_ARCH_3_1. Libraries use IFUNC resolvers to select a VSX or scalar implementation of a function once, at load time, rather than branching per call. Below the OS, the PVR (Processor Version Register) identifies the implementation, and firmware device-tree properties describe what is present.

This is the practical payoff of "all-or-nothing per facility": glibc can bind memcpy to a VSX variant once and never check again.

6From categories to subsets — the history

The subset model was not the first attempt. Versions 2.03 through 2.07 used categories, a legacy of the 2006 merge: the spec was tagged so that Server, Embedded, Vector, VSX, Floating-Point and others could be included or excluded, and an implementation declared which categories it supported.

Categories (v2.03–v2.07)

Orthogonal, fine-grained tags scattered through the document. Flexible in principle — but the combinations were effectively unbounded, so "which categories?" produced a long answer that software could not reason about simply.

Subsets (v3.0 onward)

A small number of named, nested, ordered tiers, plus independent optional facilities. "Which subset?" has four possible answers, and each one implies a concrete set of guarantees.

The design lesson is worth stating plainly, because it generalises well beyond Power: fine-grained configurability produces a combinatorial explosion that nobody can target. A small number of named tiers, each meaning something concrete to software, is far more useful than an arbitrary feature matrix — even though it is strictly less expressive. The category mechanism has not vanished from the document, but subsets are the mechanism that actually gets used.

7Case study: Microwatt

Microwatt is IBM's open-source Power ISA core, written in VHDL and released alongside the 2019 open-sourcing. It exists precisely to demonstrate that the subset model works.

Roughly what a small open Power core looks like
   IMPLEMENTED                          OMITTED
   ├─ 64-bit Base architecture           ├─ VMX / VSX vector units
   ├─ 32 GPRs, full fixed-point set      ├─ MMA
   ├─ scalar floating-point              ├─ decimal floating-point
   ├─ branch / CR / CTR / LR model       ├─ transactional memory
   ├─ load/store incl. atomics           ├─ hypervisor state
   ├─ interrupts and privilege           └─ most storage-control instructions
   └─ an MMU sufficient to boot Linux

   Result: a legitimately Power-compliant core, small enough to fit a modest
   FPGA, that boots real software — without implementing a server architecture.

Two things about Microwatt are instructive beyond the core itself:

  • It is readable. A few thousand lines of VHDL implementing a real ISA is a genuinely good way to learn processor design — far more approachable than any commercial RTL.
  • It proves the licensing claim. A core that anyone can build, extend and ship without an architecture licence is the concrete demonstration that "open" means something here.

The family also includes Chiselwatt (the same idea in Chisel) and IBM's larger opened A2I and A2O server cores, which sit much higher up the subset ladder.

8Extending the ISA — and how not to

Open does not mean unconstrained. If everyone adds instructions in whatever encoding space they like, the ecosystem forks and the openness becomes worthless.

The encoding-space constraint

This is where Power differs sharply from RISC-V, and it is an honest weakness. RISC-V reserved custom opcode space from day one, so a vendor extension has a defined home that will never collide with a future standard extension. Power's 32-bit encoding has been filled in over thirty years — primary opcode 31 alone carries hundreds of extended opcodes — so there is far less free space, and adding instructions requires care and coordination rather than a private corner.

  • Unallocated encodings are reserved, not free: an implementation should treat them as illegal (raising a Program interrupt), because a future revision may define them.
  • v3.1's prefixed encoding did open genuine new space — an 8-byte instruction has room that a 4-byte one does not — which is part of why it matters strategically, not just for 34-bit displacements.
  • The practical guidance for anyone extending Power is to go through the RFC process rather than squatting on encodings, precisely because the alternative is a fork nobody's toolchain supports.
caveman mode

Spec is shared village map. Anyone may propose new building — but must ask council, or two people build on same plot and both houses fall. RISC-V left empty field for private huts. Power's land mostly used already, so must ask.

9What the ISA deliberately leaves to the implementer

Subsets are about which architecture you implement. Separately, the architecture leaves an enormous amount to the microarchitect — this is the Lesson 1 point, made concrete.

Two related ideas that are easy to conflate but must not be:

  • Subsets change what software may assume exists. Getting this wrong means an illegal-instruction trap.
  • Microarchitecture changes how fast software runs. Getting this wrong means a slow program, not a broken one.

10The honest trade-off

Subsets solve a real problem, and they create a real one. It is worth being able to argue both sides.

What it buys

Small implementations become possible and legitimate. Vendors can make a compliance claim that is testable. Software gets a small number of tiers to target rather than an unbounded feature matrix. The open-source promise becomes actionable rather than theoretical.

What it costs

"Power ISA" no longer names one thing. A binary built for a POWER10 will not run on an SFFS core. Distributions must pick a baseline — which is why ppc64le Linux effectively targets POWER8 or POWER9 as a floor, and why the useful question is always "which subset, which optional facilities, which ISA version?"

Every configurable ISA faces this, and each answers it differently: Arm ships profiles (A/R/M) and architecture versions; RISC-V ships an extension-letter soup plus curated profiles (RVA23 and similar) precisely because the soup proved unmanageable. Power's four ordered tiers are on the conservative end of that spectrum — less expressive, harder to fragment.

practical consequence

When someone says "it runs on Power", that is not yet a complete statement. The complete statement names the ISA version (v3.0? v3.1?), the subset, and the optional facilities assumed — and for distribution binaries, the baseline the toolchain targeted. Getting this wrong is how you ship a binary that dies with an illegal-instruction trap on a customer's older machine.

12Interview Q&A

Explain Power's compliancy-subset model.
From v3.0, an implementation must provide the Base architecture — the register model, 32-bit fixed encoding, load/store and branch semantics, the storage and ordering model, and the interrupt and privilege framework — plus exactly one named compliancy subset, plus any optional facilities it chooses. The subsets nest in order: SFS is integer-only, SFFS adds scalar floating-point, LCS is what mainstream Linux needs, and ACS is the full server surface AIX depends on. Optional facilities like VSX, MMA, DFP, transactional memory and the hypervisor sit above that and are individually all-or-nothing.
Why was this added, and why does it matter for open hardware?
Because "implement the whole specification" is an impossible bar for anything smaller than a server processor, so partial implementations existed anyway but had no way to make a meaningful compliance claim. Naming and ordering the tiers turns "are you compliant?" — which had one honest answer, no — into "which subset?", which has four answers a vendor can claim and a test suite can check. Without it, open-sourcing the ISA in 2019 would have been a gesture: nobody outside IBM could have built something and legitimately called it Power.
Which subset would you target for a new design, and why?
It follows from the software. If the part runs firmware or an RTOS and never needs floating point, SFS keeps it as small as possible. Add scalar FP and you are at SFFS, which is where most FPGA softcores and teaching cores sit — Microwatt-class. The moment the product needs to boot mainstream Linux, you are committing to LCS, which means a real MMU, the full privilege and interrupt model, and the atomic primitives the kernel's locking depends on — a significant step up in verification effort. ACS is really only for server processors intended to run AIX or IBM i.
Why must optional facilities be all-or-nothing?
So software can test once and then rely on it. On Linux a library checks AT_HWCAP2 at load time and binds, say, memcpy to a VSX implementation through an IFUNC resolver — one check, then full confidence. If implementations could ship 90% of VSX, every library would have to probe individual instructions or defensively avoid the facility, which destroys the value of having it. Omitting a facility entirely is clean; implementing it partially fragments the ecosystem.
How do you change the Power ISA?
Through an RFC — a Request for Change — to the Instruction Set Architecture Technical Working Group under the OpenPOWER Foundation, which is itself hosted by the Linux Foundation. Members submit directly and there is a public path for non-members. The TWG reviews encoding-space impact, software and toolchain consequences, verification burden, and interaction with existing facilities and subsets, and accepted changes land in a future revision. That governance is the difference between an open specification and an abandoned one.
What are the downsides of the subset model?
"Power ISA" stops naming a single target. A binary compiled for POWER10 with MMA and prefixed instructions will not run on an SFFS core, so distributions must choose and publish a baseline — which is why ppc64le Linux effectively floors at POWER8/POWER9. The complete description of a target is version plus subset plus optional facilities, and getting it wrong ships binaries that die with illegal-instruction traps on older machines. Every configurable ISA has this problem; Power's four ordered tiers are a conservative answer compared with RISC-V's extension matrix.
What does the ISA leave to the implementer, as distinct from the subset choice?
Everything about how it goes fast. Pipeline depth and width, in-order versus out-of-order, SMT degree — POWER9 shipped SMT4 and SMT8 variants of the same architecture — cache sizes, associativity and hierarchy depth, branch predictors and prefetchers, and which of the supported page sizes are actually implemented. The distinction that matters: a subset mismatch means an illegal-instruction trap, a microarchitecture difference means a slower program. One is a correctness boundary, the other a performance one.
Compare Power's approach to configurability with Arm's and RISC-V's.
Arm ships profiles — A for application, R for real-time, M for microcontroller — plus numbered architecture versions with mandated features per version, and controls the whole thing centrally. RISC-V started maximally granular with per-extension letters, discovered that the combinatorial space was untargetable, and layered curated profiles on top. Power sits in between and on the conservative end: four ordered, nested tiers plus a modest set of independent optional facilities. Less expressive than RISC-V, harder to fragment, and easier for software to reason about than a feature matrix.

13Recap & key terms

  • Compliance = Base + exactly one subset + optional facilities (v3.0 onward).
  • Subsets nest: SFS ⊂ SFFS ⊂ LCS ⊂ ACS. The decisive step is SFFS → LCS, i.e. "can boot Linux".
  • Optional facilities (VSX, MMA, DFP, TM, radix, hypervisor, PEF, prefixed) are all-or-nothing individually.
  • Software discovers facilities via AT_HWCAP/AT_HWCAP2 and binds once with IFUNC; PVR identifies the implementation.
  • Categories (v2.03–2.07) were replaced by subsets because unbounded combinations are untargetable.
  • Microwatt is the proof case: SFFS-class, boots Linux, fits a modest FPGA, no architecture licence.
  • Unallocated encodings are reserved, not free; extensions go through the TWG RFC process.
  • Microarchitecture — pipeline, SMT, caches, predictors — remains entirely the implementer's choice.
