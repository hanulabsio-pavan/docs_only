Unified decoder and pipeline integration

Four extensions, one decoder, one clock period. This lesson is about composition — what happens when I, M, A and C all have to coexist in the same ID stage without blowing your timing budget.

By the end of this lesson you can

  • Draw the decode tree from inst[1:0] down to individual operations.
  • Split decode into stages and justify where each boundary sits.
  • List the control bundle a five-stage RV32IMAC core needs.
  • Argue one-hot versus encoded control on timing and area.
  • Enumerate every illegal-instruction condition across the four extensions.
  • Identify the ID critical path and give three ways to shorten it.
  • Explain what happens when misa disables C at an odd PC.

1The interview frame

crux

Each extension was designed to be cheap in isolation. The integration cost is not the sum of the parts. C adds a stage to the front, M adds a variable-latency writeback path, A adds a non-speculative point in MEM. The decoder must serve all three without becoming the critical path.

Panels ask this to see whether you have actually closed timing on a core, or only simulated one. Be specific about your period, your slowest path and what you did about it.

the composition insight

M costs one extra funct7 comparison at level 3 of an existing branch. A costs one new leaf at level 1. C costs a whole new subtree at level 0 plus an expander. That is why C dominates the integration cost even though its instructions are the simplest.

3Three decode stages

In a core with C, decode is naturally three sequential pieces. Where you put the pipeline registers is a design decision.

Length determination — in IF

Pure function of inst[1:0]. One gate per halfword. It must complete in IF because next-PC depends on it.

  • Drives the PC increment select: +2 or +4.
  • Drives the fetch buffer's consume amount.
  • Drives the boundary scan for the next instruction.

This is the one part of decode that cannot be deferred. Everything else can move later.

Expansion — end of IF or start of ID

16 bits in, 32 bits out, combinational. No state, no faults, no stalls.

Placing it at the end of IF means it shares a cycle with the fetch buffer read and any rotation. Placing it at the start of ID means it shares a cycle with the main decode. Either can be right; the question is which of those two cycles has slack.

carry the length forward

Once expanded, the instruction is indistinguishable from a native 32-bit one. So the original length must travel down the pipeline as a separate bit — it is needed for the link value of a compressed call and for the mepc value on a trap.

Main control decode — in ID

32 bits in, a control bundle out. This is where the levels of the decode tree are evaluated. Runs in parallel with the register file read and the immediate generation, neither of which depends on it.

Split the outputs by when they are needed:

the key optimisation

Only the first two rows are timing-critical. Everything else can be computed in ID and registered, or even computed one stage later from the registered instruction word. Moving illegal-instruction detection off the ID critical path is the single easiest decode timing fix.

Choosing the pipeline cut
ArrangementStagesTrade-off
Expand and decode both in IDIF ID EX MEM WBClassic five stages. Tight ID. Simplest control.
Expand at end of IF, decode in IDIF ID EX MEM WBBalances the two stages. Needs IF to have slack.
Separate expand stageIF IX ID EX MEM WBSix stages. Best timing, one more cycle of branch mispredict penalty.

Adding a stage costs one cycle on every mispredict and every taken branch redirect. In a core with a weak or absent predictor that is expensive. Only do it if ID genuinely will not close.

4The control bundle

What decode actually emits. Be able to list this — it is a common whiteboard request.

SystemVerilog — RV32IMAC control bundle
typedef struct packed {
  // --- operand selection ---------------------------------------
  logic [4:0] rs1, rs2, rd;
  logic       rs1_used, rs2_used;   // for hazard comparators
  logic       rd_we;                // gated with (rd != 0)
  logic [31:0] imm;
  logic       op_a_is_pc;           // AUIPC, JAL, branches
  logic       op_b_is_imm;

  // --- execute --------------------------------------------------
  alu_op_e    alu_op;               // ADD SUB AND OR XOR SLL SRL SRA SLT SLTU
  logic       is_branch, is_jump;
  br_cond_e   br_cond;              // 3 bits, straight from funct3

  // --- M extension ----------------------------------------------
  logic       md_valid;             // issue to mul/div unit
  md_op_e     md_op;                // 3 bits, straight from funct3

  // --- memory + A extension -------------------------------------
  logic       mem_req;
  logic       mem_we;               // store, or AMO write phase
  logic [1:0] mem_size;             // funct3[1:0]
  logic       mem_signed;           // ~funct3[2]
  logic       is_amo, is_lr, is_sc;
  amo_op_e    amo_op;               // from funct5
  logic       aq, rl;

  // --- writeback ------------------------------------------------
  wb_sel_e    wb_sel;               // ALU | MEM | PC_NEXT | MD | CSR

  // --- C extension + traps --------------------------------------
  logic       is_compressed;        // drives PC+2 link value and mepc
  logic       illegal;
  logic       is_ecall, is_ebreak, is_fence;
} ctrl_t;
notice what is free

br_cond, md_op, mem_size and mem_signed all come straight from funct3 with no decode at all. amo_op comes straight from funct5. The ISA encoding was designed so that operation selects can be wires into the functional units. Point this out — it is the payoff of everything in Lesson 01.

5One-hot versus encoded control

One-hotEncoded
Decode logicWider — one signal per operationNarrower
Pipeline register bitsMore flops per stageFewer
Consumer-side logicDirect mux select, no re-decodeMust decode again at the consumer
Timing at the consumerBest — enable is a wireOne decode level added
PowerMore toggling flopsFewer
the practical rule

One-hot for signals consumed right at the end of a long path — mux selects into the EX operand network. Encoded for everything carried several stages, where the flop count matters and the consumer has slack to re-decode. Most real cores mix the two.

A concrete example: keep wb_sel encoded in two or three bits, since WB has three stages of slack to decode it. Keep the forwarding mux selects one-hot, since they sit directly in front of the ALU.

the design trap

It is tempting to build the decoder as a priority casez with a default that does something harmless. That silently aliases reserved encodings onto real instructions and passes every directed test. The correct structure is: compute an explicit legal signal as the OR of all match conditions, then illegal = ~legal. Reserved-field checks are ANDed into each match, not handled by a default arm.

timing note

The illegal cone is wide — it touches almost every instruction bit. Keep it off the ID critical path. It is only needed at the trap point, so register the instruction word and compute illegal in the next stage. This costs a few flops and buys real slack.

  • Name the actual path from your timing report, with the start and end points.
  • State the achieved period and the slack before and after your fix.
  • Say what you traded. Every timing fix costs area, cycles or complexity. Naming the cost is what makes the answer credible.

say this

"M attacks the back end, A attacks the memory interface, C attacks the front end. They barely interact with each other, which is the nice part — but each one independently invalidates a different simplifying assumption in a textbook five-stage pipeline."

9Resource sharing

How many adders do you actually need?
UseCan share the main ALU?
R-type and I-type arithmeticIt is the main ALU
Load and store addressYes — rs1 + imm is an ALU add
AUIPCYes — PC + imm through the operand-A mux
JALR targetYes — rs1 + imm, then clear bit 0
Branch comparisonYes via subtraction, but it serialises with the target add
Branch target PC + immNeeds a second adder if the compare uses the first
Sequential PC + 2/4Lives in IF, separate incrementer

So a lean RV32IMAC core has three adders: the main ALU, the branch target adder in EX, and the PC incrementer in IF. Claiming one is wrong; claiming six means you did not share.

Running an AMO through the existing pipeline

A small core can avoid a dedicated atomic ALU by replaying the AMO through EX.

  1. Pass 1 — MEM: read the memory word, lock the line, capture the old value.
  2. Replay through EX: feed the old value and rs2 into the main ALU with the operation derived from funct5.
  3. Pass 2 — MEM: write the result back, unlock the line.
  4. WB: write the captured old value to rd.
  • Pro: no duplicate ALU. The min/max operations reuse SLT and SLTU, which already exist.
  • Con: several extra cycles per AMO, and the pipeline needs a replay mechanism and a line lock that cannot deadlock against a snoop.

Perfectly defensible for an embedded core where atomics are rare. Say the cycle count.

M unit operand capture

The M unit reads rs1 and rs2 once, at issue, and holds them. That has two useful consequences:

  • No WAR hazard — a later write to rs1 or rs2 cannot disturb the in-flight operation.
  • The unit does not need forwarding paths of its own. It takes the already-forwarded operands from the EX input muxes.

What it does need is its own result register and a request line into the writeback arbiter, which is the structural hazard covered next.

In a single-issue in-order core, almost every structural hazard reduces to one question: who gets the register file write port. That is the honest short answer, and the follow-up is your arbitration policy.

11misa and runtime extension disable

misa reports the implemented ISA. It is WARL, so an implementation may allow extensions to be disabled at runtime — or may hardwire it entirely, which is what most embedded cores do.

a genuinely hard trap

Suppose software writes misa to disable C. That raises IALIGN from 16 to 32. But the very next instruction might sit at an address that is 2 mod 4 — now illegal. What happens?

The write is suppressed. If a write to misa would increase IALIGN and the next instruction's address is not aligned to the new IALIGN, the write does not take effect and misa is left unchanged. The architecture refuses to put itself into an unreachable state.

Two further consequences worth knowing:

  • If your implementation hardwires misa, writes are simply ignored and the problem never arises. Saying "I hardwired it" is a complete and correct answer.
  • If an extension can be disabled, the decoder must gate its legality on the enable bit — an M instruction with M disabled must raise illegal-instruction, not execute. That means the enable bit is an input to the decode cone, which is one more reason to keep illegal detection off the critical path.
practical position

For Hanu 1.0, hardwiring misa is the right choice and the easy answer. Dynamic extension disable exists mainly for software compatibility testing and for platforms that share one core design across configurations. Say that you considered it and chose not to pay for it.

13Interview Q&A

Walk me through your decoder from the fetched bits to the EX operands.

Fetch buffer presents 32 bits at the current instruction start. inst[1:0] decides length; if compressed, the low halfword goes through the expander and everything downstream sees a synthesised 32-bit instruction plus an is-compressed bit.

Three things then run in parallel. Register file read using the fixed index positions. Immediate generation, which is five wire bundles and a select driven by inst[6:2]. Control decode down the tree — opcode, then funct3, then funct7 or funct5.

Hazard comparators run alongside, comparing source indices against in-flight destinations, and produce one-hot forwarding selects. At the end of ID the operand muxes choose between register data, forwarded data, the immediate and the PC, and those feed the EX registers.

Illegal detection is computed from the registered instruction word one stage later, because it touches nearly every bit and does not need to be fast.

Your ID stage misses timing by fifteen percent. Give me an ordered plan.

First, find out which path. There are at least three candidates in ID and they have different fixes, so guessing wastes a synthesis run.

If it is the decode-to-operand-mux path: move illegal detection and any trap-cause encoding out of ID into the next stage. Convert the mux selects to one-hot so the consumer is a wire, not a decode. These are free in cycles.

If it is the forwarding priority network: flatten the priority chain into parallel AND terms rather than a cascaded mux, and compute the selects from the previous stage's registered destination indices instead of from combinational ones.

If it is the expander feeding decode: move the expander into IF, where there is usually slack after the fetch buffer read.

Only if none of that is enough would I add a pipeline stage, because that costs a cycle on every branch redirect and hurts a core with a weak predictor.

Why is the immediate generator never the critical path?

Because it contains no gates. All five immediate forms are bit selections and sign-bit replication from the instruction word, so all five are available one wire delay after fetch. The only real logic is the final select, which is one mux level driven by five opcode bits.

That is a direct consequence of the encoding decisions in the base ISA — fixed sign-bit position and fixed positions for most immediate bits. It is the clearest example of the ISA buying decoder timing with encoding complexity.

Do M and A share any logic?

Almost none, and that is worth saying because candidates sometimes assume they do. M is a datapath unit in the back end with its own multiplier and divider. A is a memory-side feature: an atomic ALU and a reservation monitor near the cache, plus ordering control.

The one genuine overlap is the register file write port, which both compete for alongside loads. And if you implement AMOs by replaying through the main ALU, then A and the base ALU share, but still not A and M.

C shares with neither. It is confined to the front end.

How would you make this decoder parameterisable between RV32 and RV64?

The base is mostly clean: widen the datapath, extend the shift amount field from five bits to six, and remove the inst[25] == 0 legality check because that bit becomes shamt[5]. Add the W-suffixed instructions, which is a new funct3 decode under a new opcode.

M is similarly clean: MULW, DIVW, DIVUW, REMW, REMUW under OP-32, with sign extension of the 32-bit result — remembering that even the unsigned forms sign-extend.

A just adds the .D forms under funct3 = 011.

C is the problem. The compressed quadrants reuse encoding slots differently between XLEN — C.JAL becomes C.ADDIW, C.FLW becomes C.LD — so the compressed decode table is structurally different, not merely wider. I would keep two tables selected by the XLEN parameter rather than trying to unify them, and I would not pretend the expander is portable.

15Recap

  • Decode is a four-level tree: inst[1:0], inst[6:2], funct3, then funct7 or funct5.
  • M is one funct7 comparison. A is one new opcode leaf. C is a whole new subtree plus an expander.
  • Length determination must happen in IF. Everything else can be deferred.
  • Only regfile read enables and operand selects are timing-critical in ID. Defer the rest.
  • funct3 feeds branch condition, memory width, memory signedness and M operation directly — no decode.
  • Build illegal as the complement of an explicit legal signal, never as a default arm.
  • One-hot for the last mux, encoded for anything carried several stages.
  • Three adders: main ALU, branch target, PC incrementer.
  • A write to misa that would increase IALIGN with the next PC unaligned is suppressed.
